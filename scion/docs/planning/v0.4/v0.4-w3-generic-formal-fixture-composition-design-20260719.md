## 2. Three entry owners, no dispatcher

There is no generic dispatcher and no `helpers.py`. Each existing focused
fixture owns one strict immutable-plan entry:

1. `generic_backend_formal_case.py --plan PLAN.json` owns B0-B8 and the native
   portions of H5/H6, including B6's fixed fault/phase ABI;
2. `generic_backend_unit_observer.py --plan PLAN.json` owns acquisition-free
   run-main, ExecStopPost and closer receipt materialization;
3. `generic_backend_adversary.py --plan PLAN.json` owns only the fixed negative
   and hold scenarios enumerated by that file and this design.

Every unit command is exactly:

```text
<installed-python-3.12> -I -B <prehashed-program> --plan <prehashed-plan>
```

Each program reads one canonical, duplicate-rejecting, versioned plan from a
pinned regular file. It verifies every referenced static input and program
hash, derives only its own invocation/kernel facts, publishes with atomic
no-replace semantics and calls its existing typed execution function in the
same process. It does not exec another interpreter, spawn a launcher or
reconstruct a system-manager fact.

`--config` and strict `REQUEST.json` remain replay/debug surfaces. Formal units
use only `--plan`. Plan decoding may share no new filesystem or dispatch
module: the three small schemas are role-specific and tested independently.

## 3. Root tree, static plan and dynamic facts

### 3.1 Immutable authority tree

The root installer creates one unique tree with three disjoint authorities:

```text
<formal-root>/          root:root 0711; no unit rename/unlink authority
<formal-root>/sealed/   root:root 0555; plans/programs/units/receipts 0444
<formal-root>/input/    root:root 0555; root-sealed dynamic inputs 0444
<formal-root>/work/     <fixture-uid>:<fixture-gid> 0700; unit outputs only
<formal-root>/fifo/     root:root 0711; pre-created named FIFOs, no unit unlink
```

The static units run as one pre-existing, non-login fixture UID/GID named and
frozen by H0; they do not run as root or as the invoking developer. Every FIFO
is pre-created by the installer, owned by the fixture UID/GID, mode 0600, and
has its device/inode frozen in the plan. Its root-owned parent prevents the
unit from unlinking or replacing it. The root harness can open all endpoints.

The unit can create only within `work`. It cannot replace a plan, program,
unit, installer receipt, selector, raw property input or FIFO. The installer
and harness reject symlinks, non-regular static files, unexpected ownership or
mode and any device/inode drift. Paths alone are never authority after an
object has been opened and pinned.

### 3.2 Static plan

A plan is written before installation and contains only facts already knowable
then:

- exact role, case/scenario, run/closer unit names and fixture UID/GID;
- exact paths and SHA-256 values for the wheel extension, accepted native
  probe, every fixture program and immutable configured-property receipt;
- exact sealed/input/work/FIFO roots and each FIFO device/inode;
- the B ordinal, invocation nonce, case parameters and final materialized
  request/config path;
- for an observer, exact future root-input paths, declared acquisition owner,
  expected query unit and role-specific ready/release FIFO pair;
- for a closer, the exact future root-sealed selector path copied from the
  source invocation's ExecStopPost or H4 adversary receipt;
- for B6, one exact fault class, phase, hook identifier, target operation,
  expected invocation ordinal and phase ready/release FIFO pair.

It must not contain a guessed PID, starttime, InvocationID, service/supervisor
inode, result, post-start cgroup inventory, D-Bus object path or journal cursor.

### 3.3 Same-PID run facts

The run entry derives in its MainPID process:

- `INVOCATION_ID` from its exact systemd environment;
- MainPID from `getpid()` and starttime from `/proc/self/stat`;
- unified lineage from `/proc/self/cgroup`;
- service and supervisor device/inode from nofollow directory descriptors;
- boot ID from the pinned boot-id file;
- the frozen configured/expanded property pairs.

The formal-case entry materializes the final config and enters B without a PID
change. The B5 `GenericProcessSpec.environment` additionally carries the exact
current `INVOCATION_ID`; adversary validation remains strict.

### 3.4 Observer acquisition handshake

Each observer role owns a distinct pair of pre-created FIFOs. Before StartUnit,
the harness opens each FIFO once with
`O_PATH|O_NOFOLLOW|O_CLOEXEC`, proves its planned device/inode and retains that
identity FD. It additionally opens only the ready FIFO with
`O_RDONLY|O_NONBLOCK|O_NOFOLLOW|O_CLOEXEC`. It does not open the release writer
before the unit exists. The same observer process then:

1. derives its role-specific invocation, PID/starttime and cgroup identity;
2. publishes a canonical no-replace ARMED receipt containing those facts and
   both FIFO identities;
3. opens the ready FIFO `O_WRONLY|O_NOFOLLOW|O_CLOEXEC`, proves identity, writes
   exactly `SCION_GENERIC_BACKEND_READY_V1\n` and closes it;
4. opens the release FIFO `O_RDONLY|O_NOFOLLOW|O_CLOEXEC`; this blocking open
   is the rendezvous and has no deadline;
5. waits for exactly `SCION_GENERIC_BACKEND_RELEASE_V1\n`, requires EOF
   immediately after those bytes and closes the release descriptor;
6. revalidates its PID/starttime, invocation and FIFO identities, then reads
   root-sealed inputs and materializes the final strict request in the same
   process.

The harness consumes the ready descriptor only from event-loop readability,
accumulates until writer EOF without a polling loop and requires the exact
ready bytes with no prefix/suffix. Only after the expected ARMED receipt exists,
its D-Bus and cgroup facts cross-check, every required raw input is durably
sealed and normalized facts pass `systemd255.py` decoders does it open the
release FIFO `O_WRONLY|O_NOFOLLOW|O_CLOEXEC`. The observer is already at its
blocking reader open; the writer open is therefore the second half of the
rendezvous, not a retry. The harness proves the live writer FD matches the
retained `O_PATH` identity, writes the exact permit once and closes to provide
the required EOF. Wrong identity, early EOF, extra bytes or a missing input is
failure, never a second open or retry.

Source binding is role-specific:

- `run-main` uses its current unit/invocation and waits for active lineage and
  configured-property inputs;
- `exec-stop-post` requires the literal `INVOCATION_ID`, `SERVICE_RESULT`,
  `EXIT_CODE`, `EXIT_STATUS`, proves it is the sole `.control` process, and
  waits while the harness seals complete topology and source facts;
- `closer` has a distinct current invocation; source unit/invocation come only
  from the exact root-sealed selector copied from the still-live stop-post/H4
  receipt, and it waits while final source properties are sealed.

Raw manager properties are never generated by an observer. Journal input is
corroboration-only.

### 3.5 Fixed adversary holds

Adversary plan mode derives the current `INVOCATION_ID`, materializes its
strict request and enters the fixed scenario in the same process. Its scenario
set remains closed. This revision adds behavior, not generic commands:

- `h4-stoppost-failure` publishes the exact stop selector and `.control` ARMED
  receipt, performs the observer FIFO handshake, and returns 47 only after the
  root topology sealer releases it;
- `h9-failed-closer` performs the closer acquisition handshake on its own
  distinct FIFO pair, then publishes its failure receipt and returns 61;
- H6/H7/H8/H11 and B5's fixed double-fork descendant adversary retain their
  existing role-specific release FIFOs; a run hold and a closer acquisition
  barrier never share a FIFO, receipt or scenario identity.

Only the explicitly tests-only setsid/double-fork descendant modes may
fork/setsid. No harness or production path may.

## 4. Concrete units and lifetime pinning

Each scenario is rendered into a concrete, prehashed static unit pair. No
placeholder remains when installed. The common run template contains:

```ini
User=<exact fixture user>
Group=<exact fixture group>
ExecStart=<python> -I -B <run-program> --plan <run-plan>
ExecStopPost=<python> -I -B <stop-program> --plan <stop-plan>
CollectMode=inactive
Restart=no
KillMode=control-group
TimeoutStopSec=infinity
Delegate=pids
DelegateSubgroup=supervisor
OnSuccess=<exact closer>
OnFailure=<exact closer>
```

The common closer contains no separate `ExecStartPre` dispatcher:

```ini
User=<exact fixture user>
Group=<exact fixture group>
ExecStart=<python> -I -B <closer-program> --plan <closer-plan>
CollectMode=inactive
Restart=no
TimeoutStartSec=infinity
After=<exact run>
```

The closer program itself owns its acquisition handshake. `OnSuccess` or
`OnFailure` queues it before source collection; the harness never polls for
inactive and starts a closer. H9 substitutes only the fixed failed-closer
adversary plan. H10 is a separate rejected-control unit with literal
`CollectMode=inactive-or-failed`, no closer dependency and no positive receipt
path.

For every positive H scenario, the harness performs this event sequence on one
system-bus connection. Signal match rules and handlers exist before Manager
subscription, so `RefUnit` cannot race an unobserved UnitNew transition:

```text
pin all FIFO identities and pre-open only ready readers
install exact signal matches and handlers
Subscribe
RefUnit(run)
RefUnit(closer)
exactly one StartUnit(run, "fail")
freeze run, stop-post, closer and final receipts
ResetFailedUnit(failed unit) only after its failed-state receipt, if required
UnrefUnit(run)
UnrefUnit(closer)
observe exact UnitRemoved signals and prove cgroup/process absence
```

`RefUnit`, not signal subscription, pins successful inactive units. Every
method reply and JobNew/JobRemoved/UnitNew/UnitRemoved signal is frozen with
unit, object path, job path, boot ID, bus unique owner and sequence ordinal.
No ref is leaked. H12 owns reset/unref/UnitRemoved and final absence; no other
case may claim collection.

## 5. Root-owned system-manager harness

### 5.1 Single launch owner

The formal root adds one tests-only
`generic_backend_systemd_harness.py` using frozen host Python bindings. It is
not packaged in the wheel and production never imports it. It verifies H0,
subscribes before launch and is the sole owner of the D-Bus calls above. The
wrapper contains no executable `busctl` argv. Instead it validates one
canonical data descriptor containing:

```text
bus=system
destination=org.freedesktop.systemd1
object=/org/freedesktop/systemd1
interface=org.freedesktop.systemd1.Manager
method=StartUnit
signature=ss
unit=<exact run unit>
mode=fail
owner=generic_backend_systemd_harness.py
```

The harness consumes that descriptor only after subscription and refs. There
is no shell/systemctl/systemd-run fallback, second StartUnit or replacement
start.

### 5.2 Authoritative D-Bus receipt codec

H0 freezes the exact systemd well-known-name unique owner with
`org.freedesktop.DBus.GetNameOwner`, the unit object returned by `GetUnit`, the
boot ID and the following allowlisted systemd-255 properties and signatures:

| Interface | Properties and exact signatures |
|---|---|
| `org.freedesktop.systemd1.Unit` | `Id:s`, `InvocationID:ay`, `LoadState:s`, `ActiveState:s`, `SubState:s`, `After:as`, `CollectMode:s`, `FragmentPath:s`, `NeedDaemonReload:b`, `OnSuccess:as`, `OnFailure:as` |
| `org.freedesktop.systemd1.Service` | `ControlGroup:s`, `Delegate:b`, `DelegateControllers:as`, `DelegateSubgroup:s`, `ExecMainCode:i`, `ExecMainStatus:i`, `ExecStopPost:a(sasbttttuii)`, `Group:s`, `KillMode:s`, `MainPID:u`, `Restart:s`, `Result:s`, `TimeoutStartUSec:t`, `TimeoutStopUSec:t`, `User:s` |

Manager method/signature allowlisting is equally exact:
`Subscribe:()`, `RefUnit:s`, `StartUnit:ss`, H7-only `StopUnit:ss`, post-receipt
`ResetFailedUnit:s`, `UnrefUnit:s` and H10-only `LoadUnit:s`. Accepted manager
signals are `JobNew:uos`, `JobRemoved:uoss`, `UnitNew:so` and `UnitRemoved:so`;
property transitions are `PropertiesChanged:sa{sv}as` from the exact unit
object.

Each raw query receipt stores destination unique owner, object path, interface,
property, exact variant signature and a lossless tagged value. Strings and
string arrays remain strict UTF-8; signed/unsigned integers are canonical
decimal strings; booleans are exact booleans; `ay` and every binary/non-text
leaf are stored as length plus base64 plus SHA-256; structured arrays preserve
order, nesting and every element signature. No pretty-print parsing is
authoritative. `InvocationID:ay` must be exactly 16 bytes and its lowercase hex
must equal the actor/selector ID. The harness normalizes only after freezing
raw values, then calls `ConfiguredUnitProperties`, `InvocationLineage`,
`StopPostEnvironment`, `StopPostTopology` or `UnitHandoffProperties` before
release/publication. `ConfiguredUnitProperties` remains the exact execution
directive subset defined by the parent contract; H0 separately validates the
unit's `User`/`Group` directives and expanded service properties.

### 5.3 Scenario-specific actions

- B4 and B7 external kill/topology actions occur only after the exact armed
  receipt and pinned cgroup identity are frozen.
- H7: after the hold receipt, the harness calls exactly one
  `StopUnit(run, "fail")`, freezes its returned job object and JobRemoved
  result, and never signals a PID. systemd `KillMode=control-group` owns the
  descendant stop.
- H8: after the hold receipt, the harness opens the service/job cgroup with
  nofollow, proves the planned device/inode, creates exactly one named nested
  cgroup using dirfd-relative `mkdir`, freezes a pre/post ledger and releases
  the actor only after the drift is visible. It never reacquires authority by
  mutable path and never cleans a replacement inode.
- H10 alone omits `RefUnit`: after subscription and one StartUnit it freezes
  the failing actor selector, observes exact `UnitRemoved`, calls `LoadUnit`
  once without StartUnit, and freezes the reloaded empty `InvocationID` plus
  `loaded/inactive/dead` and non-run result facts. That evidence is labelled
  rejected identity loss and cannot satisfy any positive scenario.
- H4 remains alive in `.control` until the harness freezes its PID/starttime,
  exact sole `.control` task, empty supervisor/job tasks and complete cgroup
  inventory; only then does the release make it return 47.

### 5.4 Complete journal corroboration

Before StartUnit the harness opens `systemd.journal.Reader`, records the start
cursor and sets `data_threshold=0`. After an invocation becomes known it adds
exact boot-ID and `_SYSTEMD_INVOCATION_ID` matches. After the last producer has
terminated, root connects directly to the frozen
`/run/systemd/journal/io.systemd.journal` Unix socket and makes exactly one
NUL-framed Varlink call to `io.systemd.Journal.Synchronize` with an empty
parameter object. An error or malformed reply rejects the root. No external
`journalctl` process is used.

Only after Synchronize returns does the harness freeze the end cursor and
iterate the closed start/end interval. Every repeated field and binary or
non-printable value uses the same lossless length/base64/SHA-256 codec; no
field, byte, entry count or time interval is capped or truncated. Journal
bytes remain corroboration; typed D-Bus and no-replace receipts are authority.

H0 freezes `/usr/bin/python3.12`, harness source, `dbus-python`,
`python-systemd`, their resolved file hashes/versions, the system-bus manager
owner and the journald socket/interface device/inode/uid/gid/mode. Binding or
socket drift is a new root, not a retry.

## 6. B6 exact fault/phase ABI

B6 remains owned by `generic_backend_formal_case.py`; it does not introduce a
fourth dispatcher or a production hook. Its closed matrix is:

```text
fault = issuer-signal | capture-storage | authority-close
phase = blocked | just-released | leader-terminal |
        reaped-but-populated | empty-before-eof
```

Issuer coverage also includes the parent contract's pre-handle windows:
`backend-open`, `capture-prepare`, `job-created-pre-native` and
`native-no-handle`. Each plan maps one `(fault, phase)` to one exact current
source seam, operation ordinal and expected backend enum/reason. There is no
free-form attribute or callable name in a plan.

The issuer signal is exactly `SIGUSR1`. Before opening the backend, formal-case
requires it absent from the caller's mask and pending set, records the original
disposition, installs one fixture-local handler whose only action is to raise
`KeyboardInterrupt`, and freezes the handler source hash. It restores the
original disposition and proves the original mask/pending state before any
ordinary process continuation is published. A fail-stop case terminates the
process and the outer supervisor records that no live disposition authority
remains.

The fixture installs only a fixed allowlisted wrapper around the exact
package-private operation before opening the backend. Every issuer wrapper
must be called inside the accepted production `_IssuerSignalGuard`: at wrapper
entry its readback mask must contain `SIGUSR1`, its pending set must not, and
the plan/source-hash allowlist must prove that exact guarded callsite. A seam
that cannot prove those facts is `REQUIREMENT_MISSING`; the fixture never
blocks or restores the production mask itself. When reached, the wrapper:

1. proves its invocation counter and current observable lifecycle facts;
2. writes a no-replace ARMED receipt with PID/starttime, backend phase, job
   cgroup device/inode, target operation and FIFO identities;
3. emits the ready bytes and, while the production guard still blocks SIGUSR1,
   waits for the one release permit using the executable FIFO protocol above;
4. for `issuer-signal`, lets the scenario supervisor open and identity-check a
   pidfd, call `pidfd_send_signal(SIGUSR1)` exactly once, fsync its no-replace
   send receipt and only then open/write/close the release FIFO; PID kill is
   forbidden;
5. for `issuer-signal`, after release proves SIGUSR1 is pending and still
   blocked, calls the exact wrapped operation once and returns to the production
   guard; only that guard restores its saved mask, observes the newly pending
   issuer signal and delivers the fixed handler at the guarded seam;
6. for storage/close, after release injects the one frozen EIO/uncertainty at
   the wrapped operation and permanently disarms itself;
7. freezes whether the operation was pre-call, returned, raised or committed
   and proves the expected typed containment or fail-stop outcome.

The scenario supervisor is the root system harness when B6 is nested in H5/H6
and the tests-only delegated supervisor otherwise; it is never another process
entry or product owner. Its signal receipt includes pidfd acquisition identity,
exact SIGUSR1, single send result, send-before-release order and matching armed
SHA. Formal-case receipts include original/guarded/restored masks, pending
before/after, original/fixed/restored dispositions and handler source hash.
Internal fault receipts include the exact wrapped operation, call ordinal and
before/after ledger. Extra calls, phase mismatch, missing arm, ordinary return
from a fail-stop case, early handler delivery or any unobservable seam is
`REQUIREMENT_MISSING`/rejection, never a fabricated pass. Pure tests prove the
allowlist against the exact pushed source hash and exercise guarded pre-handle
and drain seams before delegated execution.

## 9. Installer and wrapper boundary

The wrapper performs only static preflight and final no-replace receipt
freezing. It validates all concrete unit/program/plan/harness hashes, the
canonical D-Bus data descriptor, absence of placeholders, literal properties,
identity-tree modes and exact unit names. It never opens a bus, FIFO or journal
and never installs, starts, stops, resets or reloads a unit.

The separate root installer copies prehashed concrete units to unique names
under `/run/systemd/system` and performs exactly one pre-observation daemon
reload. It may call `LoadUnit` once per concrete unit before observation solely
to resolve and freeze the FragmentPath; that installer call is disjoint from
the harness's H10-only post-GC LoadUnit. Its receipt binds each unit's SHA-256,
FragmentPath device/inode, uid/gid/mode, manager object/owner,
`NeedDaemonReload=false`, load/reload call counts and time order before signal
subscription. No load or reload occurs during positive H0-H12. After H12 and
frozen final receipts, a distinct cleanup transaction may remove the fixture
fragments and reload once; it is labelled cleanup and cannot alter accepted
evidence.

## 10. Host authority gate

This checkout's current user can run a user-manager delegated diagnostic, but
noninteractive root/system-manager authorization is not present. A user-manager
result cannot satisfy H0-H12. Formal systemd execution remains
`REQUIREMENT_MISSING` until the user supplies a root-authorized installer and
system-bus execution context.

This authority gap does not justify a transient unit, user-manager
substitution, password persistence, `sudo` fallback inside a fixture, relaxed
acceptance claim, polling, retry or a default watchdog.
