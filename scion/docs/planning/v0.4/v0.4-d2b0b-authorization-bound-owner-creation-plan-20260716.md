The slice adds no production composition importer, schema mutation, legacy

creation participants and Registry publication path required before the later
indivisible offline cutover.

## Decision

Branch and H creation do not share a semantic authorization helper.

- `ChampionStore` owns the durable current-champion participant and the sealed
  Branch creation authorization.
- a new `proposal_attempt_owner.py` owns the generated-attempt transition,
  immutable attempt-to-H binding, durable continuation lookup, and sealed H
  creation authorization;
- `owner_transaction.py` knows only authorization object identity, owner kind,
  owner ID, target digest, transaction/ledger identity, phase, write fact, and
  receipt closure;
- focused Branch/H stores require the appropriate authorization but never
  issue or infer it;
- `CampaignOwnerRegistry` is the only orchestrator and the only local owner
  root publisher.

There is no `creation_helpers.py`, generic semantic authorization owner,
caller-fed witness, callback classifier, test-only issuer, or compatibility
path for an unauthorized INSERT.

## Current blocker

The existing creation receipt proves only that one revision-zero owner row was
inserted. It does not prove why the row was authorized.

The current H success order is especially invalid for cutover:

```text
provider returns H
-> blind HypothesisStore.save(H)
-> process-local approved binding
-> append generated proposal-attempt event on another connection
```

It permits an H without a durable generated attempt, a generated attempt
without an authoritative H binding, and attachment of provider output to a
Branch revision different from the one used to construct the prompt.

The current Branch creation path similarly installs a Branch in the controller
before persistence, catches a failed save, and continues. It has no same-
transaction current-champion proof.

Neither path may be activated by merely adding Registry calls around the
existing `insert_once_in()` methods.

## Fixed responsibility boundaries

### `lineage/champion_store.py`

The final store owns fixed champion SELECT/INSERT SQL, strict durable row
decoding, and a frozen internal `StoredChampionRecord` whose storage digest
covers the exact persisted row:

```text
version
weight_revision
operator_pool_json
solver_config_hash
code_snapshot_path
code_snapshot_hash
promotion_experiment_id
promotion_dossier_ref
promoted_at
```

The digest envelope preserves the exact stored `operator_pool_json` TEXT rather
than silently normalizing it through a public `ChampionState`. Strict decoding
rejects duplicate JSON keys, non-finite numbers, malformed operator objects,
and SQLite type coercion, but historical bytes remain visible to the storage
digest. Any stronger canonical-write migration belongs to D2b.0b.C after a
real legacy inventory; the dormant participant does not rewrite history.

The current champion is selected lexicographically by
`version DESC, weight_revision DESC`. A mutable or re-anchored public
`ChampionState` is never a durable token.

The dormant foundation adds a separate `ConnectionScopedChampionStore` in
this module. It accepts a `CampaignDatabaseAuthority`; the existing production
`ChampionStore(path, snapshot_root)` constructor and methods remain
behaviorally unchanged. D2b.0b.C deletes the legacy class and promotes the
reviewed authority-bound implementation. No compatibility facade survives the
cutover.

Its immutable token has the exact shape:

```text
StoredChampionRecord(
  version: exact nonnegative int,
  weight_revision: exact nonnegative int,
  canonical_storage_payload_json: bytes,
  storage_sha256: lowercase SHA-256,
)
```

`.value()` returns a new detached `ChampionState` and new operator mapping on
every call. The fixed SELECT names the exact stored columns. Required and
optional SQLite types, duplicate JSON keys, non-finite numeric values, and
operator-object keys are decoded strictly. Legacy short semantic hash strings
are not silently promoted to a new 64-character constraint in the foundation;
the real D2b.0b.C inventory must first prove any stronger migration rule.

The connection-scoped participant accepts only the caller-owned sealed
transaction. It does not open, commit, roll back, close, acquire the champion
lock, read Branch rows, or publish in-memory state.

### `lineage/proposal_attempt_owner.py`

This new narrow owner retains `experiment_events` as the append-only transition
history. It does not build a second complete proposal-attempt store. It owns:

- strict started-attempt and prompt-receipt validation;
- connection-scoped append of one exact generated H transition;
- the immutable attempt-to-H binding row;
- sealed `HypothesisCreationAuthorization` issuance;
- exact binding classification through a caller-owned read snapshot; and
- later durable code-continuation identity lookup.

It does not call a provider, own prompt construction, select a Branch, insert

continuation policy.

The current public `PromptCallReceipt` is an audit value, not authority: a
caller can construct an equal dataclass. Field equality therefore cannot prove
that a provider call actually returned the proposal being installed.

The proposal-engine provider boundary adds a sealed, one-shot
`GeneratedHypothesisResult`. Only the real receipt-aware provider-call path may
issue it after the response and trace/raw-response persistence have completed.
Its private state binds:

```text
exact started-attempt capability identity
attempt ID and started event ID
context digest and prompt hash
actual provider-call receipt identity and durable refs
complete canonical HypothesisProposal bytes and SHA-256
provider success and parse success
thread/Context and one-shot lifecycle
```

It returns a detached H proposal for Contract processing, but the detached
proposal and the public `PromptCallReceipt` never become authority. The
proposal-attempt participant consumes the exact sealed result identity when it
constructs the generated event and H binding. There is no public or test-only
issuer; tests exercise the real provider-call boundary with a deterministic
fake transport.

## Sealed view model

### Branch creation

`BranchCreationView` reserves an absent Branch ID and binds one detached target
plus the captured owner-root generation. It contains no caller-supplied
champion token or authorization. Its private issued state binds the exact
sealed `ChampionCreationSource`, `StoredChampionRecord`, and
`ChampionLockLease` owned by the coordinator at view issuance. The stored
record is an integrity token, not authorization; only an exact same-transaction
durable-current match may turn it into authorization.

The target must already be a canonical initial Branch:

- revision-zero semantic target;
- nonempty exact ID and matching lineage ID policy;
- no existing local Branch slot;
- no local H references to the absent Branch;
- no caller-visible mutation after view issuance can change the captured
  canonical target digest.

The public Branch object returned after success is reconstructed from the
published Registry root. A controller cannot install the target before durable
commit and Registry publication.

### H generation and creation

`HypothesisGenerationView` is a read-only, one-shot source view captured before
the provider call. It binds the exact Branch token and owner-root generation
used to build the H context. It is not a mutation permit or a creation
authorization.

It also captures the exact prior H history head, or durable absence, selected
deterministically from the immutable all-H root by `(created_at,
hypothesis_id)`. Generation is rejected while an active H already owns the
Branch. The history-head token is source identity for
`parent_hypothesis_id`; it is distinct from the active-H scheduling index.

After a successful provider response, `prepare_hypothesis_creation()` consumes
that exact generation view and binds:

- the immutable exact Branch token used for the provider context;
- the immutable exact prior H history-head token, or exact absence;
- a detached initial H target and complete H storage digest;
- Branch ID, H ID, parent H ID, and proposal digest; and
- the root generation captured before the provider call.

It returns a sealed `HypothesisCreationView`. The caller cannot replace its
Branch token with a fresh post-provider read. Branch revision drift or an A-B-A
root-generation change makes the view fail before any creation commit.

The generation view must be bound to exactly one durable started attempt before
the provider is invoked. A sealed `StartedHypothesisAttempt` is issued only
after the proposal-attempt owner appends and strictly rereads the exact started
event. Registry then binds that exact receipt to the generation view and issues
the only provider-call permit accepted by the receipt-aware H call.

The generation view lifecycle is:

```text
ISSUED
-> START_RESERVED(attempt ID)
-> START_BOUND(attempt ID, started event ID, provider-call permit)
-> RESULT_BOUND(exact GeneratedHypothesisResult)
-> CONSUMED_BY_CREATION_VIEW
-> SPENT
```

Provider failure, interruption, Contract rejection, start-binding failure, or
an explicit workflow abort moves the preallocated view cleanup set directly to
`SPENT`. A view can bind only one start, one provider call, and one result. The
provider call rejects an unbound, already-consumed, copied, cross-thread, or
cross-Context permit before transport invocation. No second start or call may
reuse the view.

The creation view uses the common irreversible lifecycle:

```text
ISSUED -> CLAIMED -> SPENT
```

No state returns to `ISSUED` and no provider call is repeated by this protocol.

triggers, and:

parent H must belong to the same Branch and match the generation view's

from event order or process-local state.

## Generic creation-authorization ledger

`owner_transaction.py` adds sealed internal authorizer authority and
authorization identity types. Exact private issuers bind a participant to one
database authority and one owner kind. Static closure permits only
`ChampionStore` to issue Branch authorizations and only
`proposal_attempt_owner.py` to issue H authorizations.

Each transaction-bound authorization state contains only:

```text
authorizer authority identity
ledger/transaction/database identity
owner kind and owner ID
target payload SHA-256
phase
exact bound write fact identity, initially absent
```

The only legal phase sequence is:

```text
ISSUED
-> WRITE_BOUND
-> COMPLETED
```

- `ISSUED -> WRITE_BOUND` occurs before SQLite executes the owner INSERT and
  binds the exact preallocated write fact.
- the owner row must insert and reread exactly before its creation receipt is
  issued;
- the semantic participant performs or revalidates its durable authorization
  work and moves the exact authorization to `COMPLETED`;
- only a `COMPLETED` authorization may have its creation receipt consumed and
  staged by the Registry.

There is no cancel, reset, replay, alternate issuer, idempotent second
completion, or unbound receipt path.

Authorization issuance and write binding use fixed fail-closed ordering:

```text
preallocate authorization capability + state
-> register global weak state
-> register in ledger.creation_authorizations
-> return capability

preallocate write fact + fact state + permit
-> ledger.pending_write = fact
-> ledger.writes[fact] = fact_state
-> authorization.write_fact = fact
-> authorization.phase = WRITE_BOUND
-> execute owner INSERT
```

No fault cleanup restores `ISSUED` or clears an incomplete pending write.

Completion requires exact authorizer authority, transaction, database, ledger,
kind, owner ID, target digest, authorization and fact identity; a completed
one-row INSERT; an issued exact `OwnerCreationReceipt`; and no pending write.
Only after those checks does the final assignment set `COMPLETED`. Receipt
consumption rechecks `COMPLETED` and that the authorization's exact write fact
is the fact registered for that receipt.

`COMPLETED` is a sealed pre-commit phase, not a reusable capability. The phase
enum deliberately has no `SPENT` value. Ledger `SEALED/CLOSED`, inactive
transaction ownership, and participant authority checks are the single
revocation mechanism for authorizations in any phase; safety never depends on
an interruptible per-authorization cleanup loop. Receipt/scope state retains
the authorization strongly through classification, then releases the inert
object only after publication, proved rollback, or permanent-hold installation.

`_WriteFactState` gains exact target digest and creation-authorization identity.
`_OwnerReceiptWitness` gains the same authorization identity. UPDATE facts must
have neither field; INSERT facts must have both. A creation token must have
revision zero and its complete payload digest must equal both the write fact
and authorization target digest.

Ledger closure proves:

```text
registered creation authorizations
== authorizations bound to creation write facts
== COMPLETED authorizations
== authorizations on issued creation receipts
== authorizations on consumed receipts
== authorizations derived from exact Registry-staged receipt identities
```

The ledger accepts staged receipt identities, not caller-supplied witnesses.
Registry separately proves that every witness returned by seal is the same
object it previously obtained while consuming and staging the corresponding
receipt.

The existing mutation closure remains unchanged and its authorization set is
empty. An extra, missing, duplicated, swapped, incomplete, or cross-ledger
authorization prevents COMMIT.

## Branch creation transaction

The required outer lock/order remains:

```text
champion lock
-> Registry owner lock
-> one authority-owned BEGIN IMMEDIATE
```

The concrete API proof is the exact `ChampionLockLease`; a lock convention or
static caller name is insufficient.

Inside the Registry scope:

```text
validate the same ChampionLockLease and claim BranchCreationView
-> load the exact StoredChampionRecord bound to the claimed view
-> ChampionStore strict-read durable current champion
-> require exact composite-key equality
-> require exact complete storage bytes and storage-digest equality
-> require target.base_champion_id == champion.version
-> require target.weight_revision == champion.weight_revision
-> require target.base_champion_hash == champion.code_snapshot_hash
-> issue transaction-bound Branch creation authorization
-> BranchStore INSERT with exact authorization
-> strict same-transaction Branch reread
-> issue creation receipt bound to the authorization
-> ChampionStore revalidate/complete the authorization
-> Registry consume and stage exact receipt
-> owner/authorization ledger seal
-> COMMIT
-> publish one successor root
```

The same lease remains held until the complete Registry context has exited,
including classification, publication, connection-close cleanup, and owner-
lock release.

The Branch INSERT is insert-once and revision zero. A missing champion, current
champion drift, malformed champion row, duplicate Branch, target mismatch, or
any incomplete receipt/authorization state rolls back. There is no retry.

No production Branch creation becomes active in this slice. D2b.0b.C must also
cut over initial champion, promotion, weight optimization, schema authority,
controller installation, and every legacy Branch writer in one stopped-runner
migration. Until then the dormant path has no composition importer.

## H creation transaction

The started hypothesis attempt is persisted before the provider call. The
provider receives only the Branch projection captured by the exact generation
view.

After provider success, the one Registry transaction performs:

```text
validate and claim HypothesisCreationView
-> exact-read captured Branch token from the same transaction
-> reject Branch revision/digest/root-generation drift
-> exact-read the captured prior H history head or prove continued absence
-> require target.parent_hypothesis_id and parent revision/digest to match
-> exact-validate started hypothesis attempt
-> consume the exact sealed GeneratedHypothesisResult
-> exact-validate its provider receipt provenance
   (attempt, started event, context digest, prompt hash, provider result,
    durable refs, complete proposal bytes/digest)
-> reject any existing terminal transition or binding for the attempt
-> reject wrong campaign/phase/kind/Branch/H/proposal/parent identity
-> reject an active Branch or H evaluation lease
-> issue and register sealed H creation authorization in the owner ledger
-> append one validated generated hypothesis transition in this transaction
-> INSERT and strict-reread the immutable attempt-to-H binding
-> HypothesisStore exact-check Branch source and active-H absence
-> INSERT revision-zero H with the authorization
-> strict same-transaction H reread
-> issue creation receipt bound to the authorization
-> proposal-attempt participant revalidate binding and complete authorization
-> Registry consume/stage exact receipt
-> seal owner and authorization closure
-> COMMIT
-> publish one successor root
-> only then expose durable attempt ref and code-continuation identity
```

The binding's H foreign key is deferred, so the binding may establish the
authorization fact before the owner INSERT while the same transaction still
must provide the exact H before commit. A binding without H, H without binding,
event without both, or receipt without completed authorization cannot commit.

The H INSERT requires:

- exact captured Branch ID/revision/storage digest and complete row equality;
- exact captured prior H history-head identity, or exact continued absence;
- the exact sealed authorization and matching H target digest;
- H ID absence;
- no conflicting active H for the Branch;
- no active evaluation lease on the Branch or exact H; and
- the fixed owner protocol generation.

The SQL contains the durable predicates. A Python pre-check alone is not
authorization.

Registering authorization before the first semantic DML is mandatory. If the
body catches an exception after generated-event or binding insertion and tries
to continue another owner operation, the extra registered authorization makes
ledger closure fail and rolls the whole transaction back.

## Scope API

The dormant final surface is:

```text
branch_creation_transaction.create()
  # internally supplies exact ChampionLockLease + ChampionCreationSource

registry.acquire_branch_creation(
    target,
    sealed_champion_source,
    champion_lock_lease,
) -> BranchCreationView

registry.acquire_hypothesis_generation(branch_id)
  -> HypothesisGenerationView

proposal_attempt_owner.reserve_hypothesis_attempt(generation_view)
  -> StartedAttemptReservation

proposal_attempt_owner.append_and_bind_started_attempt(reservation, start_intent)
  -> StartedHypothesisAttempt

registry.bind_hypothesis_generation_start(generation_view, started_attempt)
  -> ProviderGenerationPermit

registry.spend_hypothesis_generation_on_terminal_failure(
    generation_view,
    terminal_attempt_receipt,
)

registry.prepare_hypothesis_creation(generation_view, target)
  -> HypothesisCreationView

with registry.owner_transaction(
    branch_creation_views=(branch_view,),
    hypothesis_creation_views=(h_view,),
    branch_views=(...),
    hypothesis_views=(...),
) as scope:
    scope.authorize_insert_and_stage_branch(branch_view)
    scope.authorize_insert_bind_and_stage_hypothesis(
        h_view,
        generated_result,
    )
```

`generated_result` is the exact sealed one-shot value issued by the real
receipt-aware provider-call boundary. The caller may supply ordinary event
metadata derived from it, but that metadata is unprivileged and the participant
reconstructs and validates the authoritative transition from the sealed result.
Neither value can carry SQL, callbacks, a transaction, a Registry, or a
precomputed owner authorization.

The two fused scope methods return no store, authorization, receipt, token, or
transaction-owned semantic capability. A successful detached Branch/H is read
from the published Registry root after the context exits.

Mixed mutation/creation scopes are legal only when their complete view set is
claimed before `BEGIN` and every view stages exactly once. They still produce
one generation increment and one root assignment.

Cross-view validation makes H source identity independent of fused-method call
order. For every H creation view:

- its captured Branch must exist in the old root and cannot be created in the
  same scope;
- the scope cannot mutate that Branch;
- the scope cannot mutate any existing H on that Branch;
- the scope contains at most one H creation for that Branch; and
- successor preparation re-proves that the exact captured Branch and complete
  prior H bundle are unchanged except for the one new H.

Mixed scopes may still mutate or create unrelated owners.

## Successor root rules

Root construction becomes action-aware:

- a mutation owner must exist in the captured root and advance exactly one
  revision;
- a creation owner must be absent in the captured root and commit at revision
  zero;
- an H creation's parent Branch must exist in the same successor root;
- a non-null parent H must exist in captured and successor `by_id`, belong to
  the same Branch, differ from the new H, and match the exact ID/revision/digest
  captured by the generation view; exact history-head absence requires a null
  target parent;
- all H for a Branch remain in the all-H map, while exactly one active H may
  populate the derived current-H index;
- duplicate reserved identities, a second active H, missing parent Branch,
  target mutation after view issuance, or mixed-kind witness mismatch fail
  before commit;
- prepared roots retain only internally reconstructed immutable tokens and
  projections, never caller targets, authorizations, receipts, or callbacks.

## Commit classification

Classification continues to use exactly one new independent authority-owned
read snapshot and two global predicates: `all_committed` and `all_expected`.

For mutation:

```text
expected  = exact prior owner token
committed = exact successor owner token
```

For Branch creation:

```text
expected  = Branch absent + exact immutable champion authorization source
committed = exact revision-zero Branch + exact immutable champion source
```

The champion source proof is always a strict `load_current` in the shared
snapshot, not a lookup of an old row by composite key:

```text
current exists
AND current composite key equals authorization witness
AND current complete stored bytes/digest equal authorization witness
AND current code snapshot hash equals authorization witness
```

The exact champion lease remains held through classification and publication.
A higher current row, same-key payload drift, malformed/missing current, or
snapshot fault is `UNCERTAIN_OR_MIXED`. A later legitimate successor can occur
only after Registry publication and lease release; it cannot retrospectively
invalidate the already classified historical authorization fact.

For H creation:

```text
expected  = H absent
            + generated event absent
            + attempt-to-H binding absent
            + exact started attempt present
            + exact captured Branch token present
            + exact complete affected-Branch old H bundle
            + exact captured prior-H history head or absence
            + no active Branch/H evaluation lease

committed = exact revision-zero H
            + exact generated event
            + exact immutable binding row
            + exact started attempt
            + exact captured Branch token unchanged
            + exact complete affected-Branch successor H bundle
            + exact captured prior-H history head retained
            + no active Branch/H evaluation lease
```

The affected-Branch H bundle comparison includes every H token, not only the
active-H index or parent. This prevents an external/mixed writer from changing
another H while an owner row/event/binding combination happens to match. The
classification witness and all semantic expected/committed projections are
fully materialized before the commit latch and held strongly through
classification; no weak semantic fact may disappear after commit starts.

Before semantic authorization completion, the responsible participant signs a
sealed `SemanticCreationOutcomeWitness` bound to the exact generic
authorization object identity. The participant privately owns and encapsulates
the complete expected/committed durable projections used above. Registry never
extracts, copies, or reconstructs those semantic fields. It strongly retains
the opaque witness, proves that its authorization identity is the same object
as the creation-receipt witness authorization, and may wrap those two opaque
references only for scope bookkeeping. Classification performs fixed exact
owner-kind dispatch and passes the same shared snapshot and participant-issued
witness back to that participant's reader. No caller value, weak lookup, or
callback is used after commit begins.

The fixed semantic participant readers receive the same snapshot and the exact
authorization object identity. Registry uses exact owner-kind dispatch; it
does not accept a caller callback or classifier object.

Only all-committed publishes. Only all-expected retains the old root and clears
the transition guard. Any partial H/event/binding state, malformed row,
mixed owner outcome, unavailable proof, or snapshot/decode fault becomes a
permanent integrity hold. Classification is never a mutation retry.

## Reopen and continuation

Startup inventory must validate complete event/binding/H groups before the
Registry seals live:

- exact complete group restores normally;
- a started attempt with no terminal event remains execution-uncertain and is
  handled by the active-attempt audit, not guessed or repeated;
- an exact pre-activation H or generated event present in the sealed legacy
  adoption inventory is completion-only and may be restored/read by its
  approved compatibility owner, but cannot start a new code continuation;
- a post-activation or non-adopted orphan generated event, binding, or H is an
  integrity hold;
- conflicting active H rows or binding natural keys are an integrity hold.

An approved code continuation derives hypothesis-attempt ID, H ID, proposal
digest, and generated event ID from the durable binding row. The process-local
`approved_hypothesis_bindings` map may remain only as a cache until cutover; it
is never authority after D2b.0b.C.

This slice does not add a caller-selectable direct/continuation source kind or
implement future D3 continuation policy.

Binding creation digests are historical facts, not permanent equality claims
against owners that legally advance later. An active H awaiting its code
continuation must still equal the revision-zero binding. A terminal historical
H may have a higher valid revision/status while the immutable binding remains
unchanged. The current Branch may likewise advance after creation; a current
revision lower than the binding source is corruption, while a valid higher
revision is not.

This slice adds no owner-transition history table and does not claim to replay
an unavailable full revision chain. Reopen treats fixed owner ID, exact owner
protocol generation, database-enforced insert-once/no-delete, database-enforced
`n -> n+1` updates, strict current-row decoding, and the applicable current
completion owner as the sufficient structural proof for a higher current
revision. An active H awaiting code continuation must still equal its
revision-zero binding exactly. Terminal higher-revision H/Branch state must
match its current Decision/rejection/promotion/recovery completion facts. Any
missing applicable completion fact, lower revision, wrong generation, ID
replacement, malformed row, or completion mismatch holds fail-closed.

D2b.0b.C also migrates research-rejection preparation and active-attempt audit
to binding/activation authority. Research rejection resolves the natural
`(campaign_id, provider_attempt_id)` binding and exact generated event/H;
process-local refs are display data. Active audit distinguishes reserved,
started, generated, bound, and legacy completion-only states using durable
activation provenance. `approved_hypothesis_bindings` participates in no
authorization, completion, or recovery decision. Decision completion continues
to use Registry Branch/H views and adds no attempt identity to DecisionFeatures.

## Acceptance matrix

### Capability and ledger

- forged, subclassed, copied, deep-copied, pickled, cross-database,
  cross-transaction, cross-thread, cross-Context, reused, or swapped
  authorization fails;
- UPDATE with authorization and INSERT without authorization fail;
- one authorization cannot bind two facts or complete twice;
- authorization kind/ID/target digest must equal fact, receipt, committed token,
  consumed witness, and staged view;
- mutation-only closure remains byte-for-byte behaviorally unchanged.
- a caller-constructed public `PromptCallReceipt`, proposal, event mapping, or
  same-shaped dataclass cannot substitute for `GeneratedHypothesisResult`.

### Branch

- missing/malformed/current-drifted champion fails;
- version, weight revision, snapshot hash, complete champion storage digest,
  Branch ID, or Branch target mismatch fails;
- duplicate Branch IDs race to at most one commit;
- promotion/weight before Branch `BEGIN` makes the old view fail;
- Branch `BEGIN` first makes later promotion wait and include the new durable
  Branch in its stale-set transaction after cutover;
- creation failure leaves no Registry/controller Branch.

### H

- provider-time Branch revision or root-generation drift fails without a
  generated event, binding, H, or root publication;
- provider-time prior-H history-head drift, wrong parent, or parent status/
  storage drift fails with the same complete rollback;
- wrong campaign, phase, attempt kind, started event, context digest, prompt
  hash, provider outcome, Branch, H, parent H, proposal digest, or target digest
  fails;
- failed/interrupted/code attempts cannot authorize H creation;
- duplicate terminal event, attempt binding, generated event, H ID, or active H
  fails;
- an active Branch/H evaluation lease blocks insertion;
- concurrent attempts on one Branch yield at most one active H and do not
  automatically retry.
- one generation view cannot append two starts, invoke the provider twice, or
  bind two generated results; failure/Contract rejection explicitly spends it.
- legacy activation inventory accepts only its exact immutable completion-only
  H/events and rejects any post-activation missing binding.
- mixed H creation plus source Branch/source-H mutation, same-Branch second H
  creation, or same-scope source creation fails before any transaction body
  method can make behavior order-dependent.

### Fault boundaries

Inject failure after authorization registration, write-fact allocation,
authorization binding, semantic event/binding write, owner INSERT, owner
reread, receipt issuance, semantic completion, receipt consume, Registry stage,
ledger seal, commit latch, commit return, deactivation, classification, and
immediately before root assignment.

Each case must end in exactly one of:

- complete committed durable facts plus the new published root;
- complete rollback plus the exact old root and clear guard; or
- a non-schedulable permanent integrity hold.

No case repeats a provider call or owner mutation.
