## Decision

Historical storage is evidence, not a source from which missing authority may
be reconstructed. D2b.0b.C therefore uses a fresh-first, explicit-target
activation policy:

1. a truly absent fresh database path may activate with empty historical
   inventories;
2. an existing database is never migrated by an ordinary runner open;
3. an existing database may activate only from one checked-in or deployment-
   pinned per-database scanner record whose final disposition explicitly allows
   it;
4. eligible legacy H and generated events are completion-only evidence and
   never receive a proposal binding or code-continuation authority;
5. missing campaign, Branch, proposal, provider, scientific-field, revision,
   or event facts are never guessed from paths, timestamps, defaults, adjacent
   rows, process-local maps, or current workspace state; and
6. every noneligible database remains byte-preserved and read-only under an
   explicit archive, integrity-hold, or malformed-quarantine disposition.

Disposition also fixes composition mode:

```text
fresh_empty_activate
  -> candidate_snapshot_v1 writable Campaign composition

exact_completion_only_adopt
  -> legacy_verified_commit_v1 completion-only composition
```

A legacy composition exposes only the query-only compatibility reader, exact
v1 pending-completion owner when its independently frozen candidate facts
match, and idempotent cleanup/recovery. It exposes no generation view, new
Branch/H creation, ordinary scheduler, provider, new candidate writer, new
Decision preparation, promotion, or weight optimization. Adoption alone never
authorizes a legacy completion. A later creative continuation opens a distinct
fresh `candidate_snapshot_v1` campaign with a typed `LEGACY_SUCCESSOR` evidence
link to the exact legacy activation inventory and physically proved champion or
clean parent. Candidate ownership mode never changes in place.

The 827 historical experiment databases are an evidence corpus, not a batch
migration target. D2b.0b.C must not mutate them merely because they were scanned.
The first production activation must use a fresh root. A later explicit
legacy target may use the same cutover only when its exact inventory has an
eligible disposition and the deployment owner separately selects that record.

This policy preserves historical research while allowing one production
storage/writer cutover without manufacturing provenance.

## Terms and authority

### Logical source snapshot

A logical source snapshot is the strict, read-only SQLite view obtained from an
isolated copy of one stable main/WAL/SHM bundle. It is bound to:

- relative database path under the named scan root;
- exact main/WAL/SHM presence, byte length, and SHA-256 before and after copy;
- exact SQLite schema SQL and schema-PRAGMA inventory;
- exact type-tagged complete table rows in the canonical multiset order frozen
  below, with declared key facts inventoried separately;
- `integrity_check`, `foreign_key_check`, and decoding outcomes; and
- the scanner protocol generation and source revision.

It is not the main-file hash alone and is not an SQLite page-layout claim.

### Storage fact versus semantic authority

A scanner or adoption row may prove that bytes and typed values existed. It
does not prove that a legacy provider response was sealed, that an H proposal
digest matched, that a historical Branch/H revision existed, or that a missing
scientific value had a particular default. Completion-only adoption grants no
generation, code, continuation, evaluation, Decision, or promotion authority.

### Activation target

An activation target is exactly one campaign database selected by its complete
per-database inventory digest. A root-set or aggregate digest is context, not a
wildcard authorizing every member. Ordinary campaign startup has no API, flag,
or fallback that can select a historical migration.

### Deployment selection manifest and capability

The offline cutover input is one canonical
`durable-owner-activation-selection.v1` manifest. It binds:

- cutover ID: SHA-256 of the canonical manifest with `cutover_id` omitted;
- canonical campaign directory and database path relative to the scan root;
- exact campaign ID for fresh open or exact existing campaign ID for legacy
  reopen;
- path-absence fact or selected per-database inventory digest;
- root-set and aggregate digests;
- final disposition and sorted reason-set digest;
- scanner protocol/source revision;
- pinned old runtime commit, pinned cutover runtime commit, and frozen schema
  bundle digest;
- candidate ownership mode required by disposition;
- preimage sentinel/digest and intended backup directory; and
- expected activation, owner, and binding protocol generations.

It uses the same canonical JSON rules as scanner evidence, has one terminal LF,
and is content-addressed. Under the execution lock, a dedicated offline
`CutoverSelectionOwner` exact-verifies it and issues one sealed, thread/Context-
bound, one-shot selection capability to the sole schema bootstrap owner. The
production runner, Campaign composition, Registry, provider, and CLI launch
path cannot import the issuer, accept a manifest path, select a disposition, or
request historical migration. Hidden claim/issue failure spends the capability
and leaves the target offline.

The normative machine-readable field/domain contract is the JSON Schema file

every record/domain to its exact required and allowed keys and value shapes.
Both implementations may parse that declarative contract but may not share

Its `x-scion-digest-contracts`, `x-scion-structured-item-schemas`,

`x-scion-metadata-semantics` members are normative: they enumerate every digest

frozen most-specific glob rule. A SHA field or array without exactly one
resolved contract entry is a contract failure, not an implementation default.
Every structured preimage item must validate against exactly one listed item

Tests belong in `scion/scion/tests/unit/tools/` or the existing unit-test

### Source safety

The scanner first creates a root-wide pre-manifest for every relative
`scion.db` target and every sibling directory entry whose basename starts with
`scion.db` (including known and unknown sidecars). Each fact binds
relative path, presence, `lstat` device/inode/mode/nlink/uid/gid/size/mtime-ns/
ctime-ns, and complete file SHA-256. `atime` is excluded because a read may
change it. After every per-database copy and inventory, it creates a
second complete root-wide manifest. The two canonical manifests and their path
sets must be byte-identical or the entire aggregate is
an invocation failure; no per-database disposition or aggregate from that
invocation is activation evidence.

A symlink or nonregular candidate/sidecar is never opened or hashed through
its target. Its root-manifest entry contains the exact `lstat`,
`content_state="unavailable_nonregular"`, NULL byte length/SHA, and the matching
frozen path reason; stable pre/post equality allows a malformed-quarantine
record. A path escape, unreadable directory, or unstable root prevents
publication of the entire invocation.

For every candidate database the scanner must:

1. treat path escape, duplicate candidate names, an unreadable parent, or an
   output directory inside the scanned root as whole-invocation failure;
   symlink/nonregular candidates are lstat-only malformed records as above;
2. open the scan root once and traverse every path component from that fixed fd
   using fd-relative enumeration and `openat(O_RDONLY|O_DIRECTORY|O_NOFOLLOW|
   O_CLOEXEC)` for directories, then `openat(O_RDONLY|O_NOFOLLOW|O_CLOEXEC)`
   for files; bind every read to pre/post `fstat` plus a
   same-device/inode re-`lstat` check;
3. stream each opened main/WAL/SHM descriptor once into a private file while
   hashing the exact bytes read; require copied length/hash to equal both the
   per-file pre-fact and post-fact;
4. classify each `lstat` fact by file type before applying link rules. A stable
   symlink or nonregular `scion.db` remains the lstat-only malformed record
   above, regardless of its `nlink`; it is never an activation source. Every
   regular root-manifest entry, including regular main/WAL/SHM and unknown
   sidecars, must have `nlink == 1` and a device/inode identity not used by any
   other regular entry. A regular hard-link alias, repeated regular
   device/inode identity, or `nlink != 1` is whole-invocation failure with no
   authoritative artifacts. This type classification is the sole precedence
   rule, so a directory named `scion.db` cannot be reclassified as a hard-link
   failure merely because directories commonly have `nlink > 1`. Repeat
   bundle presence, hashes, and stats after copy, and likewise abort the
   complete scan on any change before SQLite open;
5. hash the complete private bundle and then open only it through SQLite URI
   `mode=ro`, set `query_only=ON`, disable extension loading, and install an
   authorizer that denies ATTACH/DETACH, DDL, DML, transaction control,
   writable PRAGMAs, user functions/extensions, and every action outside the
   frozen read/metadata PRAGMA allowlist;
6. leave source bytes, mtimes, modes, ownership, main/WAL/SHM presence, and
   directory entries unchanged; and
7. remove only its private temporary copy after the inventory bytes are fully
   materialized.

The accepted basename set is exactly `scion.db`, `scion.db-wal`, and
`scion.db-shm`; every other same-directory basename beginning with
`scion.db` is inventoried as an unknown sidecar. The accepted sidecar matrix is
main-only or main+WAL+SHM. WAL without SHM, SHM
without WAL, a rollback journal, or any such unknown sidecar is
`source_bundle_incomplete`. The scanner never treats `immutable=1` on the main
file as WAL visibility and never copies only `scion.db` when a sidecar exists.
A stable malformed bundle is recorded from the isolated copy and is never
repaired in place. The malformed record uses a frozen stage/error code and
`unavailable` inventory fields; raw SQLite messages containing temporary or
absolute paths never enter hashed output.

### Canonical value encoding

Inventory JSON is UTF-8 with `ensure_ascii=false`, `allow_nan=false`, sorted
object keys, and separators `(',', ':')`. Arrays retain the frozen order below.
There is no scan time, hostname, absolute path, PID, temporary path, or other
nondeterministic field in hashed output.

Relative paths are ordered by their original UTF-8 bytes with no Unicode
normalization; a non-UTF-8 path is a scanner invocation failure. Every
structured-inventory digest preimage is a canonical domain-tagged object with
the exact outer shape
`{"domain":"scion.durable-owner-activation.<name>.v1","items":[...]}`;
no other outer key is permitted. A collection places its ordered members in
`items`; a record digest places exactly one record object, with only its own
digest field omitted, in `items`. A raw JSON array, concatenation of encoded
values, or length-prefixed stream is never such a digest preimage. Each named schema
in the normative contract freezes exact required/allowed keys and value shapes;
unknown or omitted keys fail verification. Other digest classes are disjoint:
source-bundle members hash raw file bytes; text-value SHA hashes exact UTF-8
bytes; blob-value SHA hashes raw blob bytes; path-set SHA hashes the terminal-
NUL stream frozen above; artifact SHA and `SHA256SUMS` hash complete artifact
bytes including terminal LF; contract SHA hashes exact schema-file bytes; and
runtime/source-bundle SHA uses its named structured contract. No field may
substitute one class for another. The evidence binds the scanner's complete
transitive local-source bundle and this contract file, not a Git tree/commit
that also contains the generated evidence. `scanner_source_sha256` covers
sorted relative source path, byte length, and raw-file SHA entries for every
scanner/local-helper import; a static closure test rejects an omitted local
import, and no production module is allowed. Standard-library behavior is
bound by the runtime object.

Every SQLite value is encoded as an object with the following exact key set;
no additional key is permitted:

- null: `{"type":"null","value":null}`;
- integer: `{"type":"integer","value":<decimal JSON integer>}`, with
  booleans forbidden;
- real: `{"bits":"<16 lowercase hex>","type":"real"}` containing the
  IEEE-754 binary64 network-byte-order bit pattern; NaN patterns are rejected,
  infinities are retained, and negative zero is distinct in source inventory
  even where the final owner projection canonicalizes it;
- text: `{"sha256":"<lowerhex>","type":"text","value":"<exact
  SQLite-returned Unicode>"}`; and
- blob: `{"byte_length":<integer>,"hex":"<lowerhex>","sha256":
  "<lowerhex>","type":"blob"}`.

JSON-looking TEXT is never parse-rendered for identity. Its exact returned TEXT
and UTF-8 digest are retained, so duplicate keys, whitespace, number spelling,
and key order remain visible. The source bundle hashes retain the byte-forensic
identity when SQLite text encoding differs from UTF-8.

The `final-owner-row.v1` digest never uses a generic caller-selected column
vector. Its one preimage item has exactly `column_names` and `values`, with no
embedded digest. The only accepted column-name tuples are:

```text
Branch:
branch_id,state,base_champion_id,base_champion_hash,lineage_id,
current_code_hash,last_clean_code_hash,screening_expand_count,
validation_expand_count,failure_codes,created_at,updated_at,direction,
weight_revision,branch_code_status,branch_evidence_summary_json,
infra_block_count,owner_revision,owner_protocol_generation

H:
hypothesis_id,branch_id,change_locus,action,status,target_file,
parent_hypothesis_id,suggested_weight,hypothesis_text,created_at,
base_champion_version,family_id,family_source,taxonomy_version,
predicted_direction,proposal_digest,owner_revision,
owner_protocol_generation
```

They are the literal focused-store tuples and appear in that order. Values have
the same cardinality and use the per-position schema, not merely the generic
typed-value union. Identifier/status/hash/time/JSON/protocol positions are
typed TEXT, counters/revisions are typed INTEGER, and only the explicitly
nullable source fields admit typed NULL. H
`suggested_weight` is either typed NULL or a finite binary64 REAL. Strict final
projection maps either signed numeric zero to positive-zero bits
`0000000000000000`; negative-zero bits `8000000000000000`, both infinities,
and every NaN are invalid final-owner values. They remain visible in the source
inventory where the generic source encoding admits them, but infinity/NaN
fails strict H decoding and therefore cannot produce a final-owner digest. A
legacy H has a non-NULL final-owner digest exactly when
`final_owner_eligible=true`; otherwise that digest is NULL.

Any value that Python's SQLite wrapper cannot return in one of these exact
representations, including an invalid Unicode decode, records unavailable value
facts plus `canonical_value_decode_failed`; it is never skipped or stringified.
Every unreadable derived field uses the schema's exact singleton sentinel
`{"state":"unavailable"}`. The sentinel deliberately contains no duplicated
stage or error code: top-level `decode_error_stage` and `decode_error_code` are
the sole error identity for the record. Additional sentinel keys are invalid.
It is distinct from numeric zero, an empty array, SQL NULL, and path absence;
raw exception text never enters evidence.
`inventory_state=available` requires every derived union to take its concrete
branch. `inventory_state=unavailable` requires every count, ID set/digest,
semantic projection, decode outcome, logical-row digest, and table inventory to
use that same sentinel; campaign/mode are likewise unavailable and storage
signature is `unsupported`. At `sqlite_value`, `sqlite_rows`, or
`logical_tables/unsupported_virtual_or_shadow_schema`, the already decoded
schema inventory and digest remain concrete while all logical table/semantic
fields are unavailable. At path, bundle, open, or schema stages, schema fields
are unavailable too. These are the only masks. Available ID sets and logical
table sets always hash their structured envelope, including an empty `items`
array; their digest is never NULL.

SQLite failure classification uses the primary result code
`sqlite_errorcode & 0xff`; an exposed extended code does not change the class.
Primary `SQLITE_CORRUPT` (11) or `SQLITE_NOTADB` (26) is always
`sqlite_malformed` at the operation's stage. Any other SQLite exception, or a
wrapper exception without `sqlite_errorcode`, is `sqlite_open_failed` only
during connection construction, read-only URI establishment, safety-PRAGMA
installation, extension disabling, and authorizer installation. The open
stage ends before the first inventory query. A non-corruption SQLite failure
during schema inventory or logical-row reading is `sqlite_read_failed` at
`sqlite_schema` or `sqlite_rows` respectively. Schema inventory is exactly
`database_list`, temp/main schema reads, `sqlite_schema`, `table_list`, all
per-table/index PRAGMAs, integrity/foreign-key checks, `user_version`, and
`application_id`; logical-row reading begins with the first accepted table's
complete column-vector SELECT. In-process typed-value conversion is
`sqlite_value`. At that stage `invalid_unicode_text` requires
`decode_error_location.value_kind="text"`, while
`unsupported_sqlite_value` requires `value_kind="unknown"`; neither mapping
is caller-selectable. These stage/result rules, not exception text, select
evidence.

Failure priority is path -> bundle classification -> SQLite open -> schema ->
logical-table support -> logical-row read -> value encoding -> strict semantic decoders. Within
value encoding, the scanner checks tables by UTF-8 table name and columns by
`table_xinfo` order, scans the complete column for decodability, and reports
the first failing table/column in that order; invalid Unicode precedes any
other unsupported-value code at the same location. Row fetch order never
chooses the reported failure.

Every array has one order. Relative paths, table/index/field/entity/campaign
IDs, enum names, and compile options sort by original UTF-8 bytes. Root/bundle/
private-copy facts sort by relative path then entry-kind. Tables and table-
PRAGMA groups sort by table name; index groups sort by index name. Canonical
row arrays sort by complete canonical row bytes, except `sqlite_schema`, whose
primary tuple is type/name/table followed by row bytes. Decode outcomes,
legacy-H rows, presence bitmaps, and generated pairs sort respectively by
entity ID, hypothesis ID, entity ID, and the tuple campaign/attempt/started/
generated IDs, with complete canonical item bytes as the final tie-breaker.
Presence fields, observed campaign IDs, reasons, and all name/count arrays sort
by name/ID bytes and reject duplicate names. Artifact `items` singletons remain
singletons. No query-plan, insertion, dictionary, filesystem-enumeration, or
locale order enters identity.

### Schema and row order

The schema inventory reads only schema `main` and includes every row of
`main.sqlite_schema`, including `sqlite_%` objects and NULL SQL. “Noninternal”
means an object whose name does not begin with exact ASCII `sqlite_`; that term
controls signature/reason rules only and never excludes an object or table row
from inventory. It also records exact output from `PRAGMA main.table_list`; for
every listed table it records `table_info`, `table_xinfo`,
`foreign_key_list`, and `index_list`, and for every listed index it records
`index_xinfo`. Identifiers are passed as bound values to table-valued PRAGMA
forms rather than SQL-interpolated. It records all rows from no-argument
`PRAGMA integrity_check`, `PRAGMA foreign_key_check`, `user_version`, and
`application_id`. It validates raw `PRAGMA database_list` but never hashes its
path-bearing file column; exact `(sequence=0, schema=main, nonempty private-copy
path)` is projected to the fixed path-free `isolated_private_bundle` attachment
record, and the temp schema must be empty. Views are inventoried but never executed. Unknown or
partial owner/activation schema is a hold, never a best-effort version match.

It also includes canonically sorted `table_list`, `table_xinfo`,
`integrity_check`, and `foreign_key_check` rows; views are inventoried but never
executed. Schema arrays sort by type/name/table plus their complete canonical
row bytes; PRAGMA result arrays sort by complete canonical row bytes. The
scanner runtime object has exactly these keys: `python_implementation`,
`python_version`, `python_cache_tag`, `python_sqlite3_wrapper_version`,
`sqlite_library_version`, `sqlite_source_id`, `sqlite_compile_options`,
`unicode_database_version`, and `sys_byteorder`. Compile options are sorted by
their original UTF-8 bytes; every other value is exact TEXT and no host, time,
or path field is admitted. An unknown virtual/shadow table is a hold. SHM bytes
remain host-sensitive forensic bundle facts and never become logical row
identity by themselves.

Column order comes from `table_xinfo`, including generated/hidden flags; an
unsupported virtual/shadow/generated-column schema is an explicit hold. Every
row is selected as the complete frozen column vector, encoded in process, and
the canonical row byte strings are sorted lexicographically in process. The
table digest is over that sorted multiset, so custom collations, DESC keys,
nullable ordinary-rowid primary keys, duplicate identical rows, and query plan
order cannot change the inventory. WITHOUT ROWID tables must also have a strict
non-null unique declared primary key. For ordinary tables the declared key is
inventoried separately and checked for null/duplicate values; a table without a
strict durable primary identity may be reported but cannot supply activation
authority. `rowid` never enters canonical identity.

### Required per-database record

Each JSONL record includes at least:

- scanner protocol and source revision;
- normalized relative database path and its SHA-256;
- source main/WAL/SHM file facts and a typed stable-copy witness containing
  source-before facts, private-copy length/hash facts, source-after facts,
  their three structured digests, and the exact equality/result state;
- complete schema inventory digest;
- complete logical row inventory digest and per-table counts/digests;
- campaign singleton value, all nonempty campaign IDs observed in relevant
  events/facts, and exact consistency result;
- Branch and H counts, orphan H IDs/count/digest, active-H conflicts, and exact
  strict-decode outcomes;
- physical presence versus NULL for every final Branch/H owner field;
- full legacy H source-row digest, final-owner projection eligibility, and all
  extra columns/facts not covered by that projection;
- START/generated pair identities and the full stored event-row digest;
- binding/activation/adoption/lease/completion schema and row inventories;
- integrity, foreign-key, malformed, unknown-schema, and ambiguity reasons;
- exactly one final disposition; and
- one canonical per-database inventory SHA-256 covering every field above
except that digest field itself.

The dedicated binding/adoption/completion fields are mirrors of their rows in
the complete schema/table inventory. Activation and lease inventories are
represented only by that complete schema/table inventory and are never
duplicated into a second projection; the verifier checks the three mirrors for
byte equality and derives activation/lease from the sole complete owner.

`claim_campaign_id()` output is never scanner evidence. An existing singleton
does not excuse a full relevant-row campaign-ID consistency check. A caller-
proposed ID is considered only for `fresh_empty_activate` after the scanner has
proved zero historical domain rows.

For an available regular bundle, the witness's before and after facts are
byte-identical and equal `bundle_facts`; each private-copy length/hash equals
its same-kind source member, and `copy_result` is `stable_equal`. Fresh absence
uses empty member arrays plus `not_applicable_absent`; a stable nonregular fact
uses `unavailable_nonregular`, and a stable rejected sidecar matrix uses
`unavailable_bundle_incomplete`. Any other combination is contract-invalid.

### Root and aggregate artifacts

`root-manifest-before.json` and `root-manifest-after.json` contain the complete
canonical root-wide facts described above, including unknown sidecars and the
negative-presence fact for an explicit fresh target. They deliberately contain
no phase/time field and must be byte-identical. `root-set.json` contains the
sorted relative database paths and both labeled absolute-context/portable-
relative algorithms. `databases.jsonl` is ordered by relative path and contains
one canonical object per line. Every JSON/JSONL file uses exactly one terminal
LF; JSONL has one object and one LF per record and no blank line.
`aggregate.json` binds:

- scanner protocol/source revision;
- both root-manifest digests, their required byte equality, root-set digest,
  and database count;
- SHA-256 and byte length of `databases.jsonl`;
- disposition/reason counts;
- exact schema/table/row totals and overlapping condition counts;
- main/WAL/SHM bundle counts and aggregate source-file-fact digest; and
- aggregate inventory SHA-256 over the complete canonical object excluding
  only its own digest field.

`SHA256SUMS` uses lowercase hex, two ASCII spaces, the exact relative artifact
name, lexicographic filename order, and one terminal LF. It binds the five
artifact files preceding it. Two clean scanner invocations against an
unchanged root must produce byte-identical artifacts. A second implementation
must be able to verify the artifacts without opening a production writer.

The independent verifier entry point is
`scion/tools/verify_durable_owner_activation_inventory.py`; it may share frozen
JSON fixture bytes but not the scanner canonicalizer implementation. It must
independently verify byte framing and terminal LFs, fixed artifact membership,
every SHA, canonical re-encoding and exact schema key set, path/record/table
ordering, root-manifest equality, every local/per-database/root/aggregate
digest, cross-file counts, reason normalization and disposition recomputation,
and scanner/contract/runtime identity. Artifact-only mode validates the stored
runtime object's shape and digest but does not require the verifier's current
runtime to equal it. The source-root mode independently
repeats descriptor traversal, private bundle copy/open, schema/row/value
extraction, reason normalization, disposition, and every artifact construction;
it requires byte equality with all six published files, not merely root-
manifest equality.
A static AST test proves the verifier has no direct or transitive import of the
scanner or its canonical helpers and no production store, Registry, provider,
bootstrap, or composition import.

Output is built in a new sibling directory. Every file is fsynced,
`SHA256SUMS` is written last, and the new directory is fsynced. Publication on
Linux must use a fixed parent fd and `renameat2(RENAME_NOREPLACE)` and fail
closed if that primitive is unavailable; after it succeeds, both the published
directory and its parent are fsynced. Existing evidence is never replaced in
place.

A corpus scan lstat-enumerates every directory entry whose basename is exactly
`scion.db`, regardless of file type; only regular single-link candidates are
opened, while stable symlink/nonregular candidates receive their frozen
malformed records. Cutover evidence uses reserved `.bin` names and therefore
cannot become a candidate. A fresh-target scan is
a distinct explicit invocation whose root set contains the one intended
relative target path even though it is absent; `databases.jsonl` contains its
canonical `absent.v1` record and the aggregate database count is one. An absent
target is never silently appended to the 827-root corpus artifact.

## One final disposition per database

The scanner recognizes only these storage signatures:

- `absent.v1`: target path is absent under a descriptor-pinned parent;
- `exact-empty-sqlite.v1`: an explicitly selected existing SQLite file with no
  noninternal schema object, no WAL frame, `user_version=0`, and
  `application_id=0`;
- `legacy-lineage.v1`: no owner/activation generation exists; Branch contains
  the seventeen pre-owner fields frozen by `branch_owner_store`, H contains the
  sixteen pre-owner fields frozen by `hypothesis_owner_store`, and every named
  campaign/completion/champion/event table matches an accepted legacy decoder;
  extra columns are inventoried but never interpreted as owner fields;
- `durable-owner-active.v1`: exact final schema bundle, activation, runtime
  state, triggers, indexes, and digest rows all validate; and
- `unsupported`: every other, partial, or mixed signature.

The named pre-owner fields are the exact ordered column tuples in the focused
stores with `owner_revision` and `owner_protocol_generation` removed. Physical
absence is decided before value decoding. A missing required field produces an
archive reason; a present field whose typed value fails its strict decoder
produces an integrity reason. These outcomes cannot overlap.

Relevant campaign facts are every noninternal row in a table with a physical
`campaign_id` column plus campaign identity/mode, Branch, H, champion,
experiment-event, completion, candidate, promotion, weight, optimization,
binding, activation, and adoption tables. `domain_row_count` is the total row
count of that frozen relevant-table set; unknown noninternal tables make the
signature unsupported rather than being silently excluded.

replay-pending, and telemetry-failed states, is nonterminal for historical
activation and produces `historical_nonterminal_h`.

Let `R` be the sorted duplicate-free reason set. A code outside the enum is a
scanner contract failure and produces no authoritative artifact. Before
disposition, if `R` is not one of the exact fresh/active/benign-adoption sets
below and contains none of the malformed/integrity/archive reason classes, the
scanner adds `reason_combination_invalid`. Disposition is the following total
pure function:

```text
if R == {fresh_path_absent}:
    fresh_empty_activate
elif R == {already_active_exact}:
    already_active_exact
elif R intersects {
  source_path_symlink, source_path_nonregular,
  source_bundle_incomplete, sqlite_open_failed, sqlite_malformed,
  sqlite_read_failed
}:
    malformed_quarantine
elif R intersects {
  canonical_value_decode_failed, integrity_check_failed, foreign_key_check_failed,
  unsupported_schema_signature, partial_owner_schema,
  partial_activation_schema, active_generation_mismatch,
  campaign_ids_multiple, campaign_identity_missing_for_history,
  campaign_identity_conflict, candidate_mode_conflict,
  orphan_hypothesis, duplicate_active_hypothesis,
  binding_natural_key_conflict, partial_generation_group,
  completion_owner_conflict, active_evaluation_lease,
  strict_branch_decode_failed, strict_hypothesis_decode_failed,
  strict_event_decode_failed, strict_completion_decode_failed,
  strict_champion_decode_failed, unsupported_virtual_or_shadow_schema,
  existing_activation_digest_mismatch, existing_empty_target_forbidden,
  reason_combination_invalid

    integrity_hold
elif R intersects {
  missing_final_branch_field, missing_final_hypothesis_field,
  historical_nonterminal_h, no_durable_primary_identity

    archive_only
elif legacy_completion_only in R and R is a subset of {
  legacy_completion_only, legacy_generated_pair_completion_only,
  legacy_extra_preserved, legacy_proposal_authority_unproved

    exact_completion_only_adopt

    integrity_hold
```

`already_active_exact` is a reopen-verifier result, never a migration target.
Fresh and active reason sets are exact singletons. Exact adoption requires the
literal benign subset in the function. Every other known-code combination
fails closed.

Each database therefore has exactly one disposition selected in this
precedence order:

### 1. `malformed_quarantine`

Use when the pure function above selects it. Preserve the original bytes.
Only isolated-copy forensic reads are permitted. No in-place repair, bootstrap,
resume, or production open is allowed.

### 2. `integrity_hold`

Use for a readable database with any enumerated authority ambiguity or
contradiction, including:

- more than one relevant nonempty campaign ID;
- historical domain rows but no uniquely attributable campaign ID;
- an H whose nonempty Branch ID has no exact Branch row;
- duplicate/conflicting active H, binding natural keys, or completion owners;
- partial generated event/binding/H groups;
- unknown or partial activation/owner schema;
- a strict stored row, event, completion, champion, or owner decode fault;
- a claimed singleton inconsistent with any relevant stored campaign ID; or
- any fact that would require guessing identity, ordering, provenance, or a
  missing scientific value.

An integrity-held database remains archive-readable through a legacy read-only
owner but cannot activate.

### 3. `archive_only`

Use for internally readable and attributable historical evidence that cannot
satisfy the exact completion-only adoption contract. This includes a database
whose H table lacks any final owner field required to decode its final storage
projection, or whose nonterminal H would require an unproved proposal/binding to
continue. Missing fields are recorded in the presence bitmap; they are not
filled with `exploratory`, zero, null family, current champion, or any other
compatibility default during activation.

Archive-only data may remain visible to postrun/report readers. It cannot be
opened by production campaign composition after D2b.0b.C.

### 4. `exact_completion_only_adopt`

Use only when all of the following hold:

- the bundle is stable/readable and has exactly one existing campaign identity
  consistent across every relevant row;
- every H has an exact existing Branch and, except for the two migration-
  established owner fields below, all final storage fields are physically
  present and strictly decodable without a compatibility default;
- every adopted H status belongs to the exact completion-only set above;
- owner revision/generation are the only absent storage metadata and may be
  established explicitly as migration revision zero and `durable-owner.v1`;
- all completion intents, champions, events, and Branches satisfy their exact
  migration contracts;
- every legacy extra has an exact type-tagged source representation and digest;
- every adopted generated event has a full stored event-row identity; and
- no unknown, orphan, partial, or conflicting group exists.

Proposal digest may be physically present as NULL and preserved as NULL. That
H remains completion-only and is excluded from every source-H/code-continuation
authority. The migration does not derive a digest from H text or a nearby event.

### 5. `fresh_empty_activate`

Use only for `absent.v1`. An existing SQLite file, even if it has zero
noninternal objects/rows, receives `existing_empty_target_forbidden` and must be
left untouched; a new absent target path is selected instead. A fresh schema
activates with empty adoption inventories. The first domain ownership
transaction may create the manifest's campaign identity after schema bootstrap.

For absent fresh activation, the scanner emits a canonical absence record bound
to the descriptor-pinned parent path and a `fresh-absent-preimage.v1` sentinel:

```json
{"database_present":false,"schema_objects":[],"tables":[],"wal_present":false,"shm_present":false}
```

The empty schema, row, and adoption digests each use its distinct frozen
domain-tagged object envelope with an empty `items` array; raw `[]` is never
hashed. Root/aggregate/selected-inventory fields remain present and are derived
from the explicit intended target record. The activation owner never creates
the selected target path directly. After acquiring the execution lock and
revalidating target absence, it creates a cutover-private staging database with
`O_CREAT|O_EXCL`, completes bootstrap there, closes it with no WAL/SHM or
rollback-journal member remaining, fsyncs and independently verifies it, and
retains those sealed bytes. It then copies those bytes without opening SQLite
to an `O_CREAT|O_EXCL` sibling of the still-absent target, fsyncs and hash-
verifies the copy, and publishes that copy with
`renameat2(RENAME_NOREPLACE)` plus target-parent fsync. The sealed stage remains
available for exact crash recovery. No ordinary SQLite connection factory may
create the target or set journal mode before this publication is reconciled.

### `already_active_exact`

This is an independent exact reopen-verifier result for an already activated
database. It validates final schema, activation, runtime state, campaign/mode,
and every stored digest. It is never accepted by the migration selector.

The disposition is not a research gate. It controls storage-protocol authority
before any provider or Protocol call.

## Facts that may never be invented

The migration has no authority to synthesize:

- proposal digest or proposal-H equality;
- sealed provider result, receipt, trace, manifest, raw-response provenance, or
  provider-attempt natural key;
- a pre-cutover Branch/H revision chain;
- a missing `predicted_direction`, family, taxonomy, base champion, target, or
  mechanism value;
- campaign, Branch, parent-head, binding, or event ordering identity;
- JSON semantic equality after parsing/re-rendering; or
- a clean/current workspace or champion relationship not independently proved
  from its owning artifact and digest.

Migration-established revision zero and protocol generation describe the
post-cutover storage owner only. They make no claim that legacy writers used CAS.

## Existing-database open policy

Every initial probe uses descriptor-pinned path inspection and, for an existing
file, SQLite URI `mode=ro` plus the scanner/verifier owner. It never calls the
current connection factory, creates a file, sets WAL mode, or runs `_ensure_columns`.

Before any ordinary startup, the offline `CutoverBootstrapOwner` has exactly
two selection-capability routes under the execution lock:

1. `fresh_empty_activate`: reverify the explicit absent record, run fresh
   bootstrap in the cutover-private staging database, and atomically publish
   an exact verified copy of the sealed main-only database to the absent target;
   or
2. `exact_completion_only_adopt`: open the selected `legacy-lineage.v1` target
   read-only, exact-match its inventory and unique existing campaign identity,
   then open the sole migration transaction and run legacy adoption/bootstrap.

An existing empty file has no route. A selected historical target never enters
ordinary startup before its schema transaction commits.

After D2b.0b.C, ordinary production startup distinguishes three cases:

1. exact active generation, activation singleton, matching final receipt, and
   runtime state
   `domain_opened/revision 1`: run the independent active verifier and reopen in
   the stored candidate ownership mode;
2. exact active generation and runtime state `schema_committed/revision 0`:
   ordinary startup holds; only the dedicated `CutoverRecoveryOwner` with the
   execution lock, matching recovery capability, cutover ID, pinned deployment
   receipts, and preimage may open it for forward validation or authorized
   restore; or
3. anything else, including an absent unprepared target or a selected-but-
   unactivated legacy file: raise a historical-activation-required hold with zero schema
   change and zero provider/Protocol access.

There is no opportunistic `_ensure_columns`, automatic legacy claim, timestamp
heuristic, or normal-run migration. Legacy postrun/report commands open through
a distinct query-only compatibility owner and cannot construct Campaign runtime
composition.

An existing campaign singleton is not attribution proof. Every relevant event,
H, Branch, completion, promotion, and optimization campaign fact must match the
selected inventory. Exact legacy adoption requires a preexisting campaign
singleton whose value equals the one-element set of all relevant stored
campaign IDs. Historical state with no singleton, zero IDs, multiple IDs, or a
conflicting ID is held under this addendum; the broader D2a compatibility
adoption does not override this narrower activation policy.

`claim_campaign_id(proposed)` is valid only for a fresh absent target after the
selection manifest has already fixed that ID. It can never assign a historical
or existing-empty database.

Restore classifies H rows through exact binding membership or immutable
completion-only adoption membership. Timestamp shape is never a source-kind or
authority heuristic.

`fresh_empty_activate` opens `candidate_snapshot_v1` and may advance runtime
state to `domain_opened` in the same first ownership transaction that inserts
the manifest-bound campaign identity and mode. `exact_completion_only_adopt`
opens `legacy_verified_commit_v1` through a separate completion-only
composition. That composition cannot construct Campaign scheduling or proposal
services. Any later research uses a new fresh successor database/campaign and
the frozen `LEGACY_SUCCESSOR` evidence link; the legacy mode is immutable.

The bootstrap selection capability is consumed exactly once and cannot be
reused. Before target publication/legacy schema COMMIT, a distinct
`CutoverBootstrapAttemptOwner` may reissue one one-shot attempt capability only
when the execution lock, immutable 010/020 receipt chain, selection/preimage,
pinned commits, closed deployment ledger, and exact source preimage all match
and no 030 receipt exists. For legacy, SQLite rollback must reproduce the
selected bundle. For fresh with no 025, the target must remain absent and the
private stage must be one of: absent; exact fully bootstrapped main-only bytes
whose missing 025 receipt may be reconstructed; or partial cutover-owned bytes
moved by no-overwrite rename into a unique quarantine name before a new stage
is created. Attempt ordinals form a separate one-based namespace from fixed
phase-receipt ordinals 010..092. The first attempt's
`previous_attempt_receipt_sha256` is exactly 64 ASCII zeroes; later attempts
bind the raw-file SHA of the immediately prior attempt receipt, with no gap.
`attempt_id` is the structured-inventory SHA of the exact
`scion.durable-owner-activation.attempt-id.v1` envelope containing cutover ID,
integer ordinal, and previous SHA. The no-overwrite filename uses an eight-
digit zero-padded ordinal plus attempt ID; the JSON stores the unpadded integer.
The quarantine name is `failed-prepublish/<attempt_id>-<file_sha256>`. With 025, the
sealed stage must exact-match its receipt; an absent or exact matching target-
sibling publication copy may be resumed, while a partial copy is quarantined
before it is recopied from the sealed stage. No other file may be deleted or
overwritten.

After target publication/legacy schema COMMIT, only
`CutoverSelectionOwner` may issue a distinct one-shot recovery capability. It
must revalidate the immutable selection manifest, cutover ID, target DB
activation/runtime state, exact maximal valid no-gap receipt prefix, preimage,
pinned runtime commits, and execution lock. For `schema_committed`, the allowed
prefix ends at 020 for legacy or 025 for fresh when 030 is missing, at 030 when
040 is missing, or at 040 before domain open. For `domain_opened`, it ends at
040 when 050 is missing. Every other gap, extra receipt, or DB/prefix mismatch
is a hold. Production modules cannot issue any of these capabilities.

After the first ownership transaction commits `domain_opened`, the supervisor
must publish and verify `050-domain-opened.json`. Only then may the unique
`CampaignRuntimePublicationOwner` issue the sealed capability required to
construct the Campaign runtime root. Before that capability exists, provider,
Protocol, scheduler, Registry mutation, and filesystem-publication views are
structurally unconstructable, including inside the same supervisor process. A
static import/caller/capability-closure test enforces this boundary. A crash in
that window leaves the database authoritative but ordinary startup held; the
recovery owner reconstructs the missing receipt from exact DB and filesystem
facts. External receipt absence never rolls back the DB transition.

## Clean stop and process exclusion

For one selected target, the deployment owner must, in order:

1. disable every launch source;
2. stop wrapper, runner, async weight worker, solver/executor subprocess, and
   every process able to call provider, Protocol, or the database;
3. prove recorded PIDs terminal and inspect `/proc/*/fd` for the database,
   WAL/SHM, workspace, champion, and publication tree;
4. start the pinned cutover runtime's long-lived Campaign supervisor and have
   that same process acquire `<campaign_dir>/.scion/campaign-execution.lock`
   using no-follow, create, close-on-exec, nonblocking exclusive `flock`
   semantics;
5. keep the descriptor in that same non-execing supervisor through cutover,
   in-process Campaign open, and the complete Campaign lifetime; solver/executor
   children use close-on-exec/`close_fds` and never inherit it;
6. under the lock, rerun the scanner and exact-match the selected inventory;
7. create and fsync the preimage manifest and byte-exact main/WAL/SHM backup,
   plus workspace/champion/publication identity inventory;
8. verify `/proc` visibility is complete in the current PID/mount namespace;
   permission or namespace uncertainty is a hold;
9. run bootstrap; after schema COMMIT and before domain open, use one controlled
   pre-bootstrap legacy connection to prove legacy INSERT/REPLACE and
   nonrevision UPDATE are rejected, then close it; and
10. run cutover acceptance and enter Campaign open in the same supervisor before
   any lock release.

Failure at any pre-schema step leaves source state unchanged.

## Crash, rollback, and forward-only boundary

The cutover evidence directory is fixed and no-overwrite:

```text
<campaign_dir>/.scion/durable-owner-cutover/<cutover_id>/
  selection.json
  preimage-manifest.json
  preimage/main.bin
  preimage/wal.bin
  preimage/shm.bin
  fresh-staging/main.bin
  restore-staging/main.bin[,wal.bin,shm.bin]
  attempts/<ordinal>-<attempt_id>.json
  receipts/010-prepared.json
  receipts/020-preimage-sealed.json
  receipts/025-fresh-staged.json
  receipts/030-schema-committed.json
  receipts/040-validated.json
  receipts/050-domain-opened.json
  receipts/090-restore-prepared.json
  receipts/091-restore-in-progress.json
  receipts/092-restore-verified.json
  failed-prepublish/<attempt_id>-<file_sha256>
  failed-postbootstrap/main.bin[,wal.bin,shm.bin]
```

The directory is mode-restricted, rejects symlink/hardlink/path escape, and is
created under the execution lock. `selection.json` and
`preimage-manifest.json` are canonical content-addressed files. Preimage files
are copied by pinned descriptors, fsynced, hash/length matched, and published by
no-overwrite rename followed by file and directory fsync. They and every receipt
are retained permanently after `domain_opened`; no cleanup API exists.

Each receipt is a separate canonical no-overwrite file binding cutover ID,
selection/preimage digests, pinned old/new runtime commits, receipt kind,
monotonic receipt ordinal, previous-receipt SHA-256, exact database bundle
facts, workspace/champion/publication facts, and applicable schema/domain
digests. It is written to a sibling temporary file, fsynced, published with
`renameat2(RENAME_NOREPLACE)`, and its directory fsynced. A receipt is audit/recovery evidence;
the database runtime state remains open authority.

The fresh target-sibling publication name is exactly
`.<target-basename>.scion-cutover-<cutover_id>-<attempt_id>.publish.bin` under
the descriptor-pinned target parent. It is the only publication scratch name
the attempt owner may inspect or create. Legacy restore scratch members use
only the fixed `restore-staging/{main,wal,shm}.bin` paths above; absent source
members have absent scratch members. No PID, random suffix, time, or directory
enumeration heuristic participates in recovery.

The normal forward phases are:

```text
prepared
-> preimage_sealed
-> fresh_staged                 # fresh only; legacy omits this phase
-> schema_committed
-> validated
-> domain_opened
```

The selection manifest creates the immutable cutover ID. For fresh activation,
025 binds the fsynced, closed, main-only sealed staging DB and its exact active
verification. Publication copies its bytes to an exclusive target sibling,
fsyncs and rehashes the copy, then uses `RENAME_NOREPLACE` and fsyncs the target
parent; 030 binds the published inode and database digests. For legacy, 030
directly follows the in-place COMMIT. The schema transaction inserts the exact
runtime-state singleton at `schema_committed/revision 0` and the activation
singleton with the same ID. `CampaignOpenStore` is the only
production caller authorized to issue the exact SQL UPDATE admitted by the
runtime-state trigger. It CASes state to `domain_opened/revision 1` in the same
first ownership transaction that creates/revalidates campaign identity and
candidate ownership mode. Provider, Protocol, scheduler, Registry mutation,
and filesystem publication are unavailable until that transaction commits.

Receipt/DB crash reconciliation is exact:

- a complete, exact 090 -> 091 -> 092 `restore-verified` chain is terminal and
  takes precedence over the ordinary 030 reconciliation cases below: a legacy
  target must exactly match its preimage bundle and a fresh target must satisfy
  the descriptor-pinned absence verifier;
- no target DB activation singleton: only `prepared`/`preimage_sealed` are
  legal for legacy; fresh may additionally have 025 only while the target is
  absent and the private staged DB exact-verifies. The attempt owner may resume
  only under the reissue contract above;
- DB `schema_committed` with no matching receipt: the recovery owner validates
  DB cutover/selection/preimage IDs and publishes the missing receipt;
- receipt `schema_committed` with DB absent/legacy and no complete 092 terminal
  chain: conflict, hold; it is never interpreted as a committed schema;
- DB `schema_committed` plus matching receipt: only dedicated forward recovery,
  validation, or the restore protocol below is authorized;
- exact restore prefix ending at 090 or 091 is owned only by
  `CutoverRestoreRecoveryOwner`; it is neither an ordinary receipt gap nor an
  extra-receipt conflict;
- DB `domain_opened` with no receipt: recompute exact state and publish the
  missing audit receipt; rollback remains forbidden; and
- any ID, ordinal, previous-hash, runtime commit, bundle, schema, domain,
  workspace, champion, or publication mismatch is a permanent offline hold.

- Before legacy schema COMMIT, SQLite rollback plus exact source re-scan permits
  the pinned old runtime to resume after the deployment ledger is closed. A
  fresh pre-publication crash leaves the target absent and resumes only through
  `CutoverBootstrapAttemptOwner` and the 020/025 rules above.
- After schema COMMIT, the old runtime is forbidden from opening the target.
  A crash or validation failure remains offline under the execution lock and
  must first attempt idempotent forward validation/recovery.
- Whole-preimage restore is allowed only when durable state remains exactly
  `schema_committed`, every post-bootstrap domain-table digest matches the
  activation record, no provider/Protocol call occurred, and workspace,
  champion, publication, and artifact inventories are unchanged. Restore is a
  byte-exact main/WAL/SHM bundle operation under the lock.
- At or after `domain_opened`, downgrade and preimage restore are permanently
  forbidden. Recovery is fail-closed and forward-only.

No code path may decide rollback eligibility from wall time, process exit, an
absent report, or operator assertion alone.

Because target SQLite may be partly or wholly absent after 091, a separate
offline `CutoverRestoreRecoveryOwner` is the sole issuer of a one-shot restore-
resume capability. Issuance does not require opening the target DB. It requires
disabled launch sources, the execution lock, an exact no-gap prefix ending at
090 or 091 with no 092, immutable selection/preimage and pinned commits, zero
SQLite/file descriptors, and a complete descriptor-pinned file-state match
across target, fixed restore-staging members, and `failed-postbootstrap`. At
090 it resumes copy/fsync/verify and then publishes 091; at 091 it resumes only
the literal member-move/restore/fsync state machine. A complete 092 permanently
closes this issuer; production composition cannot import it.

Before raw restore begins, the supervisor closes every bootstrap, recovery,
active, and verifier SQLite connection, waits for finalizers, and rechecks
`/proc/*/fd` in the pinned PID/mount namespace to prove zero descriptor to the
target main/WAL/SHM names or inodes. It holds the non-exec execution lock; no
SQLite handle may be opened until 092 is durable.

Authorized legacy restore publishes `restore-prepared`, copies and fsyncs every
preimage member to the fixed restore-staging names, and verifies them before
touching the active names. Authorized fresh restore instead binds the absence
sentinel and has no preimage SQLite member to copy. Both then publish
`restore-in-progress`,
move every active main/WAL/SHM member into the no-overwrite
`failed-postbootstrap` directory, and fsync all affected directories; legacy
then renames the complete preimage members into place. Any crash after
`restore-in-progress` forbids SQLite open and resumes only this file-state
machine from selection/preimage facts.

Member order is fixed as `shm`, `wal`, then `main` when moving the active bundle
to `failed-postbootstrap`, and `main`, `wal`, then `shm` when publishing a
legacy restore bundle. After every no-replace rename, both source and
destination directories are fsynced before the next member. The 090 stage
copies in `main`, `wal`, `shm` order, fsyncs each member, then fsyncs
`restore-staging` before verification and 091 publication.

Legacy may publish `restore-verified` only after the restored bundle
byte-matches the preimage and the independent legacy read-only verifier passes.
Fresh may publish it only after descriptor-pinned verification that target
main/WAL/SHM/rollback/unknown sidecars are all absent and all moved files remain
sealed in `failed-postbootstrap`. The supervisor leaves every launch source
disabled and exits. After legacy restore a later operator may start only the
pinned old runtime commit under the normal execution lock; after fresh-absence
restore no campaign runtime may start and any later activation requires a new
cutover selection.
