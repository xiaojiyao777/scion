## Dependency and responsibility boundary

```text
durable_owner                 sqlite_connection
      ^                              ^
      |                              |
branch_owner_store  ---->  owner_transaction  <----  hypothesis_owner_store
             \                              /
              campaign_owner_registry (later slice)
```

- `sqlite_connection.py` owns generic transaction lifecycle, materialized
  results, thread/Context ownership, and the private authorizer bridge.
- `owner_transaction.py` owns only Branch/H permits, preallocated write facts,
  the transaction ledger, sealed receipts, exact receipt-set closure, and the
  store/Registry importer contract. It owns no owner SELECT, payload column,
  row decoder, schema generation query, SQL parser, or durable payload check.
- `branch_owner_store.py` and `hypothesis_owner_store.py` exclusively own their
  fixed SELECT/INSERT/CAS SQL, full strict row decoding, exact pre-state guard,
  and same-transaction authoritative post-state token.
- `campaign_owner_registry.py` later owns view claiming, receipt consumption
  and staging, one-root publication, and commit classification. None of that is
  implemented in this slice.

The existing legacy `lineage/branch_store.py` remains untouched and active
until the indivisible offline cutover. The new focused modules remain dormant.

## Connection-scoped operation

A focused mutation performs one fixed sequence:

1. Resolve the exact ledger already attached to the sealed transaction.
2. Strictly read and decode the complete durable owner row in that transaction.
3. Require exact immutable-token equality with the caller's expected token, or
   durable absence for insert-once.
4. Construct the target revisioned token from the detached target value.
5. Ask `owner_transaction` for one table/kind/action permit around one fixed
   store-owned SQL statement. The write fact is registered before SQLite runs.
6. Require exactly one changed row.
7. Strictly reread the complete row in the same transaction and require exact
   equality of ID, revision, canonical bytes, digest, protocol generation, and
   (for H) owning Branch with the constructed target token.
8. Privately register the authoritative reread token against the pending write
   fact and return only an opaque sealed mutation or creation receipt.

No public store method accepts SQL, parameters, a ledger, a write fact, or a
caller-supplied committed token. An exception anywhere after write-fact
allocation leaves the ledger incomplete, so normal commit is denied and the
transaction rolls back.

## Exact SQL and importer closure

The four owner execution/issuance paths remain private. AST-based static tests
must prove:

- Branch authority, execute, and receipt-issuance internals are called only by
  `lineage/branch_owner_store.py`;
- Hypothesis equivalents are called only by
  `lineage/hypothesis_owner_store.py`;
- ledger attach/consume/seal/close have no production importer until the future
  Registry slice;
- the focused store public signatures contain no SQL, parameter, ledger,
  write-fact, or committed-token argument;
- every owner DML call site passes one module-level fixed string constant;
- the new focused SQL contains no `REPLACE`, `INSERT OR`, `UPDATE OR`,
  `ON CONFLICT`, owner `DELETE`, dynamic formatting, or `executemany`; and
- no existing production module imports either dormant focused store.

The dormant test exception for the legacy combined store is removed only in
the offline cutover, when that store and all blind writers are deleted.

## Acceptance matrix

The focused tests must cover both owner kinds and both mutation kinds:

- complete strict read and insert/CAS round trips;
- same revision with different semantic bytes;
- durable post-row with correct revision but wrong payload digest;
- caller target mutation after token construction;
- wrong owner ID, zero-row CAS, duplicate insert, and exact `n -> n+1`;
- actual Hypothesis `branch_id` movement and malformed complete rows;
- write success followed by reread/receipt failure;
- valid write without receipt, receipt without consume/stage, and unsealed
  ledger all deny commit;
- wrong database, transaction, store kind, thread, Context, trigger, non-main
  database, owner DELETE, second permit, and replay;
- receipt/proof/result object graphs retain no raw connection or cursor; and
- exact-importer/call-site AST closure, focused suites, full Scion suite,
  `compileall`, and `git diff --check`.
