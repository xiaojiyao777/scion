# v0.4 CVRP F1 Fixed Ancestry Matrix Design

*Date: 2026-07-18*
*Status: design candidate; no F1 implementation or execution authority until independent review and manifest preflight are accepted*

## 1. Decision and scientific question

F1 is a no-LLM, fixed-candidate decomposition of the accepted R11c CVRP
trajectory. R11c evaluated H2/SWAP* only after inheriting H1's rejected route-
elimination and scheduler edits. F1 asks whether the observed H2 behavior came
from SWAP* itself, the inherited H1 treatment, or their cumulative composition.

The formal matrix has four executable arms:

1. the exact R11c champion comparator;
2. H1-only on that champion;
3. SWAP*-only on that champion;
4. the exact cumulative H1+H2 candidate evaluated by R11c.

The earlier requirement for “three no-LLM arms” names the three historical
candidate treatments; the champion is the necessary fourth comparator. F1
does not generate or repair a candidate, mutate a campaign, select a production
profile, make a promotion decision, weaken Protocol, or authorize B2/B3 by
itself. It adds no proposal/round budget, output cap, truncation, automatic
retry, resume, or interim gate. The frozen case/seed population and the
historically resolved scientific solver limits define observations, not an
adaptive stopping budget.

## 5. Exact serial schedule

Use one isolated runner and at most one live CVRP solver. For A=`champion`,
B=`h1_only`, C=`swap_only`, and D=`cumulative`, use the Williams sequences:

```text
ABDC
BCAD
CDBA
DACB
```

Within each stage, cell order is case order then seed order. Stage-local cell
ordinal `i` uses Williams row `i mod 4`. Each stage has 32 cells, so every arm
appears in every serial position eight times and every ordered adjacent arm
pair appears eight times. The manifest stores all 256 job ordinals; runtime
does not recompute or adapt their order.

The formal root must be absent before materialization. F1 may launch only when
no W3 or other solver experiment owns this host's scientific execution lane.
Host isolation is part of attribution, not a quality gate.

## 6. Manifest, materialization, and preflight

The implementation must produce a canonical
`scion.cvrp_f1_ancestry_manifest.v1` before formal execution. It binds:

- this accepted design's raw SHA-256 and git commit;
- the R11c root, runtime commit, protected artifact paths and raw hashes;
- all base, patch, code, snapshot, and per-file identities for every arm;
- the exact complete imported solver/source/config closure for each sealed
  workspace, not only the three changed modules;
- problem spec, protocol, matrix, split, seed ledger, time-limit policy, BKS,
  paired `.vrp`/`.sol` case bytes, Python, platform, dependency, and native-
  library identities;
- all 64 cells, their stage-local order, resolved time limits, four Williams
  positions, and all 256 job ordinals;
- runner, parser, report-builder, closer, and receipt source identities;
- output-root identity and proof it was absent before creation;
- `llm=false`, `campaign_mutation=false`, `retry=false`, `resume=false`,
  `reuse=false`, `automatic_rerun=false`, and `interim_adaptation=false`.

Materialization starts from one source-byte copy of the exact champion and
applies only full-file bytes already held by the protected v3 formal artifacts.
It explicitly excludes every `__pycache__` directory and `*.pyc`/`*.pyo` file
already present in the historical champion; those generated artifacts are not
source authority. Their count must be exactly zero before and after import
probes and before and after formal execution. Any occurrence is an integrity
failure. All other declared non-generated champion files remain byte-bound. It
must not apply a fuzzy patch, infer a file from prose, use a current repository
version, or execute from an R11c directory. Preflight byte-compares every file,
recomputes complete identities, imports each arm, and runs the existing
verification/solution-validity smoke checks without altering arm bytes.

Cases and source workspaces are sealed inside the output root with files mode
`0444`, directories mode `0555`, and `PYTHONDONTWRITEBYTECODE=1`. After
sealing, formal jobs read neither repository source nor original R11c/CVRPLIB
paths. Preflight records a complete regular-file inventory before and after
import probes, and the runner recomputes it before and after formal execution;
any generated bytecode path, source, config, membership, or byte drift is an
integrity failure.
The exact solver invocation is an argv array, never a shell string, and is
stored per job with its clean environment and working directory.

Solver interchange output uses a runner-owned fresh `O_EXCL` path. For every
declared job the runner emits either a validated solver row or a typed solver-
failure row. It canonicalizes the row into a same-directory `O_EXCL` temporary,
writes and fsyncs the complete file, publishes it atomically with the accepted
no-replace primitive, fsyncs the directory, and removes only its own temporary.
A partial final row can therefore never block byte replay. A job never
overwrites another row. Stdout/stderr are bounded only by the solver process's
natural output and are retained or content-addressed in full; F1 adds no
truncation.

## 7. Required raw evidence

Every job row must bind at least:

- manifest hash, root ID, job and cell ordinals, stage, arm, schedule position,
  case identity, seed, time limit, command, environment, and workspace hash;
- exit and signal status, start/end monotonic and wall times, validity, fleet
  feasibility, objective tuple, total distance, BKS gap, and stop reason;
- initial-solution identity and objective;
- initial VNS, embedded VNS, ALNS core, repair, polish, and residual phase time;
- ALNS iterations and throughput, best updates, SA/acceptance trajectory, and
  deadline/budget-hit telemetry already emitted by the solver;
- SWAP* attempts, accepted moves, delta, and elapsed time;
- route-elimination selections, `destroy_empty`, repair invocations,
  acceptances, best updates, and elapsed time;
- interchange, parsed payload, stdout, and stderr identities.

Missing telemetry is represented as typed missing evidence, never zero. An
unknown field may limit a mechanism claim but may not silently delete a valid
objective observation.

## 8. Preregistered analysis

The case is the primary scientific unit. Four seeds are paired repeated
measurements, not 256 independent samples. Report screening and validation
separately; a combined 16-case view is diagnostic and cannot erase a stage-
specific reversal.

For each contrast, `treatment improvement = reference distance - treatment
distance`; positive values mean the treatment is shorter. Each seed with a
fleet difference still enters the existing lexicographic W/L/T comparison but
does not enter the distance delta. Every case reports its four seed outcomes,
equal-fleet distance denominator, and typed missing reasons. Case outcome is
the existing strict comparison: treatment seed wins greater than reference
seed wins means treatment win, fewer means treatment loss, and equality means
tie; seed ties do not vote for either arm.

Report case median improvement, exact case sign counts, and case-level median
bootstrap intervals as descriptive uncertainty. The bootstrap reuses
`scion.protocol.stats.bootstrap_ci` exactly with `n_boot=1000`, `alpha=0.05`,
and `seed=42`; its inputs are one equal-fleet median paired improvement per
eligible case, never the individual seed rows. Screening and validation are
bootstrapped separately. The combined view is diagnostic only. Every result
records total cases, valid cases, equal-fleet cases, bootstrap input count, and
all missing reasons. No small subgroup receives an inferential claim. Do not
invent a new acceptance threshold or feed F1 through a promotion gate.

The frozen contrasts are:

| Role | Treatment | Reference | Question |
|---|---|---|---|
| primary | `swap_only` | `cumulative` | direction, magnitude, and uncertainty of removing rejected H1 ancestry from SWAP* |
| secondary | `swap_only` | `champion` | SWAP* on a clean base |
| secondary | `h1_only` | `champion` | total effect of the rejected H1 treatment |
| secondary | `cumulative` | `champion` | exact reproduction target for the historical H2 treatment |
| secondary | `cumulative` | `h1_only` | incremental SWAP* effect on the inherited H1 base |

F1 reports fixed-population direction and magnitude; it does not classify any
difference as “material” with an unfrozen threshold.

For each stage, contrast direction is `treatment_better` when treatment case
wins exceed reference case wins, `reference_better` when fewer, and otherwise
uses the sign of the median eligible case improvement; exact zero is `tie`.
“Directionally consistent with R11c” means the `cumulative`-treatment versus
`champion`-reference F1 direction is `treatment_better` in screening and,
separately, `treatment_better` in validation, matching the two historical H2
case directions. This check never counts R11c's cached champion pairs as new F1
observations.

Preregistered heterogeneity views are:

- exact `tai150a` starvation probe, all four validation seeds;
- validation 60-second large cases: `tai150a`, `tai150b`, `X-n190-k8`;
- validation 45-second cases: `X-n120-k6`, `X-n129-k18`;
- screening 45-second cases: `CMT4`, `M-n200-k17`;
- remaining 30-second cases by stage.

For SWAP-only and cumulative, report SWAP* activation, initial-VNS occupancy,
zero-ALNS incidence, ALNS iterations/throughput, and objective jointly. For
H1-only and cumulative, report whether route elimination remains dead and how
its extra scheduler/RNG allocation changes the search. More ALNS iterations or
more SWAP* accepts are mechanisms, not quality improvements by themselves.
SA cooling remains iteration-based, so time-allocation and temperature-path
effects must not be collapsed into one wall-time explanation.

## 9. Closure and acceptance

The closer is problem-owned and accepts immutable inputs only after execution
is terminal. It verifies manifest/source/case/job identities, Williams balance,
interchange/raw inventories, validity accounting, and environment isolation.
Closure state and scientific acceptance are separate:

- a solver failure with a live runner produces one typed failure row, so a
  terminal root can still own all 256 declared rows while its usable population
  is explicitly reduced or invalid;
- a runner interruption or missing row may publish an integrity-only
  `invalid_or_incomplete` receipt listing observed, missing, extra, and partial
  job identities; it never fabricates a row or a scientific contrast;
- only an exact 256-row terminal population with the preregistered usable-
  evidence rules may publish an accepted scientific report.

The successful closer publishes with atomic no-replace semantics:

- `cvrp_f1_ancestry_report.v1.json`;
- `cvrp_f1_ancestry_receipt.v1.json`.

The report embeds or hashes every analysis input and records complete, invalid,
and caveated populations explicitly. An incomplete root publishes no
scientific report. An existing report or receipt can only be checked byte-for-
byte; it is never replaced. Replay on the same immutable inputs must reproduce
identical bytes.

F1 is accepted only when:

1. design review and implementation review each report P0=0/P1=0;
2. dry manifest/preflight independently reproduce all protected identities,
   arm derivations, 64 cells, 256 jobs, and schedule balance;
3. the fresh root is terminal with one closed receipt, exact 256-row complete
   inventory, and no live solver;
4. closer integrity, byte replay, focused tests, compileall, formatting, and
   diff checks pass;
5. an independent science review confirms that claims stay within the fixed
   ancestry design.

Allowed terminal root dispositions are `accepted_diagnostic`,
`accepted_with_declared_caveats`, or `invalid_or_incomplete`; only the first two
are scientific-evidence acceptance. None promotes an arm or selects the
canonical search profile. A positive SWAP-only result remains a fixed-candidate
finding; future generative or transplant claims still require the separately
frozen D/L and B2/B3 sequence.

## 10. Implementation boundary and launch order

F1 belongs in the CVRP problem-owned evidence layer. Core may provide only
generic immutable-artifact and no-replace-publication primitives; it must not
learn H1, SWAP*, VNS, ALNS, CVRPLIB, or ancestry-specific statistics. Implement
one cohesive problem-owned manifest/materializer/runner/closer surface with a
thin CLI and focused fixtures, reusing accepted B1 primitives where their
contracts are genuinely identical rather than copying helper piles.

Execution order is fixed:

1. freeze this design after two independent reviews;
2. implement and independently review the problem-owned surface;
3. build and inspect a dry manifest in a disposable root;
4. commit and push the accepted exact code/design;
5. launch one fresh formal serial root only after the host lane is free;
6. poll at low frequency and do not mutate the live root;
7. close, replay, and independently review before updating `TASK.md` and
   `current-state.md`.

No step authorizes an automatic rerun. A defect is analyzed first and any new
root requires a new explicit accepted disposition.
