# Scion v0.4 D2b.0b Foundation Transaction Publication Correction

*Status: frozen correction contract; no production activation*
*Date: 2026-07-16*

Three independent reviewers accepted this correction after six adversarial
rounds with no open P0/P1. Changes to database authority, participant SQL
surface, owner-table permit/receipt issuance, startup authority state,
commit-outcome classification, view lifecycle, or one-root publication require
a new design review before implementation continues.

This correction amends only the dormant D2b.0b.F implementation boundary in
`v0.4-d2b0b-global-durable-owner-migration-plan-20260716.md`. The frozen
storage schema, immutable owner-token shape, CAS rules, lock order, completion
bindings, offline cutover, snapshot publication, and production cutover order
remain unchanged.

The first foundation implementation exposed two invalid seams:

1. a participant could escape the transaction owner through connection-changing
   SQL or a wrapped raw cursor; and
2. the Campaign registry could install a local owner before durable commit,
   omit installation after commit, or throw halfway through a multi-owner
   post-commit installation.

Those are ownership defects, not reasons to add a retry, budget, cap, timeout,
gate, truncation, or experiment policy. The faulty foundation remains dormant
and is rewritten before any owner store or schema package proceeds.

## Corrected outcome

D2b.0b.F may continue only when the following composition is encoded by the
APIs rather than left as a caller convention:

```text
acquire detached mutation view
-> CampaignOwnerRegistry owner lock
-> registry-bound Campaign owner transaction
-> focused participant CAS issues a sealed mutation receipt
-> consume and prevalidate every receipt/local replacement
-> prove claimed views == durable mutation ledger == staged publications
-> COMMIT
-> publish one complete prepared Campaign-owner root by one reference swap
-> release owner lock
```

`PROVEN_ROLLED_BACK`, incomplete staging, invalid returned tokens, and
participant-policy violations publish nothing. An interrupted/raising commit
publishes only when independent classification proves the complete durable
commit. A caller cannot obtain an install method that works before commit,
cannot forget the post-commit publication step, and cannot retain a raw SQLite
cursor or connection through a participant result.

## Shared SQLite capability

### Corrected module boundary

The correction adds one responsibility-focused module, not a generic helper:

- `lineage/sqlite_connection.py` owns private connection construction,
  `CampaignDatabaseAuthority`, the generic immediate-transaction lifecycle,
  materialized results, statement-class filtering, and thread/context binding;
- `lineage/owner_transaction.py` owns only Branch/H table write permits, the
  transaction mutation ledger, sealed mutation/creation receipts, and their
  exact-importer validation; and
- `core/campaign_owner_registry.py` owns only startup/live Registry phase,
  view capabilities, immutable local owner roots, staging, transition guard,
  and monotonic conflict refresh.

Branch/H stores consume the first two boundaries but continue to own their
focused SQL and strict row decoding. Schema bootstrap owns DDL and authority
issuance. None of these modules owns research policy, evaluation lease mutation,
retry, or Campaign orchestration.

### Private connection factory and Campaign database authority

The raw connection factory in `lineage/sqlite_connection.py` becomes private.
Only that module's transaction contexts and the exact
`lineage/schema_bootstrap.py` bootstrap adapter may use it. No workflow,
transaction-owner, service, store, or participant receives a raw connection or
imports the private factory. Schema bootstrap receives a distinct sealed
bootstrap authority; it does not expose that authority after startup.

Successful bootstrap/open issues one sealed `CampaignDatabaseAuthority`. It
binds the canonical absolute database path, held no-follow file identity
(`st_dev`, `st_ino`), Campaign ID, durable-owner schema generation, and the
already-held Campaign execution lock identity. Reopen verifies the same path,
file identity, campaign identity row, schema-generation singleton, and
connection policy before issuing it. The authority is not caller-constructible.

`CampaignOwnerRegistry`, Branch/H stores, and every transaction participant are
constructed with the exact same authority object. Registry transaction entry
accepts no path and no replacement authority. Every issued transaction records
that authority identity; a store or receipt bound to another authority is
rejected. Selecting the authoritative database occurs once during the frozen
startup/open sequence, not at each mutation call.

The factory continues to establish and verify:

- explicit autocommit mode outside an owned transaction;
- `cached_statements=0`, so every statement re-enters the authorizer;
- WAL;
- `synchronous=FULL`;
- `foreign_keys=ON`;
- `recursive_triggers=ON`; and
- the explicit busy timeout already frozen by the parent plan.

The busy timeout is SQLite lock acquisition policy. It is not a research
runtime cutoff and does not bound an experiment.

Every new connection revalidates the authority's canonical path and held file
descriptor identity before open, verifies the opened `main` path and file
identity after open, and proves the Campaign execution lock is still held by
the authority. Path replacement, inode drift, released execution lock,
Campaign-ID mismatch, or schema-generation mismatch closes the connection and
fails before `BEGIN`.

### Narrow participant statement surface

An `ImmediateTransaction` is authority, not a general connection facade. It
exposes no public raw `execute()` method to workflow owners. Exact allowlisted
participant modules use the internal materializing execution primitive, which
accepts one nonempty SQL statement whose first effective top-level keyword,
after whitespace, comments, and empty semicolon statements, is one of:

```text
SELECT, INSERT, UPDATE, DELETE, WITH
```

Everything else is rejected before SQLite sees it. In particular, a
participant cannot issue transaction/savepoint control, `PRAGMA`, `ATTACH`,
`DETACH`, `VACUUM`, DDL, or an empty leading statement that hides one of those
operations. The private connection factory explicitly keeps SQLite extension
loading disabled; `SELECT load_extension(...)` receives its own rejection
test. Schema bootstrap uses its sealed bootstrap surface rather than weakening
participant authority.

The scanner owns only statement-class recognition; SQLite remains the SQL
parser. It must handle leading line comments, block comments, whitespace, and
any number of empty semicolon statements. `WITH` is allowed because SQLite
restricts it to a following data statement. Multiple executable statements
remain rejected by `sqlite3.execute()` and receive an explicit regression test.

Branch/H owner tables have a second boundary. The connection authorizer denies
all `INSERT`, `UPDATE`, or `DELETE` against `branches` or `hypotheses` by
default. A focused Branch/H store participant can open one exact table/kind
write permit through a private, exact-importer API bound to its store authority
and current transaction. The permit closes around the one owner statement.
Generic event/champion/completion/workflow participants cannot obtain it, and a
trigger or direct statement cannot silently add an unattributed owner write.

Owner-capable connections always use `cached_statements=0`; toggling a permit
therefore cannot leave a prepared statement authorized after the permit closes.
An owner permit matches exactly one action (`INSERT` or `UPDATE`), the `main`
database, one owner table/kind, and a top-level authorizer event whose trigger
source is null. It permits one `execute()` call only. Owner `executemany`,
`DELETE`, trigger-originated owner DML, a second statement, or the same SQL
replayed after permit close is denied. Multi-owner CAS uses multiple exact
statements/permits inside one caller-owned transaction and still rolls back as
one unit.

### Materialized result view

Participant execution eagerly captures the cursor result while the capability
is active, closes the raw cursor, and returns a narrow materialized result:

```text
ImmediateResult(private_rows, rowcount, lastrowid, description)
```

Rows are captured into a private immutable tuple before rowcount is frozen; the
raw cursor is then closed. Rows and metadata retain no raw cursor or connection
reference. `fetchone`, `fetchmany`, `fetchall`, iteration, rowcount, lastrowid,
and description each require the exact active capability. After transaction
exit the result is unusable. Recursive object-graph tests prove that no public
or private result field contains a `sqlite3.Cursor` or `sqlite3.Connection`.

### Thread and context ownership

An issued capability is valid only when all of these are simultaneously true:

- it is present in the module's issuance registry;
- its state is active and its connection is in a transaction;
- the current OS thread is the issuing thread;
- the thread's active-owner registry points to this exact capability; and
- the current `ContextVar` points to this exact capability.

The thread registry prevents an empty/fresh Context from opening a second
immediate transaction on the same thread. The exact ContextVar check prevents
that fresh Context from using the outer capability. Cross-thread use, forged
objects, ended capabilities, nested transactions, and a second transaction in
the same thread all fail closed.

The active thread owner is stored in thread-local state rather than a reusable
bare thread-ID dictionary. Commit, rollback, and close failure tests freeze
exception precedence and chaining. Regardless of failure, the capability is
deactivated and thread/context ownership is cleared before connection cleanup.

For a coordinated Campaign owner transaction the fixed exit order is:

```text
pre-commit closure -> COMMIT -> deactivate/clear ownership
-> one-root Campaign publication -> connection close
```

Transaction outcome has exactly three states, but proof depends on whether the
commit boundary was entered:

- `PROVEN_COMMITTED`: `commit()` returned normally, or a new independent,
  authority-verified connection proves a nonempty complete receipt set's
  committed state in one read snapshot; publish the prepared root;
- `PROVEN_ROLLED_BACK`: before commit is entered, `BEGIN` failure proves no
  transaction and a normal rollback proves the active transaction ended without
  commit; after commit is entered, normal rollback of a still-active original
  transaction plus a new independent, authority-verified connection must prove
  the same nonempty complete receipt set's exact expected state (or absence for
  creation) in one read snapshot; retain the old root and clear the transition
  guard; and
- `UNCERTAIN_OR_MIXED`: independent classification cannot prove either complete
  state; retain a permanent integrity hold and expose neither root as
  schedulable until restart/rebuild from durable truth.

The commit boundary is entered only after pre-commit closure proves a nonempty,
complete receipt/staging ledger; its latch is set before calling `commit()`.
CAS conflict, duplicate creation, participant/body failure, missing receipt, and
pre-commit closure failure occur before that latch. A normal rollback on those
paths is sufficient proof and does not require a receipt that was never issued.
Rollback failure or uncertain close retains an integrity hold.

After the latch, the original possibly open transaction connection is never
classification evidence because it can see its own uncommitted writes. A normal
commit publishes before connection close, so a later close failure cannot
suppress publication. If commit was interrupted or raised after the latch,
cleanup first deactivates the capability, attempts rollback/close of the
original connection, then uses a new authority-verified connection for the
three-state classification while the owner and execution locks remain held.
Classification never replays a mutation.

Exception precedence is fixed. A body/pre-commit-closure error is primary and
rollback/close errors are chained. Without a body error, commit error is
primary and rollback/close errors are chained. After proven commit, a
publication-classification integrity hold is primary and close is chained;
otherwise close is the typed primary cleanup error after successful
publication. Capability/view spending and transition-guard safety run in
cleanup regardless of which error is primary.

## Campaign-local staged publication

### One registry-owned transaction context

The separate outer `commit_scope` and caller-opened inner transaction are
replaced by one entry:

```python
with registry.owner_transaction(branch_views=(branch_view,)) as scope:
    receipt = branch_store.compare_and_swap_in(
        scope.transaction,
        branch_view.owner,
        branch_view.target,
    )
    scope.stage_branch_success(branch_view, receipt)
```

`owner_transaction(...)` acquires the owner lock, validates and claims the
nonempty mutation/creation view set, opens exactly one transaction from the
registry's bound
`CampaignDatabaseAuthority`, yields one sealed scope, performs pre-commit
closure, commits, publishes, closes, and releases the lock. It accepts no
database path or transaction capability from the caller. It is the complete
commit boundary; there is no outer scope in which code can run after its inner
commit but before owner-lock release.

An empty view set is rejected before `BEGIN`, and pre-commit closure requires at
least one issued, consumed, and staged owner receipt. The all-committed and
all-expected classifications can therefore never both be vacuously true.

Production Campaign owner workflows cannot call standalone Branch/H mutation
wrappers or generic immediate-transaction contexts. Static exact-importer and
call-site rules enforce this. Database ownership has no backward edge:

```text
OFFLINE_STANDALONE
-> DRAINING_STANDALONE (deny new issuance; finish active transactions)
-> RESTORING (all durable owner writes forbidden)
-> seal restored root and revoke startup-restore authority
-> LIVE_REGISTRY (owner_transaction and creation enabled)
```

A single startup-authority mutex and condition variable own this transition.
Each standalone transaction checks `OFFLINE_STANDALONE`, increments an active
lease count, and retains that lease through commit/rollback and connection
close. `begin_restore()` first moves to `DRAINING_STANDALONE` under the same
mutex, permanently denies new issuance, then waits on the condition until the
active lease count is zero. It enters `RESTORING` and permits the first durable
load only after that drain. There is no polling loop, retry, attempt count, or
artificial wait cutoff.

`owner_transaction(...)` is rejected before `LIVE_REGISTRY`. `seal_live()`
publishes the complete restored root, revokes restore authority, and only then
enables live creation/mutation; no standalone authority can be reissued between
live transactions.

Champion-sensitive workflows retain the frozen outer order:

```text
champion lock -> Campaign owner transaction
```

### Sealed durable mutation receipts

Connection-scoped Branch/H CAS does not return a bare token. After the exact
payload/revision/lease predicate succeeds and the row is strictly reread in the
same transaction, the focused store privately registers one durable mutation
fact in the transaction ledger and returns a sealed receipt:

```text
OwnerMutationReceipt(
  transaction identity,
  Campaign database authority identity,
  owner kind and ID,
  expected revision and storage digest,
  committed revision and storage digest,
  fully decoded committed token
)
```

The receipt constructor is sealed and issuance is recorded in module-private
state. It is valid only in its exact active transaction and can be consumed
once. The store's temporary owner-table write permit and receipt issuance are
one focused participant operation; failure before receipt issuance leaves the
ledger incomplete and pre-commit closure rolls back.

Standalone `BranchStore.compare_and_swap(...)` and H equivalents unwrap their
receipt only after their standalone transaction commits and return the frozen
public token shape required by the parent plan. Campaign workflows use the
receipt-returning connection-scoped participant only.

Insert-once has a symmetric creation protocol. The Registry issues sealed,
one-shot `BranchCreationView` and `HypothesisCreationView` values that reserve
an absent owner ID and bind the detached initial target to its required
Campaign/champion/Branch/proposal-attempt owner context. The focused store's
exact `INSERT`, authorization predicate, and strict same-transaction reread
issue a sealed creation receipt with no expected revision and committed
revision zero. Claimed creation views, creation receipts, transaction ledger,
and staged new slots enter the same exact closure and one-root publication as
CAS receipts. Duplicate ID, missing authorization, insert without stage, or
forged receipt rolls back without a local owner.

`restore_branch()` and `restore_hypothesis()` require a sealed startup-restore
authority issued only after the `DRAINING_STANDALONE -> RESTORING` transition
has revoked and drained standalone mutation. `seal_live()` revokes
only restore authority and enables live owner transactions before scheduler,
recovery dispatch, provider, or Protocol access. Restore cannot be called in
the live phase. New live owners always use creation views/receipts rather than
restore or an insert-then-install seam.

### Staging before commit

`stage_branch_success()` and `stage_hypothesis_success()` consume the exact
sealed receipt bound to `scope.transaction`. Staging performs every operation
that can reject an expected result:

- validate issued view identity, generation, revision, and digest;
- validate receipt issuance, transaction, database, kind, ID, expected token,
  and one-use status;
- decode the receipt's immutable committed token and build its detached
  projection;
- for mutation, require unchanged owner identity, exact `n -> n + 1`, and a
  semantic payload change;
- for creation, require the reserved absent identity and committed revision
  zero;
- rebuild the token from the bound target and require exact storage digest;
- reject duplicate staging; and
- build the replacement local slot without mutating the registry.

The token itself remains an integrity/concurrency value, not an authorization
capability. It may be constructed from semantic bytes. Authorization comes from
the one-shot registry view, focused owner-table write permit, exact durable CAS
predicate, and sealed same-transaction mutation receipt. Production expected
tokens originate only from owner-store reads or registry views; a caller-
computed SHA is never treated as a MAC, durable mutation fact, or permission.

Before commit, the scope proves exact multiset equality by sealed receipt
identity/count among claimed mutation/creation views, issued transaction-ledger
receipts, consumed receipts, and staged local publications. Owner IDs alone are
not sufficient and cannot collapse duplicates. The connection authorizer also
proves no unattributed Branch/H write occurred. Validation-only exact-owner
guards use immutable tokens directly, issue no mutation receipt, and do not
claim mutation views. They cannot open `owner_transaction(...)` by themselves.
A validation-only transaction that writes an intent phase, event, or other
durable fact uses its focused transaction owner and that owner's nonempty,
sealed durable outcome witness for uncertain-commit classification. It never
borrows an empty Campaign-owner receipt ledger. An incomplete, extra,
duplicate, cross-database, or mixed set raises before commit, so the database
transaction rolls back.

### Prepared local publication

All Campaign-local schedulable owner state lives inside one immutable root:

```text
_CampaignOwnerState(
  branch_slots,
  hypothesis_slots,
  publication_generation
)
```

Every registry reader captures `self._owner_state` once under the owner lock and
uses only that root. Slot mappings are immutable views over private maps whose
builders are discarded; slots and nested projections are not exposed for
in-place mutation. Pre-commit closure constructs one complete successor root.
All dictionary copies, detached projection construction, token reconstruction,
digest checks, generation arithmetic, receipt consumption, and purge-set work
occur before commit. The prepared root retains only internally rebuilt immutable
tokens/slots and detached projections, never caller target or receipt references.

Mutation/creation view authorization is deliberately outside the projection
root in a sealed capability registry with an irreversible lifecycle:

```text
issued -> claimed -> spent
```

Entry validates every view first and then claims the complete set under the
owner lock. Claimed capabilities become spent in cleanup after BEGIN failure,
body failure, CAS conflict, rollback, commit failure, or success; they never
return to issued and no rejected target can replay. View validity requires both
an issued capability and exact token/generation agreement with the captured
owner root. Successful publication or conflict refresh need not mutate an
issued-view map for safety: any leftover older capability fails the root
generation/token check. Weak issuance records may be cleaned later without
changing owner truth.

`claimed -> spent` is a preallocated, no-fail state change performed before any
cleanup that can allocate or call external code. If unexpected cleanup failure
occurs, the transition guard stays raised; it never restores a claimed view to
issued.

After transaction ownership is deactivated and outcome is
`PROVEN_COMMITTED`, publication performs exactly one critical assignment:

```python
self._owner_state = prepared_owner_state
```

There is no second map/index/generation assignment and no per-owner loop.
Publication performs no decoding, copying, hashing, allocation-dependent
collection construction, SQL, or policy work. The owner lock remains held, so
readers observe the complete prior root or the complete successor root. Scope
publication success is derived from root identity/generation; it does not
depend on a second correctness-critical flag write.

Before `BEGIN`, the registry raises a local transition guard that makes every
scheduler/read/mutation entry fail closed. It is cleared only after rollback is
proved with no durable change, or after the successor root is published. If a
`BaseException` or signal lands after commit starts but before root publication,
cleanup keeps the guard raised and classifies durable truth under the held
execution lock using a new authority-verified connection and every receipt's
exact expected/committed revision and digest. Mutation expected state is its
exact prior revision/digest; creation expected state is durable absence. Only
`PROVEN_COMMITTED` publishes. Only `PROVEN_ROLLED_BACK` clears the guard while
retaining the old root. Mixed or unclassifiable state converts the guard to a
permanent integrity hold. This is classification, not mutation retry.

No process-global signal handler is installed. Trace, `KeyboardInterrupt`,
`SystemExit`, SIGINT, and SIGTERM fault injection at commit return, transaction
deactivation, classification, and immediately before root assignment must leave
the new root, the proved old root after rollback, or a non-schedulable integrity
hold. If a second asynchronous exception interrupts cleanup, the already-raised
guard remains fail closed. Uncatchable process death is recovered by startup
restore from durable truth before scheduling.

### Conflict refresh and reentrancy

CAS conflicts must propagate through and exit the complete
`owner_transaction(...)` context. Only after rollback/close releases the owner
lock may the caller reload durable truth and request monotonic refresh. Swallowing
a conflict inside the context fails pre-commit receipt closure and rolls back.
Public snapshot, acquisition, restore, discard, and conflict-refresh methods
detect same-thread active-scope reentrancy and raise a typed error instead of
deadlocking on the non-reentrant owner lock.

Refresh semantics remain unchanged: install only a higher revision; ignore a
lower revision; require identical bytes at an equal revision; purge older
views only when a higher durable owner is installed. A rejected target is never
replayed.

## Immutable token hardening

The accepted SQL-free token design remains unchanged. Its implementation adds
two defensive closures before later stores depend on it:

- owner IDs, digests, semantic strings, list strings, and mapping keys are
  normalized or validated as exact built-in `str`, preventing stateful string
  subclasses from entering registry keys; and
- recursive evidence/JSON failures are translated into
  `DurableOwnerIntegrityError` rather than leaking `RecursionError`.

No evidence-depth limit is introduced. This is typed failure normalization,
not truncation or a new payload budget. Optional legacy text compatibility is
frozen later by bootstrap/store inventory tests; it is not silently normalized
in this correction.

## Required tests

### SQLite boundary

- leading `; COMMIT`, commented transaction control, and every disallowed
  statement class fail before execution;
- `PRAGMA ignore_check_constraints=ON` cannot weaken a CHECK;
- participant results expose no cursor/connection and cannot call early commit;
- one-row, multi-row, empty, DML, `RETURNING`, and `executemany` materialization;
- `SELECT load_extension(...)` remains disabled and fails;
- `executemany` mid-batch and `RETURNING` materialization failures close the
  cursor, propagate, and roll back partial DML;
- capability use after exit, forged use, cross-thread use, fresh-Context use,
  fresh-Context nesting, and ordinary nesting all fail;
- commit failure rolls back when possible, rollback failure preserves the
  commit/body error as primary with chaining, and close failure does not leave
  active ownership state;
- commit success followed by close failure publishes the prepared Campaign root
  before reporting the typed cleanup error;
- an interrupted/raising commit is classified only through a new independent,
  authority-verified connection, never through the original connection;
- real commit followed by wrapper interruption classifies
  `PROVEN_COMMITTED`; pre-commit interruption plus proved rollback classifies
  `PROVEN_ROLLED_BACK`; rollback/close/classification failure remains
  `UNCERTAIN_OR_MIXED` integrity hold;
- owner-table DML without the exact store permit is denied and cannot create a
  mutation receipt;
- with `cached_statements=0`, replaying byte-identical owner SQL after permit
  close re-enters the authorizer and is denied;
- owner `executemany`, owner-writing triggers, non-main DB writes, and owner
  `DELETE` permits are denied;
- every transaction rechecks database inode/identity and held execution lock.
- restore transition racing an already-entered standalone transaction denies
  new issuance, waits on the startup-authority condition for commit/rollback
  and close, and performs no restore read before the active count reaches zero.

### Registry composition

- rollback after staging leaves both durable and local revisions unchanged;
- empty mutation/creation view or receipt sets are rejected before `BEGIN` and
  can never classify a commit outcome;
- interrupted validation-only durable writes use their focused intent/event
  witness and never enter Campaign owner publication;
- no callable pre-commit install API exists;
- missing/extra/forged/cross-transaction receipt fails before commit and
  publishes nothing;
- caller-constructed valid token without store CAS cannot become a receipt or
  local publication;
- direct owner-table DML and store CAS without receipt staging both roll back;
- a cloned/wrong database authority cannot enter the Registry transaction;
- Branch/H creation publishes revision-zero slots through creation receipts;
- duplicate creation, insert-without-stage, forged creation receipt, and
  creation rollback leave no local owner;
- beginning restore atomically and permanently revokes standalone mutation;
- owner transaction is rejected during restore, while startup restore is
  permanently rejected after `seal_live()`;
- concurrent authority transition tests expose no issuance/revocation TOCTOU;
- wrong target/digest/revision fails before commit;
- one successful commit publishes exactly once;
- a mixed Branch/H commit performs one `_owner_state` root assignment and
  publishes the complete local state together;
- asynchronous failure injection around the former map/index assignment points
  observes only the complete old or complete new root;
- an injected fault before commit leaves every local slot unchanged;
- an injected commit failure classified `PROVEN_ROLLED_BACK` leaves every local
  slot unchanged, while one classified `PROVEN_COMMITTED` publishes the new
  root;
- commit success plus injected close failure leaves durable and local revisions
  advanced together;
- body fault, CAS conflict, BEGIN failure, and pre-commit rollback irreversibly
  spend every claimed view while leaving owner root/projection revision
  unchanged;
- commit failure also spends every claimed view; the root then follows its
  proved committed/rolled-back outcome or remains behind an integrity hold;
- CAS conflict, duplicate creation, and body failure before receipt issuance
  clear the transition guard after normal pre-commit rollback without requiring
  a nonexistent receipt; rollback uncertainty retains an integrity hold;
- commit-return, deactivation, and pre-root-swap signal/trace faults leave the
  new root or a non-schedulable integrity hold, never a schedulable old root;
- duplicate receipts for one owner fail multiset closure;
- same-thread public refresh/snapshot inside a scope raises rather than
  deadlocks;
- a swallowed CAS conflict fails receipt-set closure before commit;
- conflict reload after scope exit remains monotonic in the three-party race.

### Static closure

- no existing production module imports the dormant owner token, store,
  Campaign registry, or schema-bootstrap modules;
- the private raw SQLite factory has an exact importer allowlist containing only
  `sqlite_connection` internals and the schema-bootstrap adapter;
- production Campaign workflows contain zero generic immediate-transaction or
  standalone Branch/H mutation calls;
- only focused Branch/H store modules import owner-table write-permit/receipt
  issuance internals;
- participant result objects contain no raw cursor/connection;
- no `install_*_success` pre/post-commit caller API remains;
- focused tests, complete correctly rooted Scion tests, `compileall`, and
  `git diff --check` pass before the dormant foundation commit.

## Non-goals

This correction does not activate schema, migrate a writer, start an
experiment, modify VRP/ALNS/VNS research behavior, add lease DML, or change any
frozen v1 byte. It adds no retry, replacement, attempt limit, gate, budget,
time cutoff, cap, or truncation. D2b.0b.F remains dormant until this correction
and the remaining foundation packages pass adversarial review.
