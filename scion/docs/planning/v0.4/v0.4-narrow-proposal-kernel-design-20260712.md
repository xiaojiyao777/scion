# Scion v0.4 Narrow Proposal Kernel Design

*Date: 2026-07-12*
*Status: implementation design; production switch waits for R3/R4*
*Authority: `scion/design/scion-architecture-v3.md` sections 5, 17, and 18*

## Decision

The v0.4 default proposal runtime will return to the v3 two-round path:

```text
host builds complete exposed context
  -> one hypothesis model call
  -> Contract approval boundary
  -> one code model call
  -> Contract -> Verification -> Protocol -> Decision
```

The existing agentic planner is retained temporarily as an explicit ablation
adapter. It is not the production default and is not the architecture into
which the direct path must be absorbed.

This design does not add prompt budgets, truncation, top-N selection, evidence
omission, or prompt-content changes.

## Why This Is a Kernel Change

`ProposalPipeline` already contains a direct hypothesis/code path, but both
prepared campaign launchers always append `--agentic-proposal`. The effective
production default is therefore the large `AgenticProposalSession`, including
target-intent calls, model tool selection, preview loops, repair loops, and a
wide compatibility/artifact surface.

The repair is to make the existing direct v3 path observable and production
capable, then switch launcher policy. Extracting the current 30
`agentic_session*.py` modules into more runtime abstractions before changing
the default would preserve the wrong control flow.

## Runtime Modes

Introduce one explicit campaign-facing mode:

```text
direct_v3          default; deterministic host retrieval + hypothesis + code
agentic_ablation   current AgenticProposalSession for controlled comparison
```

Compatibility mapping during migration:

```text
--agentic-proposal              -> agentic_ablation (deprecated alias)
no runtime flag                -> direct_v3
prepared launcher manifest     -> records the resolved mode, not only a bool
```

The mode is campaign configuration. It must not be inferred from whether a
test injected a session object.

## Stable Outer Boundary

The kernel ends at a tainted proposal attempt. It does not own:

- branch scheduling or lifecycle decisions;
- Contract, Verification, Protocol, or Decision policy;
- CVRP/VRP/warehouse semantics;
- promotion or resource allocation;
- prompt evidence selection.

The outer pipeline remains:

```text
ProposalAttempt
  -> Contract
  -> materialize
  -> Verification
  -> Protocol
  -> Safe Feature Extractor
  -> deterministic Decision
```

## Minimal Durable Attempt Surface

Both runtime modes must produce the same small committed attempt record. The
record is a projection of existing proposal and artifact data, not a new
decision input:

```python
ProposalAttemptEnvelope(
    schema_version,
    attempt_id,
    campaign_id,
    branch_id,
    champion_version,
    runtime_mode,
    phase,                 # hypothesis | code | complete | failed
    hypothesis,
    patch,
    prompt_snapshot_refs,
    context_digests,
    transition_reason,
    failure_lane,          # infra | proposal_repair | research_iteration
    tainted_artifact_refs,
)
```

It contains no DecisionFeatures, scheduler instruction, promotion label, raw
case metric, or validation/frozen detail.

Do not create this model until existing `AgenticProposalOutput`, hypothesis
records, prompt manifests, and direct-path artifacts have a field-by-field
migration table. Prefer adapting existing owners over adding another parallel
truth source.

## Required Direct-Path Parity

Before launchers switch, `direct_v3` must have parity for:

1. `PromptTurnSnapshot` manifest/trace/provider identity;
2. problem id/spec, split, seed, campaign, branch, and champion anchors;
3. hypothesis and patch problem-quality hooks, each exactly once;
4. structured failure lane and transition reason;
5. append-only tainted artifacts and lineage refs;
6. resume identity or an explicit non-resumable terminal record;
7. balance/transient-provider routing without counting an infra retry as a
   research iteration.

Parity does not mean copying planner ledgers or tool-loop counters into the
direct path. Those fields are mode-specific diagnostics.

## Implementation Slices

### K0 Characterize Both Modes

- run the same synthetic warehouse and CVRP contexts through direct and
  agentic modes with deterministic fake creative layers;
- record call kinds, hypothesis/patch values, anchors, quality-hook counts,
  artifacts, failure lane, and transition reason;
- prove direct mode makes no `tool_selection` call;
- do not compare model quality at this stage.

### K1 Make Runtime Mode Explicit

- add the resolved runtime mode at CLI -> campaign composition ->
  `ProposalPipeline`;
- keep `--agentic-proposal` as a deprecated alias;
- reject conflicting mode/alias combinations;
- record resolved mode in launch env, prepared contract, run status, and
  postrun inventory.

No launcher default changes in K1.

### K2 Direct-Path Attempt Artifacts

- reuse the existing `PromptTurnSnapshot` and prompt manifest;
- emit one hypothesis transition and one code transition;
- persist the tainted attempt before observers/status summaries;
- give direct failures the same three accounting lanes without adopting
  agentic tool ledgers.

### K3 Switch Prepared Launchers

- make warehouse and CVRP prepared launchers resolve to `direct_v3` by
  default;
- allow `agentic_ablation` only through an explicit launch option and manifest
  declaration;
- remove unconditional `--agentic-proposal` from generated commands;
- keep full Contract/Verification/Protocol enabled.

### K4 Disable Planner Work on the Default Path

- assert zero target-intent and tool-selection model calls in `direct_v3`;
- source retrieval remains deterministic and problem-owned;
- code context includes the approved target source and interface contract;
- one local structural repair may normalize host-known metadata, but must not
  regenerate a scientifically unchanged hypothesis;
- verification repair is a code repair transition, not a new research round.

### K5 Delete Compatibility Surface

After both problem families pass controlled validation:

- remove bool-only runtime plumbing after manifest migration;
- delete fallback lookups used only by the default path;
- keep agentic-only modules behind the ablation adapter;
- publish a deletion ledger with files, call sites, and artifact fields
  removed;
- require a net reduction in proposal/core public surface and Python files.

## Warehouse and CVRP Acceptance Matrix

| Evidence | Warehouse | CVRP/VRP |
| --- | --- | --- |
| Direct hypothesis/code fake-path parity | required | required |
| Correct problem-owned context and target source | required | required |
| No tool-selection model call | required | required |
| Contract/Verification/Protocol unchanged | required | required |
| Typed telemetry activation | problem-owned | problem-owned |
| Short deterministic smoke campaign | required | required |
| One formal campaign | regression/control | non-target-bound research |
| Promotion-grade improvement | retain known capability | required v0.4 goal |

Warehouse is the positive framework control: the refactor must not destroy its
ability to generate and evaluate useful research. CVRP is the research test:
the agent must choose a coherent mechanism without a prepared exact mechanism
binding, reach Protocol without a mechanical gate loop, and produce
attributable evidence.

## Rejection Conditions

Reject an implementation slice if it:

- changes provider-visible prompt content while claiming runtime extraction;
- introduces prompt budgets or truncation;
- moves problem semantics into generic core;
- weakens Contract, Verification, Protocol, or Decision;
- copies all agentic ledgers into the direct path;
- creates a second durable proposal truth source;
- changes launcher defaults before direct artifacts and failure lanes pass;
- treats one green synthetic test as evidence of warehouse/CVRP research
  effectiveness.

## Production Switch Preconditions

The K3 launcher switch is blocked until:

1. R2 lossless context inventory is byte/hash verified;
2. R3 forced-target versus tainted-mechanism responsibilities are settled;
3. R4 typed telemetry can distinguish activation from direct effect;
4. artifact replay/readiness validates both runtime modes;
5. direct-mode owning suites pass for warehouse and CVRP;
6. the generated launch contract declares the resolved runtime mode.

After K3, run one warehouse control campaign before the non-target-bound CVRP
campaign. A negative CVRP result is still useful only if the mechanism was
independently chosen, implemented coherently, activated under typed telemetry,
and evaluated by the unchanged full-solver Protocol.
