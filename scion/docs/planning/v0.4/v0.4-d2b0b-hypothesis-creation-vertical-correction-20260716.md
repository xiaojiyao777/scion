# D2b.0b Hypothesis-Creation Vertical Correction

Status: accepted dormant implementation contract. Independent SQL,
state/recovery, and dependency/authority reviews close at P0=0/P1=0/P2=0.
Checkpoint A implementation is authorized; checkpoint B remains ordered after
A's independent acceptance. Production composition, migration, and activation
remain unauthorized.

This document narrows and corrects the H-creation portion of
`v0.4-d2b0b-authorization-bound-owner-creation-plan-20260716.md`. The original
plan remains authoritative except where this document explicitly replaces an
API, dependency direction, SQL responsibility, or classification ownership.
The generic creation ledger and the already accepted champion participant are
unchanged.

## Why a correction is required

The first dormant checkpoint proved exact generic authorization closure, strict
champion authorization, committed START provenance, and a real provider-issued
result. The next layer cannot be implemented safely as an isolated event/binding
helper because the frozen plan contains three incompatible requirements:

1. `HypothesisStore` must enforce Branch/history-head/binding/active-H/lease
   predicates in one SQL INSERT, while an earlier responsibility sentence says
   it owns only H-table SQL.
2. The proposal-attempt participant is asked to classify the complete
   Branch/H/event/binding outcome from one snapshot, while Branch/H SQL belongs
   to focused stores and Registry is the only module allowed to import both
   focused stores.
3. The generation lifecycle contains `RESULT_BOUND`, but the frozen public
   surface has no operation that binds a result to the exact generation view;
   its later creation call can therefore be tempted to accept fresh Branch or
   prior-H reads after provider return.

Implementing around these conflicts would create cross-module helpers,
callbacks, or caller-fed semantic mappings. This correction instead freezes one
end-to-end dormant H-creation vertical before any additional code is written.

## Registry generation and creation views

`HypothesisGenerationView` is sealed, one-shot, thread/Context-bound, and tied
to one Registry root identity and publication generation. Its private state
contains:

- the exact immutable `RevisionedBranchRecord` used for prompt context;
- the complete immutable H bundle for that Branch;
- the deterministic prior history head by `(created_at, hypothesis_id)`, or
  exact empty history;
- proof that no active H exists in that captured bundle;
- the complete H-bundle storage digest;
- a Branch-local generation reservation identity;
- the exact sealed code-source identity, selected `source_kind`, and selected
  canonical source-manifest digest;
- the exact prompt source and bound-prompt identities;
- the exact START, permit, and later outcome object identities; and
- in checkpoint B only, the exact configured Contract and target-factory
  authority identities, protocol generations, and frozen config digests.

The complete H-bundle digest is SHA-256 over a domain-separated canonical
object with schema `hypothesis-generation-source-bundle.v1`, Branch ID, exact
bundle count, and an array sorted by `hypothesis_id`; each array item contains
only exact H ID, owner revision, and owner storage SHA-256. Encoding uses
`ensure_ascii=true`, `allow_nan=false`, sorted keys, separators `(',', ':')`,
and UTF-8. Prior-head identity remains a separate exact triple so bundle
membership cannot substitute for ordering authority.

`proposal/hypothesis_code_source_owner.py:HypothesisCodeSourceOwner` is a
narrow source reader, not a generic filesystem helper. Its exact instance is
installed in the checkpoint-A composition bundle
with a sealed `CampaignWorkspaceAuthority` for the exact campaign root and the
existing connection-scoped champion participant; no request accepts a path,
root, file mapping, or code string. Registry issues an
exact `HypothesisCodeSourceRequest` from the captured view and invokes the fixed
owner through a Registry-owned read snapshot. Source selection is a frozen v1
protocol over the captured Branch, never a caller choice:

| Captured Branch facts | `source_kind` | Required source proof |
|---|---|---|
| state is `STALE` or `STALE_WEIGHT_UPDATE` | `base_champion` | exact append-only `StoredChampionRecord` matches captured champion ID, weight revision and complete `base_champion_hash` manifest |
| `current_code_hash` or `last_clean_code_hash` is absent | `base_champion` | same exact champion proof; this is the normal new-Branch and provisional-unverified fallback |
| both hashes exist, state is not stale, `branch_code_status == "clean"`, and `current_code_hash == last_clean_code_hash` | `verified_branch_workspace` | sealed workspace complete manifest equals both captured hashes |
| any other combination | none | deterministic fail-closed source rejection before START; no workspace or champion substitution |

This deliberately tightens the old `BranchController.get_code_base()` fallback:
the old selector establishes the initial/stale champion cases, while the new
authority refuses to call unverified current bytes "clean" merely because both
hash fields are populated. The owner resolves only the selected root from its
authority, loads the exact champion record when `source_kind` is
`base_champion`, hashes the complete canonical manifest with the existing
workspace/snapshot algorithm, and issues `HypothesisCodeSource`. Its private
state owns `source_kind`, selected manifest digest, captured current/last-clean
hashes, exact champion identity, and an immutable normalized
relative-path-to-bytes map for the selected source. It does not expose or
retain an unselected source map. `ContextManager` may select problem-owned
research surfaces from those bytes, but cannot read the filesystem again or
replace them. Missing, changed, symlink-escaped, noncanonical, mismatched, or
selection-inconsistent sources spend the view before START and call no
provider.

`HypothesisPromptSource` binds the exact code source, `source_kind`, and

immutable Branch/H facts for context
construction but remains the only authority that a hypothesis prompt may bind.
It also owns a canonical `HypothesisOwnerContextProjection` containing exact
Branch ID/revision/storage digest, current-code hash, base champion

exactly as selected; it never presents a missing or unverified workspace as
current authoritative code.
Actual code bytes must hash to the captured owner hashes; every history H
reference must resolve to the captured bundle and the full bundle identity
spine is bound in host-side governance. Inside the Registry-owned prompt-source
issuance operation, the exact checkpoint-A `ContextManager` instance atomically
claims the view-retained code-source token before consuming its configured
problem runtime, deep-normalizes only the existing allowlisted non-source

`HypothesisProblemEvidenceProjection`. These
fields are deliberately tainted scientific input rather than owner identity,
but every prompt-affecting byte is detached and digest-bound; the token carries
no path, Branch/H/source field, issuer, callback, or mutable mapping. Duplicate
or overriding source keys fail before token issuance. Only the prompt
projection authority may consume this token, and it must match the exact code
source/view. Thus rich problem evidence remains problem-owned without allowing
ordinary caller data to replace durable owner source or mutate after bind.

The prompt projection owner consumes the exact source and issues

`issue_hypothesis_prompt_source()` is one Registry-owned composite authority,
not a request for caller inputs. It changes the retained code source
`ISSUED -> EVIDENCE_IN_FLIGHT`, invokes the one exact configured
`ContextManager` once, and receives either one sealed evidence projection or a
typed deterministic rejection/unexpected failure. On success Registry verifies
the exact source/view identity, advances the source to `EVIDENCE_BOUND`, binds
the projection `ISSUED -> VIEW_BOUND`, advances the view
`CODE_SOURCE_BOUND -> PROBLEM_EVIDENCE_BOUND`, then issues one prompt source
that privately embeds both exact tokens and records `PROMPT_SOURCE_ISSUED`.
Only that prompt source may advance the code source to `PROMPT_SOURCE_BOUND`.
The Context Manager is not publicly callable with a generation code token; no
caller can request two projections, choose between mutable-runtime snapshots,
or pass a projection back into Registry. Deterministic evidence rejection moves
the source to `EVIDENCE_REJECTED`; unexpected failure moves it to
`EVIDENCE_UNKNOWN`. Both spend the view through the corresponding explicit
pre-START path and release the local reservation without issuing a prompt
source or calling the provider.

`start_hypothesis_generation()` owns the caller-side coordinated transaction
and calls the connection-scoped proposal participant; the participant itself
does not begin, commit, roll back, close, or publish. START must commit and be
strictly visible through a new independent snapshot before a provider permit is
returned.

START commit uncertainty has a fixed three-way classification. `EXPECTED`
means no START row and no open attempt for the reservation; it spends the view
and clears the still-local reservation without issuing a permit. `COMMITTED`
means exactly one strict START and zero terminal; it advances to `START_BOUND`.
Malformed, duplicate, extra-terminal, snapshot-fault, or partial state is
`MIXED`, spends the view, and holds the Branch reservation. A permit is issued
only after `COMMITTED`.

`prepare_hypothesis_creation()` asks the leaf authority to perform the
non-consuming exact result/permit/START/prompt/approval/target/view binding
check and advances the generation view:

```text
PERMIT_ISSUED -> RESULT_BOUND -> CONTRACT_APPROVED
-> TARGET_BOUND -> CREATION_VIEW_ISSUED -> SPENT
```

`SPENT` here applies only to `HypothesisGenerationView`; the newly issued
`HypothesisCreationView` has its own one-shot lifecycle. It stores the exact
permit, START, bound prompt, receipt, result, approval, and approved target in
the creation view. The later transaction method therefore accepts no second
result, receipt, Branch token, prior-H token, target builder, callback, or
caller mapping.

The state machines are distinct and never move backward:

| Capability | Allowed phases |
|---|---|
| Branch reservation | any pre-START rejection/fault: `LOCAL -> RELEASED`; committed path: `LOCAL -> DURABLE_OPEN -> OUTCOME_BOUND -> RESOLVED`, with `DURABLE_OPEN -> UNCERTAIN_HOLD` terminal |
| `HypothesisGenerationView` | success: `CAPTURED -> CODE_SOURCE_IN_FLIGHT -> CODE_SOURCE_BOUND -> PROBLEM_EVIDENCE_BOUND -> PROMPT_SOURCE_ISSUED -> PROMPT_IN_FLIGHT -> PROMPT_BOUND -> START_IN_FLIGHT -> START_BOUND -> PERMIT_ISSUED -> RESULT_BOUND -> CONTRACT_APPROVED -> TARGET_IN_FLIGHT -> TARGET_BOUND -> CREATION_IN_FLIGHT -> CREATION_VIEW_ISSUED -> SPENT`; deterministic pre-START rejection: an eligible code-source/evidence/prompt phase `-> PRESTART_REJECTED -> SPENT`; unexpected pre-START fault: an eligible in-flight source/prompt phase `-> PRESTART_UNKNOWN -> SPENT`; post-START terminal: any eligible bound phase `-> TERMINAL_OUTCOME_BOUND -> TERMINAL_IN_FLIGHT -> SPENT`, or `-> UNCERTAIN_HOLD` |
| `HypothesisCodeSourceRequest` | `ISSUED -> SOURCE_IN_FLIGHT -> SOURCE_BOUND`; or `SOURCE_IN_FLIGHT -> SOURCE_REJECTED | SOURCE_UNKNOWN` |
| `HypothesisCodeSource` | `ISSUED -> EVIDENCE_IN_FLIGHT -> EVIDENCE_BOUND -> PROMPT_SOURCE_BOUND`; or `EVIDENCE_IN_FLIGHT -> EVIDENCE_REJECTED | EVIDENCE_UNKNOWN` |
| `HypothesisProblemEvidenceProjection` | `ISSUED -> VIEW_BOUND -> PROMPT_BOUND`; invalid raw evidence issues no token |
| `HypothesisPromptSource` | `ISSUED -> PROMPT_IN_FLIGHT -> PROMPT_BOUND`; or `PROMPT_IN_FLIGHT -> PROMPT_REJECTED | PROMPT_UNKNOWN` |
| `BoundHypothesisPrompt` | `ISSUED -> START_BOUND -> PROVIDER_BOUND | TERMINALIZED` |
| `StartedHypothesisAttempt` | `ISSUED -> DURABLE_BOUND -> PROVIDER_BOUND -> CREATION_BOUND | TERMINALIZED` |
| `ProviderGenerationPermit` | `ISSUED -> CLAIMED_BEFORE_TRANSPORT -> SUCCESS_BOUND | FAILURE_BOUND | CLAIMED_UNKNOWN`; or `ISSUED -> CANCELLED` |
| `GeneratedHypothesisResult` | `ISSUED -> CONTRACT_IN_FLIGHT -> CONTRACT_APPROVED -> CONSUMED`; or `CONTRACT_IN_FLIGHT -> CONTRACT_REJECTED -> TERMINALIZED`; or `CONTRACT_IN_FLIGHT -> CONTRACT_UNKNOWN` hold |
| `FailedHypothesisGeneration` | `ISSUED -> TERMINALIZED` |
| `AbortedHypothesisGeneration` | `ISSUED -> TERMINALIZED` |
| `HypothesisContractApproval` | `ISSUED -> TARGET_IN_FLIGHT -> TARGET_BOUND`; or `TARGET_IN_FLIGHT -> TARGET_UNKNOWN` |
| `HypothesisContractRejection` | `ISSUED -> TERMINALIZED` |
| `ApprovedHypothesisTarget` | `ISSUED -> CREATION_IN_FLIGHT -> CREATION_VIEW_BOUND`; or `CREATION_IN_FLIGHT -> CREATION_UNKNOWN` |
| `TerminalAttemptReceipt` | `ISSUED -> RESERVATION_RESOLVED` |
| `HypothesisCreationView` | `ISSUED -> CLAIMED -> STAGED -> SPENT` |

`START_IN_FLIGHT` becomes `START_BOUND` only after committed independent-snapshot
classification. A provider permit may be issued only from `START_BOUND`.
Provider claims that permit before transport and binds either one exact success
or one exact failure; neither path can return to `START_BOUND`. Registry, not
provider, performs the non-consuming verification that advances its view from
`PERMIT_ISSUED` to `RESULT_BOUND`. If transport began but process/thread loss
prevents either outcome from being issued, the permit is `CLAIMED_UNKNOWN` and
the durable START remains unresolved; no failure is fabricated.

The non-success view paths are explicit:

- before START commit, abort spends the local view/reservation and has no
  durable terminal event;
- after START but before permit issuance, Registry may issue an abort only after
  the leaf proves no permit exists; after permit issuance but before claim,
  Registry asks the leaf to atomically change the exact permit
  `ISSUED -> CANCELLED` and issue the exact abort token; provider claim and abort
  therefore cannot both win;
- provider failure terminalization non-consumingly verifies the exact
  permit/failure/view and binds `PERMIT_ISSUED -> TERMINAL_OUTCOME_BOUND`;
- Contract rejection terminalization first non-consumingly verifies the exact
  success/permit/result/rejection/view, advances
  `PERMIT_ISSUED -> RESULT_BOUND -> TERMINAL_OUTCOME_BOUND`, and introduces no
  separate view `CONTRACT_REJECTED` phase;
- terminal persistence uses `TERMINAL_OUTCOME_BOUND -> TERMINAL_IN_FLIGHT`, then
  a committed receipt resolves/spends the view and reservation, rollback
  restores no reusable capability and retains `UNCERTAIN_HOLD`;
- `CLAIMED_UNKNOWN`, `CONTRACT_UNKNOWN`, or any mixed classification spends the
  view and retains `UNCERTAIN_HOLD`.

View-state updates need not be atomic with a leaf transition to be safe: leaf
permit/result state is the transport/decision latch. Registry always rechecks
the exact leaf state during cleanup, so a fault after permit cancellation or
Contract claim can only retain a hold; it cannot re-enable claim or validation.

The same claim-before-work rule covers non-transport issuance. Registry first
claims the exact code-source request before any filesystem read; unexpected
failure becomes `SOURCE_UNKNOWN`, moves the view through
`PRESTART_UNKNOWN -> SPENT`, and releases the still-local reservation. A
deterministic selection/hash/path rejection instead binds
`SOURCE_REJECTED`, moves the view through `PRESTART_REJECTED -> SPENT`, and
clears its still-local reservation through `LOCAL -> RELEASED`; it writes no
durable event and creates no hold. After `SOURCE_BOUND`, Registry's composite
prompt-source operation moves the code source to `EVIDENCE_IN_FLIGHT` before
invoking Context Manager. Deterministic raw-evidence rejection binds
`EVIDENCE_REJECTED`; unexpected projection failure binds `EVIDENCE_UNKNOWN`.
Success instead binds the sole evidence projection to the view, advances
`PROBLEM_EVIDENCE_BOUND`, and only then records `PROMPT_SOURCE_ISSUED`. The
prompt owner atomically claims that exact prompt source before rendering;
deterministic render rejection binds `PROMPT_REJECTED`, spends the pre-START
view, and releases the local reservation, while an unexpected fault becomes
`PROMPT_UNKNOWN`, spends the view through `PRESTART_UNKNOWN`, and also releases
that reservation. Evidence rejection/unknown follows the same respective
`PRESTART_REJECTED`/`PRESTART_UNKNOWN` plus local-release paths. These
pre-START unknowns are not replayed on the same view, but cannot hide provider
transport or a committed mutation and therefore create no durable hold. Target
factory
atomically claims the exact approval before classifier/clock/UUID work; an
unexpected fault becomes `TARGET_UNKNOWN`. Registry atomically claims the exact
approved target before creation-view validation/issuance; an unexpected fault
becomes `CREATION_UNKNOWN`. Every UNKNOWN spends the usable view. Post-START
`CLAIMED_UNKNOWN`, `CONTRACT_UNKNOWN`, `TARGET_UNKNOWN`, and
`CREATION_UNKNOWN` retain the durable Branch reservation; pre-START source or
prompt UNKNOWN follows the explicit local-release rule above. None permits a
second bind, target build, or prepare call.
Every deterministic pre-START rejection performs no automatic replacement or
provider call. `RELEASED` is final for that view only; a later scientific
attempt requires a new scheduler decision and new reservation.

`prepare_hypothesis_creation()` may only observe an already bound success and
consumes the generation view as it issues the creation view.
Claiming a creation view is irreversible even when its database transaction
later rolls back or has an uncertain commit return. That outcome is classified;
the provider is never called again and no second H-creation frame is opened.

`FailedHypothesisGeneration` is issued only by provider after an exact claimed
permit and binds the real failure receipt/trace facts. A Contract rejection is
issued only by Contract Gate and binds the exact successful result. Contract
Gate must atomically claim `ISSUED -> CONTRACT_IN_FLIGHT` before validation and
may issue exactly one approval or rejection. An unexpected exception after
claim becomes `CONTRACT_UNKNOWN`; validation is not repeated and the Branch is
held. An explicit
abort is a distinct Registry authority and is legal only before permit claim;
leaf issuance atomically cancels the exact permit, so it cannot impersonate
provider failure or race a real provider call. Proposal owner consumes an exact
terminal outcome in a Registry-owned transaction, inserts and strictly rereads
one terminal event, and after independent committed classification issues a
sealed `TerminalAttemptReceipt`. Only that receipt resolves the Branch
reservation. Process loss after permit claim, failed terminal persistence, or
any mixed classification leaves the durable START in `UNCERTAIN_HOLD`.

Terminal commit classification is fixed. `EXPECTED` is exact START plus zero
terminal: no receipt is issued, the global transaction guard clears, and the
Branch reservation remains `UNCERTAIN_HOLD`. `COMMITTED` is exact START plus
exactly the one expected terminal and no extra terminal: proposal owner issues
the exact sealed receipt and Registry resolves the reservation. Any wrong,
duplicate, malformed, partial, or snapshot-fault state is `MIXED` and holds.
Classification never synthesizes a terminal outcome or repeats persistence.

Every terminal token maps truthfully into the existing
`proposal-attempt-transition.v1` schema; no new status or caller-selected reason
is introduced:

| Sealed outcome | status | transition_reason | failure_lane | prompt outcome |
|---|---|---|---|---|
| provider interruption | `interrupted` | `provider_call_interrupted` | null | exact receipt; `ok=false`, real `provider_ok`, category `provider_call_interrupted`, real error type, `non_resumable=true` |
| provider/transport/trace failure | `failed` | `provider_call_failed` | `infra` | exact failure receipt and refs; exact booleans/category/type |
| provider parse/schema failure | `failed` | `proposal_response_invalid` | `invalid_response` | exact parse-failure receipt and refs; `provider_ok=true`, `ok=false`, real parse category/type |
| Contract rejection | `failed` | `hypothesis_contract_rejected` | `invalid_response` | exact successful receipt and durable refs; receipt success/error fields remain unchanged |
| explicit post-START pre-claim abort | `failed` | `provider_call_cancelled_before_transport` | `infra` | START context/prompt hashes; refs null; `provider_ok=null`, `ok=false`, category `provider_call_cancelled_before_transport`, error type `AbortedHypothesisGeneration` |

All terminal rows preserve START schema/campaign/Branch/attempt/runtime/phase,
attempt kind, no-continuation fact, and anchors. They set H ID/digest and patch
digest to null, omit proposal fingerprint, and derive ordered tainted refs only
from the exact receipt. `trace_persistence_error` is included only when the
sealed receipt proves it. Contract rejection deliberately records no H memory;
its sealed rejection/result still preserve the proposal digest for internal
classification without putting a caller-authored H identity in the terminal
event. The rebuilt payload passes the full v1 validator plus exact-type checks
before INSERT and strict storage reread.

At acquisition and again inside the START `BEGIN IMMEDIATE`, Registry/proposal
owner prove that the Branch has no strict START with zero terminal. One local
reservation is allowed per Branch. Restore scans strict attempt groups; every
unresolved or malformed group reinstalls a Branch-local hold before a new view
can be issued. Thus a different attempt ID cannot bypass an unresolved provider
call. Resolving a terminal reservation performs no scheduling and authorizes no
automatic retry or replacement; any later distinct scientific attempt belongs
to the separately reviewed scheduler policy. Unrelated Branches remain usable.

## Contract approval and exact target binding

An ordinary `ContractResult` is audit data and is never authority. Contract

## Historical activation is a separate blocked design surface

A read-only scan on 2026-07-16 covered exactly
`/home/clawd/research/scion-experiments` after retention batch 19. The sorted
NUL-delimited list of the 827 `scion.db` paths has SHA-256
`8a90584c6ddc717d79efc75e2fd993ba9a01b919c297ef6a6e84352af08fe123`.
Ambiguous WAL databases were inspected only through isolated copies; source
bytes were not changed. Of those databases, 825 were readable and two retained
pre-existing malformed SQLite state. None has
the proposed binding/activation tables. Across 7,792 H rows:

- all lack the final owner revision/generation and proposal digest;
- 3,906 are in schemas without `predicted_direction`;
- 1,262 are in schemas without family fields;
- 875 are in schemas without base champion version;
- 1,099 have no durable Branch row; and
- 3,846 retain legacy target/protected/novelty/mechanism JSON facts not covered
  by the current owner digest or adoption inventory.

Sixty databases contain multiple campaign IDs and sixty-five contain no
nonempty campaign ID. Forty historical generated-H transitions form valid
START/generated pairs, but their H rows cannot prove proposal-digest equality;
they are completion-only evidence, not new authority.

Therefore D2b.0b.C may not silently fill missing fields, discard legacy
scientific JSON, invent Branches/campaigns, or pretend legacy events carried
sealed provider provenance. A later migration addendum must choose and review
one of:

- immutable legacy-extra adoption with complete storage digests;
- an expanded final owner projection that preserves those fields; or
- explicit integrity hold for databases that cannot satisfy exact provenance.

It must also freeze immutable event/binding triggers, full event-storage
adoption digests, orphan/multi-campaign policy, malformed-database handling, and
resumable inventory bytes. Its first artifact must be a checked-in read-only
scanner plus per-database inventory and aggregate JSON digest so these counts
can be reproduced against a named root set. Until that addendum closes P0/P1,
offline activation
and writer cutover remain prohibited; this does not block the production-
unwired vertical implemented against explicit final test fixtures.
