## 1. Decision

This addendum closes the execution seam below the accepted fresh-only boundary.
It does not activate production, adopt history, or issue a runtime database
authority.

The fresh bootstrap identity includes the exact `campaign_id` and a reviewed
`initial_state_manifest_sha256` before the prepared receipt is durable. The
same values are stored in the immutable activation singleton and checked by the
independent verifier. Campaign identity is never added after publication by an
unbound first runtime transaction.

The implementation proceeds through sealed fixture-only slices. Until D2b-D4
and L1-L3 freeze the complete production schema, writer manifest, initial state,
and composition root, there is no production bootstrap-plan issuer, no
`CampaignDatabaseAuthority`, no WAL transition, and no runnable composition.

This is a one-time structural initialization path. It adds no proposal gate,
retry loop, model-call budget, search cap, patch limit, output truncation, or
agent hot-path check.

This execution addendum is later and explicitly supersedes three execution
details in the earlier fresh-only boundary:

1. The staging basename is not newly random after capability issuance. It is
   deterministically derived from the already high-entropy exact cutover ID
   with a fixed domain and all 64 SHA-256 hex digits, so recovery locates one
   name without scanning after a pre-prepared crash.
2. A rollback journal is not opened for automatic recovery by the default
   SQLite VFS. Because that VFS cannot prove nofollow and inode continuity for
   its actual journal handle, any journal/WAL/SHM is a deterministic read-only
   `HOLD`, not `ABORTED_PRECOMMIT`. E6 therefore accepts only main-only recovery
   goldens. Production activation remains blocked until a separately frozen
   controlled-VFS design can bind the actual journal handle, or another
   reviewed mechanism eliminates that crash state; the earlier boundary's
   unconditional hot-journal/aborted recovery acceptance is withdrawn.
3. The independent verifier generates canonical report bytes but does not own
   filesystem persistence. `receipt.py` mechanically no-replace publishes and
   syncs those exact bytes, and the bridge issues proof only after the durable
   raw SHA returns. This preserves independent semantic reconstruction while
   replacing the earlier verifier-as-file-writer wording with one artifact
   writer.

## 2. Closed identity and digest DAG

`campaign_id` is one exact nonempty UTF-8 string with no leading/trailing
whitespace or NUL. Two artifacts separate reviewed structure from per-campaign
identity:

- `initial_state_template_sha256` identifies the fixed-hash reviewed fixture
  template: the exact table/column/key sets and typed-row digest algorithm;
- `initial_state_manifest_sha256` identifies the per-campaign instance produced
  deterministically from that template, exact campaign ID, and reviewed fixture
  inputs. Producing this instance is computation, not a human approval gate.

The per-campaign instance binds the campaign ID, schema/writer generations and
manifest hashes, the closed initial authoritative table set, and exact row
counts and ordered-row digests. It binds only initial domain rows. The
activation singleton is excluded and is owned by the activation-row domain.

Its structured domain is
`scion.fresh-activation.initial-state-manifest.v1`. The closed object is:

```text
campaign_id
initial_state_template_sha256
schema_generation
writer_generation
schema_manifest_sha256
writer_manifest_sha256
tables[] ordered by UTF-8 table_name, each containing exactly:
  table_name
  primary_key_columns[] in schema order
  projected_columns[] in schema order
  row_count
  ordered_rows_sha256
```

Each `ordered_rows_sha256` uses domain
`scion.fresh-activation.initial-table-rows.v1` and one object containing the
table name, exact projected columns, and rows ordered by the canonical primary-
key tuple. Every scalar is type tagged:

```text
null    = {"type":"null"}
integer = {"type":"integer","value":"canonical base-10 integer"}
real    = {"type":"real","value":"16 lowercase hex digits of the IEEE-754 binary64 bits in big-endian byte order"}
text    = {"type":"text","value":"exact UTF-8 string"}
blob    = {"type":"blob","value":"even-length lowercase hex"}
```

Integer zero has no sign or leading zero. Binary64 bits are produced by packing
the SQLite/Python double as network-order `>d` and hex-encoding its exact eight
bytes, so `+0.0` and `-0.0` remain distinct; NaN and infinities are forbidden.
Booleans are integers. Each primary-key tuple's comparison bytes are the compact
canonical JSON bytes of
`{"domain":"scion.fresh-activation.primary-key.v1","items":[TAGGED_SCALARS]}`
under this document's canonical encoder. Tuples compare lexicographically by
those unsigned bytes, not SQLite collation or host-language mixed-type ordering.
Duplicate comparison bytes or duplicate SQLite primary keys fail.
The manifest's table set must equal the reviewed authoritative initial-domain
table set. The activation singleton table is not in that set and is verified by
its own closed rule.

The activation package does not accept a caller-supplied callback, SQL builder,
plugin, expression, or open-ended metadata map to interpret this manifest.
Fixture code and the independent fixture verifier contain ordinary deterministic
logic for the one reviewed fixture schema. A production initial-state manifest
and its deterministic verifier can be added only with the final fixed writer
and composition manifests.

The accepted bootstrap-payload and activation-row objects from the fresh-only
boundary gain three required fields:

```text
campaign_id
initial_state_template_sha256
initial_state_manifest_sha256
```

The template and per-campaign instance artifacts each have a raw SHA. The
instance's campaign ID, schema/writer generations and hashes, and template SHA
must byte-equal the bootstrap payload. Every one of those payload fields,
including both initial-state SHAs, must byte-equal the activation row. The exact
DAG is:

```text
initial_state_template -----\
schema_manifest -------------+-> initial_state_manifest
writer_manifest -------------+
campaign_id ----------------/

bootstrap_payload(
  campaign_id,
  initial_state_template,
  initial_state_manifest,
  schema/writer identity,
  cutover and pinned path/staging identity
)
  -> prepared_receipt
  -> activation_row
  -> closed staging_main bytes
  -> staging_committed
  -> prepublication_report bytes
  -> target_published
  -> postpublication_report bytes
  -> final_receipt
```

`final_receipt.independent_verifier_report_sha256` means the raw complete
postpublication report bytes including one terminal LF. The prepublication and
postpublication reports are distinct immutable artifacts and distinct fields.
No downstream digest is written back into SQLite.

Structured digests retain the accepted canonical envelope:

```json
{"domain":"EXACT_DOMAIN","items":[OBJECT]}
```

Encoding is UTF-8 with `ensure_ascii=false`, `allow_nan=false`, sorted keys,
compact separators, and no terminal LF. Reports are canonical JSON plus exactly
one terminal LF and are hashed as raw bytes.

## 3. Capability handoff

The current `source_snapshot.py` must not expose `_PinnedAuthority`,
`_HandleState`, a raw parent descriptor, or a mutable authority object to
`bootstrap.py`.

`acquire_staging_capability()` is extended at its sole issuer boundary to bind
all of these exact values before any capability exists:

```text
campaign_id
cutover_id
policy_generation
schema_generation + schema_manifest_sha256
writer_generation + writer_manifest_sha256
initial_state_template_sha256 + initial_state_manifest_sha256
pinned campaign root + normalized target parent/basename
```

Every SHA is exactly 64 lowercase hex characters. `OfflineStagingFile` accepts
only the spent capability and no additional identity argument. The deterministic
staging basename is
`.scion-staging-{TAG}.sqlite`, where `TAG` is the full SHA-256 of canonical
domain `scion.fresh-activation.staging-name.v1` over the exact cutover ID. The
full cutover ID remains inside every later artifact and is rechecked; a name
collision or pre-existing deterministic staging path is a hold.

The next source slice adds an opaque sealed `OfflineStagingFile` whose state is
held only in a private weak registry. The only creation path is:

```text
StagingCapability
  -> spend first
  -> revalidate pinned chain and target bundle absence
  -> open staging basename with
     O_CREAT|O_EXCL|O_RDWR|O_NOFOLLOW|O_CLOEXEC, mode 0600, dir_fd=parent
  -> prove regular file, nlink=1, permission bits exactly 0600,
     uid/euid and gid/egid exactly equal the captured issuer identity,
     exact device/inode, non-inheritable descriptor
  -> OfflineStagingFile
```

The original staging capability is permanently spent before file creation.
Failure, exception, cancellation, fork, finalization, or identity drift never
restores it.

The sealed staging handle binds issuing PID and thread, pinned parent
device/inode/mount ID, target and staging basenames, staging device/inode,
mode/uid/gid, cutover ID, campaign ID, policy/schema/writer generations and
manifest SHAs, and both initial-state SHAs. It is non-copyable, non-serializable,
non-subclassable, and one-shot.

`source_snapshot.py` retains that handle in its private registry until
`receipt.py` returns the exact durable prepared proof. It then atomically
consumes `OfflineStagingFile + PreparedDurableProof`, advances the same live
session, and installs a new sealed `PreparedOfflineStagingContext` directly in
the private `offline_sqlite.open_fixture_session` registry. That context is the
leaf's only database input and resolves the exact existing staging inode for
SQLite `mode=rw` use. `bootstrap.py` orchestrates only closed facts/proofs and
never receives, forwards, copies, or retains either sealed handle. The leaf
does not return the parent descriptor or authority state. Settlement remains
in `source_snapshot.py`:

- precommit abort may unlink only the exact regular nlink-1 staging inode after
  the SQLite connection is closed and every journal/WAL/SHM sidecar is proven
  absent; any sidecar or uncertain close is a read-only hold;
- committed or uncertain settlement retains the inode for explicit recovery;
- post-rename settlement never unlinks the target;
- every settlement closes descriptors and releases the directory lock once.

A crash after staging creation but before a complete prepared final artifact
leaves the deterministic staging/pending names in a read-only hold. Recovery
can locate them but has no durable predecessor authorizing inspection, deletion,
or completion. The live issuing process may clean its own exact inode while it
still holds the original session; a later process may not infer that authority.

No public package export or production import is added in this slice.

and ordinary callers never see those descriptors.

callback:

- live issuance consumes the still-live offline session, exact

permit, bind the same complete upstream digests/inodes and durable report raw

PID/thread/lock-session bound, nonserializable, and cannot exist for a gap,

permit issuer. Production issuer and caller count remain zero through E6 and
are reconsidered only after E7 design.

## 4. External artifact owner

`fresh_activation/receipt.py` exclusively owns artifact names, canonical bytes,
digest domains, readers, and no-replace publication.

For `cutover_tag = sha256(cutover_id UTF-8)` using all 64 lowercase hex digits,
the only final basenames are:

```text
.scion-cutover-{cutover_tag}.prepared.json
.scion-cutover-{cutover_tag}.staging-committed.json
.scion-cutover-{cutover_tag}.prepublication-report.json
.scion-cutover-{cutover_tag}.target-published.json
.scion-cutover-{cutover_tag}.postpublication-report.json
.scion-cutover-{cutover_tag}.final.json
.scion-cutover-{cutover_tag}.aborted.json
```

Every object contains the full exact cutover ID; readers recompute the basename
tag and compare the full ID. A tag match alone grants no authority.

Each final artifact has one deterministic sibling ending `.pending`. Publication
is exact:

1. `openat` the pending name with `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW|O_CLOEXEC`
   and mode `0600`;
2. write all expected bytes and reject short/extra data;
3. `fsync` the pending file;
4. `renameat2(..., RENAME_NOREPLACE)` pending to final under the pinned parent;
5. `fsync` the pinned parent directory.

Every pending/final artifact is a regular `nlink=1` file with permission bits
exactly `0600` and the acquisition-captured effective uid/gid. `receipt.py`
proves those facts with descriptor-relative nofollow observation before a file
is accepted or recovered. A mismatch is `HOLD`, not cleanup authority.

There is no `os.rename`, `os.replace`, `Path.replace`, `shutil.move`, hard-link,
or weaker-platform fallback. Recovery for the same explicit cutover may inspect
only its deterministic pending names. It may complete or clean a pending file
only when the complete exact durable predecessor phase exists and uniquely
determines the expected canonical bytes. In that case, exact pending bytes may
be renamed no-replace; partial/different bytes may be unlinked only after
nofollow regular/nlink-1 identity proof, parent sync, and deterministic
reconstruction. This is phase recovery, not a retry of SQLite work.

Without the exact predecessor, any pending file—including `prepared.pending`—
is a read-only hold and is never deleted. The closed conflict table is:

- final absent + pending absent: advance only from the exact predecessor;
- final absent + pending exact + exact predecessor: finish no-replace publish;
- final absent + pending partial/different + exact predecessor: exact pending
  recovery described above;
- final exact + pending absent: accept after parent sync, including recovery
  from rename-success/before-parent-fsync;
- final exact + any pending: hold as interference;
- final malformed/competing + any pending state: hold;
- any phase without its exact predecessor, any fork, or aborted plus later
  phase: hold.

Unknown files are never scanned, selected, or deleted.

All artifacts live under the same pinned parent as target and staging. Phase
order is append-only; an existing exact phase is verified byte-for-byte and is
never overwritten.

## 5. Offline SQLite owner

`fresh_activation/bootstrap.py` is independent of
`lineage.sqlite_connection._connect_sqlite`,
`_connect_authority_sqlite`, `LineageRegistry`, and every legacy store. Those
paths create/open final paths, use WAL, or perform in-place schema evolution and
are forbidden here.

`offline_sqlite.py`, not `bootstrap.py`, owns the SQLite connection. It opens
only the already-created exact staging inode in SQLite `mode=rw` without create
permission. The complete prepared final artifact and its parent-directory
`fsync` must succeed before the first SQLite connection is opened and therefore
before any SQLite PRAGMA, implicit recovery, or transaction can occur.

A private fresh-owned native bridge is compiled against the same SQLite library
as the Python connection. It captures the actual `sqlite3*` belonging to that
one connection; it is not a path-based substitute. At each checkpoint it calls
`sqlite3_file_control(db, "main", SQLITE_FCNTL_HAS_MOVED, &moved)` and requires
`moved == 0`, while the sealed staging descriptor and a descriptor-relative
nofollow stat of the basename both equal the capability's exact regular,
`nlink=1`, device/inode identity. The conjunction binds SQLite's actual open
main file to the sealed inode. Checkpoints are mandatory immediately after
open and before any PRAGMA, immediately before `BEGIN IMMEDIATE`, immediately
before `COMMIT`, immediately after successful commit, immediately before close,
and on both open and pre-close of the later read-only inspection connection.
An unavailable native bridge, `sqlite3*` mismatch, `HAS_MOVED` failure, identity
drift, or close uncertainty is a hold. Reusing the WAL runtime connection
factory or proving only the pathname is forbidden.

Before the transaction the owner sets and then separately reads these exact
values:

```text
PRAGMA journal_mode = DELETE  -> exact returned mode "delete"
PRAGMA synchronous = FULL     -> exact read value 2
PRAGMA foreign_keys = ON      -> exact read value 1
PRAGMA locking_mode = EXCLUSIVE -> exact returned/read mode "exclusive"
```

Every result must be one scalar of the stated type and value. Extra rows,
coercion, or a different setting is a hold.

It uses explicit `BEGIN IMMEDIATE`, individual fixed statements, and one
explicit commit. `executescript`, `IF NOT EXISTS`, migration, callback SQL, and
runtime connection factories are forbidden. The single transaction creates the
complete fixture schema, inserts the exact initial domain state, and inserts one
immutable activation row. The activation-row digest is computed with its own
digest field omitted. The fixture schema includes fixed triggers that reject
every UPDATE or DELETE of the activation singleton; the singleton primary key
and cardinality are fixed rather than caller-selected.

Still inside the same transaction and before `COMMIT`, the owner independently
reconstructs the exact schema projection, activation singleton and digest,
campaign/payload equality, complete initial-state table projection, row counts
and ordered-row digests. It also requires `PRAGMA integrity_check` to return the
single text row `ok` and `PRAGMA foreign_key_check` to return zero rows. A
failure rolls back; it cannot be repaired after commit.

After the post-commit actual-main checkpoint, the owner closes the connection,
fsyncs the sealed exact staging descriptor, fsyncs the pinned parent, and
proves:

- the pinned staging inode/device/nlink did not change;
- `-wal`, `-shm`, and `-journal` are absent;
- the exact schema manifest, activation singleton, campaign identity, and
  initial-state manifest agree;
- `PRAGMA integrity_check` returns exactly `ok`;
- `PRAGMA foreign_key_check` returns zero rows;
- a read-only inspection creates no sidecar;
- the raw main-file SHA is stable across inspection.

The read-only inspection uses a distinct `mode=ro` connection, the same native
actual-main checkpoints, and exact `query_only=1`, `foreign_keys=1`, schema,
activation, state, integrity, and foreign-key reads. It is closed before the
second raw-main hash and may not create any sidecar.

Only then may `staging_committed` be published. This slice uses one in-code
fixture schema and plan with no production issuer. A fixture plan is not a
generic bootstrap API.

## 6. Closed state machine

Volatile in-process lifecycle and durable recovery phase are separate
coordinates. Lifecycle describes only the live sealed objects:

```text
ACQUIRED
-> STAGING_CREATED
-> PREPARED_DURABLE
-> DB_COMMIT_IN_FLIGHT
-> DB_COMMITTED_MAIN_ONLY
-> STAGING_COMMITTED_DURABLE
-> PREPUBLICATION_VERIFIED_DURABLE
-> PUBLISH_ATTEMPTED
-> TARGET_DIRECTORY_DURABLE
-> TARGET_PUBLISHED_DURABLE
-> POSTPUBLICATION_VERIFIED_DURABLE
-> FINAL_DURABLE
-> DORMANT_REOPEN_PROOF
```

It disappears on process death and is never reconstructed from guesses. The
durable phase is derived only from exact final artifacts and is one of:

```text
NONE | PREPARED | STAGING_COMMITTED | PREPUBLICATION_VERIFIED |
TARGET_PUBLISHED | POSTPUBLICATION_VERIFIED | FINAL | ABORTED | HOLD
```

Except for terminal `ABORTED`, durable artifacts must form the one complete
prefix in that order. A gap, later artifact without every predecessor, two
terminal branches, or any conflicting artifact is `HOLD`.

`ABORTED_PRECOMMIT` is permitted only after exact recovery proves there is no
committed activation row. Every contradiction is `HOLD`. `FINAL_DURABLE` and
`DORMANT_REOPEN_PROOF` remain non-runnable and cannot be converted into a
`CampaignDatabaseAuthority` in these slices.

The publication permit binds the complete staging/prepublication facts and is
marked spent before the target `RENAME_NOREPLACE` syscall. Success, known
failure, exception, cancellation, or uncertainty leave it spent.

Conflict classification precedes every happy-path or recovery action. Highest
priority is read-only `HOLD` for malformed/noncanonical phase bytes, unknown or
duplicate campaign-phase artifacts, final-plus-pending coexistence, phase gap
or fork, aborted-plus-later phase, target/staging identity conflict, unexpected
SQLite sidecar, lock/parent/staging identity drift, or an unprovable native
SQLite state. Next, an exact complete final chain returns only a dormant proof;
an exact aborted chain returns aborted. Only a remaining unique exact prefix may
enter the recovery matrix. No lower-priority row may mutate away a higher-
priority conflict.

## 7. Exact recovery matrix

Recovery accepts only `recover_cutover(exact_cutover_id)`. It reacquires the
same directory/basename lock and never falls back to create-fresh, scans for a
candidate, or opens a competing target.

| Durable observation | Only allowed result |
|---|---|
| no prepared and no phase artifact, regardless of absent staging | return not-found/hold; no mutation or fresh creation |
| no prepared but deterministic staging or prepared pending exists | read-only hold; no inspection or deletion |
| prepared; no staging inode; target absent | read-only hold; absence cannot prove precommit abort |
| prepared; exact staging plus any rollback journal, WAL, or SHM observation | read-only hold; no SQLite open or sidecar recovery is authorized |
| prepared; exact staging; no sidecar; no activation row after read-only inspection; main-only | unlink the exact staging inode, sync parent, append aborted-precommit |
| prepared; exact staging; exact activation row/schema/state; main-only; no staging-committed | recompute stable main SHA and append staging-committed; never rerun DDL/INSERT |
| prepared; staging state cannot prove committed or rolled back | read-only hold |
| staging-committed; exact staging; target absent; no prepublication report | independently verify and append the one prepublication report |
| prepublication report; exact staging; target absent | consume one recovered publication permit and execute one no-replace rename |
| prepublication report; staging absent; exact target inode present | treat rename as completed, fsync parent, append target-published |
| prepublication report; both target and staging present, or neither identity matches | read-only hold |
| target-published; postpublication report absent | independently verify exact target and append postpublication report |
| postpublication report; final absent | verify the full DAG and append final |
| exact final | return dormant reopen proof |
| competing target, unknown sidecar, phase regression/fork, digest or inode drift, partial final artifact | read-only hold |

No hot-journal recovery is authorized in E1-E6. Any `-journal`, `-wal`, or
`-shm` observation is a read-only hold before SQLite open because the default
SQLite VFS cannot prove nofollow and inode continuity for its actual rollback-
journal handle across the path-open boundary. A later controlled-VFS design may
add that authority only through a separately frozen addendum. With all sidecars
absent, recovery may use one read-only connection with the same fresh-owned
native `sqlite3*` actual-main/HAS_MOVED checkpoints; it performs no DDL, domain
DML, PRAGMA mode transition, or implicit recovery. The activation row and full
schema/state facts then decide exact committed reconstruction versus a proved
precommit abort. Recovery never repeats schema or domain writes.

`reopen_exact(cutover_id, final_receipt)` accepts only the exact final chain and
returns a sealed dormant `ReopenProof`. It does not enable WAL or issue runtime
authority.

## 8. Independent verification

The verifier remains outside `fresh_activation.*` and imports none of those
modules. It independently owns Linux descriptor/no-follow observation,
`renameat2` capability checks, artifact naming/canonicalization, SQLite
read-only inspection, schema/state comparison, digest reconstruction, and phase
policy.

Immediately before publication the verifier emits exactly one canonical
prepublication report to its response pipe and never opens an artifact name.
The bridge validates those bytes and passes them to `receipt.py`, the sole
owner that writes, no-replace publishes, and syncs the immutable report. Only
after `receipt.py` returns the durable raw SHA may the bridge issue the bound
`PrepublicationProof`. The identical single-writer flow publishes the separate
postpublication report after target-directory durability. Postpublication
verification does not claim to reconstruct past absence; it validates the
bound prepublication report and same-inode publication result.

The E6 `PrepublicationBeforeRename` recovery branch is deliberately read-only:
its revalidation context carries no writer. `receipt.py` opens the exact
existing final through its sealed read handle; the bridge issues
`RecoveredPrepublicationProof` only when a fresh verifier run reproduces those
canonical bytes exactly and their raw SHA equals the variant-bound durable SHA.
It never rewrites or republishes the report.

Implementation and verifier may share only literal schema definitions and
closed artifact shape files after those files are fixed-hash reviewed. They do
not share canonicalization, path syscalls, SQLite inspection, policy functions,
or digest code.

The verifier endpoint is one fixed executable identity frozen before E4. The
bridge invokes only:

```text
VERIFIER --parent-fd N --request-fd R --response-fd W
```

with `close_fds=true` and `pass_fds=(N,R,W)`. `N` is a duplicate of the same
already-locked parent open-file-description held by the issuing session, not a
newly opened directory and not a path argument. `R` carries one canonical,
length-delimited closed request and `W` accepts one canonical report; both are
one-way pipes. The parent retains its original descriptor for the entire child
lifetime.

The lock is Linux `flock(LOCK_EX|LOCK_NB)` on the pinned parent directory and
is associated with the shared open-file-description. The child proves rather
than assumes the handoff in this order:

1. `fstat(N)` must equal the request's directory device/inode and the
   independently observed mount ID;
2. `openat(N, ".", O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)` creates a
   distinct probe OFD `Q` for the same identity;
3. `flock(Q, LOCK_EX|LOCK_NB)` must fail with exactly `EWOULDBLOCK`, proving an
   exclusive lock already exists;
4. `flock(N, LOCK_EX|LOCK_NB)` must succeed, proving the inherited OFD—not an
   unrelated competing OFD—is the lock owner;
5. close `Q`; never call `LOCK_UN` on `N`.

Any other result is a hold. The report binds
`lock_proof={scheme:"linux_flock_ex_nb",distinct_ofd_probe:"EWOULDBLOCK",inherited_ofd_reassertion:"success"}`.

The child checks the frozen executable SHA bound by the request. Any extra
argument, environment-selected executable, inherited descriptor, bootstrap
fallback, or parent path reopen is a hold. Requests reject unknown/missing
fields recursively and use the section-2 canonical bytes. Both request schemas
contain exactly:


The prepublication request fixes schema/phase to
`scion.fresh-activation.prepublication-request.v1` / `prepublication` and adds
exactly `target_must_be_absent=true`. The postpublication request fixes them to
`scion.fresh-activation.postpublication-request.v1` / `postpublication` and
adds exactly `prepublication_report_raw_sha256`,
`target_published_receipt_raw_sha256`, `target_database_identity`, and
`staging_must_be_absent=true`. Identity objects use the exact nested shapes

## 9. Implementation slices

Each slice is separately reviewed and remains dormant:

1. `E0`: freeze this addendum and adversarial fixtures.
2. `E1`: source capability to sealed `OfflineStagingFile`; no SQLite import.
3. `E2`: `receipt.py` plus pure closed `policy.py`; no database or target.
4. `E3`: fixture-only offline bootstrap through durable staging-committed; no
   publication permit issuer.
5. `E4`: independent prepublication verifier and complete permit binding.
6. `E5`: no-replace target publication, postpublication verifier, and final
   receipt.
7. `E6`: exact cutover recovery/reopen goldens returning only dormant proof.
8. `E7`: after D2b-D4 and L1-L3, separately freeze the production schema,
   writer, initial-state, and composition manifests and only then design a
   production issuer.

No slice may silently absorb the next slice to make a happy-path demo runnable.
