## 1. Decision

The next implementation slice promotes the accepted native blocked-child ABI
into one generic process-containment layer. It does not patch, wrap or call the
rejected Warehouse lifecycle. It does not modify the ordinary campaign
`Runner` abstraction.

This slice owns exactly three responsibilities:

1. create and pin one sibling job cgroup beneath the current systemd-delegated
   service root;
2. use the accepted native ABI to keep a child blocked, release it exactly
   once, reap its leader by the original pidfd, drain complete binary streams
   and prove the job cgroup empty;
3. freeze and validate the systemd-255 topology and run-to-close handoff facts
   that a later guardian/terminal layer must acquire and publish.

The slice adds no scientific gate, model call, retry, resume, runtime timeout,
budget, byte cap, line cap, truncation, tail replacement or fallback spawn.
Waiting indefinitely for an owned process/cgroup to settle is an integrity
hold, not a solver budget. Kernel-I/O continuation after `EINTR` is not an
experiment retry.

No solver or W3 formal job is authorized by this contract. Implementation
remains locked until two independent reviewers report P0=0/P1=0 on one exact
raw SHA of this file.

## 2. Why the old lifecycle is not a migration base

The untracked, rejected Warehouse candidate currently forms a second complete
execution authority:

- `w3_execution.py` uses `subprocess.Popen(start_new_session=True)`, process
  groups, `killpg` and fixed five-second waits;
- it has no accepted native handle, original pidfd owner, job-cgroup identity
  or descendant-empty proof;
- it stores stdout/stderr digests rather than complete bytes, removes solver
  output before generic evidence exists and asserts zero live processes without
  a cgroup proof;
- it writes Warehouse STARTED, INCOMPLETE, COMPLETE and raw rows itself;
- `w3_analysis.py` and the thin tool form a second terminal/artifact writer and
  expose callable `run`, `close` and `check-existing` paths.

The ordinary `runtime/runner.py` and `runtime/subprocess_runner.py` are also not
this layer. They intentionally implement campaign timeouts, resource limits,
inline-output offload, threads and process-group cleanup. Their behavior is
valid for ordinary v3 Runtime Isolation, but incompatible with the stronger
optional W3 evidence boundary.

Therefore the implementation must be new generic code with a closed dependency
direction. The old Warehouse execution and terminal code is later decomposed
into pure science or deleted; it is never incrementally upgraded into the
accepted owner.

## 3. Slice boundary and package shape

The implementation uses one coherent namespace:

There is no `helpers.py`, generic filesystem grab-bag, alternate runner,

Deferred to later slices:

- external authority, sealed materialization, installation and nonce claim;
- PREPARED/STARTED/ACTIVE_JOB/JOB_EVIDENCE/ROW/RAW_COMPLETE/INCOMPLETE durable
  state and no-replace publication;

Test-only systemd fixtures are allowed in

## 5. Public model

All persisted or problem-visible facts are frozen, exact, non-subclassable
where practical, immutable and slot-backed. Strict decoders reject booleans for
integers, unknown/missing fields, duplicate keys, noncanonical text, invalid
UTF-8 in textual fields and non-lowercase SHA256 values. Raw process streams
remain bytes and are never text-decoded by this layer.

### 5.1 `GenericProcessSpec`

The lower backend accepts a process-only spec:

```text
GenericProcessSpec:
  opaque_job_key: nonempty canonical ASCII string
  executable: exact absolute bytes
  argv: nonempty tuple[bytes, ...], argv[0] == executable
  environment: canonical sorted tuple[bytes, ...]
  cwd: exact absolute bytes
  spec_sha256: canonical digest of every field above
```

It has no seed, arm, cell, Oracle, Protocol, solution, stopping rule or output
interpretation. The accepted native ABI remains the final validator of its
exact exec inputs.

The future high-level `GenericJobSpec` adds the guardian-owned fresh-output
identity and invocation/job ordinal. The future public
`start_job(InvocationToken, GenericJobSpec) -> BlockedJob` API composes this
lower spec; this slice must not invent a forgeable substitute invocation token.

### 5.2 Immutable observations

`ProcessIdentity` contains PID, `/proc/<pid>/stat` starttime, pidfd-backed
identity facts observable through the poll duplicate and creator process
identity copied while the child is blocked. Settlement still uses only the
original pidfd retained inside the native handle; the duplicate never becomes
a second wait/reap authority.

`WaitFact` contains exactly the accepted native wait tuple fields:

```text
pid, uid, si_code, si_status, wait_status, return_code, signal, core_dumped
```

`CapturedStream` contains exact complete bytes, byte length and SHA256.

`CgroupIdentity` contains copied service/supervisor/job names, device/inode
identities and the exact service-relative lineage. It contains no open FD and
no absolute path that can be used as authority.

`CgroupEventsFact` retains the exact raw `cgroup.events` bytes plus the strict
decoded `populated` and `frozen` fields. Unknown future keys are retained and
permitted; missing, duplicate or malformed required keys are rejected.

`JobCgroupKey` contains a uint64 ordinal and the full 64-lowercase-hex
invocation nonce. Its only valid rendered name is:

```text
job-<ordinal>-<first-16-nonce-hex>
```

`ordinal` is canonical unsigned decimal (`0` or a nonzero digit followed by
digits), with no sign or leading zero. The exact grammar is
`job-(0|[1-9][0-9]{0,19})-[0-9a-f]{16}` plus the decoded uint64 bound, so the
maximum name is 41 ASCII bytes, below `NAME_MAX`. Its canonical digest binds
the full nonce, ordinal and rendered name; the short name is never treated as
the complete invocation identity.

`ClosedSpawnObservation` contains only:

- opaque job key and canonical process-spec digest;
- copied executable/argv/environment/cwd digests;
- start/end wall and monotonic nanoseconds;
- process identity and exact wait fact;
- complete stdout/stderr bytes, lengths and digests;
- clean exec-error EOF;
- initial and final cgroup events and copied lineage/empty proof;
- whether leader exit was zero, nonzero or signalled as a mechanical fact.

It contains no FD, callback, mutable path, native handle, cleanup method,
Warehouse type, Protocol result or publication capability. A nonzero/signalled
executed solver may still form this mechanical observation; only the later
problem validator decides whether it is a valid typed scientific-failure row.

An exact 12-byte exec-error record is a generic spawn failure, not a solver
result. Partial, trailing, malformed, multiple or identity-incoherent
exec-error bytes are an integrity uncertainty.

### 5.3 Live capabilities

`BlockedSpawn` is unforgeable, noncopyable, non-pickleable and creator-process
bound. It owns the native `BlockedChild`, the three moved capture readers, the
poll-only duplicated pidfd and one live job-cgroup authority after an exact
move from its backend. It exposes copied identity only; release is performed
through the same backend, not a public native handle. Passing it to settlement
atomically changes the same wrapper to `CONSUMED`, so every Python alias becomes
unusable.

`SettledJob` is also a live, unforgeable capability. It contains one immutable
`ClosedSpawnObservation` and internally owns the still-present, proved-empty
job cgroup after a second exact move. The cgroup is deliberately not removed
during collection. A later guardian must first durably publish the appropriate
JOB_EVIDENCE/ROW cleanup fact, then consume `SettledJobCleanup` exactly once
through the same backend. Consumption changes every alias to `CONSUMED`,
removes the still-pinned exact inode and returns the backend to `IDLE`.
`SettledJobCleanup` is an internal name for this authority, not a separate
public helper object.

The final `ClosedJobObservation` is built later from copied
`ClosedSpawnObservation` plus the guardian-owned exact output bytes. It never
contains `SettledJob` or its cleanup authority.

`BackendOpenFailure` is the immutable result of consuming `ServiceCgroup` but
failing to establish the backend before any job/cgroup/native call. It contains
the copied service lineage and no live authority. Its phase is exactly
`SERVICE_CONSUME`, `CAPTURE_DIRECTORY_ACQUIRE` or `BACKEND_ALLOCATION`; its reason is exactly
`INVALID_SERVICE_AUTHORITY`, `CAPTURE_DIRECTORY_INVALID`,
`CAPTURE_DIRECTORY_OPEN_FAILED`, `BACKEND_ALLOCATION_FAILED` or
`ISSUER_INTERRUPTED`. The previously verified service lineage is always
required. `capture_directory_acquired` is explicit, and its copied identity is
required iff true. Errno is required only for
`CAPTURE_DIRECTORY_OPEN_FAILED` and absent otherwise; no job/process/stream
field is legal. An exact-type/programming misuse before authority consumption
raises without changing a valid wrapper; once consumption begins, every
failure follows this typed closed result. It may return only after every alias
observes `CONSUMED` and every acquired FD closes successfully. Allocation that
prevents construction of the failure fact, or any close ambiguity, fail-stops.

`PreHandleFailure` is returned only when no native handle reached Python. Its
phase is exactly one of `SPEC_VALIDATION`, `CAPTURE_PREPARE`, `JOB_CREATE`,
`PRE_NATIVE_READY` or `NATIVE_NO_HANDLE`; its reason is exactly one of `SPEC_INVALID`,
`CAPTURE_TMPFILE_UNSUPPORTED`, `CAPTURE_ALLOCATION_FAILED`,
`CAPTURE_OPEN_FAILED`, `JOB_CREATE_FAILED`, `NATIVE_NO_HANDLE` or
`ISSUER_INTERRUPTED_PRE_HANDLE`. It contains:

- `native_called` and `native_handle_acquired=false`;
- `child_creation` equal to `NOT_CALLED` when native was not called, or
  `NATIVE_INTERNAL_SETTLED` when native raised under its accepted no-leak
  contract; it never falsely claims that clone was physically impossible;
- `job_cgroup_created`;
- no process/wait fact;
- a copied job-cgroup identity and initial/final empty events iff a fully pinned
  job cgroup was created;
- stdout/stderr/exec-error availability fixed to `NOT_STARTED` and all related
  byte/length/digest fields absent.

Validation and initial `O_TMPFILE` failures happen before cgroup creation and
before the native call. If the accepted native call raises without returning a
handle, `native_called=true`; the accepted ABI has already settled any internal
blocked child, and the backend independently requires the pinned job cgroup
empty. A partial cgroup creation without a pinned identity, or uncertainty
about native settlement, fail-stops instead of returning this type. An issuer
interruption before native-handle acquisition uses
`ISSUER_INTERRUPTED_PRE_HANDLE`, records the exact phase, fills or omits the
job-cgroup facts according to whether a fully pinned cgroup existed, closes all
authority and poisons the backend. It is never forced into a process/wait fact
that does not exist.

`ContainedSpawnFailure` is returned only when a native handle reached Python
and the backend then proves exact leader wait/reap, complete authority closure
and job cgroup empty. It is never row-eligible and permanently ends the
invocation's job sequence. Its reason is exactly one of
`ACTIVE_NOT_DURABLE`, `RELEASE_UNCERTAIN`, `EXEC_FAILED`,
`DESCENDANT_SURVIVED`, `CAPTURE_FAILED` or `ISSUER_INTERRUPTED`; its phase is
the exact lifecycle state at first failure.

For both failure types each stream has an availability enum. `COMPLETE`
requires exact bytes/length/SHA256; `UNAVAILABLE` requires all three fields
absent; `NOT_STARTED` is legal only for `PreHandleFailure`. A
`ContainedSpawnFailure` always contains process/wait, cgroup initial/final
events, `populated=0` and the retained failed-job cgroup identity. Before either
failure returns, all backend/native/pidfd/capture/job/service/capture-directory
FDs are closed and the backend is permanently `POISONED_CLOSED`. Only copied
facts remain. No normal cleanup permit exists for a failed job cgroup: the
future guardian first publishes durable INCOMPLETE, and `ExecStopPost` later
reopens through its independent service-root lineage and verifies the copied
identity.

## 6. APIs and state machine

The lower interface is exact:

```text
ServiceCgroup.open_current(expected_unit_lineage) -> ServiceCgroup
ServiceCgroup.close_unconsumed() -> None

SpawnBackend.open(ServiceCgroup, pinned_capture_directory)
  -> SpawnBackend | BackendOpenFailure
SpawnBackend.start_blocked(JobCgroupKey, GenericProcessSpec)
  -> BlockedSpawn | PreHandleFailure | ContainedSpawnFailure
SpawnBackend.settle_blocked(BlockedSpawn, reason) -> ContainedSpawnFailure
SpawnBackend.release_and_collect(BlockedSpawn)
  -> SettledJob | ContainedSpawnFailure
SpawnBackend.remove_after_durable_cleanup(SettledJob, cleanup_permit) -> None
SpawnBackend.close_idle() -> None
```

`cleanup_permit` is an internal exact-type, noncopyable, one-shot capability
bound to backend generation, job-cgroup key and observation digest. It is not
exported from `execution.__init__` and cannot be a boolean/string. This slice
contains no production issuer. A package-private acceptance-test issuer has an
AST-enforced callsite allowlist containing tests only; it exercises positive
removal and alias invalidation without pretending that a durable commit
occurred. The future guardian contract adds the sole production issuer after
verifying its real durable-commit receipt, without changing backend ownership
or cleanup semantics. Until that callsite migration is separately accepted,
production composition remains impossible.

`SpawnBackend.open` consumes `ServiceCgroup` for every outcome by atomically
changing the original wrapper to `CONSUMED`; retaining a Python alias does not
retain usable authority. It also takes sole ownership of its duplicate of the
live nofollow `pinned_capture_directory` dirfd supplied by the future invocation
composition and never accepts or stores a mutable capture path. Open failure
closes all acquired FDs and leaves no backend. An unused `ServiceCgroup` has the
one explicit `close_unconsumed` path; destruction while still open fail-stops.

Only `SpawnBackend` may create a job cgroup. `JobCgroup` is package-private and
is never returned to its caller. `start_blocked` validates every input and
opens both unnamed spool files before creating the job cgroup, then creates the
one exact name from `JobCgroupKey` and calls native spawn. It moves the three
capture readers once and duplicates the pidfd for polling. Any failure after
native returns follows explicit settlement; it never leaks a partially
assembled `BlockedSpawn`.

Backend typestate is enforced on the same exact object. `IDLE` permits one
`start_blocked`. `BLOCKED_OWNED` and `SETTLED_PENDING_CLEANUP` reject another
start. Positive cleanup returns to `IDLE`; `close_idle` explicitly closes the
service/capture authorities and enters `CLOSED`. Every failure enters
`POISONED_CLOSED`, closes all live authorities and permanently rejects
create/start/cleanup. There is no route from failure to another job.

The only live state graph is:

```text
UNIT_BOUND_IDLE
  -> CGROUP_PINNED_EMPTY
  -> BLOCKED
  -> RELEASED_DRAINING
  -> LEADER_TERMINAL
  -> LEADER_REAPED_DRAINING
  -> [SETTLING_DESCENDANTS]
  -> CLOSED_CGROUP_RETAINED
  -> CLEANED
  -> UNIT_BOUND_IDLE

BLOCKED
  -> SETTLING_BLOCKED
  -> POISONED_CLOSED

any deterministic failure after possible release
  -> FAILED_SETTLING
  -> POISONED_CLOSED

any ownership/identity/reap/kill/drain/close uncertainty
  -> UNCERTAIN_FAILSTOP
```

State transitions are exact one-shot operations. There is no destructor-owned
normal path. In particular, a RELEASED or POISONED native handle must never be
abandoned to its fail-stop destructor. Wrapper destruction in BLOCKED state is
tested, but production explicitly signals/reaps/drains and closes its cgroup.
Destroying an unconsumed `ServiceCgroup`, open backend, `BlockedSpawn` or
`SettledJob` is itself fail-stop; a clean destructor is permitted only after
the wrapper has reached `CONSUMED`, `CLOSED` or `POISONED_CLOSED`. In a forked
noncreator process, methods reject and only that process's duplicate FDs close;
formal production code never forks.

Only `CLOSED_CGROUP_RETAINED` can expose a positive immutable observation. It
requires all of the following simultaneously:

1. the original native pidfd produced one coherent terminal fact and performed
   the exact reap;
2. the poll-only pidfd was never used for settlement;
3. stdout, stderr and exec-error all reached EOF and every byte was retained;
4. exec-error was clean EOF;
5. the exact pinned job cgroup reports `populated=0`;
6. the service child-cgroup inventory and supervisor member set equal their
   allowed job-boundary forms;
7. all capture and pidfd duplicate FDs are closed exactly once;
8. the still-present job cgroup inode equals the created identity.

Leader reap, pipe EOF and cgroup empty are three independent facts. None may
stand in for another.

## 7. cgroup-v2 contract

### 7.1 Opening the delegation

`ServiceCgroup.open_current` reads the current unified cgroup lineage, requires
the current process to be in a leaf named `supervisor`, opens it nofollow, opens
its parent service root by dirfd and pins both identities. It verifies:

- unified cgroup v2 and required control files;
- systemd >=255 contract supplied by the caller;
- service root `cgroup.procs` is empty;
- current guardian PID/starttime is the sole permitted supervisor task at the
  idle/job boundary;
- the configured unit property is literally `Delegate=pids` and its configured
  property receipt names no additional controller;
- `pids` is effective for the subtree; additional controllers merely listed as
  available in `cgroup.controllers` are recorded but never enabled or used;
- service-root and supervisor inode/device identities match the supplied
  invocation lineage;
- no unexpected sibling/nested cgroup exists.

The implementation must not freeze a literal `/system.slice/...` path because
static templates may be placed in a generated slice. The actual
`ControlGroup`, `/proc/self/cgroup` result and pinned inode form the identity.

### 7.2 Job creation and ownership

Job names are derived inside the backend from the exact `JobCgroupKey` grammar
in section 5. Callers cannot pass a rendered path, path separator, precreated
cgroup or `JobCgroup`. Creation is relative to the pinned service-root dirfd
with exclusive mkdir semantics, followed by nofollow open, identity check and
exact initial `cgroup.events` proof of `populated=0/frozen=0`. Existing names,
partial creation without a pinned identity or any unexpected sibling enter an
integrity hold; they are not adopted or removed.

The accepted native `spawn_blocked` receives only the pinned job dirfd. Python
never writes a PID to `cgroup.procs`; atomic `CLONE_INTO_CGROUP` remains the
sole formal placement operation.

After the child is born blocked, the backend copies PID/starttime and verifies
the member identity while the original pidfd prevents reuse ambiguity. Before
release, sentinel/output fixtures must still be absent.

### 7.3 Empty proof and descendant handling

`cgroup.events` is read and polled through its owned FD. Drain uses event-driven
waiting with no deadline and no high-frequency sleep. A leader terminal event
does not stop stream draining.

If the leader is terminal/reaped while job `populated=1`, a descendant escaped
leader lifetime. The backend:

1. records a containment failure;
2. writes `cgroup.kill` through the pinned job dirfd;
3. waits without timeout for `populated=0` while continuing to drain all
   inherited stream writers to EOF;
4. validates the service/supervisor/job inventory;
5. returns only `ContainedSpawnFailure`, never a row-eligible observation.

A double-fork or `setsid` descendant that closes stdio is still detected by
`cgroup.events`. A descendant keeping a stream open cannot deadlock the parent
pipe before the cgroup kill because all streams and pidfd readiness are drained
in one selector loop.

Unexpected nested/sibling cgroups, a task in the supervisor other than the
guardian, inode replacement, malformed events, failed kill, failed empty proof
or ambiguous remove identity enters `UNCERTAIN_FAILSTOP`. The backend does not
walk an absolute path to clean a replacement inode. The systemd service then
owns outer `KillMode=control-group` containment.

Normal empty job removal happens only after the future durable cleanup permit.
Failure settlement leaves the empty job cgroup named and returns its copied
identity so later `ExecStopPost` can include it in an INCOMPLETE drain receipt.

## 8. Complete capture and settlement

The backend is single-threaded. It rejects a process with more than one
`/proc/self/task` entry before native spawn. It uses nonblocking
`poll`/`selectors` over stdout, stderr, exec-error, the duplicated poll pidfd and
`cgroup.events`.

stdout and stderr are drained into separate supervisor-owned `O_TMPFILE`
regular files opened beneath a caller-supplied, pinned generic capture directory
authority. There is no named-temp fallback. The child never receives these
spool FDs. Each write handles partial writes and `EINTR`; any other write,
allocation, seek, readback or fsync failure makes the invocation incomplete.

The exact open is relative path `.` with
`O_RDWR|O_TMPFILE|O_CLOEXEC`, mode `0600`, followed by mode/regular-file,
device/inode and CLOEXEC verification. The spool is never linked, so there is no
`linkat` path. `EOPNOTSUPP`, `EINVAL` or legacy `EISDIR` from this exact open is
`CAPTURE_TMPFILE_UNSUPPORTED`; `ENOSPC`, `EDQUOT` or `ENOMEM` is
`CAPTURE_ALLOCATION_FAILED`; another stable open errno is
`CAPTURE_OPEN_FAILED`. All occur before job-cgroup creation and require a test
counter proving native `spawn_blocked` was called zero times. Directory
identity drift or ambiguous close is uncertainty and fail-stops rather than
being classified as an ordinary pre-handle failure.

On storage/allocation failure the backend still settles containment: it kills
the job cgroup, drains remaining pipe bytes into a failing/discard sink only to
reach EOF, waits/reaps the leader and proves empty. It cannot return accepted
stream bytes or a positive observation. If settlement itself becomes
uncertain, it fail-stops.

At closure, the backend fsyncs, rewinds and copies every byte from each unnamed
spool, computes length/SHA256, verifies EOF and closes the spool. Binary NUL and
invalid UTF-8 are ordinary bytes. No decode, line splitting, suffix selection,
compression threshold, offload prefix or maximum size is allowed.

The fixed exec-error channel must be either clean EOF or exactly one accepted
12-byte record. A valid record plus exit 127 is a contained spawn failure.
Clean EOF with any wait status is mechanically closed. Any other byte shape,
record/wait mismatch or channel uncertainty fail-stops.

## 9. Deterministic failure semantics

- Spec/capture failure occurs before cgroup creation and native call and returns
  `PreHandleFailure` with both creation flags false. An exclusive job-name
  conflict or partial cgroup authority is integrity uncertainty, not adoption.
  A native exception without a returned handle is accepted only when the
  accepted ABI contract plus an independent final empty-cgroup proof settle the
  attempt; it returns the phase-correct `PreHandleFailure`.
- ACTIVE_JOB publication failure while BLOCKED invokes explicit pre-release
  settlement: the child is killed/reaped without exec, streams are drained and
  the cgroup is proved empty. It is never released.
- Release `EPIPE`, close failure or native POISONED state is treated as
  possibly released. The backend uses pidfd/cgroup kill and full settlement; it
  never relies on the POISONED destructor.
- An accepted exec-error record is generic `EXEC_FAILED`, ends the invocation
  INCOMPLETE and cannot become a normal solver row.
- Executed solver exit nonzero or signal can be a positive mechanical
  observation only after complete reap/empty/drain; Warehouse alone decides its
  scientific meaning.
- Any surviving descendant is killed/drained and produces
  `DESCENDANT_SURVIVED`, never a row-eligible observation.
- Issuer signal/`KeyboardInterrupt`/`BaseException` after ownership acquisition
  but before a native handle uses the phase-correct closed backend/pre-handle
  failure above. After a native handle reaches Python it is remembered,
  containment is settled, and only then is `ContainedSpawnFailure` reason
  `ISSUER_INTERRUPTED` returned/raised to the guardian. Neither path can open
  the next job.
- A wedged or uninterruptible descendant remains unaccepted indefinitely.
  There is no hidden deadline, forced success or operator override success
  path.
- Identity, original-pidfd wait/reap, kill, empty, close or cleanup uncertainty
  does not return ordinary Python control flow. The main process fail-stops so
  systemd assumes outer containment.

No deterministic failure in one invocation permits a second job. The future
guardian transitions the invocation to INCOMPLETE; it does not retry, resume or
replace the failed job. Before a failure fact crosses the boundary, the backend
is already `POISONED_CLOSED`; no retained alias can create, start, clean or
remove anything.

## 10. systemd-255 contract

### 10.1 Production boundary in this slice

`systemd255.py` owns strict typed facts and validation only. It does not invoke
`systemctl start`, `systemd-run`, `nohup`, shell, the ordinary launcher or a
solver. The later root installer owns exactly one formal `StartUnit`. The later
terminal layer owns authoritative D-Bus/property acquisition and durable
UNIT_DRAINED/UNIT_FINAL publication.

This slice defines and tests:

- `ConfiguredUnitProperties` for exact expanded property validation;
- `InvocationLineage` for boot ID, unit, `INVOCATION_ID`, actual ControlGroup,
  service/supervisor inode and main PID/starttime;
- `StopPostEnvironment` for literal `SERVICE_RESULT`, `EXIT_CODE`,
  `EXIT_STATUS` and same-invocation identity;
- `StopPostTopology` for sealer-only `.control` and empty supervisor/job facts;
- `UnitHandoffProperties` for strict nonempty source invocation identity and
  final result/status fields.

These types are copied facts, not proof by themselves. Only the later sealed
reader/guardian can issue authoritative receipts from them.

### 10.2 Required formal property correction

Both future static templates must explicitly set:

```text
CollectMode=inactive
```

This is added to the parent template contract and property receipt. It is not a
default-value assumption. `CollectMode=inactive-or-failed`,
`systemd-run --collect` and any pre-observation `reset-failed` are forbidden.

The run template retains:

```text
Restart=no
KillMode=control-group
TimeoutStopSec=infinity
Delegate=pids
DelegateSubgroup=supervisor
OnSuccess=scion-w3-close@%i.service
OnFailure=scion-w3-close@%i.service
CollectMode=inactive
```

The closer retains:

```text
After=scion-w3@%i.service
Restart=no
TimeoutStartSec=infinity
CollectMode=inactive
```

`OnSuccess`/`OnFailure` queues the closer before run-unit collection, and
`After` pins the source unit while the closer reads its exact final properties.
The closer does not depend on `MONITOR_*`, because one closer named as both
success and failure trigger can have ambiguous propagation candidates. It
queries the exact source unit selected by the root-owned launch ID and requires
a nonempty matching `InvocationID`.

A successfully inactive unit may be collected quickly even with
`CollectMode=inactive`; therefore an external observer must never poll until
inactive and then start the closer. A failed unit with `CollectMode=inactive`
retains result facts until explicit cleanup. GC followed by static-template
reload can show `loaded/inactive/success` with empty `InvocationID`; this is
unknown, not success.

### 10.3 Topology facts

On systemd 255 with `DelegateSubgroup=supervisor`:

- the main process is in `<service>/supervisor`;
- service-root `cgroup.procs` is empty;
- `ExecStopPost` runs in `<service>/.control`;
- the configured unit/template and configured property receipt are exactly
  `Delegate=pids`; additional available controllers reported by cgroupfs are
  retained as host facts but are not additional configured delegation and are
  never enabled or used by this layer;
- `.control` may be observed only while the control process is running.

`ExecStopPost` receives the same invocation's `INVOCATION_ID`,
`SERVICE_RESULT`, `EXIT_CODE` and `EXIT_STATUS`. Its future sealer requires
`.control` to contain only its exact PID/starttime, supervisor empty, and the
allowed job inventory. Journal bytes are corroboration only; typed unit state
and no-replace receipts remain authoritative.

## 12. Static rejection rules

Any one of the following is P0 and rejects the implementation:

- formal `fork`, `vfork`, `posix_spawn`, `subprocess`, `Popen`, PID kill,
  `killpg`, `waitpid`, process session or second spawn fallback;
- two owners for original pidfd, release, reap, capture readers or job cgroup;
- a live capability passed without exact consume/alias invalidation, or a
  backend that can start while blocked/pending-cleanup/failed;
- automatic release or an API that cannot keep the child BLOCKED;
- leader reap treated as output EOF or cgroup empty;
- descendant survival returning a row-eligible observation;
- stdout/stderr/exec-error cap, truncation, tail replacement, decode replacement
  or drain timeout;
- retry, resume, replacement job, outer runtime timeout or hidden stop deadline;
- ordinary return after lifecycle identity/reap/kill/empty/close uncertainty;
- removal of the empty job cgroup before a durable cleanup permit;
- FD, mutable path, callback or cleanup authority in an immutable observation;
- generic imports or literals for Warehouse/CVRP/Oracle/arm/cell/Protocol;
- accepted composition importing the rejected Warehouse lifecycle or ordinary
  `LocalSubprocessRunner`/launcher;
- Warehouse code able to signal/wait/remove cgroup or write generic terminal
  state;
- `Restart` other than `no`, `KillMode` other than `control-group`, finite
  stop timeout, configured delegation other than exact `pids`, missing
  supervisor topology or failed result loss;
- formal template/receipt missing literal `CollectMode=inactive` or any
  pre-observation `reset-failed`.

P1 rejection includes swallowed poll/close/storage errors, path-based cgroup
authority after pinning, missing systemd success/failure GC fixtures, ambiguous
cleanup-capability ownership, missing full binary receipts, or a fixture that
quietly uses product timeout/retry semantics.
