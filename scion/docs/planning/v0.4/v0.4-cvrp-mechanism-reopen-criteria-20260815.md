# v0.4 CVRP Mechanism Reopen Criteria

*Date: 2026-08-15*
*Status: active research-planning guidance; non-production and non-gating*

## Purpose

Scion is a continuous research process. It must remember prior algorithm
evidence without turning that memory into an opaque blacklist or an automatic
novelty judge.

This guidance defines how a human review classifies a mechanism, direct
variant, implementation repair and outcome-known confirmation before a future
experiment is preregistered. It complements the historical
[candidate disposition and research ledger design](v0.4-candidate-disposition-and-research-ledger-design-20260716.md),
which separates evidence continuity from code inheritance.

It does not add a Contract, Verification, Protocol, Decision, prompt, hash or
provider gate. A ledger row cannot automatically reject an H, select a
candidate, allocate a budget or authorize a run.

## Three-axis state

Do not compress validity, effect and disposition into one mutually exclusive
label.

### Validity

- `VALID_ISOLATED`: the intended mechanism was implemented, active and
  compared against the correct immediate base.
- `VALID_CUMULATIVE`: the evaluated source was valid, but the effect belongs to
  a cumulative branch rather than the latest edit.
- `IMPLEMENTATION_INVALID`: the intended mechanism was not faithfully
  implemented or could not execute as specified.
- `ACTIVATION_OR_OPPORTUNITY_INVALID`: the code ran, but the intended event had
  no eligible opportunity or never activated.
- `INFRA_INVALID`: infrastructure prevented the declared evidence stage from
  completing.
- `PROCESS_EVIDENCE_ONLY`: the record concerns research transport, expression
  or failure semantics rather than an algorithm effect.

A mechanism may have more than one validity state across historical variants.

### Effect flags

- `NOT_ESTIMABLE`: validity or activation did not permit an algorithm effect
  estimate.
- `GENUINELY_UNTESTED`: no prior proposal, attempt or valid evidence exists for
  the exact causal core or a direct extension. A history containing only an
  invalid attempt remains `IMPLEMENTATION_INVALID / NOT_ESTIMABLE /
  CONDITIONAL_REOPEN`; it is not made novel by invalidity.
- `NEGATIVE_AT_DECLARED_SCALE`: valid evidence failed the declared quality
  rule or showed harm at that population/budget/MDE.
- `MIXED`: material benefits and harms or protected-case reversals coexist.
- `POWER_LIMITED`: the valid estimate is too small or uncertain for the
  declared MDE/threshold.
- `POSITIVE_UNRETAINED`: a declared stage passed but the full promotion funnel
  did not complete.
- `RETAINED_POSITIVE`: the exact candidate completed the required promotion
  and independent retained comparison.
- `VARIANT_HETEROGENEOUS`: a family rollup contains distinct nodes or scopes
  and has no single aggregate effect.
- `NOT_APPLICABLE`: the row is process evidence rather than an algorithm
  effect claim.

Effect flags are not mutually exclusive. A weak positive can be both
`POWER_LIMITED` and `NEGATIVE_AT_DECLARED_SCALE` with respect to a fixed gate;
protected-case heterogeneity should be recorded separately rather than hidden
inside one scalar label. A future node-level record should therefore preserve
at least direction, declared-gate result, MDE/power relation and protected-case
heterogeneity.

### Disposition

- `OPEN`: a genuinely distinct causal question remains and can be
  preregistered without selecting it from the same outcome evidence.
- `CONDITIONAL_REOPEN`: the question is old or outcome-known but a specific
  repair, isolation or confirmation could still produce useful evidence.
- `EXHAUSTED_FOR_SCOPE`: the tested causal core and its listed direct variants
  should not consume another run on the stated scope.
- `SEE_MEMBER_SCOPE`: a family rollup has no aggregate disposition; consult
  each exact child node.

Recommended display form:

```text
<DISPOSITION> / <EFFECT_FLAGS>@<SCOPE> / <VALIDITY> / <SELECTION_AND_INDEPENDENCE>
```

## Mechanism identity

Record a causal core separately from its implementation variants.

```text
core = (
  search_role,
  state_transformed,
  route_scope,
  membership_effect,
  primitive_move,
  move_arity,
  transition_or_reconnection_class,
  causal_mediator,
  acceptance_role,
  resource_displacement,
  invariants
)

variant = (
  enumeration,
  candidate_filter,
  cap,
  ordering,
  trigger,
  deadline_polling,
  delta_evaluator,
  telemetry,
  target_locus
)
```

Changing only a variant field does not establish a new frontier. In
particular, changing seeds, cases, budget, thresholds, cache placement,
polling, filters, order, call-site wiring, local variable placement, O(1)
evaluation, telemetry or source formatting is a direct extension unless it
changes reachable transitions, the stated causal mediator, resource
displacement, invariants or the predeclared interaction. Field names do not
determine identity by themselves; a candidate filter that changes the
reachable neighborhood may define a distinct core.

Combining two known mechanisms is not automatically new. It is a distinct
interaction question only when the preregistration names both component
baselines and includes contrasts capable of estimating the interaction rather
than merely evaluating a cumulative source.

A family rollup is an inventory aid, not a causal identity. It must not carry
one aggregate effect or exhaustion verdict; each exact child needs its own
source, baseline, population, seed, budget, MDE and protected-case scope before
these criteria can be applied mechanically.

## Evidence-fusion rules

1. Preserve every valid terminal observation, including negatives.
2. Never merge changed implementations, partial stages or different source
   ancestry into one W/L/T or effect estimate.
3. Treat case as the scientific unit when seed rows are repeated measurements;
   retain pair evidence descriptively.
4. Within comparable exact source, estimand, population, budget and evidence
   unit, give complete long/frozen evidence priority over short screens while
   retaining the short screen as a stage-specific fact. Across incomparable
   scopes the evidence is a partial order; one record does not overwrite the
   other.
5. Do not convert an implementation-invalid observation into algorithm-
   negative evidence.
6. Do not convert a valid active negative into an implementation problem
   merely because a later hypothesis suggests a plausible repair.
7. A cumulative branch can support candidate-versus-B0 quality, but not the
   latest edit's incremental causal attribution without an immediate-base
   contrast.
8. Outcome-known follow-up is exploratory confirmation. Record candidate
   selection, evaluation-population blindness and stage replication as three
   separate facts; an unseen holdout can make a stage outcome-blind without
   making the outcome-selected candidate discovery independent.
9. Never pool a partial interrupted validation with a later fresh run.
10. A provider-free semantic or activation diagnostic updates validity only;
    it does not supply algorithm-quality evidence.

## Legitimate continuation types

### Clean replacement after invalidity

An `IMPLEMENTATION_INVALID` or `INFRA_INVALID` run may receive one fresh clean
replacement when the defect is concrete, causally predicts the observed
failure, is fixed without using algorithm outcomes to choose a different
mechanism, and the replacement uses a new root. The invalid run remains in the
record and contributes no effect estimate.

Examples include a same-file serialization repair, ENOSPC replacement or a
static activation-recognizer correction. Repeated repairs after valid quality
evidence become outcome-adaptive research.

### Predeclared exact-stage continuation

Screening, expansion, validation and frozen holdout may reuse the same exact
source when this progression and its thresholds were frozen before results.
This can create Decision evidence, but it is not independent replication and
does not make the mechanism novel.

### Outcome-adaptive repair or confirmation

After activation, W/L/T, protected-case or runtime outcomes are known, a repair
or exact-source confirmation may still be useful. It must record:

```text
candidate_selection_outcome_known = true
candidate_discovery_independent = false
evaluation_population_outcome_blind = true | false
execution_replication_independent = true | false
selection_basis = <exact prior evidence>
```

It may not be described as a fresh discovery. The next population, cases,
seeds, budgets, thresholds, baseline and failure policy must be frozen before
the new outcome is observed.

These separate fields replace one ambiguous independence boolean. A fresh
root, unseen population, isolated host and independent execution can provide
an independent replication of fixed-source-versus-baseline performance even
when the source was selected after seeing its original result. That does not
make candidate discovery independent or identify the latest edit's causal
effect in a cumulative source.

## Conditional-reopen checklist

All applicable items must be answered in a preregistration; this document does
not answer them automatically.

- exact canonical mechanism ID and alias/direct-extension search completed;
- exact source and immediate base bound by ordinary source equality;
- validity defect or remaining causal uncertainty stated;
- why the question is not only a cap/threshold/seed/budget/filter/order/wiring
  variant;
- historical outcome knowledge and selection basis disclosed;
- isolated versus cumulative ancestry disclosed;
- mechanism opportunity, activation and completion denominators defined;
- fresh population, cases, seeds, order, budgets and MDE frozen;
- protected feasibility, fleet and case obligations frozen;
- host isolation, cache and order policy frozen;
- screening, expansion, validation, frozen and Decision route frozen;
- retry/resume/repair/substitution policy frozen;
- failure classification distinguishes candidate, comparator and local infra;
- claim boundary records `candidate_selection_outcome_known`,
  `candidate_discovery_independent`, `evaluation_population_outcome_blind` and
  `execution_replication_independent` separately;
- positive screening stops at the preregistered next stage and never promotes
  automatically.

## Stop rule for a reopened mechanism

One causally sufficient implementation repair is allowed per frozen reopen
question. If the repaired mechanism is valid, active and negative at the
declared scale, park that causal core for the scope. Do not create an unlimited
repair loop by changing another variant after each result.

If evidence is power-limited, the project must choose prospectively between a
larger predeclared study and stopping. Adding cases, seeds or time after reading
the result is adaptive expansion, not independent confirmation.

## Current application

The companion
[longitudinal audit](../../experiments/v0.4/v0.4-cvrp-longitudinal-mechanism-reopen-audit-20260815.md)
finds no current genuinely untested frontier. Its strongest conditional reopen
is the exact cumulative R3 source evaluated after the route-removal round,
which is positive-unretained but has unknown component attribution; the final
route-removal edit was neutral against its immediate base. Any confirmation
must bind the whole cumulative source, restart on a fresh root with zero use of
the old partial validation and disclose the positive selection result.

The [machine-readable ledger](../../experiments/v0.4/v0.4-cvrp-longitudinal-mechanism-ledger-20260815.json)
is a descriptive convenience. Human review remains responsible for applying
these criteria and obtaining a separate authorization before any provider or
solver action.
