## Generic authority and nonce API

`runtime.execution.launch_authority` owns:

```text
AcceptedLaunchAuthority.from_bytes(raw)
InstallationRecord.from_bytes(raw, authority)
NonceClaimOwner.claim(ledger_parent, invocation_control, authority, installation)
inspect_nonce_claim(...)
```

The authority is canonical duplicate-free JSON and deliberately excludes its
own digest and every launch-ID-derived path. It binds problem kind, pushed
commit/tree, exact manifest identity, root basename, nonce, fixed ledger
parent, row/artifact contract, sealed-store/environment aggregates, static
template/source hashes, scientific/correction design hashes, the native
acceptance-contract hash, the external native acceptance-record hash and one
sorted provenance table. Provenance is an exact closed union of `git_blob`,
`external_evidence` and `generated`.

The installation record is separately canonical and binds the already
computed authority digest, launch ID, accepted run root, sealed-store and
environment roots, projection root, template hashes, exact run/closer unit
names and the configured-property-pair digest. Its fields cannot flow backward
into the authority. The canonical terminal root is mechanically
`<run-root>/control/invocation`; the unit reaches it through the fixed
`<projection-root>/run/control/invocation` bind alias. External installation
acceptance must prove all six fixed projection entries and their source
identities.

`NonceClaimOwner` publishes the same canonical claim first as
`<nonce>.claim.json` in the external fixed ledger and then as
`invocation_claimed.v1.json` in the invocation control directory. Both use
`O_CREAT|O_EXCL`, complete write, file fsync and directory fsync. External
publication consumes the nonce even if root publication later fails. There is
no delete, retry, resume, reuse or repair API.

The generic terminal gains a claimed-open path. A formal `TerminalPolicy`
binds the expected claim digest; `InvocationWriter.open_claimed` requires that
exact durable root claim. Existing claim-free `open_fresh` remains only for
isolated generic use and rejects a claim-bound policy. Every later terminal
inventory retains the claim fact.

## Systemd acquisition and wiring API

`runtime.execution.systemd_acquisition` owns:

```text
SystemdPropertyReader                       # exact manager transport protocol
Systemd255Acquirer.acquire_configured_pair(...)
Systemd255Acquirer.acquire_self_lineage(...)
Systemd255Acquirer.acquire_stop_post_topology(...)
Systemd255Acquirer.acquire_unit_final(...)
parse_unit_template(raw)
```

The acquirer, not Warehouse code, chooses the fixed property sets and
normalizes them into the existing exact `ConfiguredUnitProperties`,
`InvocationLineage`, `StopPostEnvironment`, `StopPostTopology` and
`UnitHandoffProperties` values. Linux facts come from descriptor-pinned
`/proc` and cgroup-v2 paths. Manager properties are copied through one
allowlisted reader protocol; the reader has no start/stop method.

Before nonce claim, configured-pair acquisition also compares the manager's
loaded `ExecStart`, `ExecStopPost`, closer command, `User`, `Group`, `UMask`,
protection flags and exact read-only/read-write projection paths with the two
authority-bound templates. Template bytes alone are not proof that the manager
loaded those bytes.

Final `ExecStopPost` acquisition retains its structured
`a(sasbttttuii)` command status. Exactly one command must match the
installation-bound executable/argv and yield the normalized terminal
code/status used by `UnitHandoffProperties`.

The duplicate-rejecting unit parser preserves exact directive spelling.
Warehouse wiring validation requires the fixed `%i` projection-only
`ExecStart`, `ExecStopPost` and closer commands, reciprocal
`OnSuccess`/`OnFailure`/`After`, `Restart=no`, `KillMode=control-group`,
infinite stop/start limits, delegated `pids/supervisor`, and the frozen
read-only/read-write projection paths. A hash match without semantic wiring is
insufficient.

## Warehouse composition

`problems.warehouse_delivery.w3_composition` is the sole problem-aware
composition. It:

- independently re-verifies the accepted dry manifest and zero formal jobs;
- requires Warehouse problem kind, exact manifest/source/root identity,
  172 rows and the three frozen artifact names;
- cross-binds authority, installation, configured-property digest and both
  semantic unit templates;
- proves the external nonce claim, invocation directory and dynamic terminal
  names are absent;
- returns one immutable `WarehouseW3LaunchReadyFact` without mutation;
- can create a claimed `InvocationWriter` only through one explicit
  `prepare_invocation` call.

The composition delegates live process/cgroup ownership to `SpawnBackend`,
observation/row/terminal publication to the accepted generic terminal and
scientific validation/replay/artifact construction to the accepted Warehouse
problem layer. It does not introduce a second spawn, cgroup, row or artifact
owner.

`SpawnBackend.remove_after_opaque_commit` accepts only the exact durable,
writer-issued `OpaqueRowCommit` for its active `SettledJob`;
`remove_after_incomplete_commit` accepts only the corresponding writer-issued
observation and durable `INCOMPLETE`. Directly constructed lookalike facts have
no cgroup-cleanup authority.

The sealed thin tool has exactly three installed selectors:

- `run` reopens the accepted chain, reacquires loaded manager wiring and
  invocation lineage, consumes the nonce, executes the frozen 172-job sequence
  only through `SpawnBackend`, and seals `RAW_COMPLETE`;
- `seal-unit-drained` runs only in the same invocation's `.control` subgroup
  and may publish `UNIT_DRAINED` only for the exact successful service result
  and empty delegated topology;
- `close` requires the structured `a(sasbttttuii)` `ExecStopPost` result and
  final unit facts, replays all 172 rows through Warehouse validation/analysis,
  then asks the generic terminal to publish `UNIT_FINAL / COMPLETE / CLOSED`.

None of these selectors can ask systemd to start, stop or restart a unit.

## Acceptance

The focused suite must cover:

- canonical/duplicate/schema/provenance/path/acyclic authority rejection;
- installation cross-binding and copied-root rejection;
- external-first nonce consumption, root-claim failure, duplicate claim and
  claim-bound terminal opening;
- fixed systemd property sets, proc/cgroup inode and PID/starttime binding,
  structured `ExecStopPost`, final same-invocation and topology failures;
- unit template hash plus semantic wiring, duplicate directive and alternate
  executable/path rejection;
- real accepted zero-job dry-root read-only readiness with identical pre/post
  content identity;
- composition rejection for wrong manifest/root/source/row/artifact/property
  identity and every present claim/dynamic path;
- durable row commit before `SpawnBackend` cgroup cleanup;
- Python 3.12/3.13 focused and execution-core gates plus unchanged exact H11
  oracle/C2a/official gates.

Passing this slice accepts dormant composition code only. A later external
root-owned installation acceptance must freeze exact authority/installation
bytes, projection/mount identities and manager property receipts on one fresh
zero-job root before a human may authorize one `StartUnit`. This plan itself
authorizes no formal execution.
