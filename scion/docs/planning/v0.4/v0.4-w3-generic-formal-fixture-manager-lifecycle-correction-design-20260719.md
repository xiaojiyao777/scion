## 2. Non-negotiable boundary

This correction adds no budget, deadline, timeout, watchdog, polling loop,
sleep, retry, cap, truncation, automatic restart, rollback, replacement start,
or automatic accepted-evidence cleanup. Event waits remain indefinite. An
unprovided H11 permit leaves the root unaccepted indefinitely.

The generic core remains problem-neutral. No Warehouse/VRP/ALNS/VNS meaning is
added to these fixtures. All changes remain tests-only acceptance
infrastructure except the already accepted production generic execution
owner.

## 3. One exact static-asset authority

### 3.1 Inventory read and lookup

The PREFLIGHT `inventory_manifest` full reference is the sole static inventory
authority. The harness must open it once with nofollow, bind
path/SHA-256/device/inode/mode/owner, read through that descriptor, and parse
those exact bytes. It must not validate a reference and later reopen a mutable
path for parsing.

One exact lookup consumes the parsed inventory and a requested semantic kind.
It opens the selected asset once with nofollow and returns a retained static
asset containing its descriptor, exact raw bytes and full reference. Hashing,
identity validation, schema decoding and every later static semantic check
must consume that same descriptor/raw byte object; no decoder may validate and
then reopen the path. The descriptor remains open until the asset's last use,
and at least through its post-StartUnit ARMED cross-binding when the unit will
execute or name that asset.

The lookup accepts exactly one item only when all of these agree with the
retained file:

```text
role
kind
path
sha256
device
inode
mode=0444
root ownership when privileged
```

This lookup is used for:

- the StartUnit descriptor (`start-descriptor`);
- the executing harness program (`harness-program`), also equal to `__file__`;
- the installer program frozen in the install receipt (`installer-program`);
- every observer/adversary/formal role plan and program;
- the B5 descendant plan and descendant program reached transitively from the
  formal plan;
- every other sealed static input named by a scenario.

Same-byte inode replacement, a same-hash alternate path, kind substitution,
duplicate matches and identity drift all fail before manager, journal, FIFO or
StartUnit activity.

Immediately before StartUnit, each retained executable/plan/descriptor asset
is revalidated against its frozen path identity without reopening for content.
The executing harness program additionally proves that `__file__` names the
same retained harness-program inode. Static plan and descriptor decoders accept
raw bytes, not paths. B5 keeps its transitive plan/program descriptors through
the live descendant/ARMED authority handoff. A path replacement after lookup
therefore fails rather than changing the consumed bytes or executable claim.

### 3.2 Static prevalidation must not consume runtime ARMED

ARMED is a unit-produced runtime receipt. Formal-case, observer and adversary
can create it only after StartUnit. Prevalidate therefore must not decode,
hash, stat as present or otherwise consume an acquisition ARMED path.

Before StartUnit, role validation freezes only:

- exact inventory-bound plan and program identities;
- plan schema/mode/unit and its declared program/plan relationship;
- the predeclared ARMED destination, which must be absent;
- ready/release FIFO path/device/inode and role ownership;
- request/output/selector destinations and their required absence or sealed
  static authority.

It returns one immutable static-role authority object. After StartUnit, the
harness waits for ready readability, consumes the newly created ARMED receipt
and cross-binds every dynamic field to that frozen object. Only this post-start
stage may read ARMED. A preexisting ARMED file, an ARMED created before
StartUnit, or a ready event without one exact ARMED receipt fails closed.

Pure helpers must follow the same chronology; they may not precreate ARMED to
make prevalidate pass.

### 3.3 Root execution manifest is not a self-hashed asset

The per-root harness execution manifest is intentionally not an item inside
the inventory it references: that would introduce a manifest/inventory hash
cycle. It is a distinct root-operator input created no-replace after install
under the exact root authority layout:

```text
<formal-root>/authority/harness/<scenario-id>/MANIFEST.json
```

It must be root:root `0444`. `decode_manifest` opens it once with nofollow,
freezes path/SHA-256/device/inode/mode/uid/gid and parses only those bytes. The
decoded manifest retains this source binding. Prevalidate rechecks the path
identity immediately before external observation, and H0 plus the terminal
harness receipt record the same binding. The fixture UID cannot create,
replace or rename it. The trusted root operator remains the authority that
selects a scenario root; the harness does not falsely claim that this dynamic,
post-install input was sealed by PREFLIGHT.

## 4. H11 explicit operator permit

H11 must not pass through the ordinary automatic acquisition release path.
Its run-main release is a two-owner transaction.

### 4.1 Predeclared authority

The harness execution manifest contains one H11-only permit declaration:

```text
schema = scion.generic_backend.h11_operator_permit_authority.v1
permit_path
permit_parent path/device/inode/mode/uid/gid
permit_ready_path
permit_ledger_path
expected scenario = H11
expected run unit
```

The permit and PERMIT_READY paths are absent before StartUnit, globally
non-aliased and under their exact output/root-only authorities. A permit
creation watch and parent descriptor are retained before StartUnit. Non-H11
policies reject this object.

After run acquisition, the harness first freezes absence of every accepted
terminal/formal/final-freeze output into one canonical, fsynced, no-replace
`scion.generic_backend.h11_permit_ready.v1` receipt. It binds the execution
manifest, run ARMED receipt, boot/unit/invocation, the complete absent-path
inventory and the declared permit authority. This PERMIT_READY receipt is the
only fact that authorizes the external operator transaction to begin.

### 4.2 External authorization transaction

The existing root installer gains one explicit command,
`authorize-h11-release`. The harness never calls it. The operator invokes it
only after inspecting the live root. Its root-owned authorization manifest
binds:

- formal-root and harness execution-manifest identity;
- H11 scenario and run unit;
- the exact run ARMED receipt path/SHA/device/inode;
- the exact PERMIT_READY path/SHA/device/inode and its absent-path inventory;
- boot ID, invocation ID and ARMED receipt SHA;
- the exact permit destination;
- equality between the permit authority in PERMIT_READY and the requested
  destination.

The authorization manifest itself is root:root `0444`, no-replace and under
the exact root authority layout. The installer opens it once with nofollow,
freezes path/SHA-256/device/inode/mode/uid/gid, parses only those bytes and
records that source binding in the permit. It validates all fields and
revalidates every PERMIT_READY absent-path claim before mutation, then writes
one canonical root:root `0444` permit no-replace and fsyncs the file and
parent. The permit carries PERMIT_READY's complete
path/SHA-256/device/inode/mode binding, not only its digest. The harness ledger
cross-binds both the authorization-manifest source and complete PERMIT_READY
reference. There is no retry, replacement or cleanup command for a permit. A
permit authorization manifest that lacks or predates PERMIT_READY is invalid.

### 4.3 Harness consumption

After the run-main acquisition is frozen, H11 records that all accepted
terminal outputs are absent, publishes PERMIT_READY and waits only on the
preinstalled creation watch. It reads and pins the permit, cross-binds it to
PERMIT_READY, the live ARMED receipt, boot/unit/invocation and execution
manifest, and durably writes the H11 permit ledger. Only then may it write the
ordinary release bytes to the run-main release FIFO.

The ledger orders:

```text
run acquisition
< pre-permit accepted-output absence
< PERMIT_READY publication/fsync
< operator permit publication
< permit validation/ledger fsync
< run-main release
< terminal evidence
```

Without the external permit, none of the terminal, formal-final, H12 or final
freeze receipts can be accepted.

## 5. Closed manager job transactions

ScenarioPolicy gains an exact job policy. H0 has no job. Every executable row
expects the run StartUnit job result `done`. Rows with a closer expect one
closer job; its result is `failed` only for H9's fixed failed closer and `done`
otherwise. H10 has the run job and no closer. H7 additionally retains its one
explicit StopUnit job with result `done`.

### 5.1 StartUnit job

For every non-H0 root, the harness proves exactly one common tuple across:

```text
StartUnit method arguments and reply path
JobNew numeric ID / path / run unit
JobRemoved numeric ID / path / run unit / ScenarioPolicy result
```

The required event ordering is:

```text
StartUnit begin < JobNew < StartUnit reply < JobRemoved
```

The job path is unique and cannot alias a closer or StopUnit job. H10 must not
discard its StartUnit job; the validated transaction precedes its UnitRemoved
and negative LoadUnit evidence.

### 5.2 Manager-triggered closer job

OnSuccess/OnFailure creates exactly one closer JobNew and one closer
JobRemoved. Numeric ID, path and closer unit agree; result equals policy. Its
ordering is:

```text
run JobRemoved < closer JobNew < closer JobRemoved
```

The closer terminal receipt must name the same unit and its live invocation.
Missing, extra, duplicated, wrong-unit, wrong-result, mismatched-ID/path or
reordered signals fail closed.

The unified manager-event receipt carries the validated run/closer/optional
StopUnit job transactions. UnitNew/UnitRemoved rules from the first correction
remain unchanged.

## 6. H8 lifecycle-owned negative cleanup

H8's drift leaf is a source constant in ScenarioPolicy, not free text supplied
by `scenario_input`. The harness creates exactly that one leaf using the
retained service dirfd, opens and retains its directory descriptor, freezes
the recursive negative inventory and publishes
`rejected-unexpected-topology/H8_EXTRA_TOPOLOGY`.

The harness must not call `rmdir`, unlink, rename or any generic cleanup on the
leaf. Its ledger states:

```text
fixture_cleanup_performed = false
systemd_cleanup_pending = true
```

Only after the negative evidence is durable does the harness release the held
actor. systemd owns process termination, cgroup trimming and UnitRemoved. H12
uses the retained service/leaf descriptors to prove:

- the pinned drift inode did not change;
- the drift name is absent from the retained service directory after
  UnitRemoved;
- the service cgroup path and every actor are absent;
- no harness cleanup method contributed to the result.

If systemd does not remove the topology, H8 remains unaccepted. A pure test may
simulate the manager lifecycle by removing the leaf outside harness code, but
must prove that the harness itself issued no removal.

## 7. Journal interval closure

Journal remains corroboration, not typed authority. Nevertheless a nonempty
frozen `end_cursor` must be encountered exactly and must be the last captured
entry. EOF or iterator termination before it is an error. An empty interval is
accepted only when both the frozen end cursor and captured entries are empty.
The reader performs one forward pass through the frozen interval; no polling,
retry or second search pass is added.

## 8. Final freeze adjudication

The current O_TMPFILE publication rule remains:

1. all evidence files, hashes and directories are fsynced;
2. the unnamed FROZEN inode is fully written, mode-frozen and fsynced;
3. `linkat(AT_EMPTY_PATH)` publishes `FROZEN` no-replace as the final namespace
   mutation;
4. only descriptors are closed afterwards.

There is deliberately no post-link directory fsync. A crash may
conservatively lose the final link and therefore make the root unaccepted, but
cannot expose `FROZEN` pointing to partial or unpersisted evidence. Requiring
the marker itself to survive every crash would be a different design and may
not be added as an ad hoc post-link mutation.
