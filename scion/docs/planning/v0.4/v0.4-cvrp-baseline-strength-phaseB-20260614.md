# v0.4 CVRP Baseline-Strength Phase B

*Date: 2026-06-14*
*Status: pre-registered; launch after launcher support and git commit*

## Purpose

Phase B tests whether CVRP research becomes more effective when Scion starts
from a lower-noise, larger-headroom research surface. It is a matched agentic
campaign contrast between:

- `alns_vns`: the copied ALNS+VNS control snapshot from Phase A.
- `alns_only`: the copied ALNS-only snapshot from Phase A, with only
  `USE_VNS=False`.

This is not a raw solver-quality contest. ALNS-only is materially weaker than
ALNS+VNS in Phase A paired characterization, so any ALNS-only promotion is
evidence about research-surface measurability, not proof that Scion beat the
canonical ALNS+VNS CVRP champion.

## v3 Boundary

The v3 control boundary remains unchanged:

- LLM output is tainted proposal material.
- Formal decisions must flow through Contract, Verification, Protocol,
  safe feature extraction, and deterministic Decision.
- MDE, BKS gap, baseline strength, VNS activity, prompt trajectory, and raw
  A/A diagnostics are research-analysis facts only. They must not enter
  `DecisionFeatures`.
- The ALNS-only arm remains a copied problem-owned snapshot. The canonical CVRP
  baseline in the repository is not mutated.

- Repeats: `rep01`, `rep02`, `rep03`.
- Arms per repeat: `alns_vns`, `alns_only`.
- Rounds per cell: `8`.

- Proposal path: `--agentic-proposal`.
- Early stop: `--disable-early-stop`.
- Measurement governance: `--measurement-governance on`.
- Prompt context: `--proposal-context-ablation compact-measurement-diagnostics`.
- APS timeout: `--agentic-session-timeout-sec 900`.
- Data root: `SCION_PROBLEM_DATA_ROOT=/home/clawd/research/or-autoresearch-agent/vrp`.

Protocol inputs intentionally use the Phase A 8-case/8-seed calibration config
instead of the current canonical 4-seed formal config. This makes postrun MDE
interpretation directly comparable to Phase A. The tradeoff is cost: each
screening candidate is heavier than the ordinary formal campaign. The accepted
Phase A caveat also carries forward: `CMT4` used the current resolver behavior
captured by the Phase A config rather than being silently mixed with a later
45s CMT4 rule. Do not overclaim exact CMT4 runtime fidelity from this Phase B.

## Acceptance

A cell is usable only if:

- `run_status.json` and `campaign/run_status.json` exist.
- Wrapper exit is `0`.
- `run_validity.valid=true`.
- Requested rounds are complete, or any incompletion is explicitly classified as
  infrastructure and excluded from formal comparison.
- The launched command and `launch.env` match the pre-registered controls.

Formal outcomes:

- Count screening, validation, frozen, and promotion only through the campaign
  database, protocol rows, and `DecisionFeatures`.
- A promotion requires a formal frozen `PROMOTE` decision.
- Compare each arm against its own Phase A MDE and headroom.

Research-analysis outcomes:

- Branch depth by distinct formal hypotheses, not artifact retries.
- Same-mechanism follow-up and mechanism-family transfer.
- Proposal/code failure taxonomy and source-identity health.
- Runtime/fresh-replay noise.
- Cost per effective protocol row and per accepted research insight.
- Proposal trajectory manifests and compares using matched `control_pair_key`.
  These are report-only and observational; they are not deterministic LLM replay.

## Interpretation Rules

- If ALNS-only produces more validation/frozen/promotion, interpret it first as
  a measurement/headroom effect.
- If ALNS+VNS remains below MDE while ALNS-only becomes measurable, v0.4 should
  treat baseline strength as an experimental variable in Scion value studies.
- If both arms remain below MDE, the next repair is protocol/measurement design,
  not lifecycle tuning.
- If ALNS-only creates useful branch depth but weak final solver quality, it is
  still a useful research-surface ablation, not a production solver improvement.
