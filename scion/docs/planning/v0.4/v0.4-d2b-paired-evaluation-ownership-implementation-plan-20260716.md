# Scion v0.4 D2b Paired Evaluation Ownership Implementation Plan

*Status: frozen implementation contract; production-disabled until D2-D4 complete*
*Date: 2026-07-16*

Three independent boundary audits accepted this plan after five adversarial
rounds with no open P0/P1. Any implementation change to owner identity,
transaction order, lease/guard lifecycle, capability sealing, or result
classification requires a new design review before code proceeds.

This plan translates the frozen D2 contract in
`v0.4-candidate-disposition-and-research-ledger-design-20260716.md` into a
cohesive implementation boundary. The frozen design remains authoritative.
This document narrows module ownership, transaction order, value codecs, and
acceptance tests; it does not change the scientific policy.

## Outcome and slice boundary

D2b ends with one of these exact durable states:

```text
committed snapshot + pending slot
committed snapshot + dispatched slot + dispatch claim
committed snapshot + execution_uncertain slot + control record
committed snapshot + blocked_infra slot + infrastructure record
committed snapshot + receipted slot + immutable receipt
```

D2b does not create a Decision, disposition, next evaluation slot, v2 Decision
completion, continuation base, SourceLedger, promotion, formal replay, formal
experiment event, experiment count, StepRecord, or legacy formal artifact. A
formal receipt freezes future count eligibility, but D2b itself always leaves
the formal count at zero.

Production composition remains unchanged. No Campaign, Scheduler,
EvaluationOrchestrator, Finalizer, CLI, or launcher imports the D2b owner until
D2c-D4 are complete and the release-integrity preflight is accepted.

## Non-negotiable invariants

1. D2b consumes an already completed D2a `CampaignOpenResult`. It verifies the
   exact `campaign_identity + candidate_snapshot_v1` pair and never calls a
   lazy mode-claim API.
2. Snapshot and initial slot have one positive owner. They are prepared in one
   SQLite transaction and become production-positive only when a final paired
   owner phase advances from `prepared` to `active` after descriptor-pinned
   artifact publication and the internal snapshot/slot state updates.
3. Callers cannot supply `candidate_id`, `evaluation_id`, source/slot digests,
   receipt digests, formal-observation flags, or derived Branch transitions.
4. Dispatch claim and Branch Scheduler CAS commit before any canary or Protocol
   call. Only the transaction winner receives a sealed
   `EvaluationDispatchAuthority`; no boolean or evaluation ID alone grants
   execution authority.
5. Reopen never redispatches an unreceipted dispatch. It records
   `execution_uncertain`; only an evaluation-ID-aware backend may later install
   the exact terminal receipt.
6. `blocked_infra -> pending` requires an explicit append-only operator
   resolution. It creates no automatic retry, cap, budget, or replacement.
7. Receipt formal eligibility is derived from a closed, claim-bound terminal
   fact union. Presence of a `ProtocolResult`, a caller-selected canary category,
   or free-text failure markers is not sufficient.
8. Mutable Branch state, timestamps, diagnostics, report projections, public
   summaries, and physical workspace paths never enter `evaluation_id`.
9. Snapshot, comparison, raw metrics, and candidate-parent artifacts remain
   digest-pinned and physically resolvable whenever their owner is validated.
10. Opposite-mode rows are negative conflict evidence only. They never select,
    restore, consume, or complete ownership.

## Module ownership

D2b adds no generic `helpers.py`. It uses responsibility-focused modules and
one explicit global Branch-store prerequisite.

### `durable_owner_codec.py`

Extract only the reusable pure Branch/H projections and strict SQLite row
decoders currently embedded in
`decision_completion_transaction.py`:

- `branch_to_payload`, `branch_from_payload`, and `branch_payload_from_row`;
- the frozen v1 H payload/row codec, byte-identical to current v1 behavior;
- a distinct stable source-H identity projection described below.

Decision v1, research-rejection completion, active audit, and the legacy
candidate reader move to this owner without changing payload bytes or golden
fixtures. SQL mutation does not belong in the codec. D2b must not import private
codecs from a Decision module.

### Global durable Branch/H owner prerequisite

Before dispatch authority exists, `BranchStore`, `HypothesisStore`, and every
non-test Branch or H writer must use one global owner protocol:

- migrate existing databases by adding non-null monotonic `owner_revision`
  columns with default zero to both `branches` and `hypotheses`; these are
  storage metadata excluded from frozen v1 Branch/H payloads, stable source-H
  identity, and goldens;
- `load_revisioned_branch()` and `load_revisioned_hypothesis()` return typed
  `RevisionedBranchRecord`/`RevisionedHypothesisRecord` values containing the
  decoded public value plus its expected revision. Insert-once creation returns
  revision zero. Connection-scoped CAS accepts only that typed token, updates
  exactly one row, increments the revision, and returns the refreshed token;
- replace `INSERT OR REPLACE` with insert-once plus
  `UPDATE ... WHERE owner_revision = expected_revision` CAS for both owners;
- make connection-scoped Branch/H mutation live with the transaction owner that
  also changes its completion/slot/lease state;
- ordinary writers use one SQL CAS predicate requiring both the expected
  revision and absence of an active Branch/H evaluation lease. Evaluation
  participants use the complementary predicate requiring the exact lease and
  current evaluation ID. A Python pre-check is never an authorization boundary;
- migrate `HypothesisStore.save()/mark_status()` and every direct Branch/H SQL
  writer in failure, Decision v1, rejection, promotion, and finalization paths;
- update Decision v1 and research-rejection completion to the same CAS primitive
  without changing their payload bytes. Prepared v1 intent/recovery rows bind
  expected Branch/H revisions in auxiliary durable columns outside canonical
  intent JSON, so reopen repeats the same CAS rather than silently rereading a
  newer owner;
- hold the champion lock through weight/champion mutation and authoritative
  Branch stale handling, reload the durable Branch/H before mutation, and never
  overwrite an active evaluation owner. The lease's pre-first-dispatch guard
  prevents the pinned comparison revision from changing through pair activation
  and the first pending claim; champion drift after dispatch is deferred to
  D2e's frozen stale/reconcile overlay;
- refresh the controller's in-memory Branch and H projections from the committed
  authoritative rows after every transactional mutation.

The migration includes claim races against generic persistence, failure paths,
Decision/rejection completion, H status writers, promotion, and champion/weight
stale writers. A stale in-memory Branch or H must lose CAS rather than overwrite
an evaluation lease or dispatch claim.

### `candidate_evaluation.py`

Own only frozen enums, dataclasses, and pure invariant functions:

- `EvaluationStageKind = initial | expansion`;
- `CandidateEvaluationStatus = prepared | pending | dispatched |
  execution_uncertain | blocked_infra | receipted | decision_invalid |
  promotion_pending | consumed`; the last three are reserved and unreachable
  through the D2b public facade;
- comparison champion, code-parent, scientific request, source anchor, slot,
  dispatch claim, sealed dispatch authority, closed terminal-fact union,
  backend attestation, control/infrastructure record, formal observation, and
  receipt values;
- stage/ordinal/count and legal Branch transition tables.

It imports no Decision coordinator, disposition mapper, promotion, D3 planner,
SourceLedger, formal artifact writer, report writer, or production composition.

### `candidate_evaluation_codec.py`

Own the sole canonical payload, JSON, ID, and digest derivation for slot, claim,
the public authority payload, terminal facts, control record, complete typed
canary/Protocol evidence, formal observation, and receipt. The secret dispatch
seal is deliberately outside every codec and decoder.
Every decoder requires exact keys, exact primitive types, typed enums,
lowercase full SHA-256 values, canonical relative refs, finite numeric values,
and canonical JSON:

```python
json.dumps(
    payload,
    sort_keys=True,
    separators=(",", ":"),
    ensure_ascii=False,
    allow_nan=False,
)
```

The complete Protocol wire DTO must retain every fact required to reproduce
SafeFeature extraction without rerunning Protocol, including EvalStats,
metric stats, pair/case feedback, objective comparisons, runtime facts,
candidate/champion failures, surface facts, opportunity diagnostics, and
mechanism evidence. `exposed_summary` is retained only if required for exact
typed reconstruction; it is explicitly non-authoritative and never selects
formal eligibility or Decision input. Top-level and nested framework-owned DTOs
have exact fields. `objective_comparison` is either null or the exact
`ObjectiveComparison/MetricComparison` DTO; it never accepts arbitrary `Any`.
Problem-owned evidence maps use one recursive primitive policy: string keys,
JSON null/bool/string, finite numbers, arrays, and mappings only. Unknown
framework fields, nonfinite numbers, arbitrary objects, and lossy fallback
serialization fail closed. Decode reconstructs the typed Protocol value, and a
golden test requires SafeFeature input/output equality before and after receipt
round trip.

### `candidate_evaluation_store.py`

Own the single positive writable D2b facade:

```text
record_for_evaluation(candidate_request, initial_slot_request)
recover_pending_pairs()
validate_inventory()
claim_dispatch(evaluation_id) -> EvaluationDispatchAuthority | no-authority
record_execution_result(authority, ClosedExecutionResult)
resolve_blocked_infra(evaluation_id, typed_operator_resolution)
mark_dispatched_uncertain_on_reopen()
reconcile_uncertain(EvaluationBackendAttestation)
load_pair / load_slot / load_claim / load_receipt
```

`record_execution_result()` is the only live-authority result writer. Its
closed union has four disjoint variants and privately dispatches to exactly one
receipt, blocked-infrastructure, or uncertain transaction. There is no public
`record_blocked_infra()`, `record_uncertain()`, or overlapping terminal writer.
Operator resolution and reopen recovery are separate because neither possesses
a live dispatch capability.

The store composes D1 closure building, descriptor-pinned artifact publication,
and pinned ancestor verification. It does not duplicate snapshot replay or
materialization logic. A raw-metrics resolver returns exact internal ref bytes;
the store computes and verifies their digest. A comparison-manifest resolver
does the same for the immutable comparison champion. Store-only
connection-scoped participants expose reserved `decision_invalid`,
`promotion_pending`, `consumed`, and optional next-slot mutations to later
D2c/D2e/D4 transactions without opening them on the D2b facade or starting a
nested transaction.

## D1 API refactor

The current D1 `record()` cannot remain a production-facing positive owner
because it commits a snapshot without a slot. Refactor D1 into internal phases:

```text
build desired closure/artifact/registry record
prepare registry row on caller-owned connection
publish and verify artifact without choosing DB completion
mark registry row committed on caller-owned connection
```

Standalone recording and snapshot-only recovery are renamed as explicit
internal foundation-test capabilities and are not exported by the production
package. More importantly, they inspect durable campaign ownership before any
row or artifact write: when a D2a `campaign_identity` and snapshot mode exist,
they fail closed with zero snapshot row, temporary byte, or final artifact.
D2b owns the only positive write, `record_for_evaluation()`.

Connection-scoped D1 registry primitives accept a caller-owned SQLite
connection and never begin, commit, or roll back it. Internal foundation wrappers
may use the primitives only in D1 tests without a D2a-open production campaign.
Pairing logic is not added to the snapshot codec or materializer.

## Initial slot request and derived source ownership

`InitialEvaluationSlotRequest` is expected-intent only. It contains the typed
Protocol stage, `initial`, and ordinal zero. It cannot author any stable owner
or scientific request field. The store derives or exact-checks every value from
one source matrix:

| Field | Sole authority |
|---|---|
| campaign ID/mode | D2a durable open result and SQLite singleton pair |
| direct origin | durable completed code-phase attempt bound to the exact campaign/Branch/H |
| reconcile origin | durable typed reconcile transition bound to the exact campaign/Branch/H/Patch/parent |
| prospective/previous mechanism owner | durable continuation-plan completion when the selected base is provisional |
| verified mechanism owner | trusted derivation from exact Patch Contract plus authoritative parent-to-candidate touched-file Verification |
| snapshot/code parent/source code | D1 closure, exact-matched against the durable origin and Verification owners above |
| H structural fields and proposal digest | exact durable H row |
| source state and expansion counts | exact durable Branch row |
| comparison version/hash/revision/ref/manifest | current champion under lock plus pinned manifest resolver |
| problem/spec/Protocol/split/seed identities | immutable store construction context |
| priority cases and comparison runtime policy | trusted Protocol request planner over durable owners |
| stage/kind/ordinal | durable Branch state plus expected-only initial request |

Any duplicate field in `CandidateSnapshotRequest`, the expected request, D1
closure, durable Branch/H, champion, configuration, or planned Protocol request
must agree exactly. A mismatch creates no pair or artifact. Callers cannot
replace a derived fact with an internally consistent alternative.

The first transaction performs this origin and mechanism-owner validation
before preparing any row or byte. For `direct_code_attempt`, it accepts only a
durable completed code-attempt owner with exact campaign, Branch, H, Patch, and
Verification identities. For `reconcile_transition`, it accepts only the exact
typed transition owner with the same anchors. H IDs, process-local session refs,
formal candidate IDs, and caller assertions are not origins. The store itself
derives `VerifiedCandidateOwner`; it does not decode a caller-authored owner
string. When the durable continuation plan selected `PROVISIONAL_CURRENT`, the
previous, prospective, and verified owners must be the same known owner before
snapshot preparation. Clean/champion bases may retain typed `UNCLASSIFIED`.
The direct and reconcile source H must be exactly `status=active`; any other H
status is a conflict, not a codec interpretation or implicit transition.

Production `record_for_evaluation()` therefore consumes a store-validated
candidate handoff backed by these durable readers. Test fixtures may construct
the input data but cannot bypass the readers. Until the D3 origin/continuation
owners needed by the production path exist, the D2b facade remains
production-inaccessible; D2b never weakens this dependency by trusting a raw
`CandidateSnapshotRequest`.

It has no candidate ID, snapshot ref/digest, evaluation ID, source digest,
comparison anchor, action/surface, count, configuration identity, priority
case, runtime policy, absolute workspace, mutable Branch object, Patch object,
report payload, or caller-computed hash.

After D1 builds the closure, the store derives `SourceCodeAnchor` from:

```text
campaign / Branch / lineage
snapshot candidate ID, ref, artifact hash
candidate code, executable, and execution-manifest hashes
H ID, stable source-H digest, and proposal digest
typed code-parent ID/hash/ref/manifest
screening and validation expansion counts
```

The stable source-H projection binds only:

```text
hypothesis ID, Branch ID, parent H ID
proposal digest
base champion version
change locus, action, target file, suggested weight, predicted direction
family ID/source and taxonomy version
```

`status`, `owner_revision`, `created_at`, diagnostics, runtime facts, and public
summaries are preconditions or projections, not source-H identity. Pair
creation separately requires the durable H to be exactly `active`.

`source_code_anchor_digest` is the SHA-256 of the domain-separated stable
source payload. It excludes Branch state, created/updated timestamps, direction,
weight copy, failure history, infra counts, evidence summaries, Scheduler
control, diagnostics, and public reports.

## Canonical scientific evaluation request

Do not hash the current path-bearing `EvaluationRequest`. A trusted Protocol
request planner derives a typed scientific request containing only inputs that
affect Protocol execution:

- Protocol stage, stage kind, ordinal, and both cumulative expansion counts;
- hypothesis action and selected structural surface;
- ordered unique priority case IDs;
- typed comparison-runtime policy, including whether fresh comparison runtime
  is scientifically required;
- problem/spec, Protocol, split, and seed identities.

It excludes candidate/champion workspace paths, live Branch state, timestamps,
status progress, in-flight markers, mutable maps, Patch objects, public
summaries, diagnostics, report refs, failure history, and counters. Its digest
is derived by the codec and bound into the slot. The exact known failure-code
sequence needed to reproduce current SafeFeatures comes from the receipt-bound
dispatch claim's immutable pre-Branch payload; it does not enter the scientific
request or `evaluation_id`. No sort/dedup/filter rewrite changes that sequence.

## Candidate evaluation slot identity

`candidate-evaluation-slot.v1` uses its schema as a domain separator. The exact
identity payload contains:

```text
campaign_id
snapshot_candidate_id
snapshot artifact ref and SHA-256
branch_id, lineage_id, hypothesis_id, stable source-H SHA-256
source_code_anchor_digest
code-parent kind, candidate ID, code hash, executable hash, ref, manifest hash
comparison champion version, code hash, weight revision, ref, manifest hash
problem_spec_sha256, protocol_version_sha256,
split_manifest_sha256, seed_ledger_sha256
Protocol stage, stage kind, stage ordinal
screening and validation expansion counts
hypothesis action and selected structural surface
canonical evaluation-request digest
```

`evaluation_id` is the full SHA-256 of that payload. The database stores both
exact canonical `slot_identity_json` and its digest; status, current references,
and timestamps are never encoded in it. `evaluation_id`, payload digest, and
decoded identity must agree. A readable Protocol label may be stored only as
nonidentity display data and cannot replace `protocol_version_sha256`.

Initial slots have ordinal zero. Expansion slots have a positive ordinal equal
to the prospective count for their stage; the other stage count remains
unchanged. Frozen expansion is invalid. D2b freezes and tests this codec but
creates only the one initial slot paired with a new snapshot. Creation of later
exact-reuse slots belongs to D2e completion.

## SQLite owner schema

All D2b connections enable WAL, `synchronous=FULL`, foreign keys, and explicit
transactions.

### `candidate_evaluation_slots`

Stores exact immutable slot identity JSON/digest, identity columns, status,
current dispatch claim, current control/infrastructure record, receipt digest,
and timestamps. `snapshot_candidate_id` is not unique because later exact reuse
creates distinct evaluation IDs. Initial ownership is expressed only by the
pair table below; there is no duplicate `is_snapshot_initial_slot` boolean.

The status CHECK freezes the complete v1 lifecycle, including reserved
`decision_invalid`, `promotion_pending`, and `consumed`. D2b triggers and public
methods expose no transition into those states. Restricted connection-scoped
participants let D2c/D2e/D4 join their later state transactions without schema
changes, copied SQL, or nested transactions.

### `candidate_snapshot_initial_pairs`

An identity-immutable paired owner binds exactly one snapshot candidate ID to
exactly one initial evaluation ID and owns `phase = prepared | active`. Only
`prepared -> active` may update. This distinguishes internal D1 foundation rows
from production paired rows without weakening the immutable D1 snapshot
identity. Production readers accept only `phase=active`; a committed snapshot
or pending slot is never positive by itself. Production inventory rejects any
snapshot-mode snapshot without this owner and never adopts or guesses a slot.

### `candidate_evaluation_leases`

The permanent pair identity is not the mutable execution lock. A separate
durable lease binds one Branch, one source H, and the exact current evaluation
ID. It owns `state=active|released`, a
`comparison_guard=pre_first_dispatch|historical` field, the pinned comparison
revision for the current evaluation, and exact Branch/H acquisition revisions.
The guard remains
`pre_first_dispatch` across both prepared and active/pending pair states and
changes to `historical` only in the first `pending -> dispatched` transaction.
Partial unique indexes permit at most one active lease per Branch and at most
one per source H.
The lease is inserted in the first pair transaction and is the common SQL
authorization owner used by Branch, H, comparison-preparation, slot, and claim
CAS predicates.

The active interval is explicit:

```text
pair prepared / slot prepared                                      active
slot pending / dispatched / execution_uncertain / blocked_infra    active
slot receipted / decision_invalid / promotion_pending               active
slot consumed with exact next pending slot                          transfer in same txn
slot consumed with terminal no-next completion                      released in same txn
```

`candidate_snapshot_initial_pairs.phase=active` remains permanent historical
ownership and never by itself locks Branch or H. D2e exact reuse consumes the
current slot and transfers the same lease to the newly inserted next pending
slot in one `champion lock -> BEGIN IMMEDIATE` transaction. That transaction
selects and verifies the next slot's current comparison, then atomically:

```text
old current evaluation + historical guard + exact consumed predecessor
  -> exact Branch target CAS
  -> H active -> advanced, or exact advanced -> advanced
  -> new pending evaluation and current comparison anchor
  -> lease current evaluation + refreshed Branch/H revisions
  -> lease pinned comparison revision + pre_first_dispatch guard
```

The rearmed guard prevents comparison mutation between transfer and the new
evaluation's ordinal-zero claim, which flips it back to `historical`. An
operator resume belongs to the same evaluation and never changes or rearms its
historical guard. No lease-free gap and no two-active-slot state is legal.
`promotion_pending` retains `advanced`; only D4 may commit
`advanced -> promoted`. Terminal no-next completion consumes and releases in
one transaction. D2b can reserve and validate these suffix semantics but cannot
call them.

### `evaluation_dispatch_claims`

Append-only claims contain claim ID/ordinal, predecessor claim, transition kind,
optional operator-resolution identity, exact pre/post Branch JSON and digests,
and exact canonical claim JSON/digest. `(evaluation_id, claim_ordinal)` is
unique. First claim ordinal is zero; explicit operator-resume successors have
increasing ordinals with no automatic retry and no attempt cap.

### `evaluation_control_records`

One append-only typed union stores `execution_uncertain`, `blocked_infra`, and
`operator_resolution` facts with exact predecessor, claim, Branch pre/target
payloads where applicable, evidence digest, and operator authorization. An
incident is never updated to appear resolved.

### `protocol_evaluation_receipts`

One immutable receipt per evaluation stores exact canonical receipt JSON,
receipt digest, current dispatch claim, formal-observation object, raw metrics
ref/digest, and timestamps. UPDATE and DELETE are forbidden.

Cross-table triggers protect positive state edges and exact current references:

- pair insertion requires the exact prepared snapshot and exact prepared
  initial ordinal-zero slot plus the exact active Branch/H lease;
- snapshot `prepared -> committed` requires the exact phase-prepared pair and
  linked prepared initial slot; a committed snapshot without that owner is
  rejected at the row edge, not merely held by startup inventory;
- slot `prepared -> pending` requires its linked snapshot already committed and
  the exact pair still prepared; a pending slot can never reference a
  noncommitted snapshot;
- pair activation requires exact committed snapshot plus pending linked slot;
- dispatched requires the current claim for the same evaluation;
- blocked-infra and operator resolution require the current typed control
  record;
- receipted requires the unique exact receipt for the current claim;
- identity columns and pair identities are immutable;
- D2b cannot execute a reserved suffix transition.

Ordinary Branch/H CAS statements include `NOT EXISTS` for an active matching
lease; evaluation participants require the exact lease/current evaluation. The
partial unique indexes and these SQL predicates, not a Python check, close
pair/writer and transfer races. Comparison mutation similarly rejects a pinned
`pre_first_dispatch` guard, whether the pair is prepared or active/pending. The
first dispatch changes the guard to `historical` in the same transaction as the
claim; only then may comparison advance, with D2e owning the stale overlay.

Startup inventory additionally detects old or directly corrupted combinations
that triggers cannot retroactively prevent. SQLite immediate triggers cannot
make a multi-row transaction physically simultaneous; the pair phase is the
sole production-positive commit point. Dormant dangling append-only rows created
by raw SQL are not positive owners and make inventory fail closed.

## Paired prepare, publication, and commit

One comparison champion lock is held continuously from before the first
transaction through artifact publication and the second commit. The first
transaction also acquires the durable Branch/H evaluation lease, so a process
crash releases the process lock but leaves a database guard that prevents the
pinned comparison revision, Branch, or source H from drifting before exact
recovery:

```text
BEGIN IMMEDIATE
verify exact D2a campaign identity and snapshot mode
verify durable direct/reconcile origin and derived mechanism ownership
verify durable Branch/H and current comparison anchors
insert snapshot prepared
insert slot prepared
insert exact active Branch/H evaluation lease pinned to comparison revision
insert initial-pair owner with phase prepared
COMMIT
```

Without releasing the champion lock, the store writes/fsyncs the D1 temporary
artifact, performs the descriptor-pinned rename and directory fsync, verifies
exact bytes and closure, and revalidates authoritative parent/candidate
manifests. The second transaction advances internal rows, then flips the sole
positive pair phase last:

```text
champion lock
BEGIN IMMEDIATE
revalidate mode, current comparison, stable Branch/H source anchors,
origin/mechanism owners, exact active lease, pair identities, and artifact owner
snapshot prepared -> committed
slot prepared -> pending
pair phase prepared -> active
COMMIT
release champion lock
```

Ordinary operation therefore has no champion/weight drift window between the
two transactions. After a crash, `recover_pending_pairs()` reacquires the
champion lock and accepts only the exact durable prepared lease and pinned
revision; comparison mutation is SQL-blocked while that guard exists. A
pre-existing mismatch or corrupt bypass is an integrity hold requiring a new
campaign or explicit repair outside D2b. The store never substitutes a new
comparison, silently cancels the pair, or activates a stale pair.

Same-origin/same-payload calls are idempotent. Any natural-key payload drift is
a typed permanent conflict. A crash at any filesystem or SQLite boundary
converges only from the exact pair-phase-prepared `prepared/prepared` owner and
exact artifact bytes.
Snapshot-only, slot-only, malformed status pairs, missing bytes, or identity
drift are held; recovery never manufactures a slot.

## Dispatch claim and Branch CAS

`claim_dispatch()` acquires `champion lock -> BEGIN IMMEDIATE`, verifies the
active pair, committed snapshot, pending slot, stable source H, pinned artifacts,
the claim-kind-specific comparison precondition, and exact active Branch/H
lease, reads both
revisioned durable owners, and derives the only legal Branch transition. H is
CAS-guarded but not semantically changed by dispatch. Its required status is
slot-specific: only the snapshot's paired screening-initial slot accepts
`active`; every D2e-created screening-expansion, validation-initial,
validation-expansion, or frozen-initial slot accepts only the exact transferred
`advanced` H payload/revision:

| Slot | Pre-Branch | Post-Branch |
|---|---|---|
| screening initial | `EXPLORE` | `EXPLORE` typed identity transition |
| screening expansion | `EXPLORE_EXPAND` | `EXPLORE` |
| validation initial | `READY_VALIDATE` | `VALIDATING` |
| validation expansion | `VALIDATING_EXPAND` | `VALIDATING` |
| frozen initial | `READY_FROZEN` | `FROZEN_TESTING` |

For claim ordinal zero, dispatch requires the still-current comparison and the
lease's `pre_first_dispatch` guard. The same transaction changes the guard to
`historical`; no active/pending gap exists. An explicit operator-resume claim
after blocked infrastructure instead requires the exact pinned historical
comparison, predecessor claim, and `historical` guard; it does not require the
global champion still to be current or reacquire a scientific owner.

The comparison weight revision is owned by the slot. Dispatch does not create a
second scientific owner by rewriting the Branch weight copy; any later champion
drift is frozen by D2e's overlay. The immutable claim owns exact pre/post Branch
payloads, the exact slot-specific H precondition, exact Branch/H revisions and
digests, and the active lease identity.
Claim insertion, Branch revision CAS, unchanged-H revision/lease authorization,
first-claim comparison-guard transition when applicable, and
`pending -> dispatched` commit in one transaction.

The durable claim stores a public deterministic
`EvaluationDispatchAuthorityPayload` containing:

```text
authority ID and deterministic backend invocation ID
evaluation ID and slot identity/digest
dispatch claim ID/digest/ordinal
snapshot, source, comparison, and request anchors
pinned logical candidate/comparison refs
exact canonical scientific request value and bytes
```

That payload is auditable, encodable, and reconstructible; it is not execution
authority. In the winning transaction the store generates a 256-bit CSPRNG seal
nonce, writes only a domain-separated SHA-256 seal digest bound to the current
claim/evaluation/invocation, and after commit returns a privately constructed
`EvaluationDispatchAuthority(payload, seal_nonce)`. The canonical codec never
serializes or decodes the nonce. Claim/slot/load APIs expose only the public
payload and seal digest. Result writers recompute the digest, exact-match the
current claim and lease, and reject a public-payload reconstruction, guessed
nonce, stale claim, or conflicting second submission; an exact duplicate result
returns the existing immutable owner idempotently. The remote executor receives
the capability only over the configured trusted in-process/secure transport and
does not log or persist the nonce.

The future executor accepts only this capability and constructs all physical
execution inputs from its canonical request and pinned refs. It cannot reread
live Branch/maps/workspaces to rebuild an `EvaluationRequest`. Concurrent
losers, repeated callers, reopen, and database readers receive no capability and
therefore cannot invoke canary or Protocol. Losing the nonce after claim commit
is handled as uncertainty and backend attestation, never capability recreation.

After an explicit blocked-infra resolution, the Branch is restored by revision
CAS to the
already-running post-dispatch state and the slot returns to pending. Its next
claim is an explicit operator-resume identity transition; it does not apply the
Scheduler transition a second time.

Every ordinary Branch/H writer checks the explicit evaluation lease. From lease
acquisition in pair preparation through atomic transfer or release, generic
persistence, H status changes, failure handling, weight stale marking,
promotion, and legacy finalization cannot update those owners. D2b/D2e/D4
connection participants are the only allowed mutation owners. A champion change
after dispatch leaves the pinned observation running and records no competing
Branch/H truth; D2e later applies the deterministic stale/reconcile overlay.

## Infrastructure and uncertainty

The claim-bound executor returns one `ClosedExecutionResult`; callers do
not choose a canary category or formal flag:

```text
ProtocolCompletedFacts
CandidateCanaryFailedFacts
InfrastructureBlockedFacts(
  canary_configuration | champion_shared_evidence | dispatch_not_started
)
ExecutionUncertainFacts
```

Candidate/config attribution uses an explicit typed result produced by the
trusted executor. D2b never calls the legacy free-text canary heuristic and
never trusts a caller-supplied `failure_category`. A `dispatch_not_started`
classification requires typed proof from a configured trusted issuer. A generic
transport/provider exception after dispatch that cannot prove whether execution
began is `ExecutionUncertainFacts`.

On reopen, every dispatched slot without an exact receipt or infrastructure
owner becomes `execution_uncertain` in one append-only control transition. It
stays there unless an evaluation-ID-aware backend provides an
`EvaluationBackendAttestation` binding evaluation ID, current claim, invocation
ID, backend job identity or deterministic invocation-key lookup, outcome, result
digest, and exact evidence. An injected attestation verifier must accept it. The
normal authority API cannot write a result into an uncertain slot.

The attestation outcome table is exhaustive:

| Verified backend outcome | Durable edge |
|---|---|
| exact `ProtocolCompletedFacts` or `CandidateCanaryFailedFacts` | `execution_uncertain -> receipted` |
| `verified_not_started`, bound to the invocation key and typed infrastructure proof | `execution_uncertain -> blocked_infra`; later resume requires explicit operator resolution |
| `running` | remain `execution_uncertain`, append no false terminal owner |
| `unknown`, nonterminal partial, or unverifiable infrastructure assertion | remain `execution_uncertain`, append no false terminal owner |

There is no direct uncertainty-to-pending edge and no automatic redispatch.
When a backend has no job ID, only its configured authoritative lookup by the
deterministic invocation key may prove `verified_not_started`.

Blocked infra records the exact running Branch and blocked Branch owner. Only an
explicit operator-resolution record may restore the prior running control state
and move the same evaluation ID to pending. No H/C call, count, Decision, or
candidate cleanup occurs on either edge.

Every edge is one `BEGIN IMMEDIATE` transaction with exact current-claim and
revision CAS:

- uncertain control insert + `dispatched -> execution_uncertain`;
- infrastructure insert + Branch block CAS + `dispatched -> blocked_infra`;
- operator-resolution insert + Branch restore CAS + `blocked_infra -> pending`;
- receipt insert + `dispatched -> receipted`;
- attested receipt insert + `execution_uncertain -> receipted`;
- attested-not-started infrastructure insert + Branch block CAS +
  `execution_uncertain -> blocked_infra`.

Receipt and blocked-infra races have one winner. A transaction crash rolls back
all its rows and state. Directly injected dormant dangling rows are never
positive and make inventory fail closed.

## Receipt and formal-observation derivation

`record_execution_result()` accepts the exact current
`EvaluationDispatchAuthority` capability and a `ClosedExecutionResult` envelope
that repeats and binds authority ID,
evaluation ID, claim ID, request digest, invocation ID, and typed terminal fact
digest. The store reloads every owner and exact-matches the envelope before it
derives the receipt or control edge. A late result from an older claim can never
bind to a resumed claim.

| Typed execution facts | Receipt | Future formal eligibility |
|---|---|---|
| `ProtocolCompletedFacts`: canary passed, complete matching Protocol and raw bytes | terminal | true |
| `CandidateCanaryFailedFacts`: typed candidate failure, no Protocol/raw | terminal | false |
| `InfrastructureBlockedFacts` | none; blocked-infra record | none |
| `ExecutionUncertainFacts` | none; uncertain control record | none |

For a formal Protocol receipt, strict DTO structure, stage, request, case IDs,
seeds, raw metrics ref, raw bytes digest, stats, and comparison/snapshot/claim
anchors must agree. “Complete” is an integrity predicate only; it introduces no
statistical sufficiency or quality gate. For a candidate canary receipt,
Protocol and raw metrics are absent. A validation/frozen champion/shared
evidence incident is infrastructure even if a partial Protocol object exists.

The exhaustive remaining combinations fail closed without a receipt:

- canary pass with missing Protocol;
- candidate canary failure with Protocol or raw metrics;
- configuration/infra failure presented as candidate failure;
- malformed, lossy, stage/request/case/seed-mismatched Protocol;
- missing, escaped, symlinked, or digest-mismatched raw metrics;
- a normal authority result submitted to an uncertain slot;
- an attestation for a stale claim/invocation/backend result.

The formal-observation identity binds evaluation ID, typed reason, canary
digest, optional complete Protocol digest, raw metrics digest, cases, and seeds.
The receipt digest then binds the full slot/snapshot/comparison/request/claim
owners plus that formal object. Same receipt is idempotent; any conflict is
permanent. A later global champion change does not invalidate a receipt if its
pinned historical comparison artifact remains intact.

The current `EvaluationPipeline`/`EvaluationOutcome` and
`EvaluationExecutionResult` are explicitly invalid receipt inputs: they sanitize
later-stage Protocol feedback and compute SafeFeatures before durable receipt
ownership. Future production integration must introduce a claim-bound executor
that captures complete terminal facts before sanitization or feature extraction.
D2c replays SafeFeatures only from the strict receipt and may not consume the
old mutable `decision_features` result.

## Recovery and inventory

`recover_pending_pairs()` may only publish or commit an exact pair-phase-prepared
`prepared/prepared` pair. `validate_inventory()` accepts:

```text
pair phase prepared + prepared snapshot + prepared initial slot + exact active lease
pair phase active + committed snapshot +
  pending/dispatched/execution_uncertain/blocked_infra/receipted slot + exact active lease
pair phase active + reserved suffix state + structurally valid lease/dependency reference
```

A newly paired or D2e-transferred pending evaluation has no claim and must own
the rearmed `pre_first_dispatch` comparison guard. A same-evaluation pending
slot created by explicit blocked-infra resolution has a predecessor claim and
must retain `historical`. Any other pending/guard/claim combination is held.

It holds every snapshot-only, slot-only, `committed/prepared`,
`prepared/pending`, duplicate-initial, dangling claim/control/receipt,
missing/duplicate/mismatched Branch/H lease, two active slots, canonical-payload
mismatch, opposite-mode conflict, or artifact mismatch. It
does not delete scientific owners, call a provider, run Protocol, produce a
Decision, or infer missing data.

D2b inventory validates only its own structure and returns a typed unresolved
dependency for a reserved suffix state. It does not import or decode D2c/D2e/D4
owners. The later composite startup inventory supplies the corresponding owner
validator and proves the exact dependency; absence or mismatch holds startup.

## Implementation sequence

1. D2b.0a: extract pure `durable_owner_codec.py`; prove v1 goldens and current
   completion/rejection behavior byte-compatible.
2. D2b.0b: migrate all Branch/H writers from replace semantics to the global
   typed revision/CAS protocol, install the dormant evaluation-lease schema,
   partial unique indexes, and SQL writer predicates, and close generic/failure/
   Decision/rejection/promotion/weight/H-status races before any positive lease
   writer or dispatch exists.
3. D2b.1: implement values and strict codecs with mutation, exclusion,
   ordinal/count, complete Protocol, and round-trip tests.
4. D2b.2: refactor D1 into connection-scoped primitives; implement the positive
   lease/pair/slot writers, remaining paired schema and triggers, facade, crash
   recovery, inventory, and concurrency tests.
5. D2b.3: implement sealed dispatch authority, claim-bound executor DTOs,
   champion/Branch CAS, uncertainty, blocked infra, and operator resolution.
6. D2b.4: implement exact raw-metrics ownership, claim-bound receipt derivation,
   backend attestation, immutable receipt storage, and classification tests.
7. D2b.5: run two independent adversarial reviews, affected compatibility
   suites, full Scion tests, compileall, Black, and diff checks. Confirm static
   zero production references to the positive candidate-evaluation
   owner/store/facade and zero early formal/event/count writes. Shared pure codec
   imports are allowed; Campaign, Scheduler, EvaluationOrchestrator, Finalizer,
   CLI, and launchers form an explicit denylist for D2b positive APIs.

Each slice is reviewed before the next begins. D2b is accepted only when all
P0/P1 findings are closed. No generative campaign starts after D2b because D3
and D4 capability is still absent.
