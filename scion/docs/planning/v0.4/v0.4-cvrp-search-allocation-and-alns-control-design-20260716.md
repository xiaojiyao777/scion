# v0.4 CVRP Search Allocation and ALNS Control Design

*Date: 2026-07-16*
*Status: accepted design; R11c boundary complete, implementation active*
*Architecture authority: `scion/design/scion-architecture-v3.md`*

## Decision

The next CVRP work is not another gate repair and not a blind deletion of VNS.
It has three separate purposes:

1. make measured search-time allocation visible to the next Hypothesis without
   changing Protocol or Decision;
2. compare current direct-v3 research behavior from canonical ALNS+VNS and a
   true pure-ALNS starting profile;
3. remove solver interchange-file leakage and establish an explicit experiment
   retention policy so disk pressure cannot terminate research.

These purposes must remain separate. Search-allocation evidence is proposal
context, formal quality still comes only from Protocol, and an ALNS-only result
is judged first against its own weaker champion.

## Existing Evidence That Must Not Be Repeated Blindly

The repository already contains an older baseline-strength program:

- Phase A measured ALNS+VNS A/A MDE `9.6` and ALNS-only A/A MDE `4.65`;
- paired ALNS-only versus ALNS+VNS was `7/56/1`, with mean BKS gap
  `6.50%` versus `4.20%`;
- Phase B gave ALNS-only the only screening row with a positive CI lower bound;
- Phase C reached validation/frozen more often from ALNS-only but produced no
  promotion, and its strongest candidates collapsed on frozen/large-X;
- the later four-arm no-LLM matrix rejected broad VNS removal. Disabling only
  initial VNS helped CMT2 and P-n76 under that matrix, while embedded VNS still
  mattered on some cases.

Those runs used an older runtime, context shape, model, and lifecycle. They are
prior evidence, not a substitute for a current direct-v3 matched control.

## Current Causal Gap

Raw CVRP runtime already records:

- `solver_algorithm_phase_runtime_ms`;
- `solver_algorithm_phase_move_attempts`;
- `solver_algorithm_phase_accepted_moves`;
- `solver_algorithm_phase_delta_sum`;
- `solver_algorithm_alns_iteration_trace`;
- before/after objective probes inside the solver runtime.

The next Hypothesis currently receives only the problem-owned ALNS repair
summary: iterations, repair attempts/accepted/best updates/elapsed,
route-limit, and repair-error. It does not receive `vns_initial`,
`vns_embedded`, `alns_core`, VNS runtime share, phase move contribution, or
repair-to-polish marginal improvement.

R11b illustrates the consequence. Candidate embedded VNS consumed about
`84.7%` of algorithm time and ALNS iterations were `1333` versus champion
`1633`, yet embedded polish improved `1142/1333` observed repair candidates.
The correct research question is therefore not "is VNS bad?". It is "is the
measured marginal value of each search phase worth its measured time, and can
the agent reallocate that time?"

The model already receives complete current solver source and can edit
`config.py`, `scheduler.py`, and `local_search.py`. The missing capability is
measured attribution, not source access.

## Workstream A: Problem-Owned SearchAllocationEvidence

### A0. Boundary

Extend the existing CVRP proposal-mechanism evidence path. Do not add a generic
core helper, interactive LLM tool loop, DecisionFeature, gate, runtime cap,
forced target, retry, budget, or truncation.

The packet is screening-only, proposal-only, association-only, and carried by
the existing canonical screening record. Validation/frozen facts remain hidden.

### A1. Schema

Use one problem-owned schema:

```text
scion.cvrp.search_allocation_evidence.v1
```

Required top-level fields:

```text
schema_version
evidence_scope = screening_search_allocation
hypothesis_attribution = unbound
interpretation_constraint = association_only
gate_influence = false
coverage
candidate
champion
comparison
```

Each side must contain complete observed aggregates, without top-k selection:

```text
solver_algorithm_elapsed_ms
phase_runtime_ms
phase_runtime_share
runtime_residual_ms
alns.iterations
alns.iterations_per_second
alns.accepted
alns.best_updates
alns.route_limit
alns.repair_error
post_repair_polish.observed
post_repair_polish.improved
post_repair_polish.unchanged
post_repair_polish.worsened
post_repair_polish.delta_sum
destroy_operators
repair_operators
destroy_repair_pairs
move_phases
```

Runtime shares must use the explicit phase-runtime map and expose residual time.
Nested move counters are not additive phase runtimes; the packet must state this
instead of double-counting CROSS/VNS child activity.

The provider reads only this existing runtime allowlist:

```text
solver_algorithm_elapsed_ms
solver_algorithm_phase_runtime_ms
solver_algorithm_phase_move_attempts
solver_algorithm_phase_accepted_moves
solver_algorithm_phase_delta_sum
solver_algorithm_phase_best_updates
solver_algorithm_phase_improvement
solver_algorithm_alns_iteration_trace
```

It does not reflect arbitrary runtime mappings into the prompt. Trace rows use
an explicit field allowlist and are aggregated inside the problem provider;
case paths, case ids, seeds, raw refs, and unrecognized trace fields never enter
the packet.

Operator lifecycle names are semantic, not cosmetic. Destroy aggregation must
separate `selected`, `nonempty`, and `empty`. Repair aggregation must separate
`selected`, `invoked`, `completed`, `accepted`, and `best_updates`. A repair
name paired with `destroy_empty` was selected by the schedule but was not
invoked and cannot be described as a repair attempt. Iteration wall time is
`selected_iteration_elapsed_ms`, not repair elapsed time. Post-repair polish
reports observed/improved/unchanged/worsened counts and a signed delta; it does
not imply that polish caused the full candidate/champion difference.

`destroy_repair_pairs` is the complete observed cross-product present in the
iteration trace, keyed by the two selected operator identities and carrying the
same selected/nonempty/invoked/completed/accepted/best-update lifecycle. It is
not reconstructed by multiplying the two marginal tables. This is required for
R11c H3, which changes twelve joint pair weights: the next Hypothesis must be
able to distinguish activation/effect of an exact pair from shifts in either
marginal. Existing trace rows already contain both identities, so this remains
an A1 aggregation and does not justify new solver instrumentation.

Missing is not zero. An absent side, absent runtime mapping, absent trace, or
malformed field is represented as unavailable coverage. Within an observed
mapping, an absent known operator key may be counted as zero. Candidate versus
champion comparison uses only the paired intersection on which both sides have
the relevant observed field. Runtime share divides by
`solver_algorithm_elapsed_ms`, never by the sum of phases.

### A2. Implementation ownership

- aggregation belongs under `scion/problems/cvrp/evidence/`;
- `CvrpProposalMechanismEvidenceProvider` calls it from the existing provider;
- the existing generic proposal-evidence envelope and ContextManager transport
  it unchanged;
- tests assert exact packet content, coverage, candidate/champion comparison,
  no raw pair/case/seed leakage, and absence from DecisionFeatures.

The acceptance fixture derived from R11c H1 must preserve these exact facts:

```text
candidate.alns.iterations = 2300
champion.alns.iterations = 1589
candidate.destroy.route.selected = 511
candidate.destroy.route.nonempty = 0
candidate.destroy.route.empty = 511
candidate.repair.regret3_existing.selected = 511
candidate.repair.regret3_existing.invoked = 0
candidate.repair.regret3_existing.completed = 0
candidate.destroy_repair_pairs.route__regret3_existing.selected = 511
candidate.destroy_repair_pairs.route__regret3_existing.invoked = 0
candidate.post_repair_polish.observed = 1789
champion.post_repair_polish.observed = 1589
candidate.phase_runtime_ms.vns_embedded = 662010
champion.phase_runtime_ms.vns_embedded = 701990
candidate.move_phases.vns_embedded.attempted = 36185
champion.move_phases.vns_embedded.attempted = 36448
```

Focused verification covers aggregate math, missing/malformed inputs, the R11c
fixture, provider envelope, direct-v3 Hypothesis round-trip, no leakage, and
byte-for-byte unchanged SafeFeature/Decision outputs with the provider present
or absent. Old records remain on their old schema and are not rewritten.

The first implementation uses existing runtime fields only. Do not add new
solver instrumentation in the same slice.

### A3. Optional operator attribution

Only if A1 evidence remains insufficient, add a compact problem-owned
`record_search_allocation(scope, operator, ...)` aggregation to CVRP
`AlgorithmContext`, forwarded by `_DeadlineContext`. It may distinguish
`initial_vns` and `embedded_vns` default neighborhoods, but records one compact
mapping per solver invocation rather than raw per-move events.

Do not build an interactive `inspect_search_allocation` LLM tool. Direct-v3 is
a one-call structured proposal runtime; a new generic multi-tool loop would add
more complexity and noise than the typed packet solves.

## Workstream B: Current Direct-v3 Research-Surface Contrast

### B0. Profile identity

Prepare two copied, problem-owned champion profiles from the same exact pushed
commit:

```text
canonical_alns_vns
pure_alns_no_polish
```

The pure profile explicitly sets:

```text
SOLVER_VARIANT = alns_vns
USE_VNS = False
ENABLE_INITIAL_VNS = False
ENABLE_EMBEDDED_VNS = False
ENABLE_SIZE70_TWO_OPT_FALLBACK = False
```

Setting only `USE_VNS=False` is not a pure ALNS control in the current solver,
because it activates the size-70 two-opt fallback.

Each profile records parent commit, exact config diff, profile manifest hash,
snapshot hash, data/problem/protocol/split/seed identities, and champion profile
id. The arms use separate campaigns, ChampionStores, caches, and champion v1
snapshots. A pure-profile promotion never replaces the canonical champion.

The profile is a starting point, not a permanent constraint. If the agent
autonomously reintroduces VNS, record that as research behavior; do not add a
gate to forbid it.

### B1. No-LLM current characterization

After R11c terminates and after A1 is implemented, run four serial profiles on
the current formal screening cases and seeds:

1. canonical ALNS+VNS;
2. initial VNS disabled;
3. embedded VNS disabled;
4. pure ALNS without polish.

Use the Protocol-resolved per-case scientific limits, not one uniform matrix
timeout. Rotate execution order and never run two arms concurrently on one
host. Report objective/fleet validity, phase time and residual, ALNS
iterations/second, repair-to-polish value, best-update density, acceptance/SA
trajectory, and case/seed heterogeneity. This is diagnostic evidence only.

SA cooling is iteration-based, so removing VNS changes both time allocation
and the number/temperature trajectory of ALNS iterations. The analysis must not
attribute every change to VNS time competition.

### B2. Matched direct-v3 campaigns

Run at least two order-balanced repeats after B1:

```text
repeat 1: canonical -> pure ALNS
repeat 2: pure ALNS -> canonical
```

Each cell is a fresh eight-observation root using the same exact pushed code,
`gpt-5.6-sol`, direct-v3 runtime, formal inputs, scientific solver limits, and
postrun acceptance. There is no resume, forced surface/action/target, provider
retry, semantic budget, truncation, or automatic repair.

Compare research behavior relative to each arm's own baseline and current A/A
measurement floor:

- evaluated hypotheses and implementation rejection rate;
- branch depth and evidence-backed direction changes;
- search-allocation response in the next Hypothesis;
- screening/validation/frozen reach;
- case/pair effect, CI, BKS gap, runtime failure, and replay integrity;
- cost per valid Protocol observation and per accepted research insight.

If a cell ends with an exact candidate waiting at validation/frozen, finish that
stage only through a distinct exact-candidate eval-only continuation. It makes
no new H/C call and is not reported as part of the fresh generative root.

### B3. Cross-profile fixed replay

For every pure-profile candidate that reaches validation, plus the final
verified cumulative candidate from each pure cell:

1. materialize its exact patch closure on the canonical profile;
2. rerun Verification;
3. perform a no-LLM three-way replay of canonical champion, pure champion, and
   transplanted candidate on the same cases/seeds.

An improvement over the weaker pure champion is not evidence that canonical
ALNS+VNS improved. Only the transplant replay can establish transfer.

## Workstream C: Solver Interchange-File Ownership

`LocalSubprocessRunner.run_solver()` creates `/tmp/scion_run_*.json`. Failure
paths delete it; successful paths return `output_path` and production callers
normally never unlink it. The solver output is already parsed and copied into
formal metrics, so these files are duplicate interchange artifacts, not
scientific evidence.

Do not patch every caller with ad-hoc `unlink` calls. The design is:

1. runner owns the interchange file for its entire lifetime;
2. parse the complete payload into the model-owned in-memory result;
3. remove the file in one outer `try/finally` on success, failure, invalid JSON,
   read error, and cancellation;
4. migrate verification/final-evaluation consumers away from persistent
   `output_path` and remove volatile `/tmp` paths from champion cache payloads;
5. preserve `campaign/metrics`, v8 nondeterminism artifacts, and raw Protocol
   evidence unchanged.

The atomic contract for this slice is:

- `SolverOutput` owns the complete parsed solver mapping and exposes one
  deterministic `to_raw_mapping()` reconstruction. Framework keys
  (`objective`, `feasible`, `runtime`) have one typed owner; all other solver
  keys stay in `solution_payload`. No second raw-payload field is added.
- `RunResult.output_path` is removed rather than retained as a deprecated or
  usually-null escape hatch. A returned result is self-contained and has no
  borrowed filesystem lifetime.
- `run_solver()` creates the interchange file and encloses creation, child
  registration, communication, parsing, result construction, and cleanup in a
  single ownership boundary. An internal same-class method may keep the control
  flow readable, but no new lifecycle service/helper layer is introduced.
- cleanup runs under `BaseException`, not only ordinary `Exception`; an active
  child is killed before the original cancellation/system exception is
  re-raised. `FileNotFoundError` during cleanup is already-clean success; other
  unlink failures are observable warnings and do not replace the primary
  result or exception.
- a successful process with missing, unreadable, non-object, or invalid JSON is
  a crash result with `output=None`. Timeout/OOM/crash classifications remain
  unchanged.
- cache payloads persist the typed output and stable stdout/stderr content or
  digests, never the temporary pathname. Legacy cache reads may ignore an old
  `output_path`, but new writes cannot produce it.
- shared canary, standalone V5/V6/V7/V8, final evaluation, protocol cache, and
  test fakes consume `SolverOutput.to_raw_mapping()` or construct a complete
  `SolverOutput`. They do not reopen, unlink, or expose runner interchange
  files.

This slice does not create `runtime/solver-output-tmp` inside the candidate
workspace: doing so would mix framework interchange ownership with the research
source/artifact tree. Campaign-owned temporary-directory injection may be
designed later only if evidence shows hard-SIGKILL remnants remain material;
it is not part of the current fix.

Acceptance covers success, timeout, crash, invalid JSON, Popen/read errors,
BaseException, active-child termination, zero residual interchange files after
join, cache path hygiene, and the full suite. Focused tests must also prove
concurrent runs clean only their own files, a `MemoryError`/Popen failure does
not leave a file, the V8 artifact remains formal and durable, and a static
production search finds no reads or construction of `RunResult.output_path`.

## Workstream D: Experiment Retention

Disk cleanup is evidence lifecycle, not arbitrary age deletion.

Always retain:

- every live root/runtime and its ancestors;
- roots named by active TASK/current-state work;
- current R6-R11c evidence until v0.4 closeout;
- baseline-strength Phase A/B/C accepted anchors needed by this design;
- unique raw evidence that has no accepted tracked report;
- exact candidate/replay artifacts still needed by a queued experiment.

Eligible first for deletion:

- prepared-only roots that were never launched and are explicitly superseded;
- invalid/no-experiment roots whose terminal facts are already captured in a
  tracked report and are not needed for a repair replay;
- duplicate staging/analysis copies with a verified accepted canonical copy;
- zero-evidence smoke/preflight failures;
- package caches and inactive runner interchange files.

Every batch requires a dry-run manifest containing path, size, classification,
supporting report/supersession evidence, and live-owner check. Delete exact
paths only, record reclaimed bytes, and never mutate a retained historical root
in place.

## Sequencing

```text
R11c terminal audit
  -> commit this design and retention inventory
  -> C: runner-owned interchange lifecycle
  -> A1: SearchAllocationEvidence from existing fields
  -> B0/B1: current four-profile no-LLM characterization
  -> B2: two order-balanced matched direct-v3 repeats
  -> B3: cross-profile fixed replay
  -> optional A3 operator-level attribution only if evidence proves necessary
  -> hot-path modularization after behavior boundaries are stable
```

Historical experiment cleanup can proceed in audited batches alongside this
sequence, but it cannot delete an input required by a later step.

## Non-Goals

- no VNS blacklist or forced VNS target;
- no claim that pure ALNS is a better production solver;
- no new gate, retry, budget, cap, top-k, compression, or truncation;
- no validation/frozen leakage into proposal context;
- no generic Scion core ownership of CVRP/ALNS/VNS semantics;
- no scheduler refactor mixed into the evidence-projection slice;
- no broad large-file movement mixed into these behavioral slices.

## Completion Criteria

This design slice is complete only when:

- R11c has a terminal read-only audit;
- inactive solver interchange files no longer accumulate;
- next-H visibly receives complete compact search-allocation evidence;
- a current direct-v3 canonical/pure matched comparison is complete;
- pure-profile positives are interpreted through canonical transplant replay;
- retained/deleted experiment roots have a durable audit manifest;
- implementation leaves generic core boundaries and formal Decision inputs
  unchanged.
