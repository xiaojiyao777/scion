# W3 root-owned installation, manager acceptance, and first launch

*Date: 2026-07-23*
*Status: amended implementation plan; root application is forbidden until this exact hash has two independent zero-P0/zero-P1 review closures*
*Architecture authority: `design/scion-architecture-v3.md`*
*Parent source contract: `v0.4-w3-composition-launch-readiness-plan-20260723.md`*

## 1. Decision and boundary

This slice closes the external deployment owners deliberately left outside the
accepted W3 composition. It may prepare one candidate without privilege, apply
that exact candidate as root, load but not initially start the two units,
persist a complete loaded-manager acceptance, and only then execute the
separately recorded human-authorized first `StartUnit`. The active task grants
prospective authority for the unique installation selected by this plan, but
that grant is usable only after it is bound to the revised plan hash, the
verbatim user statement, the deterministic selection rule and the exact
accepted installation receipts.

The accepted problem dry root and the launch source have distinct provenance:

- the immutable problem root was prepared from problem-source commit
  `b879bbc1e73550234c863e829ddaecd877f6876e`;
- the launch authority `source_commit/source_tree` identify the later exact
  pushed commit that contains every runtime, composition, package and
  installation-owner source used by the installed environment.

No launch input may be represented as a Git blob of the earlier problem
commit. Every `git_blob` tuple must be resolved from the launch commit with
exact path, blob OID, raw SHA-256 and size. The accepted problem manifest is a
separate `external_evidence` input with its stable device/inode and bytes.

The earlier synthetic unit fixtures use placeholder Git OIDs and are test
scaffolding only. They cannot produce deployment authority.

This is a deployment transaction, not a scientific or model gate. It adds no
provider call, retry, resume, research budget, content limit, truncation,
problem decision or alternate job lifecycle.

The 2026-07-24 hard cut adds four non-negotiable authority boundaries:

- root accepts launch source only from one root-owned fixed-source receipt
  produced from a descriptor-walked, content-bound root-owned bare Git mirror
  with no alternate/promisor/shallow/graft/replace authority and exactly two
  zero-P0/zero-P1 closures having distinct reviewer and task identities;
- the namespace-final probe runs non-root through fixed root-owned
  `/usr/bin/bwrap` at the exact future visible environment path, and root later
  rehashes that executable identity;
- a durable transaction trace precedes the first launch-specific root mutation,
  and K0 binds both its expected and post-import acquired final absence;
- K3/K5 publications and the complete loaded-manager pair are reopened around
  the final start gate, including after durable `START_ISSUED` and immediately
  before `RefUnit`/`StartUnit`.

inventory and read-only rehash only. The installed dispatcher may import that

  inputs;
- exact Git-object acquisition from one clean pushed commit;

The thin CLI exposes exactly:

```text

prepare-candidate
verify-candidate
apply-root
verify-installed
record-start-authorization

```

`accept-fixed-source` requires effective UID zero and publishes only beneath
`/var/lib/scion/source-acceptances/w3`. `prepare-candidate` and
`verify-candidate` reject effective UID zero.
`apply-root`, `verify-installed`, `record-start-authorization`, `start` and

The normal installed W3 dispatcher remains limited to `run`,
`seal-unit-drained` and `close`; it still has no manager mutation method. Before
claiming the nonce, `run` must verify the exact root-owned `START_ISSUED`
receipt and the installed acceptance it references. This is a governance
barrier against stale or accidental execution, not a privilege boundary:
trusted root can bypass or replace any local service policy and is explicitly
inside the threat boundary.

## 3. Canonical candidate

The caller supplies only:

- the accepted problem dry-root path;
- the exact root-owned fixed-source acceptance path;
- one exact pushed launch commit;
- one exact remote name and full `refs/heads/...` ref;
- the accepted native external-record path;
- the exact Python executable used to build the environment.

The preparer requires clean HEAD/tree equality at that commit. The root
fixed-source owner separately verifies one root-owned bare mirror without
network access using fixed `/usr/bin/git`, binds the exact
commit/tree/blob inventory plus a descriptor-walked aggregate of every
root-owned repository directory and regular file. It requires bare and
non-shallow state; rejects alternates, promisor/partial-clone state, grafts,
replace refs, linked-worktree delegation and non-regular/hardlinked repository
content; and consumes two scopes with separately distinct reviewer identities
and task identities. Candidate preparation must reopen that immutable receipt
and obtains source bytes with `git cat-file`, never from working-tree bytes.
The root receipt, rather than a movable remote ref or candidate copy, is the
enduring source authority.

Before nonce generation, `CandidatePreparationOwner` derives one selection key
from the active task-event identity, fixed reviewed plan SHA, exact launch
commit/tree, fixed-source acceptance SHA, dry-root manifest SHA and
native-record SHA. Under the fixed
user-owned experiment parent it creates one exact
`.scion-w3-selections/<selection-key>/intent.v1.json` with `O_EXCL` and fsync;
that intent fixes the canonical candidate root as
`v04-w3-launch-<selection-key>-claw`. The closed selection directory may
contain only `intent.v1.json` and, after success, `committed.v1.json`.
`prepare-candidate` refuses an existing intent, candidate root or commit and
has no second selection/nonce path.

The owner then creates one random 256-bit nonce before authority bytes are
frozen and commits the exact nonce, authority SHA, launch ID, candidate-root
identity and intent SHA no-replace. Both selection receipts are copied into
the candidate, included in its exact inventory and independently reopened by
root. The nonce is not a claim and is never published in either claim location
during preparation or installation. The launch ID is deterministic:

```text
sha256(
  b"scion.w3-launch-id.v1\0"
  + authority_sha256 ASCII
  + b"\0"
  + nonce ASCII
)
```

The candidate inventory is exactly:

```text
candidate.v1.json
authority.json
installation.json
sealed-store/
environment/
units/scion-w3@.service
units/scion-w3-close@.service
receipts/source.v1.json
receipts/sealed-store.v1.json
receipts/environment.v1.json
receipts/candidate-verification.v1.json
receipts/selection-intent.v1.json
receipts/selection-committed.v1.json
```

The sealed store additionally contains the exact fixed-source acceptance
receipt and the wheel plus its v3 receipt. Root staging parses the acceptance,
requires its embedded source receipt to equal the imported source receipt, and
verifies actual wheel ZIP/RECORD/member bytes against the trusted Git
snapshot; candidate or installed Python is never executed by root.

Every receipt is canonical UTF-8 JSON with sorted keys, compact separators and
one terminal LF. Unknown or duplicate fields are rejected.

The candidate is complete before any root path changes. Verification reopens
and rehashes every byte, rebuilds both authority objects with the accepted
parsers, reruns dry-root composition readiness with installation absent, and
proves both nonce-claim locations and the source terminal root absent.

The user-owned candidate is never a trusted root input. Root imports it through
a pinned source-root dirfd and a component-by-component no-follow walk into a
fresh root-owned staging directory on the destination filesystem. The import
records and revalidates `(dev, ino, mode, uid, gid, nlink)` for the source root,
every directory and every leaf before and after copying. It rejects device,
FIFO, socket and other special files, multi-link regular files, every symlink
in either sealed store or environment, and any directory identity change.
After import, no privileged operation reads the user-owned candidate again.

## 4. Sealed store and environment

The sealed store contains:

- every exact launch/runtime Git blob needed by the installed W3 composition;
- the accepted problem manifest as external evidence;
- the accepted native external record;
- the exact wheel used for installation;
- an exact copy of `scion_w3_tool.py` at `sealed/bin/scion-w3-tool`;
- both unit templates at their authority-declared sealed paths.

The complete relative inventory records kind, path, mode, size, SHA-256 and
provenance. Directories, regular files and symlinks are separate closed types.
Symlinks are forbidden in the sealed store. Its aggregate is the SHA-256 of
the canonical complete inventory and is bound by the launch authority.

The wheel is double-built offline from two immutable Git archives of the
launch commit. The builder is exactly
`/home/clawd/miniconda3/envs/claw/bin/python3.12 -I -m pip wheel --no-deps
--no-build-isolation`; its compiler, flags, locale, isolated HOME/TMPDIR/PATH
and `SOURCE_DATE_EPOCH` are rederived from the accepted native build
transaction. Both builds must have identical complete member inventories and
must reproduce accepted native ELF SHA
`3d747973bc2eb3b0f6fda68f288987c7b988820eb24df2ff617aa567071803fc`.
The wheel must contain:

- `scion.tools.scion_w3_tool`;
- both `systemd/*.service` package-data files;
- the accepted `_spawn_into_cgroup` extension;
- every required W3 and generic runtime module.

The native extension source must match the accepted native contract and its
built ELF SHA must match the accepted external record. A new wheel may add
later pure-Python W3 source, but it cannot silently substitute another native
binary.

The candidate environment is created with exact runtime
`/usr/bin/python3.12 -m venv --without-pip --copies`, without
`--system-site-packages`. The preparer preflights `/usr/bin/python3.12 -m pip`
and uses its `--python <environment>/bin/python install --no-compile --no-deps
--no-index <wheel>` surface; it never installs an OS package or uses ensurepip.
The exact D-Bus
Python package and `_dbus_bindings`/`_dbus_glib_bindings` extensions used by
the service are copied into the environment and inventoried with their package
version and ELF/shared-library paths. Every file that can be loaded outside
the environment—including the executable, Python standard library, dynamic
loader and shared libraries—is either copied into the immutable environment
or explicitly inventoried by path, device/inode, size and SHA-256.
Its complete relative file/symlink inventory, external-runtime inventory,
wheel identity, native ELF identity, import table and D-Bus provenance form
`environment-content.v1`. This content receipt contains no final digest-derived
path; its raw SHA is bound by authority and installation. No package install
occurs after that receipt.

Before inventory, the builder removes activation scripts, the unused `scion`
console script, `lib64` and all bytecode/cache files, deletes the
candidate-path `command` line from `pyvenv.cfg`, and rejects every symlink or
occurrence of the candidate/selection roots in any remaining byte string. Only
the exact copied Python entrypoints used by the units remain executable. A
candidate-path probe and an independent non-root namespace-final probe both
pass before closure. The latter uses `/usr/bin/bwrap` with a fresh network
namespace, `NoNewPrivs`, no writable host bind and the exact future
`/var/lib/scion/environments/w3/<environment-receipt-sha>` visible path. Its
receipt binds bubblewrap bytes and `(dev, ino, mode, size)`, producer UID/GID,
network/mount namespace identities, both probes and their complete evidence
digest.

The environment is tested only after relocation to its exact final
`/var/lib/scion/environments/w3/<environment-receipt-sha>` path. The test
records `sys.executable`, `sys.prefix`, `sys.path`, all imported module files,
native-extension/shared-library resolution, D-Bus acquisition and exact
dispatcher argv in a separate root-ledger `environment-relocation.v1` receipt
that references the already fixed content receipt. This separation avoids a
digest/path identity loop. The identical content and external-runtime
inventories are rehashed by the installed dispatcher immediately before nonce
claim and, after all 172 rows are durable, immediately before `finish_raw()`
publishes `RAW_COMPLETE`. A pre-claim drift refuses the initial claim; a
completion-proof drift occurs while the terminal writer is still open and
uses its existing `mark_incomplete()` path instead of publishing
`RAW_COMPLETE`. No `RAW_COMPLETE -> INCOMPLETE` transition is added.
Installation-time success is not a substitute for either runtime proof.

Both candidate trees become immutable before candidate verification. Root
validates only its root-owned imported staging, publishes without byte
transformation, and makes the final sealed/environment roots root-owned and
read-only. Before the candidate inventory is frozen, all sealed/environment
directories and executable files are normalized to mode `0555`, and all other
regular files to `0444`; every projection ancestor is searchable by `clawd`.
Root changes only owner/group after import and never changes an inventoried
mode.

## 6. Root application transaction

Root application begins only when every final target, both unit fragments, all
drop-in directories, both nonce claims and the source terminal root are absent.
It refuses an existing or partial installation; it does not overwrite, merge,
repair or reuse it.

Before any launch-specific mutation, root pins the candidate-root dirfd with
`O_NOFOLLOW`, pins the deterministic selection directory, records both
identities, reads only the bounded canonical candidate header, derives the
complete expected final-absence receipt, and publishes
`/var/lib/scion/imports/w3/trace.<launch-id>.v1.json` no-replace. Any trace
without an accepted launch is permanently `PARTIAL_HOLD`. It then creates
root-owned quarantine
`/var/lib/scion/imports/w3/<candidate-header-sha>/`, writes the import intent,
and imports into same-filesystem staging there. Only after full staging and
preparation-receipt verification succeeds does `RootCandidateSelectionOwner`
create and fsync exact root-owned
`/var/lib/scion/selections/w3/<selection-key>.json` with `O_EXCL`. That receipt
binds the imported staging aggregate, nonce, authority, launch ID, preparation
receipts and source dirfd identities. It defines the unique root-selected
candidate; no assertion is made about user-owned paths before root first pins
them. After import and before K0 commits, root descriptor-walks every final
path and exhaustively scans procfs, accepting only explicit `ENOENT`; it
persists and reopens `ROOT_FINAL_ABSENCE.v1.json`. K0 binds the trace SHA, the
trace's expected absence SHA and the acquired absence SHA. Only then does root
no-replace create the authoritative `<launch-id>` receipt root. A failed
import remains a typed quarantine hold and does not consume a root selection
or authoritative launch-ID slot.

The authoritative receipt root is fixed:

```text
/var/lib/scion/acceptances/w3/<launch-id>/
  install/
  start/
  terminal/
```

The hierarchy is root-owned. The launch root remains `0755`; `install/` becomes
`0555` after installation acceptance, `start/` becomes `0555` after
`START_RETURNED`, `START_REJECTED` or dispatch-unknown classification, and
`terminal/` remains `0755` until final terminal acceptance or preserved
incomplete classification. Thus root can append to the active phase while
`clawd` can only read. Receipt files are mode `0444`. Candidate-local receipts
are preparation evidence or diagnostic copies only and never authorize a
privileged action. Every receipt is created no-replace, fsynced, and followed
by parent-directory fsync.

The root receipt store is an append-only phase ledger. For every external
effect it persists an intent before the action and a committed receipt after
reopening the resulting fact:

```text
ROOT_STAGING_IMPORTED
CANDIDATE_SELECTED
STORES_PUBLISHED
AUTHORITY_PUBLISHED
PROJECTION_MOUNTED
UNITS_PUBLISHED
MANAGER_RELOADED
INSTANCES_LOADED
INSTALLATION_ACCEPTED
START_AUTHORIZED
START_ISSUED
START_RETURNED
START_REJECTED
```

On every invocation the transaction reopens filesystem, mount and manager
facts and classifies the launch as exactly `ABSENT`, `PARTIAL_HOLD` or
`ACCEPTED`. A crash between intent and commit is `PARTIAL_HOLD`; there is no
automatic cleanup, rollback, completion or retry. The field-level receipt DAG
is forward-only: each phase names only the immediately required predecessor
raw SHAs and launch identity, with cycle/self-reference rejected.

The fixed order is:

1. descriptor-pin the candidate and selection roots, bounded-read the
   canonical header, derive expected absence, publish the transaction trace,
   create quarantine and persist `ROOT_STAGING_IMPORTED` intent;
2. no-follow import the complete candidate into fresh root-owned
   same-filesystem staging, verify only root-owned staging, the fixed-source
   acceptance, actual wheel bytes and selection receipts, rehash the recorded
   bubblewrap binary, reacquire/persist/reopen final absence, persist the
   import commit, root-select the exact imported candidate no-replace, then
   create the authoritative root receipt hierarchy;
3. no-replace publish the sealed store and environment with
   `renameat2(RENAME_NOREPLACE)`, then reopen/rehash;
4. no-replace publish `authority.json` and `installation.json`, fsyncing their
   files and parent directories;
5. fresh-create both the root-owned nonce-ledger parent, mode `0755`, and its
   `clawd`-owned `claims` child, mode `0700`; final absence independently binds
   both paths before K0;
6. create the exact six-entry projection;
7. descriptor-pin all four sources and destination parents, clone each source
   with `open_tree(source_fd, "", AT_EMPTY_PATH|OPEN_TREE_CLONE|
   OPEN_TREE_CLOEXEC)` and attach only through
   `move_mount(tree_fd, "", destination_parent_fd, exact_leaf,
   MOVE_MOUNT_F_EMPTY_PATH)`; no source or destination parent is resolved from
   a pathname after validation;
8. convert every bind destination with exact recursive-private
   `MS_PRIVATE|MS_REC`, then remount sealed/environment read-only and retain
   run/nonce-claims read-write;
9. publish exact projection authority/installation regular files;
10. no-replace publish both exact unit fragments under
    `/etc/systemd/system`;
11. invoke D-Bus `Manager.Reload`;
12. on one D-Bus connection record boot ID, full Version and the
    `org.freedesktop.systemd1` unique owner; `RefUnit` run then closer,
    `LoadUnit`/`GetUnit` both and verify the object paths, acquire the complete
    pair, persist/fsync/reopen the manager receipt, recheck owner/boot/version,
    then `UnrefUnit` closer followed by run;
13. persist installation, projection, unit and absence receipts and reopen the
    complete transaction;
14. publish one top-level installed acceptance last.

An exception leaves the root ledger in typed `PARTIAL_HOLD` and authorizes no
cleanup or start. The tool has no automatic rollback, overwrite or retry path.

The projection receipt proves exact inventory and, for each directory bind,
source/destination device, inode, mount ID, filesystem type, mount root,
read-only/read-write state and propagation flags. Directory identity alone is
insufficient. It also binds the boot ID, `/proc/self/ns/mnt` and
`/proc/1/ns/mnt` identities and the destination parent chain. The dry-root
tree rehash and projected-run comparison both use the pinned run-root inode.
The two mount namespaces must match. Each bind destination has exact private
propagation: its canonical selected mountinfo row has no `shared:`, `master:`
or `unbindable` optional field after the recorded `MS_PRIVATE|MS_REC` call.
The receipt stores the complete parsed selected-row fields and their canonical
JSON digest rather than a pseudo-file inode. Each destination retains the
source device/inode but has a distinct mount ID; sealed/environment are
read-only and run/nonce-claims are read-write. Reboot, namespace change,
remount or mount-ID change invalidates the installed acceptance. The authority
and installation entries are exact root-owned regular files, mode `0444`.

## 7. Loaded-manager and pre-start acceptance

The generic systemd-255 acquisition ABI is corrected before any candidate is
built. D-Bus `InvocationID` has signature `ay`; exactly 16 bytes are normalized
to 32 lowercase hexadecimal characters. An all-zero pre-start value represents
current absence. Any other shape or length is rejected. Real systemd-255
fixtures must cover inactive absence, active self-lineage and structured
`ExecStopPost` final acquisition; the corrected source and wheel identities are
part of the launch commit.

The manager adapter permits only `Reload`, `LoadUnit(exact-unit)`,
`RefUnit(exact-unit)`, `UnrefUnit(exact-unit)` and, later,
`StartUnit(exact-run-unit, "fail")`. It exposes no stop, restart, kill, reset,
enable or generic method passthrough. Each acquisition refs both
`CollectMode=inactive` instances before the first property read, acquires the
complete pair under one boot/manager owner, and unrefs only after its receipt
is durable. The start path repeats the same pinning and retains the run-unit
reference through `StartUnit`. The adapter resolves the systemd well-known
name to its unique D-Bus owner immediately before and after every property
batch and rejects any change; client unique-name identity is not manager
identity.

The installed unit gate proves:

- systemd major version exactly `255`;
- fragment path and raw bytes equal the two accepted templates;
- no drop-in paths or transient overrides;
- strict path absence for both template and both selected-instance drop-in
  directories, not merely empty D-Bus `DropInPaths`;
- load state `loaded`, active state `inactive`, substate `dead`;
- no queued unit job and no invocation ID;
- exact `ExecStart`, `ExecStopPost`, closer `ExecStart`, user/group/umask,
  delegation, lifecycle, timeout, kill, OOM, protection and path properties;
- all three Python commands use isolated `-I -B`, so manager `PYTHONPATH`,
  `PYTHONHOME` and user-site state cannot precede the installed environment;
- the complete raw property mapping and the normalized configured-pair digest;
- exact `FragmentPath`, `DropInPaths`, unit object path, `Job`,
  `InvocationID`, boot ID and full manager version.

`systemd-analyze verify` runs only after the final projection paths and mounts
exist, so missing pre-install `ExecStart` paths are not misclassified as a
candidate defect.

The pre-start absence gate proves:

- external and invocation nonce claims absent;
- `control/invocation`, raw rows, artifacts and dynamic terminal facts absent;
- no W3 process or delegated job/supervisor cgroup;
- no `START_ISSUED` ledger entry, plus current manager/nonce/terminal/process/
  cgroup absence; it does not infer a historical “never started” claim from an
  inactive snapshot;
- accepted root remains exact `43 cells / 172 jobs / 0 formal`;
- read-only composition inspection with the live configured pair returns
  `LAUNCH_READY`, `filesystem_mutated=false`.

The top-level installed receipt has state
`INSTALLATION_ACCEPTED_NOT_STARTED`, binds every subordinate raw receipt SHA,
and records `formal_jobs_started=0`. It carries no implicit start permission.
Before dispatch, K3 authority/installation/nonce publications, K5 run/closer
fragments and all four drop-in absence paths are reopened around the complete
loaded-manager pair. Projection, environment, dry-root, process/cgroup/nonce
absence and runtime-account facts are then reacquired, followed by publication
and loaded-manager checks again; a stored manager receipt alone is never a
launch capability.

## 8. Human authorization and first `StartUnit`

After the top-level installed receipt is independently verified, a separate
canonical authorization records:

- exact launch ID, authority, installation and installed-acceptance SHAs;
- the verbatim authorizing user statement, task event identity and UTC time;
- the fixed revised plan SHA, selection key, user preparation-commit SHA and
  exact root-owned selection receipt SHA;
- exact unit and one allowed manager action: `StartUnit(unit, "fail")`;
- `retry=false`, `resume=false`, `reuse=false`.

The prospective authorization supplied in the active task on 2026-07-23 is not
misrepresented as approval of then-unknown receipt hashes. It authorizes the
unique first candidate that later satisfies all of these facts: exact fixed
reviewed launch-source commit; exact accepted problem dry root and native
record; the unique candidate selected no-replace by
`RootCandidateSelectionOwner` for the derived selection key; candidate built
by the fixed reviewed builder; two fixed-source reviews with P0=0/P1=0; root
installation state
`INSTALLATION_ACCEPTED_NOT_STARTED`; and an independently reopened exact
receipt DAG. A missing or non-exact root selection receipt, or a second
selection/nonce under its closed root-owned key, makes authorization unusable.

`StartPermitOwner` consumes that authorization exactly once. In one root
process it:

1. reacquires and verifies the full installed, environment, mount, manager,
   dry-root and absence gates;
2. creates and fsyncs `START_ISSUED` with `O_CREAT|O_EXCL`, binding the
   authorization, boot ID, full manager version, exact unit, installation and
   fresh pre-start receipt plus the exact loaded-manager receipt SHA;
3. after durable issue, reopens K3/K5 publications and reacquires the complete
   run/closer loaded-manager pair on the same manager identity; any failure is
   consumed unknown state and no manager reference or start call occurs;
4. calls D-Bus `StartUnit("scion-w3@<launch-id>.service", "fail")`;
5. if the call returns, persists `START_RETURNED` with its exact job object
   path; if D-Bus returns a definite error, persists `START_REJECTED` with a
   bounded canonical error-name/message projection.

The durable `START_ISSUED` record is the one-shot spend. A crash, timeout or
lost response after it exists yields `START_DISPATCH_UNKNOWN`; inspection may
continue, but the call is never reissued. Any existing issue/attempt record
causes `start` to reject unconditionally. The tool does not retry, restart,
stop, kill or claim success. The systemd run process owns nonce claim and
execution. `START_REJECTED` is a definite consumed terminal dispatch result,
not an unknown result and not permission to retry.

The installed dispatcher verifies before nonce claim that the exact
`START_ISSUED` receipt is readable from the root acceptance store, matches its
launch/installation/unit and current systemd self-lineage, and that the
pre-claim environment probe succeeds. A missing or mismatched receipt is a
pre-claim refusal. The thin installed tool seals a one-to-one exit-status ABI
for typed pre-claim failures and writes no problem-root evidence:

```text
70 START_PERMIT_REFUSED
71 ENVIRONMENT_INTEGRITY_REFUSED
72 INSTALLED_IDENTITY_REFUSED
73 SYSTEMD_LINEAGE_REFUSED
```

Only the exact typed exception owner may emit its assigned status; unexpected
exceptions, signals and all other statuses are outside this ABI.

Monitoring is read-only and normally every three minutes. `inspect-terminal`
prints canonical unit and terminal-chain progress without causing another
manager action or writing a receipt. Root-only `accept-terminal` may persist
that report only after independently reacquiring its facts. If `run` exits
before nonce claim or terminal-root creation, it writes no problem root;
`accept-terminal` instead persists `PRECLAIM_REFUSED` in the root terminal
ledger only when exact `Result=exit-code`, `ExecMainCode=CLD_EXITED`, one
assigned `ExecMainStatus`, no nonce claim and no terminal root all agree. The
failure class is mechanically derived from that status and is therefore
reconstructible after process exit. Any other claim-free exit/signal/crash is
persisted separately as `PRECLAIM_TERMINATION_UNKNOWN`. Both consume the
one-shot start and are terminal no-retry classifications.

Terminal acceptance requires:

- exact one external/root nonce claim;
- `RAW_COMPLETE / UNIT_DRAINED / UNIT_FINAL / COMPLETE / CLOSED`;
- exact 172 opaque rows and no incomplete fact;
- both units terminal with the structured accepted `ExecStopPost` result;
- exact three artifacts;
- independent Warehouse replay/analysis reproducing accepted bytes;
- no remaining supervisor/job cgroup;
- full authority, installation, environment, sealed-store and manager
  identities unchanged.

A nonzero or incomplete result is preserved and analyzed; it is never
automatically rerun.
