## Decision

The previous E1 implementation and all earlier cancellation-correction designs
are rejected. In particular, the candidate at Python source SHA-256
`a9a129f2b5482efe8cfd6e08e192e0134ff0754c77a73d2136b7d5eda63a26a9`
could lose an FD after a successful kernel return but before Python assignment,
could retry a reused FD number after `close`, and could retain a locked session
through an exception traceback. The broader native designs then attempted to
solve those defects with CPython audit, tracing, monitoring, frame-offset,
signal-policy, loader, seccomp, and hostile-callback controls. Those controls
are rejected too: they exceed E1, make ordinary refactoring an activation gate,
and add framework noise without improving the research loop.

The replacement is deliberately narrow:

1. one small native owner installs every successfully created E1 descriptor in
   a preallocated strong record before Python can run again;
2. one outer native call enters one accepted synchronous E1 body and settles
   every live record before a return or exception can escape;
3. one one-shot plan and a small native role transition prevent replay,
   cross-thread use, and out-of-order E1 operations;
4. E1 acceptance uses only `E1_ACCEPTANCE_ONLY`. It does not claim that the
   later E2-E6 production composition, verifier transfer, recovery, or reopen
   topology is designed or runnable.

This is descriptor-lifecycle safety, not a new scientific gate or an in-process
sandbox. It adds no model call, retry, budget, cap, truncation, context
compression, candidate decision, solver timeout, or experiment stop policy.

## 1. Exact scope and non-goals

This correction changes only the lifetime mechanism below the already frozen
fresh-only activation boundary and parent execution addendum. Their identity
DAG, deterministic staging name, spend-first rule, durable receipt ownership,
SQLite ownership, no-replace publication, and recovery policy remain
authoritative.

It supersedes exactly two parent lifetime statements: the Python
`source_snapshot.py` private registry is no longer the strong owner of live E1
descriptors, and Python-level settlement/finalization is no longer the final
close boundary. The parent's E1-E6 operation identities and problem/core
ownership remain design input, but no live E1 session is handed to E2 in this
acceptance slice. That handoff requires the later production-composition
addendum named below.

E1 acceptance covers this exact synchronous sequence:

```text
external accepted launch authority
  -> exact trusted e1_bootstrap._run_acceptance issuer
  -> one canonical startup binding and E1AcceptancePlan
  -> native run_e1_acceptance()
     -> exact installed Python E1 body
        -> use the already pinned parent and acquire its lock
        -> create exact offline staging inode
        -> perform closed descriptor-relative observations
        -> explicit close-only, staging-retained E1 settlement
     -> closed E1AcceptanceResult(staging_retained=true)
```

The acceptance body creates no SQLite connection, receipt writer, verifier
child, publication permit, target rename, recovery session, or production
activation. It returns no live descriptor, capability, selector, dispatcher,
session, path authority, or native record.

The following are explicitly outside this design:

- hostile Python, hostile extension modules, arbitrary native threads, memory
  corruption, direct third-party `close`, native `longjmp`, `pthread_cancel`,
  and fatal synchronous signals;
- a seccomp, audit, monitoring, trace/profile, frame-offset, bytecode-offset,
  import-hook, ELF/loader, W^X, ptrace, or callback sandbox;
- supported `fork` continuation, Python at-fork callbacks, verifier-child FD
  transfer, E4-E6 process topology, production recovery, and production reopen;
- race-free deletion of a name that may be concurrently replaced. Linux has no
  conditional `unlinkat` by expected `(device,inode)`, so E1 acceptance never
  unlinks its staging name;
- physical power-loss claims beyond the parent contract's existing durable
  artifact rules.

The accepted E1 composition is trusted, exact source from the accepted pushed
commit. It is reviewed to contain no fork, thread creation, async task,
generator, coroutine, signal-handler installation, tracing, or deferred
authority continuation. The native boundary still rejects an authority call
from a thread or process epoch different from the one that entered the scope.

## 2. External authority and immutable installation

E1 creates no launcher or second root of trust. Existing Scion launch authority
must first verify the clean pushed commit and the exact accepted source bundle.
The sole accepted issuer is
`scion.fresh_activation.e1_bootstrap._run_acceptance` at the exact source hash
in that bundle. It is the first activation call in a fresh process and invokes
exactly:

```text
_install_e1_acceptance(canonical_startup_bytes, canonical_plan_bytes)
run_e1_acceptance()
```

The private names are composition boundaries, not a security claim against
hostile Python. The issuer and its process are trusted exact source under the
threat boundary in section 1. The startup binding prevents accidental source/
plan mismatch; it is not claimed to authenticate an adversarial caller. No
other call site exists in the accepted composition.

`canonical_startup_bytes` uses domain
`scion.fresh-activation.e1-startup-binding.v1`, canonical UTF-8 JSON, one
terminal LF, sorted exact keys, no duplicate or unknown field, and binds:

- exact pushed commit;
- this correction's final accepted design SHA-256;
- parent execution-addendum SHA-256 and fresh-only-boundary SHA-256;
- native extension source and built-binary SHA-256;
- exact E1 body and every authority-bearing Python module/source SHA-256;
- canonical `E1_ACCEPTANCE_ONLY` composition-root SHA-256;
- interpreter executable identity and supported CPython ABI;
- exact issuer module/function/source SHA-256;
- process-start identity and a random one-use binding ID;
- exact canonical `E1AcceptancePlan` bytes and SHA-256.

The native extension accepts the binding once, rejects noncanonical bytes and
unknown fields, rechecks the installed exact body/module/source identities,
stores the exact E1 body and operation table, and changes installation state
`UNINSTALLED -> E1_READY`. A second install, a mismatched binding, or a binding
replay fails before a plan or descriptor exists. The binding is not an
experiment budget; it is one activation-authority capability. Installation
consumes its canonical plan bytes and creates
the sole opaque `READY` plan record. There is no Python plan constructor and no
API for a caller to replace campaign, path, source, or operation fields.

One fresh E1 acceptance process admits exactly one binding, one plan and one
scope. Its terminal installation state is `E1_SPENT`; that process can never
return to `UNINSTALLED` or `E1_READY`. A later separately authorized activation
must start a new clean process. This is process isolation, not retry.

Only the `E1_ACCEPTANCE_ONLY` composition is recognized in this slice. Names or
dormant entries for fresh production, recovery, reopen, verifier, or
publication are rejected rather than silently accepted for future use. A later
fixed-hash addendum must extend the native record and bind the complete E1-E6
composition before any production bootstrap becomes runnable.

## 3. Closed plan and scope lifecycle

`E1AcceptancePlan` contains only closed scalar identities already authorized by
the parent contract: campaign/cutover identity; one normalized root-to-parent
component vector; expected parent device/inode/`STATX_MNT_ID`; target basename;
deterministic staging basename; and required policy/source digests. Every path
component and basename is nonempty canonical UTF-8, contains no slash, NUL,
`.` or `..`, and is bound by the startup SHA. It contains no callback, function,
module, raw FD, caller-selected path, environment lookup, generic mapping, or
caller-selected operation.

The native owner keeps a consume-once plan table:

```text
READY -> ENTERED -> SPENT
```

`run_e1_acceptance` atomically consumes `READY -> ENTERED` before calling
Python. Every terminal path changes it to `SPENT`; it never returns to `READY`.
Failure before scope entry consumes nothing only when no plan state or kernel
resource changed. Once entry begins, interruption, validation failure, or
settlement failure is terminal and cannot be retried as the same plan.

The outer native call preallocates the process's sole `CompletedScopeRecord`,
assigns the binding-derived nonzero `scope_generation`, and records:

- process epoch and process-start identity;
- exact issuer `PyThreadState` and native thread ID;
- startup binding ID, plan SHA and composition-root digest;
- current role and terminal outcome;
- every slot state and terminal close fact;
- the first integrity or syscall failure, if any.

The record is keyed by `(process_epoch, scope_generation)` and exists before
the first descriptor-producing operation. There is no generation counter to
wrap because the process admits one scope. No memory allocation is required to
settle its slots or publish its in-process terminal fact.

Nested scope entry is rejected. Inner E1 operations require the same process
epoch, scope generation, issuer thread, startup binding, and next role transition.
They do not inspect Python frames, bytecode offsets, trace state, or module
globals. The exact installed body and a private native dispatcher are the
composition boundary. `run_e1_acceptance()` takes no Python plan or path
argument; it consumes only the installed opaque plan.

## 4. Native descriptor owner

Each scope has exactly three named slots:

- `ROOT_ANCHOR`;
- `PINNED_PARENT`, which is also the sole lock-owning OFD;
- `STAGING_MAIN`.

There is no generic slot allocator and no API that accepts an integer FD.
The body receives one opaque, non-serializable `E1ScopeSelector` containing
only the scope generation and a random native cookie. It has no FD/slot/path
field, getter, close method, finalizer, weak-reference support, or cross-process
meaning. The registry, not the selector's lifetime, owns resources.

Before calling the Python body, the outer native function executes the exact
`PIN_PARENT` transition. It opens `/` with `O_PATH|O_DIRECTORY|O_CLOEXEC` and
installs the successful return immediately in `ROOT_ANCHOR`. It then joins the
already validated plan components with `/` and calls `openat2` relative to that
anchor using `O_RDONLY|O_DIRECTORY|O_CLOEXEC` and
`RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV`.
It installs the successful return immediately in `PINNED_PARENT`, then requires
`fstat`/`statx` device, inode, type and mount ID to equal the plan. Drift enters
close-only settlement before Python is called. Thus the first authority-
producing syscall is covered by the same syscall-to-slot invariant; Python
never supplies or observes the parent FD.

Every descriptor-producing operation is one native function that:

1. verifies the installed scope, issuer thread, process epoch, slot state and
   exact next role; body-requested operations also verify the selector cookie;
2. performs the Linux syscall with atomic close-on-exec semantics
   (`O_CLOEXEC`, `F_DUPFD_CLOEXEC`, or an equivalent accepted primitive);
3. on failure, records the typed error while the slot remains `EMPTY`;
4. on success, installs the returned integer and its expected identity in the
   named slot before returning to Python;
5. validates the required `fstat`/lock/identity facts from the owned slot;
6. advances the native role only after the operation's complete postcondition.

The function holds the GIL, does not release it, calls no Python callback, and
does not check pending Python exceptions between the successful syscall and
slot installation. Therefore an arbitrary CPython `BaseException` delivered at
the next Python bytecode boundary cannot observe an unowned successfully
returned FD.

Descriptor-relative read, sync, lock, and observation calls take the sole opaque
selector and operate through fixed slots. Python never receives, duplicates,
inherits intentionally, or closes a raw FD. The accepted source table contains
no `os.close`, `os.dup*`, raw `fcntl`, `subprocess`, multiprocessing, or fork
call in the E1 body.

## 5. Close-once settlement

Settlement is native and close-only. It closes owned descriptors and releases
the lock, but never calls `unlink`, `rename`, link, create, reopen, publication,
receipt, or recovery. If `STAGING_MAIN` was created, the closed result records
`staging_retained=true` plus its already copied closed identity facts. This
avoids claiming an impossible race-free conditional unlink by inode.

For every owned slot, settlement performs:

```text
EMPTY       -> EMPTY
OWNED(fd)   -> CLOSE_ISSUED(no fd retained) -> CLOSED(close result recorded)
CLOSED      -> CLOSED
```

The owner clears the reusable integer from authority state and marks
`CLOSE_ISSUED` before invoking Linux `close(2)`. It invokes `close` exactly
once. It never retries after `EINTR` or any other error, because on Linux the
descriptor may already be closed and its integer may be reused. A close error
poisons the scope and is preserved in the completed record; it cannot authorize
a second close.

The accepted body completes `fsync(STAGING_MAIN)` and `fsync(PINNED_PARENT)`
before requesting normal settlement. Settlement then closes `STAGING_MAIN`,
closes `PINNED_PARENT` to release its lock, and closes `ROOT_ANCHOR`. Exceptional
settlement follows the same close order without attempting new sync or namespace
mutation. Cleanup continues through all independent slots after the first
failure and records the first error plus a closed per-slot terminal vector. It
does not allocate, call Python, or replace the original exception.

The outer native call enforces closure on every exit:

- normal body return with all roles terminal: verify no live slot, mark plan
  `SPENT`, and return one closed
  `E1AcceptanceResult(staging_retained=true)`;
- normal body return with a live or nonterminal record: perform close-only
  settlement, mark `SPENT`, then raise typed `E1IntegrityError`;
- escaping Python `BaseException`: fetch and preserve its exact exception,
  traceback, and cause/context state; perform close-only settlement and mark
  `SPENT`; store the cleanup summary only in the preallocated completed-scope
  record; restore and re-raise the original exception without attaching a
  selector, frame, wrapper exception, or new cause/context;
- impossible C-API result/error inconsistency: settle first, mark the native
  runtime permanently poisoned, and terminate the process after recording the
  in-process terminal fact as far as safely possible.

Because settlement occurs inside the still-active outer C frame, a retained
traceback cannot retain a live resource owner. Python object finalization is not
part of the safety argument.

The retained staging inode is not accepted production state and E1 never deletes
it. Each acceptance case runs in a disposable externally owned test root; only
after the E1 process has terminated may the external test harness delete that
whole root. A future production exact-inode cleanup or E2 handoff requires a
separately frozen namespace/isolation design and cannot inherit an unlink claim
from E1 acceptance.

## 6. Roles and operation authority

The E1 acceptance operation table is literal and cannot grow during
implementation:

| Operation | Source -> target role | Native work | Slots affected |
|---|---|---|---|
| `PIN_PARENT` | `SCOPE_ENTERED -> PARENT_PINNED` | fixed `/` open; plan-bound `openat2`; `fstat/statx` identity | install `ROOT_ANCHOR`, `PINNED_PARENT` |
| `LOCK_AND_CONFIRM_ABSENCE` | `PARENT_PINNED -> LOCK_HELD` | `flock(LOCK_EX|LOCK_NB)` on parent; nofollow `statx` requires target and staging absent | no new slot |
| `CREATE_STAGING` | `LOCK_HELD -> STAGING_CREATED` | parent-relative `openat2` with `O_CREAT|O_EXCL|O_RDWR|O_CLOEXEC`, mode `0600`, `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV`; `fstat` | install `STAGING_MAIN` |
| `OBSERVE_AND_SYNC` | `STAGING_CREATED -> OBSERVED_SYNCED` | closed fixed observation; `fsync` staging then parent | no new slot |
| `SETTLE_STAGING_RETAINED` | `OBSERVED_SYNCED -> SETTLED` | close-once staging, parent/lock, root; no namespace operation | terminalize all slots |

`PIN_PARENT` is executed by the outer native call before the Python body. The
body can request only the remaining four exact operations through its one
selector. No role or syscall family is caller-selected. Wrong role, selector,
thread, process epoch, or second use poisons the scope and permits only the same
close-only settlement.

Every nonterminal role has one failure edge to `SETTLEMENT_ENTERED`; there is
no edge back to an earlier role.

## 7. Thread, fork, and process rules

E1 does not require the whole interpreter to have only one thread. It requires
all authority operations for one scope to execute on the exact issuer thread
that entered `run_e1_acceptance`. The trusted E1 body creates no thread and
does not hand selectors to another thread. A wrong-thread call cannot mutate a
slot and poisons an active scope for close-only settlement.

Fork is unsupported by the E1 accepted composition. The source/composition
manifest contains no fork producer, and E1 tests do not treat child continuation
as successful activation. The extension nevertheless registers a minimal
`pthread_atfork` child handler as a leak-safety backstop. Its fixed preallocated
registry requires no inherited mutex: in the child it invokes `close` at most
once for each snapshot-owned integer, clears all records, advances the process
epoch, and marks the runtime child-poisoned. It performs no allocation, Python
call, unlink, sync, receipt, or continuation. The child must exit without using
E1 authority.

This handler is not the E4 verifier topology and does not make Python at-fork
callbacks or arbitrary external fork safe. A later E4-E6 addendum must define
any deliberate descriptor transfer and child lifecycle independently.

## 8. Failure classification

E1 records only closed deterministic outcomes:

- `E1_ACCEPTED_CLOSED` — expected roles completed and every slot is terminal;
- `E1_BODY_FAILED_CLOSED` — the original body exception escaped after closure;
- `E1_INTEGRITY_FAILED_CLOSED` — role, identity, selector, thread, or closure
  invariant failed after close-only settlement;
- `E1_PROCESS_POISONED` — safe continuation cannot be proved.

`E1_ACCEPTED_CLOSED` is the normal closed result. On a body exception the caller
sees only the restored original exception. The other enum and per-slot cleanup
facts remain passive diagnostics in `CompletedScopeRecord`; after no active
scope exists, `read_last_completed()` may return one immutable scalar copy with
no selector, FD, path capability, callback or continuation authority. It cannot
change plan/runtime state and its absence never changes acceptance.

These are activation/infrastructure facts. They are not Contract,
Verification, Protocol, Decision, or scientific gate outcomes. They do not
schedule a retry. This one-scope process cannot begin another activation under
any outcome; a later externally authorized activation requires a new clean
process.

SIGKILL, process crash, or machine loss cannot run userspace cleanup. The
kernel closes process descriptors. Any deterministic staging inode is handled
only by the parent contract's separately authorized recovery/reopen design;
E1 acceptance itself does not reopen it or call it success.

## 9. Implementation ownership

The implementation may add one cohesive native extension and one narrow Python
adapter under `scion/fresh_activation/`. It must not add another generic helper
layer, duplicate the parent path/identity rules, or create Warehouse/CVRP
semantics in generic core.

Required implementation artifacts are:

- native owner, fixed slot/role table, plan table, completed-scope record, and
  at-fork child backstop;
- exact `E1_ACCEPTANCE_ONLY` composition manifest and startup-binding verifier;
- one synchronous Python acceptance body using only opaque selectors and closed
  facts;
- a typed closed result and typed integrity/cleanup facts;
- focused tests and one acceptance report binding design, source, binary, test,
  and reviewer hashes.

No production composition symbol may be exported or reachable in this slice.
Existing rejected Python ownership code remains rejected evidence and must not
be staged as part of this implementation.

## 10. Acceptance tests

Focused tests must exercise the exact built extension and accepted composition:

1. successful acquire/create/observe/settle returns closed
   `staging_retained=true` facts and no raw FD;
2. injected `BaseException` at every Python bytecode boundary after each native
   operation closes every slot before the traceback escapes, with each injection
   case in its own fresh process;
3. retaining the exception and traceback retains no live record or selector
   authority;
4. syscall failure before FD return leaves the named slot empty;
5. successful FD return is installed before a pending Python exception runs;
6. close returning success, `EINTR`, and another error each causes exactly one
   close call and never closes a deliberately reused integer;
7. cleanup continues across independent slots, preserves the original body
   exception, and exposes cleanup facts only through passive
   `read_last_completed()`;
8. normal early return with live roles settles and raises typed integrity
   failure;
9. plan replay, selector replay, wrong role, wrong thread, wrong process epoch,
   nested entry and startup-binding replay fail closed;
10. fork child backstop closes the snapshot-owned descriptors once, exposes no
    continuation authority, and exits; the parent record remains valid;
11. source/composition/startup-binding hash drift blocks installation before any plan or
    descriptor exists;
12. there is no reachable E2-E6, verifier, recovery, reopen, publication, model,
    retry, budget, cap, truncation, or scientific-gate behavior;
13. close-only settlement never deletes a retained staging name or a same-name
    replacement inode; external disposable-root cleanup begins only after the
    E1 process exits.

Tests must also scan the accepted E1 source/composition for forbidden raw-FD,
fork/thread/async/deferred-authority sites and verify the exact operation-to-
role table. This is a composition acceptance check, not a runtime inspection
gate imposed on research candidates.
