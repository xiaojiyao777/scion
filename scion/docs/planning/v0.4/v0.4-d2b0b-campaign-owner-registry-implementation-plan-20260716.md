# D2b.0b.F Campaign owner Registry implementation plan — 2026-07-16

## Authority and scope

This plan implements the next dormant D2b.0b.F responsibility layer under:

- `design/scion-architecture-v3.md`;
- `v0.4-d2b0b-global-durable-owner-migration-plan-20260716.md`;
- `v0.4-d2b0b-foundation-transaction-publication-correction-20260716.md`;
- `v0.4-d2b0b-focused-owner-store-implementation-plan-20260716.md`.

It is the implementation review required by the correction contract before
adding `core/campaign_owner_registry.py`. Three independent read-only audits
found no reason to change the V3 or frozen storage contract, but found four
API seams that must be closed before code is accepted:

1. commit classification and startup restore need focused-store readers over
   one independent consistent snapshot; the Registry must not own SQL or row
   decoding;
2. conflict refresh must reload through the Registry's bound stores rather
   than accept a caller-constructible token as durable authority;
3. all durable hypotheses and the derived current-H index must live inside the
   one immutable owner root; and
4. creation view, receipt, and publication composition must wait for the
   champion and proposal-attempt transaction participants that can bind the
   exact authorization identity into the write fact and receipt.

This package remains dormant. It adds no schema, production composition import,
writer migration, lease mutation, experiment, research gate, retry, attempt
limit, budget, cap, timeout, cutoff, or truncation.

## Responsibility boundary

```text
durable_owner values
        ^
        |
focused Branch/H stores -- fixed SQL and strict decode
        ^
        | Registry-only snapshot readers
        |
CampaignOwnerRegistry -- views, root, staging, publication, refresh
        |
        +-- owner_transaction -- permits, receipt ledger, exact closure
        +-- sqlite_connection -- authority, transaction and snapshot lifecycle
```

`CampaignOwnerRegistry` owns only Campaign-local owner coordination. It does
not own:

- Branch/H SQL, storage columns, canonical encoding, or row decoding;
- SQLite connection, authorizer, thread/Context, commit, or snapshot mechanics;
- owner-table permits or receipt issuance;
- Branch state-machine, scheduler, Decision, Protocol, recovery, or research
  policy;
- champion locking, proposal-attempt policy, schema, event lineage, provider,
  workspace, or filesystem operations.

`CampaignManager` remains orchestration, `LineageRegistry` remains append-only
audit lineage, and `BranchController` retains transition semantics over
detached values. None becomes a second owner root.

## Exact immutable root

The only schedulable local owner reference is:

```text
_CampaignOwnerState(
  branch_slots: immutable owner-id -> _BranchSlot,
  hypothesis_slots: _HypothesisSlots(
    by_id: immutable hypothesis-id -> _HypothesisSlot,
    current_by_branch: immutable branch-id -> hypothesis-id,
  ),
  publication_generation: int,
)
```

Each private slot contains one immutable revisioned token and one internally
rebuilt detached projection. Slots, mappings, roots, and stored projections are
never returned. Public reads capture the root once under the owner lock and
return a new value reconstructed from its token.

`hypothesis_slots.by_id` contains every restored durable H owner, and later will
contain every owner legally published by the authorization-bound creation
slice, not only the active row. `current_by_branch` is derived inside the same
successor root from exact `status == "active"` rows. Restore and staging require:

- every H parent Branch exists in the same complete root;
- every current index target exists and points back to its Branch;
- at most one active H exists for a Branch; and
- no non-active H appears in the current index.

The global root generation begins at zero when the restored root becomes live.
Every successful owner commit or higher-revision durable refresh advances it
exactly once. Any old unclaimed view therefore fails even when it names an
owner unaffected by a concurrent multi-owner publication. This is deliberate:
a view belongs to one complete captured Campaign owner root.

## Startup and availability state

One non-reentrant owner mutex is also the condition mutex for startup leases.
This avoids a startup-lock/owner-lock inversion. The phase has no reverse edge:

```text
OFFLINE_STANDALONE
-> DRAINING_STANDALONE
-> RESTORING
-> LIVE_REGISTRY
```

Availability is orthogonal:

```text
CLEAR | TRANSITION | PERMANENT_HOLD
```

`PERMANENT_HOLD` is not cleared within the process. Recovery is restart plus a
new complete durable restore before scheduling.

`begin_restore()` atomically moves to `DRAINING_STANDALONE`, permanently denies
new standalone issuance, and waits on the condition for already-entered
standalone transactions to finish commit/rollback and close. It has no polling,
retry count, or wait cutoff. It then enters `RESTORING` and, before returning,
performs the complete durable load described below.

The former caller-fed `restore_branch()` / `restore_hypothesis()` seam is not
implemented as a public token installer. The Registry instead performs one
authority-verified consistent read snapshot and asks the two focused stores to
strictly decode their complete inventories inside that same snapshot. It builds
an invisible restore root only after validating all cross-owner/current-H
relations. Any read or validation failure publishes no partial root and enters
`PERMANENT_HOLD`.

The exact startup API is:

```text
begin_restore() -> loaded_restore_authority
seal_live(loaded_restore_authority)
```

`begin_restore()` issues no authority until the complete snapshot closes and
the invisible root passes every validation. Its returned sealed authority binds
the exact prepared-root identity. A load failure enters `PERMANENT_HOLD` and
returns no authority. `seal_live()` rejects a foreign, reused, or spent
authority. This leaves no public partial-load or replacement-authority seam.

`seal_live()` accepts only the exact loaded restore authority. Under the owner
lock it first irreversibly spends that authority, then publishes the complete
restored root once, and enables `LIVE_REGISTRY` last. A fault between those
steps leaves the Registry non-schedulable and cleanup either proves the exact
published root or enters `PERMANENT_HOLD`; it can never reuse the authority or
double-seal. Restore and standalone authority can never be reissued.

The dormant package records the standalone lease protocol but adds no public
standalone mutation wrapper. Its private entry/exit seam has zero production
importers until that focused wrapper is implemented and reviewed.

## View lifecycle

The module defines sealed exact types:

- `BranchMutationView`;
- `HypothesisMutationView`.

Mutation acquisition is public only in `LIVE_REGISTRY/CLEAR`. It captures the
exact token, a detached mutable target, and the complete root generation. View
state lives outside the immutable root in a weak sealed issuance registry:

```text
ISSUED -> CLAIMED -> SPENT
```

All views are validated as a complete nonempty set and their exact cleanup set
is preallocated before any state changes. Under the owner lock, one assignment
first raises `TRANSITION` as the claim latch; only then may per-view state move
to claimed. Duplicate objects, duplicate owner identities, another Registry/
database, another generation, wrong token, wrong thread, and spent views are
rejected before that latch and before `BEGIN`.

Once the claim latch is raised, cleanup spends the complete prevalidated
requested set, including any member whose individual claim assignment was
interrupted. A signal/trace fault can therefore leave only a guarded scope or a
permanent hold, never a partially claimed set while availability remains clear.

Every claimed view becomes spent on BEGIN failure, body failure, CAS conflict,
receipt/staging failure, rollback, commit failure, or success. It never returns
to issued. A caller may retain a detached target reference, but that value is
not authority and cannot replay the spent view.

### Creation boundary

This Registry sub-slice implements no creation view, creation receipt
consumption, creation staging, or creation publication. It is the mutation/
publication Registry foundation, not completion of the full correction matrix.

Branch creation authority must originate from a future connection-scoped
champion participant that rereads and exact-matches the durable champion in the
same transaction. H creation authority must originate from a future proposal-
attempt/continuation participant that exact-checks the Branch owner and unbound
attempt before binding it. A caller-supplied champion ID, Branch token, attempt
ID, or context dataclass cannot be sealed by the Registry and promoted into
authority.

Defining a sealed placeholder witness or a test-only Registry issuer is also
insufficient. The current insert write facts and receipts do not bind a
champion/proposal-attempt authorization identity, so that witness would test
plumbing that does not satisfy the frozen authority contract.

The later creation-participant slice must atomically add the durable
authorization issuer, focused-store validation, authorization-bound write
fact/receipt, Registry creation view, staging, classification, and one-root
publication. Until then, both creation-receipt consume functions and both
focused `insert_once_in()` methods retain zero production callers. D2b.0b.C
cannot activate creation before that slice closes.

## Complete owner transaction

The only owner commit entry is:

```python
with registry.owner_transaction(
    branch_views=(branch_view,),
    hypothesis_views=(),
) as scope:
    scope.compare_and_stage_branch(branch_view)
```

The Registry constructs and privately owns the focused stores bound to its
exact `CampaignDatabaseAuthority`. Entry accepts no path, store, callback,
caller-opened transaction, replacement authority, SQL, token map, or install
function. Scope exposes the active transaction for future non-owner
participants and two fused typed owner operations:

```text
compare_and_stage_branch(view)
compare_and_stage_hypothesis(view)
```

Each fused operation calls the private Registry-owned focused store, consumes
the returned receipt, validates it against the claimed view, and stages its
replacement without returning the receipt. Scope exposes no focused store,
receipt, `commit()`, or install API. This removes forgotten staging from the
normal caller surface while ledger closure still rolls back an interruption
between the durable CAS and internal staging.

This fused scope API is an explicitly reviewed strengthening of the correction
document's illustrative external-store sketch. It preserves the focused store
as the SQL/decoder participant while making `campaign_owner_registry.py` its
only production caller and keeping `insert_once_in()` unreachable in this
mutation-only slice.

The fixed sequence is:

```text
owner lock
-> LIVE/CLEAR/reentrancy check
-> capture old root
-> validate all views and preallocate the complete claim cleanup set
-> raise TRANSITION claim latch
-> mark requested views claimed
-> open coordinated transaction
-> attach exact owner receipt ledger
-> yield scope
-> fused focused CAS/receipt consumption/staging
-> prove claimed == issued == consumed == staged == durable ledger
-> construct complete successor root
-> seal receipt ledger
-> latch commit boundary
-> COMMIT
-> close ledger and deactivate transaction authority
-> one owner-root assignment
-> clear guard from exact published-root identity
-> close connection
-> release owner lock
```

Staging performs every operation that can reject the expected result before
commit: exact view/receipt/transaction/database/kind/ID binding, one-use
receipt consumption, exact `n -> n + 1`, semantic change,
target-to-committed digest equality, detached projection rebuild,
current-H derivation, duplicate rejection, and complete successor-root
construction. The successor root retains no view, receipt, caller target,
cursor, connection, or mutable mapping builder.

Pre-commit closure is nonempty and compares exact receipt identities/counts,
not owner IDs. Owner SQL without a staged receipt, a staged receipt without a
claimed view, a swallowed CAS conflict, or any missing/extra/duplicate receipt
rolls back before the commit latch.

Same-thread snapshot, acquisition, restore, durable refresh, or nested
transaction calls fail with a typed reentrancy error before attempting the
non-reentrant owner lock. Cross-thread/Context scope use also fails closed.

This slice exposes no view-discard API. An issued view becomes unusable through
root generation change or becomes spent after entering a transaction claim
latch; explicit pre-claim cancellation is deferred unless a real workflow
requires it.

## Commit outcomes and cleanup

The result after the commit latch has exactly three classifications:

- `PROVEN_COMMITTED`: commit returned normally, or one new independent
  authority-verified snapshot strictly decodes every receipt owner and every
  row equals its committed token. Publish the prepared root.
- `PROVEN_ROLLED_BACK`: the original connection was still active and completed
  a normal rollback, and that same kind of independent snapshot proves every
  mutation owner equals its exact expected token. Retain the old root and clear
  the guard.
- `UNCERTAIN_OR_MIXED`: ambiguous-commit settlement/close, snapshot, decode, or
  exact-state proof cannot establish one complete outcome. Retain
  `PERMANENT_HOLD`; neither old nor prepared root is schedulable. This does not
  include a close failure after normal commit, capability deactivation, and
  successful local publication; that is a typed cleanup error only.

Before the latch, normal rollback and close prove no committed owner mutation.
Rollback or cleanup uncertainty still enters the permanent hold. Classification
never uses the original possibly open connection and never replays a mutation.
All owners are read through their focused stores inside one shared independent
snapshot.

Normal commit publication is one critical assignment:

```python
self._owner_state = prepared_owner_state
```

No decoding, hashing, copying, mapping construction, policy, SQL, or per-owner
installation occurs after commit. Publication happens after transaction
authority deactivation and before connection close. A later close failure is a
typed cleanup error but cannot suppress the already committed local root.
The Registry clears `TRANSITION` from exact root identity before that close;
cleanup repeats the identity check in `finally`, so an interruption immediately
after root assignment cannot strand a committed, locally published root behind
the transition guard or publish it twice.

Exception precedence follows the correction contract: body/pre-commit errors
remain primary with cleanup chained; commit errors remain primary unless an
unclassifiable outcome raises the integrity hold; proven publication followed
by close failure reports typed cleanup without reverting the root. Spending and
guard safety run regardless of which error is primary.

## Durable conflict refresh

There is no public `refresh(token)` or `install(token)` method. Public refresh
accepts only an exact owner ID. After the failed owner transaction has fully
exited, the Registry reacquires its owner lock, opens one authority-verified
read snapshot, and asks its bound focused store to strictly reload that ID.

Hypothesis refresh additionally loads every durable H for the affected Branch
inside the same snapshot. It applies monotonic comparison to the whole bundle
and rebuilds `current_by_branch` from the resulting complete local `by_id`
state. If a coherent bundle cannot remove an active-H conflict, the Registry
enters `PERMANENT_HOLD`; it never overwrites the current index with one row.
Every bundle row must retain the same affected Branch identity. The bundle must
also contain every local H already owned by that Branch; a moved H, missing
member, or second active H is an integrity hold rather than a partial refresh.

For a durable owner relative to the captured local slot:

- absent local plus a durable row proves incomplete restore or an out-of-bound
  writer and enters `PERMANENT_HOLD` in this mutation-only slice;
- lower revision is ignored;
- equal revision and equal canonical bytes is a no-op;
- equal revision and different bytes enters `PERMANENT_HOLD`;
- higher revision builds one complete successor root, advances the global
  generation once, purges older issued views, and performs one assignment.

A missing durable owner for an existing local slot is integrity failure. A
rejected target is discarded and never replayed. Registry callers cannot pass
SQL, rows, tokens, decoders, or reload callbacks.

Refresh publishes no partial root. If its authority-verified snapshot cannot
open, read, strictly decode, revalidate authority, or close normally, the
Registry enters `PERMANENT_HOLD` while retaining the prior root as
non-schedulable. If an asynchronous fault occurs after the refresh root
assignment, cleanup derives success from exact root identity, does not assign
again, and preserves the single generation increment.

## Focused-store snapshot seam

The focused stores add Registry-only private operations for:

- strict read of one owner from `_IndependentReadSnapshot`;
- strict complete-inventory read from that snapshot; and
- for H only, strict read of the complete affected-Branch H bundle.

They reuse the module's exact fixed SELECT and row decoder. Inventory SELECTs
have deterministic owner-ID order and reject malformed, duplicate, incomplete,
or noncanonical rows. Registry classification calls the per-owner readers;
startup calls both inventory readers while one shared snapshot remains active.

The Registry never imports an SQL constant or decoder. Static AST closure
requires exactly `campaign_owner_registry.py` as the production caller of
these snapshot operations and of the coordinated-session/snapshot lifecycle
internals it needs.

## Implementation sequence

1. Add focused-store snapshot readers and their exact importer tests.
2. Add private immutable root/slot/value builders and root validation.
3. Add startup phase, restore authority, same-snapshot full restore, and
   one-swap `seal_live()`.
4. Add detached snapshots, mutation views, weak issuance, atomic claim/spend,
   and reentrancy rejection.
5. Add scope-owned fused focused CAS/receipt staging for existing owners only.
6. Add exact closure, prepared root, normal commit publication, and cleanup.
7. Add interrupted-commit three-state classification using one shared
   independent snapshot.
8. Add Registry-owned durable refresh and stale-view purge.
9. Freeze all importers and prove no production composition import.

This order keeps the root and authority model visible before transaction
cleanup code is introduced. No new generic helper module or compatibility
facade is added.

## Implementation audit closure

The implemented slice received two independent adversarial code audits before
acceptance. Four concrete corrections strengthen the plan without changing its
responsibility boundary:

- Registry uniqueness is keyed by the authority-verified physical database
  `(device, inode)`, not Python authority-object identity, so two authorities
  for one database cannot create two local roots;
- transaction entry records an `open_attempted` latch before its own
  coordinated open. Only that path may recover a session whose open completed
  before the return value reached the caller; a pre-existing same-authority
  session is rejected and never deactivated, rolled back, or closed;
- standalone release removes the lease idempotently before nested-finally
  inactive/notification cleanup, so a single interruption immediately before
  or after set removal cannot strand startup drain; and
- exact tuple-kind checks, renewable Context-token proofs, preallocated view
  spend, and root-identity finalizers close forged/copy-context and
  post-assignment interruption paths.

Reproduction tests cover each corrected boundary. The Registry remains one
module because root, capability, startup, refresh, and commit classification
share one non-exportable authority state machine; splitting this slice would
expose those invariants rather than establish a new responsibility owner.

## Acceptance matrix

### Startup and root

- phase transitions are one-way and new standalone entry is denied once drain
  starts;
- condition-based drain waits for already-entered commit/rollback **and close**
  without polling or a cutoff;
- Branch and H inventories are decoded in one shared snapshot;
- malformed row, missing Branch parent, two active H for one Branch, or current
  index drift publishes no partial root and holds permanently;
- `seal_live()` performs one root assignment and permanently revokes restore;
- snapshots are detached and root/slot/mapping objects are unreachable;
- no public token-fed restore or install API exists.

### Views and staging

- stale generation/token, wrong Registry/database/thread/Context, duplicate
  view/owner, forged/copy/pickle/subclass, and empty view sets fail closed;
- all claimed views are spent after BEGIN/body/CAS/staging/rollback/commit
  failure and after success;
- signal/trace injection at the claim latch and each individual claim boundary
  never exposes availability `CLEAR` with a partial requested set;
- caller target mutation before staging fails digest equality; after staging it
  cannot alter the prepared root;
- missing, extra, duplicate, wrong-kind, cross-transaction, or forged receipts
  fail before commit;
- mutation enforces exact identity, semantic change, and `n -> n + 1`;
- no creation view/issuer/staging API exists, creation receipt consumers retain
  zero production callers, and focused inserts retain zero production callers;
- focused store classes and `compare_and_swap_in()` have exactly the Registry
  module as their production importer/caller; no store or receipt escapes scope.

### Publication and classification

- body/CAS/closure/BEGIN faults leave durable and local roots unchanged;
- mixed Branch/H success advances all durable rows and performs one root swap;
- commit success plus close failure leaves durable/local revisions advanced;
- commit interruption is classified only through a new connection and one
  shared snapshot;
- complete committed, complete expected, mixed, malformed, snapshot
  failure, settlement failure, and ambiguous-commit close failure cover all
  three outcomes;
- no old schedulable root survives an uncertain post-latch outcome;
- fault injection at commit return, deactivation, classification, and before
  root assignment yields new root, proved old root, or permanent hold only;
- restore-authority spend, startup root swap, and live-phase fault injection
  cannot reuse authority or double-seal;
- root-assignment/guard-clear/connection-close faults derive publication from
  root identity; close failure leaves the published Registry schedulable after
  owner-lock release;
- same-thread public calls inside scope raise instead of deadlocking.

### Refresh and closure

- ID-only durable refresh covers absent-as-hold, lower, equal-same,
  equal-drift, and higher-revision cases plus a three-party monotonic race;
- H bundle refresh rejects a moved H, a missing local bundle member, and two
  active durable H for one Branch;
- Branch/H refresh snapshot open, read, decode, authority-revalidation, and
  close fault injection publishes no partial root and enters hold; a fault
  after root assignment is recognized by identity without double increment;
- no caller token/reload callback can authorize refresh;
- higher refresh advances the global generation once and invalidates old views;
- every effective coherent bundle refresh advances the global generation
  exactly once regardless of how many owner slots changed;
- Registry is the sole production importer of focused stores, mutation-receipt
  consume, ledger attach/seal/close, coordinated transaction lifecycle, and
  snapshot readers; creation-receipt consume retains zero production callers;
- no existing Campaign production module imports the dormant Registry;
- Registry contains no SQL, Branch/H row decode, schema, policy, retry, budget,
  cutoff, gate, cap, or truncation logic;
- focused suites, complete Scion tests, `compileall`, and `git diff --check`
  pass before commit.
