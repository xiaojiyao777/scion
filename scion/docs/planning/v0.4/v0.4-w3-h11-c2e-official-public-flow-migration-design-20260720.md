## 1. 决策摘要

C2e 已删除 `H11RootRetainedAuthority`、`H11RootAuthorizerSession` 和测试依赖的
`_pin_h11_json_source` seam。official tests 仍把这些旧私有对象当作被测 API，因此当前
`root_c2a` baseline 的剩余失败不是 production 授权失败，而是测试仍表达旧的对象边界
和旧 policy。

本文冻结以下迁移原则：

1. official tests 只通过公开 `H11RootAuthorizationFlow` 构造、`authorize_once()`、
   `close()`、`state` 与公开 receipt 观察行为；
2. 需要注入竞态或 I/O fault 时，只允许在 `os.open`、`os.close`、`os.stat`、
   `os.fstat` 的真实 syscall boundary 建 test-only seam；
3. 不调用 production private helper，不构造 private view，不检查 `_slots`、
   `_descriptor`、`_phase_data`；资源清理由 FD 是否失效、close 次数、公开 state 与
   transaction files 是否不存在证明；
4. 旧测试中仍被当前 direct/TREE/SEAL authority graph消费的语义继续拒绝；
5. 只存在于 ARMED diagnostic payload、但不再进入 authority graph 的字段漂移改为
   明确接受测试。不得为了保留旧红灯而新增 production gate。

因此 C 组是 `21 rejection + 7 acceptance`，D 组是 `9 rejection + 2 removed
rejection cases`；被移除的两项并入 non-authority acceptance matrix。E 组只证明公开
Flow 的 no-open 与 rollback lifecycle。迁移过程不得修改 production。

Python 3.12、`-W error` 的完整 official file基线为：

```text
709 passed, 230 failed, 1 skipped
```

其中 C2a exact为`31 passed, 43 failed`；其余187个失败exact分布为C1a 11、C1b1 21、
C1b2 23、C1c 20、C2b 40、C2c 36、C2d 36，主要引用同一批已删除private classes。
本文只闭合43个C2a失败，完成后预期C2a为`74 passed`。全文件不得误报全绿；全部C1
groups与C2b/C2c/C2d必须在C2a完成后，依据
公开Flow lifecycle另起设计审计和迁移。

## 3. C：wire 与 authority drift 的现行边界

### 3.1 仍应在 READY 前拒绝的 exact matrix

以下 21 项使用现有 `_root_c2a_run_public_pre_ready_rejection`，并把 parametrization
冻结为 `(mutation, exact_error_match)`。helper 的 `os.open` guard必须证明执行没有到达
blocking READY FIFO read endpoint。

| Source | Mutations | Exact error |
| --- | --- | --- |
| READY | `missing-present-outputs`, `extra-key` | `H11 PERMIT_READY receipt fields differ from the exact closed set` |
| READY | `schema`, `scenario`, `unit`, `permit-authority-crossbind` | `H11 direct wire schema or phase cross-binding drifted` |
| ARMED | `missing-key` | `H11 run ARMED fields differ from the exact closed set` |
| ARMED | `schema`, `scenario`, `unit`, `actor-boot` | `H11 direct wire schema or phase cross-binding drifted` |
| ARMED | `actor-extra` | `H11 run ARMED actor fields differ from the exact closed set` |
| ARMED | `ready-fifo`, `release-fifo` | `H11 run ARMED FIFO projection drifted` |
| ARMED | `program-none`, `program-extra` | `H11 run ARMED program fields differ from the exact closed set` |
| ARMED | `program-identity-extra` | `H11 run ARMED program identity fields differ from the exact closed set` |
| ARMED | `program-mode-text`, `program-path-bind`, `plan-path-bind` | `H11 SEAL run ARMED plan or program class drifted` |
| ARMED | `plan-sha` | `H11 run ARMED.plan_sha256 must be one canonical SHA-256 digest` |

错误匹配使用 `\A...\Z`，不能用模糊 `raises(InstallerError)` 掩盖首拒 owner 漂移。
每个 case 都必须断言 `FAILED_PREWRITE` 且不存在 `PERMIT.pending`、`PERMIT.json`。

### 3.2 明确接受的 non-authority payload matrix

以下九项不是当前 C2e authority graph 的输入：

```text
stop-environment
cgroup-noncanonical
cgroup-raw
request-type
request-sha
ready-digest
release-digest
request-transaction-path
request-frozen-root-path
```

其中前七项来自旧 ARMED drift test，后两项来自旧 global/frozen alias tests。它们仍受
ARMED exact key-set 约束，但字段值不被 direct、TREE、SEAL、PREFLIGHT、INSTALL 或 top
alias owner解释。一个参数化 public acceptance test必须逐项走真实 FIFO peer 和完整
`_root_c2a_run_public_authorization_flow`，断言：

- `flow.state is COMPLETE`；
- receipt `phase == "permit-committed"`；
- peer只收到 exact `H11_PERMIT_COMMITTED_BYTES`。

测试名必须表达“non-authority ARMED payload drift is accepted”，不能继续使用
`rejects`。如未来确需拒绝其中任一字段，必须先提交新的 owner design、producer
projection 与 isolated negative matrix，不能在本迁移中恢复隐式 policy。

## 4. D：direct/TREE/SEAL 与 retained-view lifecycle

### 4.1 ARMED owner reference

删除“ARMED 必须属于 fixture owner”的旧表述。现行 nonroot 合同是 actual source
uid/gid 与 authorization full reference 精确相等。测试只修改
`AUTHORIZE-RELEASE.json["run_armed"]["uid"]`，通过 public pre-READY helper断言 exact：

```text
H11 run ARMED differs from authorization authority
```

不得 monkeypatch pin helper或合成 private source tuple。

### 4.2 Direct JSON source identity alias

pairwise regular-source identity uniqueness仍属于 direct owner。测试把 authorization 中
PERMIT_READY 的 `device/inode` 设成 authorization source identity；再仅在真实
`os.stat/os.fstat` boundary让 PERMIT_READY observed identity与该授权 reference一致，
使 pin/view proof真实通过并到达 direct uniqueness gate。exact拒绝为：

```text
H11 permit-ready-source class or identity drifted
```

不得直接调用 direct proof helper、构造 view或改 production metadata对象。

### 4.3 TREE acquisition 与 SEAL static role

旧 global/frozen alias cases重新按真实 owner命名和分组：

| Mutation | Owner | Exact error |
| --- | --- | --- |
| ARMED receipt path -> output path | TREE acquisition layout | `H11 acquisition exec-stop-post ARMED path drifted` |
| ARMED receipt path -> frozen root | TREE acquisition layout | `H11 acquisition exec-stop-post ARMED path drifted` |
| exec-stop-post static plan -> permit ledger staging | SEAL static binding | `H11 SEAL static role exec-stop-post plan is unbound` |

三项都使用 public pre-READY helper。旧 request transaction/frozen-root两项不属于
alias inventory，按 §3.2 转为 acceptance，不得偷偷改造成其他 rejection。

### 4.4 Same-byte replacement at the READY boundary

四个 source：`authorization`、`manifest`、`ready`、`armed`，必须通过真实 Flow 与
READY-only peer验证 retained JSON source revalidation lifecycle。唯一允许的竞态 seam：

1. 拦截 Flow 对 `/proc/self/fd/<READY FIFO retained descriptor>` 的 `O_RDONLY` open；
2. 在该 syscall boundary前，把目标 source rename到 displaced path；
3. 在原路径写回完全相同 bytes并恢复完全相同 mode；
4. 继续真实 READY frame读取；
5. Flow 在 frame之后自然执行第二轮 retained-view revalidation并拒绝。

四项 exact error label分别是：

```text
retained H11 authorization manifest drifted
retained H11 harness manifest drifted
retained H11 PERMIT_READY drifted
retained H11 run ARMED drifted
```

断言 `FAILED_PREWRITE`、READY peer无异常、所有被测试记录的 retained FD均已失效、没有
`PERMIT.pending/PERMIT.json`。不得直接调用 `revalidate()`，不得访问 Flow private state。

## 5. E：public Flow no-open 与 partial-open rollback

### 5.1 Static plan/program/request remains unopened

测试走完整 public Flow和真实双 FIFO peer。在 test-only `os.open` spy中将带 `dir_fd`
的relative path通过 `/proc/self/fd/<dir_fd>`解析成absolute observed path，断言
`run_plan`、`run_program`、`request` 从未打开。主线程应观察 exact 23 次 Flow
`os.open`；peer线程的两个 FIFO open必须按thread identity排除，不能混入计数。

最终断言 `COMPLETE`、exact commit frame与三个 forbidden paths 的open计数均为零。

### 5.2 Partial-open failure rollback

三个注入点按公开 Flow 的真实 source/open schedule冻结：

| Failure | JSON source ordinal | successful descriptors before failure |
| --- | ---: | ---: |
| `manifest` | 1 | 1 |
| `ready` | 7 | 16 |
| `armed` | 8 | 17 |

source order exact为：authorization、manifest、install receipt、install manifest、TREE、
SEAL、PREFLIGHT、READY、ARMED。READY 前另有七个directory和两个commit FIFO
descriptors，所以后两项成功计数分别为16、17。

`os.open` 在目标 source边界抛出预先构造的同一 `OSError(errno.EIO, ...)` 实例；公开
Flow必须原样传播该实例，不再沿用旧 session 的 `InstallerError("cannot pin")`/
`__cause__` 合同。`os.close` spy记录每个成功 FD恰好关闭一次。每个 case断言：

- caught exception与注入实例对象相同；
- attempted source prefix与上述顺序精确相等；
- successful FD集合唯一且数量分别为1、16、17；
- 每个FD已失效且close count exact为1；
- `flow.state is FAILED_PREWRITE`；
- 再调用 `flow.close()` 不增加任何close count；
- `PERMIT.pending`、`PERMIT.json`、`PERMIT-LEDGER.pending`、
  `PERMIT-LEDGER.json` 全部不存在。

失败均发生在READY endpoint前，不启动peer，不设置timeout或retry。
