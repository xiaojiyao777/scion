# v0.4 Warehouse W3 Fixed-Arm Matrix Design

*Date: 2026-07-18*
*Status: design candidate; no W3 execution authority until independent review and manifest preflight are accepted*
*Architecture authority: `scion/design/scion-architecture-v3.md`*

## 1. Decision and scientific question

W3 is a no-LLM, fixed-candidate posterior decomposition of the accepted R3
Warehouse research trajectory. It asks which complete R3 treatment bundle
accounts for the screening gain and validation loss:

1. the R3 destroy/rebuild replacement alone;
2. the R3 directed-merge replacement alone;
3. their cumulative composition; or
4. neither component reproducibly, relative to the frozen champion.

W3 does not generate a candidate, alter agent context, mutate campaign state,
make a promotion decision, or prove a pure operator factorial. It must not add
an agent round budget, proposal cap, output truncation, automatic retry, or a
new candidate gate. The only execution limit is the already-observed R3
scientific solver limit bound below.

These are complete treatment bundles. Their lock eligibility differs:

- champion merge may move an intact locked group;
- destroy-only retains champion merge while R3 destroy keeps locked orders
  fixed;
- merge-only uses R3 merge's conservative fixed-original source predicate;
- cumulative carries both R3 conservative predicates.

No W3 materialization may edit these components to equalize the predicates.
Consequently W3 can attribute outcomes to frozen bundles, but cannot call the
result a pure two-factor destroy-by-merge interaction.

## 5. Manifest and materialization

The implementation must create a canonical
`scion.warehouse_w3_fixed_arm_manifest.v1` before the output root becomes
executable. The manifest binds at least:

- this accepted design's raw SHA-256 and git commit;
- W1 receipt, W2 manifest, and W2 receipt identities;
- the three protected R3 roots and exact source artifact identities;
- all four arm derivations and component bytes;
- the complete imported Python/source/config closure used by every workspace,
  plus canonical tree digest and individual file digests;
- problem, protocol, split, and seed-ledger bytes;
- exact selected and explicitly non-selected W1 cases;
- exact 43-cell order, four-arm execution order per cell, phase, solver limit,
  and max iterations;
- Python executable, version, platform, dependency versions, and native-library
  digests needed by the Warehouse solver;
- runner and report-builder source digests;
- output-root identity and an assertion that it was absent before creation;
- `retry=false`, `resume=false`, `reuse=false`, `automatic_rerun=false`, and
  `interim_adaptation=false`.

Each arm workspace is materialized into the new root from one frozen champion
base, then receives only the two exact component files specified by its arm.
The preflight byte-compares every materialized file and recomputes both the
component and full tree digests. It never executes directly inside an R3 root.

Every arm uses the exact champion `registry.yaml` bytes at SHA-256
`1cf4797387d1bc1d75d2dffcb9a1d87f2fa0ce51bfdd2bf205cde3ea1a864525`.
Preflight additionally binds the parsed ordered registry semantics—operator
name, file, class, and numeric weight—under a versioned canonical semantic
digest. The R3 activation registry raw SHA-256
`4a3f8c737bb02cd3b87230ae4dad4a758287e0fef3ffb82e810a3f0592c212f1`
is parsed independently; its ordered operator/class/file/weight semantics must
equal the champion registry despite non-semantic YAML/category differences. A
missing registry, an extra/duplicate operator, a component that is not the
arm-bound file, or any fallback to hard-coded `config.py` weights is rejected.

The exact solver command shape is frozen in the manifest and constructed as an
argv array, never a shell string:

```text
PYTHON workspace/solver.py CASE --phase 1 --seed SEED --time-limit 30
  --max-iter 200 --registry workspace/registry.yaml --output FRESH_OUTPUT
```

`PYTHON`, solver bytes, registry bytes, case bytes, clean environment, working
directory, and the fresh exclusive output path are manifest-bound. `CASE`
always names the output-root-sealed case copy; after sealing, no formal job
reads the original `scion-data`, R3, or repository case path. A solver that
reports that the registry was ignored is an integrity failure.

`FRESH_OUTPUT` is a runner-owned `O_EXCL` temporary interchange file, not the
canonical raw row. The runner parses and validates it, deletes it, then
publishes the metadata-complete canonical raw row with a separate `O_EXCL`
write. Golden tests keep the solver's unsorted/no-terminal-LF interchange bytes
distinct from the canonical report contract.

## 6. Preflight-owned initial and mechanism facts

Before any solver job, preflight constructs the greedy initial solution once
for every `(case, seed)` using the same instance loader, phase, seed, and
greedy initializer as the formal solver. It records:

- canonical greedy-initial solution SHA-256;
- lexicographic initial objective;
- Oracle feasibility and issue codes;
- vehicle and order counts;
- locked-group count and locked-order count;
- each group's initial vehicle identity;
- a problem-owned formal compatible directed merge-pair count;
- an arm-owned eligible merge-pair count for champion-merge and R3-merge
  semantics, each with a versioned counting-contract SHA-256.

The formal compatible count enumerates ordered nonempty source/destination
vehicle pairs, moves the complete source vehicle as one unit, selects the same
minimum feasible type, and accepts only a reconstructed result that passes the
current Oracle. The arm-owned counts additionally reproduce the exact frozen
arm shortlist predicates. Directed fixtures must prove both counters against
exhaustive executable outcomes, including multi-order locked groups, capacity,
hazard, pickup, region, category, and nonempty amount-limit cases.

The counters are analysis covariates, not gates. A counter implementation or
identity failure blocks launch because the preregistered description is
unknown; a legitimate zero count does not block or skip a solver job.

## 7. Balanced serial schedule

Let `A=champion`, `B=destroy_only`, `C=merge_only`, and `D=cumulative`.
Use the four Williams sequences:

```text
ABDC
BCAD
CDBA
DACB
```

Stage-local cell ordinal `i` uses Williams row `i mod 4`. The 28 screening cells are
exactly balanced for serial position and first-order carryover: each arm uses
each position seven times, and every ordered adjacent arm pair occurs equally
often. The 15 validation cells are the maximal fixed prefix: each arm uses each
position three or four times and the manifest reports the exact carryover
table. The manifest stores all 172 job ordinals; runtime never recomputes an
informal order.

Execution uses one isolated runner and at most one live Warehouse solver
process. W3 does not run on the B1 host while B1 or its acceptance analysis is
active. A WSL runner is acceptable only after its `scion` environment and all
manifest-bound executable/dependency identities pass preflight; server-local
`claw` and WSL `scion` are never treated as interchangeable by name alone.

The solver owns its 30-second scientific stopping rule. The launcher adds no
automatic outer truncation. If a job fails to terminate or the service is
interrupted, the root is closed as incomplete and preserved for diagnosis; it
is not resumed or retried in place. A later fresh root requires an explicit
postmortem and a newly accepted launch decision.

## 8. Raw row contract

Every successful job exclusively creates one canonical raw JSON file whose
identity includes manifest SHA-256, job ordinal, cell ordinal, stage, case
identity, seed, arm position, arm SHA-256, workspace tree SHA-256, phase,
scientific limit, max iterations, host/process facts, start/end times, and
return code. It also records:

- complete solution and canonical solution SHA-256;
- Oracle feasibility and issue codes;
- `subcategory_splits`, `total_cost`, solver-reported runtime, and wall time;
- frozen greedy-initial SHA-256 and objective;
- the SHA-256 of the initial solution independently reconstructed inside this
  job, which must equal the preflight value;
- final intact locked-group count;
- whole-groups-moved count relative to the frozen initial vehicle map;
- split-group count, which must be zero for an accepted feasible result;
- formal compatible and arm-eligible merge-pair counts from preflight;
- available operator runtime diagnostics as observation-only fields.

Missing optional operator diagnostics remain visible as `unavailable`; they do
not fail or alter the run. Non-finite numbers, duplicate identities, malformed
solutions, case drift, or an Oracle mismatch are explicit integrity failures.

## 9. Receipt and replay

After exactly 172 unique raw rows exist, a problem-owned closer performs a
read-only integrity pass and emits:

1. `warehouse_w3_fixed_arm_results.v1.json`;
2. `warehouse_w3_fixed_arm_report.v1.json`;
3. `warehouse_w3_fixed_arm_receipt.v1.json`.

All three use canonical UTF-8 JSON with sorted keys, two-space indentation,
`ensure_ascii=false`, `allow_nan=false`, and one terminal LF. The receipt is
not self-hashed. It binds the design, manifest, every raw byte digest, ordered
aggregate digest, results digest, report digest, toolchain, source closures,
preflight facts, row counts, schedule balance, and integrity verdict.

The output root seals byte copies of every authority/source/workspace input
used by execution before the first job. `--check-existing` rereads no mutable
experiment database. It verifies canonical bytes and the root-sealed source
closure, reruns the non-mutating materialization/preflight checks from those
sealed bytes, rebuilds ordered results and report, and byte-compares both
artifacts. Current-checkout equivalence is a separate reported observation;
later checkout drift cannot erase or silently rewrite historical evidence. A
self-consistent rewrite of raw identities is not replay acceptance.

## 10. Analysis contract

Primary comparisons are paired within the exact same `(case, seed)` cell:

- each treatment bundle versus champion;
- destroy-only versus cumulative and merge-only versus cumulative as posterior
  bundle contrasts;
- screening and validation reported separately;
- lock-bearing and lock-free cases reported separately;
- compatible-pair-count strata and arm serial position reported as declared
  covariates.

The independent statistical unit is the case, not the case-seed cell. Seeds
are repeated measurements retained inside their case cluster. Each seed pair
first receives a strict lexicographic win/loss/tie. A case is a win or loss
only when that outcome has a strict majority across the case's seeds;
otherwise it is a tie. Each objective/measurement delta in the case row is the
seed median. Bootstrap resamples whole case rows and never treats the 28
screening cells or 15 validation cells as independent samples. Raw seed-level
outcomes remain visible for heterogeneity and integrity analysis. The manifest
also binds the existing Protocol case-aggregation, statistics, and gate source
digests plus the bootstrap seed and parameters used by the closer.

Report, per arm and contrast:

- lexicographic wins/losses/ties;
- paired split and cost deltas without collapsing a split regression into a
  cost gain;
- median case-level paired deltas and case-cluster bootstrap summaries;
- feasibility, group movement, and split-group violations;
- runtime and optional trajectory heterogeneity, explicitly separated from
  quality effects;
- cell-level rows so a result is not hidden by one aggregate.

The initial-six and expanded-14 screening views characterize the R3-selected
search population without double counting. The five validation cases are
stage-distinct and held out from this W3 screening matrix, but they are not a
new discovery-independent confirmatory population: historical R3 already
observed cumulative validation there and motivated this decomposition.
Validation therefore owns the corrected W3 diagnostic stage verdict, not a
fresh promotion-quality confirmation. Screening cannot promote an arm, and
historical R3 outcomes are context rather than additional W3 samples.

Allowed conclusion examples are “the frozen merge-only bundle reproduces the
screening effect but fails validation” or “the cumulative bundle's validation
loss is not present in either single replacement.” Forbidden conclusions
include “directed merge alone caused the effect” without accounting for lock
policy, “the agent improved Warehouse” when validation fails, or any claim
that W3 independently sampled all 31 W1 cases. The production cases have empty
`amount_limits`, so W3 also cannot claim production amount-limit coverage.

## 11. Acceptance and follow-up authority

W3 is accepted as posterior decomposition evidence only when:

- preservation, W1 identity, materialization, greedy-initial, and counting
  preflights all pass before launch;
- service exit is successful and there are exactly 172 unique, continuous,
  manifest-matching raw rows with no retry/resume/reuse;
- every result is complete, Oracle-feasible, and has zero split locked groups;
- schedule balance and per-cell four-arm completeness are exact;
- results, report, receipt, and `--check-existing` replay all pass;
- independent implementation/integrity and scientific reviews each report
  P0=0 and P1=0;
- the report preserves the complete-bundle and posterior-attribution caveats.

Frozen follow-up eligibility has no post-hoc winner selection. An eligible arm
is non-champion, has an expanded-screening final outcome that may enter
validation, passes the preregistered expanded-validation case-level gate, and
passes every integrity, feasibility, and locked-group check. If exactly one
treatment arm is eligible, that exact arm is the sole arm that may be proposed
for a separate frozen-stage manifest. If zero are eligible, none advances. If
two or more are eligible, none advances from W3; a separately preregistered
fixed confirmation must discriminate them. Champion is the comparison, not a
treatment-arm passer. Any later proposal is not W3 acceptance, does not reuse
W3 rows as frozen evidence, and carries no promotion authority. The current
Warehouse champion remains unchanged until a separate independent Protocol
path says otherwise.
