# Scion v0.4 D2b.0b Global Durable Owner Migration Plan

*Status: frozen implementation contract; production activation remains disabled*
*Date: 2026-07-16*

Three independent reviewers accepted this contract after three adversarial
rounds with no open P0/P1. Changes to immutable token shape, schema/cutover
order, completion revision/digest adoption, process exclusion, snapshot
publication, or lock order require a new design review before implementation
continues.

This plan is the implementation contract for the D2b.0b prerequisite in
`v0.4-d2b-paired-evaluation-ownership-implementation-plan-20260716.md`.
The frozen D2-D4 design and V3 architecture remain authoritative. This slice
does not change research policy, add a new gate, or start an evaluation. It
removes blind Branch/H persistence and gives every existing mutation path one
durable, revisioned ownership boundary before paired evaluation is introduced.

## Outcome

D2b.0b is complete only when all of the following are true:

1. Every durable Branch and H row carries storage-only `owner_revision`.
2. New Branch/H owners are insert-once; an existing ID is never replaced.
3. Every mutation is an exact typed compare-and-swap against the caller's
   previously acquired revisioned owner, and every successful semantic mutation
   advances its revision exactly once.
4. Ordinary mutation authorization and active evaluation-lease exclusion live
   in the same SQL predicate as the revision comparison.
5. Decision completion and research-rejection completion bind their source
   revisions at prepare time and atomically commit Branch, H, event, and intent
   phase through the same connection-scoped participants.
6. Generic persistence, failure recovery, verified-candidate recovery,
   promotion, and weight optimization no longer perform blind or partial
   Branch/H writes.
7. Committed authoritative rows are installed into the in-memory projections
   only after the transaction succeeds. A conflict refreshes from durable truth
   and fails closed; it never retries a stale target.
8. Frozen v1 Branch/H payloads, intent JSON, hashes, IDs, proposal compatibility,
   provider/Protocol/Decision behavior, and golden bytes remain unchanged.

The dormant lease schema is installed so ordinary SQL predicates have their
final authorization dependency. D2b.0b exposes no positive lease, slot,
dispatch, capability, receipt, retry, replacement, budget, cap, or truncation
writer. Production paired evaluation remains disabled.

## Design findings being corrected

The current implementation has one logical owner represented by several
uncoordinated write mechanisms:

- `BranchStore.save()` and `HypothesisStore.save()` use `INSERT OR REPLACE`;
- H status mutation is an ID-only `UPDATE`;
- Decision and research-rejection completion carry private direct SQL;
- ordinary Branch persistence is called again after Decision state commit;
- verified-candidate markers are committed in separate blind Branch saves;
- promotion commits champion, promoted Branch/H, and stale Branches in separate
  transactions;
- weight optimization releases the champion lock before stale Branches are
  persisted;
- batch Branch persistence swallows individual failures;
- mutable controller objects do not carry an immutable expected durable owner.

Changing only the SQL verb would preserve the same ownership ambiguity. The
migration therefore covers schema, typed tokens, transaction participants,
caller token lifecycle, completion recovery, and multi-owner commits together.

## Module boundary

No generic `helpers.py` or catch-all owner module is added. The migration uses
small responsibility-focused components so SQL ownership, immutable values,
and Campaign-local projection coordination cannot collapse into one new god
object.

### `core/durable_owner_codec.py`

Remains a pure value boundary. It continues to own byte-compatible Branch/H
projection and row decoding plus stable source-H identity. It contains no SQL,
transaction, revision, lease, retry, or in-memory registry behavior.

### `lineage/durable_owner.py`

Owns SQL-free immutable storage-owner values and typed conflicts. A token stores
canonical owner bytes, their digest, owner ID, and revision; it never stores a
public mutable `Branch` or `HypothesisRecord` object. Its `.value()` method
returns a new detached reconstruction on every call. The exact internal H
storage projection includes `proposal_digest` and every persisted semantic H
column even though the frozen v1 intent projection deliberately does not.
`owner_revision` and fixed `owner_protocol_generation` are validated token
metadata outside those semantic bytes.

This module does not know Campaign, Controller, SQLite, lease, Decision,
promotion, or evaluation policy.

### `lineage/branch_owner_store.py` and `lineage/hypothesis_owner_store.py`

Own focused durable persistence for one owner type each:

- insert-once creation and revisioned reads;
- ordinary connection-scoped CAS and exact owner guards;
- standalone transaction wrappers;
- strict row decoding into SQL-free immutable owner tokens.

The cutover deletes the old combined `branch_store.py`; no compatibility facade
retains its blind API. Neither focused store owns token maps, mutable
projections, completion policy, or future positive evaluation lease mutation.

### `core/campaign_owner_registry.py`

Owns the Campaign-local relationship between immutable tokens and mutable
Branch/H projections. It is the only API that may acquire a mutation view,
install a committed token, install an authoritative conflict refresh, or
restore the controller/current-H projections. Services and adapters receive a
typed capability from this registry; they do not read or write token dicts.

Production adapters may not use `getattr(..., lambda: None)`, a no-op store, or
an optional persistence callback for an authoritative mutation. Unit tests use
explicit typed fakes.

### `lineage/sqlite_connection.py`

Owns the one connection policy and a sealed immediate-transaction capability:
WAL, `synchronous=FULL`, `foreign_keys=ON`, explicit busy timeout, and explicit
`BEGIN IMMEDIATE`. Connection-scoped participants accept that capability, not
an arbitrary unproven deferred connection.

### `lineage/schema_bootstrap.py`

Is the sole DDL/migration owner for the shared database. It first brings all
parent tables to their final shape, including legacy champion composite-primary-
key migration, creates the complete fresh Decision/rejection completion tables,
then installs or migrates Branch/H revisions, completion auxiliary columns,
dormant lease schema, indexes, and schema-migration provenance. Store
constructors only validate their required schema; they do not run a second
competing migration.

### `lineage/registry.py`

Remains the append-only event/lineage registry. It gains explicit
connection-scoped participants for typed event, weight-optimization, and
promotion-fact insertion/validation so multi-owner transaction owners never
call a wrapper that opens a second connection.

### Transaction owners

Decision completion, research-rejection completion, campaign persistence,
verified-candidate recovery, failure lifecycle, promotion, and weight
optimization own their workflows but may mutate Branch/H only through the
lineage participant on their existing SQLite transaction.

## Storage schema

### Bootstrap order and migration provenance

One schema transaction runs before any domain ownership writer or recovery:

```text
BEGIN IMMEDIATE with foreign_keys=ON
-> create/validate campaign identity and mode parent schema
-> create/validate Branch and H parent schema
-> migrate legacy champions(version PRIMARY KEY) to the final
   champions(version, weight_revision) composite primary key
-> validate champion copy cardinality, keys, and canonical row content
-> rebuild Branch/H with owner revision, protocol generation, and CAS triggers
-> add completion auxiliary columns
-> create dormant lease table and indexes only after every parent is final
-> write exact schema generation and completion-migration provenance
-> PRAGMA foreign_key_check
-> COMMIT
```

The champion table is never renamed after the lease foreign key exists.
`ChampionStore` loses its second legacy table rebuild and validates the final
schema only. A migration collision, duplicate composite key, copy mismatch,
foreign-key error, partial auxiliary-column shape, or unknown schema provenance
rolls back the entire bootstrap.

Schema provenance records whether each completion table gained its auxiliary
columns in this exact migration. It is schema metadata, not a candidate or
research owner. After campaign identity/mode open and inventory, completion
recovery may adopt legacy null auxiliary rows only when this durable provenance
explicitly says those columns were added for that table and adoption remains
pending. Adoption marks that migration complete. Thus a crash after DDL commit
does not make eligible legacy rows indistinguishable from later corruption.

The exact metadata table is:

```sql
CREATE TABLE durable_owner_schema_migrations (
    owner_kind TEXT PRIMARY KEY CHECK(owner_kind IN (
        'decision_completion', 'research_rejection_completion'
    )),
    schema_version TEXT NOT NULL,
    auxiliary_columns_added INTEGER NOT NULL
        CHECK(auxiliary_columns_added IN (0, 1)),
    adoption_state TEXT NOT NULL
        CHECK(adoption_state IN ('not_required', 'pending', 'complete')),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    CHECK(
        (auxiliary_columns_added = 1
         AND adoption_state IN ('pending', 'complete'))
        OR
        (auxiliary_columns_added = 0
         AND adoption_state = 'not_required')
    )
);
```

Rows and state edges are exact-match/insert-once except the single
`pending -> complete` adoption CAS. A completion table created fresh in this
bootstrap gets `not_required`. Any pre-existing auxiliary shape requires exact
pre-existing provenance; missing provenance or null prepared bindings in
`not_required` state are corruption.

Schema bootstrap itself changes no Branch/H payload, completion phase,
campaign identity, candidate mode, champion value, event, or scientific owner.
The first domain ownership transaction remains campaign open.

### Branch/H owner revisions

Fresh table definitions and the final rebuilt legacy tables contain:

```sql
owner_revision INTEGER NOT NULL DEFAULT 0 CHECK(
    typeof(owner_revision) = 'integer' AND owner_revision >= 0
),
owner_protocol_generation TEXT NOT NULL CHECK(
    owner_protocol_generation = 'durable-owner.v1'
)
```

to `branches` and `hypotheses`. Existing rows receive revision zero and the
generation marker in the schema transaction; insert-once explicitly supplies
both. The generation column deliberately has no final default, so a pre-cutover
binary whose INSERT column list does not know it cannot create or replace an
owner after migration. Both values are storage metadata and are excluded from:

- `Branch` and `HypothesisRecord`;
- frozen v1 Branch/H payloads;
- stable source-H identity;
- Decision and research-rejection canonical intent JSON;
- transaction/completion IDs and golden fixtures;
- provider, Protocol, Decision, report, and prompt inputs.

Final tables also install immutable-owner triggers:

```sql
BEFORE DELETE ON branches/hypotheses
  -> RAISE(ABORT, 'durable owner deletion is forbidden')

BEFORE UPDATE ON branches/hypotheses WHEN
  NEW owner identity differs from OLD owner identity OR
  NEW.owner_protocol_generation != OLD.owner_protocol_generation OR
  NEW.owner_revision != OLD.owner_revision + 1
  -> RAISE(ABORT, 'durable owner CAS contract is required')
```

For Branch, owner identity is `branch_id`. For H it is both `hypothesis_id` and
`branch_id`; an H can never move between Branches.

The bootstrap rebuilds legacy Branch/H tables to the final shape, validates
copy cardinality/content, and only then enables these triggers. A legacy
`INSERT OR REPLACE` omits the required generation and fails atomically; an
ID-only or nonincrementing legacy UPDATE is rejected by the trigger even from a
connection opened before migration. All new connections also enable
`recursive_triggers=ON`. Migration is idempotent. A negative, null,
non-integer, noncanonical, or wrong-generation owner is an integrity error,
never a legacy fallback.

The database records the active storage protocol:

```sql
CREATE TABLE durable_owner_schema_generation (
    singleton INTEGER PRIMARY KEY CHECK(singleton = 1),
    generation TEXT NOT NULL CHECK(generation = 'durable-owner.v1'),
    activated_at TEXT NOT NULL
);
```

New runners validate this singleton before any recovery or provider access.

### Dormant `candidate_evaluation_leases`

D2b.0b installs the final authorization nucleus without exposing a positive
writer:

```sql
CREATE TABLE IF NOT EXISTS candidate_evaluation_leases (
    lease_id TEXT PRIMARY KEY CHECK(length(trim(lease_id)) > 0),
    campaign_id TEXT NOT NULL CHECK(length(trim(campaign_id)) > 0),
    branch_id TEXT NOT NULL REFERENCES branches(branch_id) ON DELETE RESTRICT,
    source_hypothesis_id TEXT NOT NULL
        REFERENCES hypotheses(hypothesis_id) ON DELETE RESTRICT,
    current_evaluation_id TEXT NOT NULL
        CHECK(length(trim(current_evaluation_id)) > 0),
    state TEXT NOT NULL CHECK(state IN ('active', 'released')),
    comparison_guard TEXT NOT NULL
        CHECK(comparison_guard IN ('pre_first_dispatch', 'historical')),
    comparison_champion_version INTEGER NOT NULL
        CHECK(typeof(comparison_champion_version) = 'integer'
              AND comparison_champion_version >= 0),
    comparison_weight_revision INTEGER NOT NULL
        CHECK(typeof(comparison_weight_revision) = 'integer'
              AND comparison_weight_revision >= 0),
    branch_acquisition_revision INTEGER NOT NULL
        CHECK(typeof(branch_acquisition_revision) = 'integer'
              AND branch_acquisition_revision >= 0),
    hypothesis_acquisition_revision INTEGER NOT NULL
        CHECK(typeof(hypothesis_acquisition_revision) = 'integer'
              AND hypothesis_acquisition_revision >= 0),
    lease_revision INTEGER NOT NULL DEFAULT 0
        CHECK(typeof(lease_revision) = 'integer' AND lease_revision >= 0),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    released_at TEXT,
    CHECK(
        (state = 'active' AND released_at IS NULL)
        OR (state = 'released' AND released_at IS NOT NULL)

    CHECK(state = 'active' OR comparison_guard = 'historical'),
    FOREIGN KEY(campaign_id) REFERENCES campaign_identity(campaign_id),
    FOREIGN KEY(comparison_champion_version, comparison_weight_revision)

);

CREATE UNIQUE INDEX IF NOT EXISTS uq_active_evaluation_lease_branch
ON candidate_evaluation_leases(branch_id) WHERE state = 'active';

CREATE UNIQUE INDEX IF NOT EXISTS uq_active_evaluation_lease_hypothesis
ON candidate_evaluation_leases(source_hypothesis_id) WHERE state = 'active';
```

`current_evaluation_id` cannot carry a foreign key until the D2b slot table
exists; D2b installs that table and its cross-owner triggers before any positive
lease API is enabled. The comparison composite foreign key pins the exact
append-only champion revision; the D2b slot owns the digest-pinned comparison
artifact.

No public D2b.0b method can insert, activate, transfer, release, or update a
lease. Tests may install exact rows directly to prove the ordinary SQL
authorization boundary. Until D2b enables the positive owner, startup requires
this table to be empty before initial-champion setup, completion recovery,
Branch restore, scheduling, or any provider call. Any active or released row is
an early integrity hold; it is never adopted, completed, or deleted by D2b.0b.

## Typed durable owner protocol

The two immutable tokens are:

```python
@dataclass(frozen=True)
class RevisionedBranchRecord:
    branch_id: str
    owner_revision: int
    canonical_payload_json: bytes
    payload_sha256: str

    def value(self) -> Branch: ...  # new detached value each call

@dataclass(frozen=True)
class RevisionedHypothesisRecord:
    hypothesis_id: str
    owner_revision: int
    canonical_storage_payload_json: bytes
    payload_sha256: str

    def value(self) -> HypothesisRecord: ...  # new detached value each call
```

Canonical bytes are constructed through strict internal storage projections
with exact keys and primitives. They are immutable and are the expected-payload
authority for every guard/CAS. Public mutable values are derived copies only;
target mutation cannot alter the token or its digest.

The final public store surface is:

```text
BranchStore.insert_once(branch) -> RevisionedBranchRecord
BranchStore.load_revisioned(branch_id) -> RevisionedBranchRecord | None
BranchStore.load_all_revisioned_active() -> tuple[RevisionedBranchRecord, ...]
BranchStore.load_all_revisioned() -> tuple[RevisionedBranchRecord, ...]
BranchStore.compare_and_swap(expected, target) -> RevisionedBranchRecord
BranchStore.compare_and_swap_many(expected_targets)
  -> tuple[RevisionedBranchRecord, ...]

HypothesisStore.insert_once(branch_owner, creation_authorization, hypothesis)
  -> RevisionedHypothesisRecord
HypothesisStore.load_revisioned(hypothesis_id)
  -> RevisionedHypothesisRecord | None
HypothesisStore.load_revisioned_by_branch(branch_id)
  -> tuple[RevisionedHypothesisRecord, ...]
HypothesisStore.compare_and_swap(expected, target)
  -> RevisionedHypothesisRecord
HypothesisStore.transition_status(expected, target_status)
  -> RevisionedHypothesisRecord
```

`HypothesisCreationAuthorization` is a sealed value issued only by the durable
proposal-attempt/continuation owner. It binds campaign ID, provider attempt ID,
Branch ID, exact Branch storage digest/revision, H ID, and proposal digest. The
insert transaction exact-checks an unbound generated attempt, inserts the H,
and binds that attempt to the new H in one connection before commit. A caller
cannot manufacture the authorization from a Branch object or event query.
Its value/factory lives with the proposal-attempt owner; `HypothesisStore` may
only consume and validate it, never sign, reconstruct, or infer it.

Read-only compatibility queries may keep returning detached bare values when no
later mutation is possible. Every mutation-capable caller must use a revisioned
token. Final production protocols contain no `save()` or ID-only
`mark_status()` method. Tests use explicit insert-once fixture builders instead
of preserving a blind compatibility alias.

### Connection-scoped participants

Each standalone method delegates to a participant receiving the sealed
caller-owned immediate-transaction capability. A participant asserts that
capability, never begins, commits, rolls back, closes, or silently replaces the
connection, and returns the authoritative token decoded through that same
transaction after its successful statement.

Before any UPDATE, the participant strictly decodes the live row and compares
its complete canonical storage bytes to the expected token. This exact payload
guard and the revision/lease SQL statement share one `BEGIN IMMEDIATE`, so no
writer can interleave between them. Same revision with different payload is a
durable integrity conflict, not permission to overwrite raw or legacy drift.

Ordinary Branch mutation has one predicate:

```sql
UPDATE branches
SET ..., owner_revision = owner_revision + 1
WHERE branch_id = :branch_id
  AND owner_revision = :expected_revision
  AND NOT EXISTS (
      SELECT 1 FROM candidate_evaluation_leases AS lease
      WHERE lease.branch_id = :branch_id
        AND lease.state = 'active'
  );
```

H mutation uses the identical shape keyed by `source_hypothesis_id`, but its
lease exclusion blocks both a lease on that exact source H and any active lease
on its owning Branch. H insert-once exact-matches the H's Branch ID, complete
Branch payload and revision, absence of an active Branch lease, absence of a
conflicting active H, and the exact durable proposal-attempt/continuation
authorization in one `INSERT ... SELECT ... WHERE EXISTS (...)` transaction. A
new H therefore cannot attach to a Branch whose durable owner changed after
proposal context was built, and concurrent provider results cannot both become
the current H. Lease authorization is never a Python pre-check.

The future complementary evaluation predicate is frozen only as a contract: it
must require exact active lease ID, current evaluation ID, Branch/H IDs, owner
revision, and acquisition revision, and later advance owner/acquisition/lease
revisions atomically. D2b.0b implements no evaluation participant and contains
no production lease INSERT, UPDATE, transfer, release, or guard-flip DML. D2b's
positive lease owner implements that sealed participant with the pair/slot
transaction; there is never a caller-selected `authorization='evaluation'`
string.

### CAS semantics

- Insert succeeds only when the ID is absent and returns revision zero.
- Duplicate insert conflicts whether the existing payload is equal or
  different; it never becomes an implicit idempotent overwrite.
- A semantic CAS requires expected ID equality and a target payload different
  from the expected payload.
- Success updates exactly one row and advances `n -> n + 1`.
- A no-op target is rejected before SQL. Validation-only transaction owners use
  an explicit exact owner guard and do not advance revision.
- Zero updated rows are classified inside the same transaction as missing
  owner, stale revision, active-lease conflict, or durable corruption.
- Classification order is fixed: missing/strict-decode failure first; revision
  mismatch next; complete payload mismatch is corruption only when revision
  matches; lease authorization is then classified. A normal stale writer whose
  payload also differs is not mislabeled as database corruption.
- Stale revision always loses, even if the live payload equals the target or has
  returned to the expected payload after A -> B -> A.
- There is no automatic reread-and-retry, payload-equality success fallback,
  last-writer-wins merge, or caller-visible force flag.
- `compare_and_swap_many` performs all predicates in one `BEGIN IMMEDIATE` and
  rolls back the entire set on the first conflict. It never loops through
  standalone auto-committing writes.
- A batch containing the same owner ID twice is rejected before mutation.
- Revision overflow is an integrity hold; SQLite numeric coercion may not turn
  a revision into REAL or wrap it.

Typed errors distinguish `OwnerNotFound`, `OwnerAlreadyExists`,
`OwnerRevisionConflict`, `ActiveEvaluationLeaseConflict`,
`OwnerPayloadConflict`, and `DurableOwnerIntegrityError`. Callers may translate
them to their domain error but may not catch and continue as if persistence
succeeded.

## Campaign-local owner coordination

`CampaignOwnerRegistry` privately stores the token maps and detached mutable
projections under one local owner lock. Callers never receive a bare mutable
projection plus permission to look up whatever token is latest later. They
acquire a bound mutation view:

```text
BranchMutationView(owner token, detached target value, local generation)
HypothesisMutationView(owner token, detached target value, local generation)
```

The view's expected token and generation are inseparable. An old `Branch`
reference cannot borrow a newer token from the registry and overwrite the owner
that produced it.

`BranchController` no longer exposes a shared mutable authoritative object.
Scheduling reads detached snapshots, and transition functions mutate only the
target carried by a bound view. Registry installation replaces the controller
projection after commit. The current-H map follows the same copy-on-install
rule. Direct field mutation of a controller/map-owned object is a forbidden
production pattern.

A local mutation commit is:

```text
acquire detached view (no long operation under owner lock)
-> derive target from that view
-> owner lock
-> reject if registry token/generation no longer equals the view
-> sealed BEGIN IMMEDIATE transaction
-> exact payload/revision/lease guard and CAS
-> COMMIT
-> install prevalidated returned token and a new detached projection
-> release owner lock
```

Ordinary owner commits use `owner_lock -> database`. Champion-sensitive commits
use the single global order
`champion_lock -> owner_lock -> database`. No path may acquire champion lock
after owner lock or database, and no provider, Protocol, or long filesystem
operation runs under either local ownership lock.

Conflict refresh is monotonic. Under owner lock it installs a reloaded row only
when its revision is greater than the local revision; equal revision requires
equal canonical bytes, and a lower revision is ignored. Therefore a loser that
reloads revision 1 cannot overwrite a later local revision 2 installation. A
durable commit result is completely decoded and validated before COMMIT so the
post-commit installation path is non-throwing. An unexpected installation
failure places the Campaign in an integrity hold and rebuilds from durable
truth; it never exposes the prior projection as schedulable.

On CAS conflict, the rejected target is discarded. The caller may reload only
to monotonically restore local authoritative truth and report the conflict; it
never replays the rejected target.

### Startup order

D2b.0b does not activate D2a mode composition or a D2b positive owner. During
the temporary unwired legacy interval its startup is:

```text
schema bootstrap only
-> create champion and CampaignOwnerRegistry locks
-> existing atomic legacy campaign-identity claim
-> empty dormant-lease and mixed-owner negative inventory
-> completion auxiliary adoption
-> R1 research-rejection recovery
-> legacy Decision v1 recovery
-> revisioned Branch/H/workspace restore
-> active-attempt audit
-> scheduler availability
```

No generative matched experiment is authorized during this incomplete-slice
interval. When D2-D4 production composition is activated, the temporary legacy
claim is replaced by the already frozen order without variation:

```text
schema bootstrap only
-> atomic campaign ID + mode open as the first domain ownership transaction
-> mode-specific inventory and mixed-owner validation
-> R1 recovery
-> paired snapshot/slot recovery and slot inventory in snapshot mode
-> mode-specific Decision recovery
-> D3 recovery
-> D4 recovery
-> revisioned Branch/H/workspace restore
-> active-attempt audit
-> scheduler availability
```

The empty dormant-lease rule applies only while D2b positive ownership is
unwired. D2b replaces it with exact lease inventory before enabling any positive
lease writer.

Branch creation becomes insert-first ownership under the champion lock: the
transaction rereads and exact-matches the durable current champion before it
inserts the Branch bound to that version/revision/hash. The generated Branch may
be staged locally, but a failed insert removes it from the controller and
aborts the step. H proposal creation similarly exact-guards the Branch token
and installs current-H state only after insert-once commits. Existing paths that
log and continue after a write failure are removed.

The evaluation path may still read a champion under the champion lock, but it
cannot later copy a new `weight_revision` into a Branch outside a tokenized
transaction. Champion binding and Branch owner revision must still match when
that state is committed.

`_persist_branch_state()` is replaced by an explicit mutation-view
commit-and-refresh operation.
`_persist_all_branch_states()` is removed as an authority surface. Callers that
truly own a batch use one typed multi-owner transaction; read-only projection
refresh has a distinct name and performs no write.

## Decision completion migration

### Prepare

`DecisionCompletionStore.prepare()` receives Branch/H mutation views plus
detached target values. Through the shared factory it opens a sealed immediate
transaction before reading owners or the intent table, then:

1. verifies exact complete source storage digests and source revisions;
2. verifies absence of active Branch/H evaluation leases through exact owner
   guards in the same transaction;
3. builds the unchanged v1 canonical payload and transaction ID;
4. inserts one prepared row with both auxiliary revision/digest bindings;
5. on natural-key conflict, compares canonical payload, intent hash, and every
   expected revision/digest binding exactly.

Same payload with different revisions is a conflict, not idempotence.
`INSERT OR IGNORE` is removed.

### State commit

For a new `prepared` row, one transaction performs:

```text
exact intent and auxiliary revision/storage-digest guard
-> exact source H guard or H CAS
-> exact source Branch CAS
-> typed Decision lineage event
-> prepared-to-state_committed phase CAS
-> commit
```

The H revision advances only when `target_hypothesis_status` changes its
semantic payload. A Decision with no H terminal change guards the exact source H
but advances only Branch. Any fault after either participant, after the event,
or before the phase update rolls back every write.

`prepared` accepts only exact source payload at the frozen revisions. The
current source-or-target fallback is removed. `state_committed` and `committed`
are validation-only: unfinished state commit requires exact target payloads and
the two stored committed revisions, validates the event, and never mutates
Branch/H or advances a revision.

This source-or-target rule concerns the live durable Branch/H rows during
recovery. It does not remove the frozen Decision v1 historical candidate-
identity fallback used when a pre-typed verified-candidate marker is absent.
Existing prepared `legacy-terminal-candidate-identity.v1` intents remain
byte-identical and recover through their exact historical path, and the frozen
golden remains a pure compatibility fixture. After the cutover, new v1 prepare
requires the positive typed legacy verified-candidate owner; it cannot create a
new fallback intent. Thus historical fallback recovery is preserved without
opening fallback creation.

The commit result returns refreshed Branch/H records and writes their exact
revisions and complete-storage digests to the intent auxiliary columns in the
same phase CAS. The finalizer
installs them through `CampaignOwnerRegistry`. Its existing post-commit Branch
persistence callback becomes an explicitly non-authoritative refresh/notification
hook and cannot perform a second CAS.

### Legacy Decision intents

After campaign identity/mode open and inventory, exact schema provenance permits
one adoption transaction per completion table:

- legacy `prepared` may become `legacy_source_v0` with expected `0/0` only when
  both live owner revisions are zero, both frozen-v1 projections equal the
  intent sources, no active lease exists, and all historically available v1
  candidate/proposal/provider identity checks pass. The adoption transaction
  then captures the live complete-storage digests; it does not claim the old
  intent had bound H fields such as `proposal_digest` that v1 omitted;
- target-shaped prepared data, partial source/target shapes, payload drift,
  nonzero revision, missing owner, lease conflict, or mixed nulls fail closed;
- legacy `state_committed` becomes `legacy_state_committed_v0` only when both
  live frozen-v1 projections exactly equal the intent targets, both revisions
  are zero, and the exact typed event exists. It captures committed complete-
  storage digests and revisions `0/0`, performs only external cleanup/final
  marking, and never writes Branch/H;
- legacy `committed` may become `legacy_committed_historical` with null owner
  revisions. Historical audit/count validation verifies immutable intent,
  event, archive/cleanup, and phase facts without requiring a mutable Branch to
  remain at the old target forever. A distinct current-owner verifier returns
  false unless an exact revision binding exists and the current rows match it;
- a schema with only some auxiliary columns, a mixed-null pair in any phase, a
  missing binding kind, or null prepared data without exact pending migration
  provenance is corruption and is never re-adopted.

The schema-provenance row and columns are committed together during bootstrap;
the later adoption transaction and provenance completion are committed
together. A crash at either boundary therefore has one unambiguous recovery
path.

## Research-rejection completion migration

Research rejection uses the same source-token, auxiliary-revision, exact
prepared CAS, target validation, and legacy migration rules. Its additional
proposal digest, provider-attempt, archive receipt, and cleanup-owner checks
remain mandatory.

The transaction order is:

```text
BEGIN IMMEDIATE
exact rejection intent and source revisions
-> H active-to-research_rejected CAS
-> restored clean Branch CAS
-> typed rejection completion event
-> prepared-to-state_committed phase CAS
COMMIT
-> external cleanup/archive convergence
-> target/event/cleanup validation
-> state_committed-to-committed
```

The private cross-module `_upsert_branch` import is deleted. Reopen never
accepts source-or-target ambiguity for `prepared`. `state_committed` recovery
preserves the existing database-then-filesystem layering and performs no second
Branch/H mutation.

Both completion stores validate their completed schema and finish eligible
legacy adoption before either recovery loop runs. Campaign composition is
reordered accordingly.

## Existing ordinary writers

Every mutation-capable protocol and call site is migrated in this slice.

### Generic Branch lifecycle

- Branch creation: insert-once, fail closed, then install token/projection.
- Scheduler and state transition persistence: one token CAS.
- block/resume/reconcile/rollback: one exact token CAS; when a typed control
  event is part of the transition, the event and Branch/H CAS share one
  transaction. A failed resume restores authoritative state and does not
  attempt a reverse blind save.
- active-attempt startup hold: revisioned load plus one CAS.
- bulk stale/close: one multi-owner transaction; no swallowed exceptions.

### H lifecycle

- Proposal creation: insert-once.
- contract/workspace/patch/Verification failure: exact status transition token.
- direct-attempt integrity failure and reconcile cleanup: exact transition.
- legacy Decision fallback: exact token, never ID-only status mutation.
- rollback terminalization: only exact `active -> blocked_infra`; already legal
  terminal states are validation-only.

Status transitions do not gain new policy. This slice only prevents an older
status owner from overwriting a newer promoted, rejected, advanced, or terminal
owner.

Agent-quality and other diagnostic event paths may report a non-authoritative
telemetry failure, but they may not swallow failure of an authoritative
Branch/H mutation. Event projection is either joined to the state transaction
or occurs after a successful owner commit with an explicit non-authoritative
contract.

### Verified-candidate markers

The existing two durable Branch stages remain semantically unchanged but each
has explicit ownership:

1. base Branch -> candidate identity plus `promotion_status=prepared`;
2. prepared marker -> `promotion_status=committed`.

Each successful CAS returns and installs a refreshed token. Reopen repair loads
the revisioned owner, validates journal/artifact identity, and performs at most
one prepared-to-committed CAS. A crash after either stage converges without a
blind save or double revision bump.

## Champion promotion and weight optimization

Filesystem snapshot preparation remains outside SQLite. Authoritative state
commit is redesigned as one transaction under the existing champion lock.

Every owner-changing connection uses one factory configuration: WAL,
`synchronous=FULL`, `foreign_keys=ON`, an explicit busy timeout, and explicit
transactions. The global lock order is always:

```text
champion lock -> CampaignOwnerRegistry lock
  -> fresh SQLite connection -> BEGIN IMMEDIATE -> commit
  -> monotonic in-memory install -> release locks
```

No path acquires the champion lock while holding the Campaign owner lock or a
database transaction. No participant uses `ChampionStore`'s persistent
cross-thread connection for a multi-owner commit, reacquires the non-reentrant
champion lock, or performs a provider call, Protocol run, or long filesystem
operation inside the database transaction.

### Champion promotion

```text
prepare/publish unique immutable snapshot bytes
-> champion lock
-> CampaignOwnerRegistry lock
-> BEGIN IMMEDIATE on the shared database
-> reload and exact-match current champion
-> descriptor-verify the exact unique snapshot path/hash
-> reject any active pre-first-dispatch comparison guard
-> query the complete eligible Branch set from durable rows
-> partition exact historical-lease deferred IDs from ordinary-stale owners
-> load exact promoted Branch/H and ordinary-stale Branch tokens
-> append new champion row through connection-scoped ChampionStore participant
-> promoted Branch CAS
-> active H-to-promoted CAS
-> every ordinary-stale Branch CAS
-> append/validate promotion state facts owned by this commit
-> COMMIT
-> install champion, Branch, and H tokens/projections before releasing locks
```

Any owner conflict rolls back champion and every Branch/H mutation. The current
hook sequence in `PromotionService.commit()` may retain preparation and
post-commit notification hooks, but it no longer performs authoritative writes
phase by phase.

The successor is derived, not caller-authored: ordinary code promotion is
exactly `(current.version + 1, weight_revision=0)`. The durable stale set is
selected after `BEGIN IMMEDIATE`; an external Branch committed before the
transaction is included, while one attempting to commit afterward waits and
must bind the new champion or fail its old champion guard. In-memory controller
membership is never the stale-set authority.

An active `pre_first_dispatch` lease blocks comparison/champion mutation. A
Branch under an active `historical` lease is excluded from ordinary stale CAS
and recorded as deferred; D2e later owns its deterministic stale/reconcile
overlay. This is not a silent success: the transaction result names the exact
deferred IDs. D2b.0b does not create such leases in production.

### Weight optimization

The champion and Campaign owner locks remain held from current-champion
validation through the single SQLite commit that appends the optimized weight
revision, records the improved optimization/invalidation facts, and marks every
durably selected ordinary eligible Branch stale. The only legal successor is
`(current.version, current.weight_revision + 1)`. In-memory champion replacement
and Branch installs happen after commit but before lock release. A stale event,
pre-first-dispatch guard, Branch CAS conflict, fact-insert fault, or champion
mismatch writes no new champion revision and no partial Branch state.

Non-improved optimization observation remains append-only evidence with no
Branch/champion mutation. For an improved result, the observation,
invalidation event, champion row, stale rows, and exact deferred historical
lease IDs share one connection and transaction through the registry's
connection-scoped participants. Failures are surfaced as typed conflicts; they
are not reduced to warning-only partial success.

`ChampionStore` therefore gains connection-scoped insert/read participants and
its standalone convenience wrapper uses a fresh shared-factory transaction. Its
old persistent cross-thread connection is removed from authoritative writes. It
remains append-only; this slice does not add champion overwrite semantics.

### Immutable snapshot publication

Promotion and weight preparation never reuse, delete, or overwrite a
deterministic `champion_v{version}` or `v{version}_r{revision}` directory. Each
plan creates a 256-bit CSPRNG `snapshot_publication_id` and exclusively creates:

```text
champions/.staging/<snapshot_publication_id>
champions/objects/<snapshot_publication_id>
```

The staging manifest binds the publication ID, exact source champion,
candidate/weight owner, intended successor, file manifest, and content hash.
Publication uses descriptor-pinned verification, a true atomic no-replace
publish primitive into the unique object path, directory fsync, and immutable
permissions. Pre-existing destination, lack of no-replace support, or any
collision fails closed without touching either object. The champion
transaction reopens and verifies the exact object bytes/hash before inserting
the row whose `code_snapshot_path` names that unique object.

Concurrent plans for the same successor therefore publish disjoint objects.
The database successor constraint chooses one winner. A loser may remove only
its own publication after a durable query proves no champion row references
that exact path/hash; it never traverses, replaces, or cleans another
publication. A process crash may leave an unreferenced object, which retention
cleanup handles by exact publication ID after the same reference check. No
mutable alias or convenience symlink is authoritative.

Retention/orphan cleanup acquires the same campaign execution lock before its
reference check and deletion, so it cannot race recovery or a snapshot commit.

This random publication object is only the current legacy promotion/weight
filesystem safety boundary. D4 still owns the frozen content-addressed
promotion artifact/ref and ancestry contract; it must not reuse a random legacy
publication ID as scientific lineage identity.

## Offline cutover and process exclusion

The production cutover is an offline campaign migration, not merely a Git
commit. Before schema bootstrap, the deployment owner must:

1. disable all launch sources for the affected Campaign;
2. cleanly stop the wrapper, runner, async weight worker, solver subprocesses,
   and any other process able to call provider, Protocol, or the campaign DB;
3. verify recorded PIDs are terminal and `/proc/*/fd` has no live handle to the
   campaign DB, WAL/SHM files, workspaces, or champion publication tree;
4. acquire the campaign's exclusive OS execution/migration lock;
5. run schema bootstrap, migration inventory, `foreign_key_check`, and the
   legacy-open-connection rejection probe;
6. install the cutover runtime before releasing migration ownership.

The fixed lock path is
`<campaign_dir>/.scion/campaign-execution.lock`. The owner opens it with
no-follow/create and close-on-exec semantics and takes nonblocking exclusive
`fcntl.flock`. The Campaign parent process alone holds the descriptor for its
full lifetime; solver/executor subprocesses do not inherit it, and async worker
threads never acquire or release it. OS process exit releases the lock.

Every post-cutover runner acquires this lock before recovery. Failure to prove
a clean stop or acquire the lock aborts migration with zero schema change. A
process that was missed despite the deployment precondition still cannot mutate
Branch/H durable owners after bootstrap:
legacy INSERT/REPLACE lacks `owner_protocol_generation`, and legacy UPDATE is
blocked by the revision trigger. This database enforcement prevents revision
reset. Legacy champion/event append surfaces do not carry the Branch/H trigger;
the hard clean-stop and execution lock are therefore mandatory to prevent any
stale-binary side effect, including provider/Protocol calls and other table
writes.

This is a one-time storage-protocol deployment boundary, not a scientific gate,
experiment budget, retry policy, or runtime cutoff.

## Implementation work packages and atomic cutover

Schema activation and writer migration are one indivisible release boundary.
If `owner_revision` were added while any `INSERT OR REPLACE`, ID-only UPDATE, or
nonincrementing direct writer remained executable, that writer could recreate a
row at revision zero and defeat ABA protection. The implementation therefore
uses the following work packages, not independently activatable patches.

### D2b.0b.F — dormant foundation

- add SQL-free immutable owner tokens/errors and strict storage projections;
- add the shared connection/transaction capability;
- add focused Branch/H participant implementations, Campaign owner registry,
  schema-bootstrap planner, and connection-scoped registry/champion
  participants behind no production import or schema activation;
- test them against isolated test schemas, including legacy champion migration,
  insert, payload guard, race, rollback, lease exclusion, and ABA;
- leave `LineageRegistry` production schema and every production writer
  unchanged;
- enforce an import denylist proving no production module imports the dormant
  owner stores, Campaign registry, or schema bootstrap before cutover.

This package may be committed independently because it cannot change a live
database or production mutation path.

### D2b.0b.C — one production cutover

The following changes may be developed and reviewed in smaller file groups, but
they are staged, committed, and pushed as one cutover only after all static
checks pass:

- activate the sole schema bootstrap, champion migration, Branch/H revisions,
  completion auxiliary schema, and empty dormant-lease inventory;
- activate Campaign owner views and migrate Branch/H creation, scheduling,
  proposal, evaluation champion binding, failure, reconcile, direct-attempt,
  verified markers, diagnostic mutation, and startup recovery;
- migrate Decision and research-rejection completion/adoption and remove their
  private SQL, target-row recovery ambiguity, and post-commit second write;
- migrate champion promotion, weight optimization, stale set derivation,
  events, and optimization facts to shared multi-owner transactions;
- delete production blind store methods, optional/no-op authority adapters,
  swallowed persistence, and partial batch commits;
- preserve frozen v1 bytes, IDs, call counts, and external cleanup order.

There is no pushed or runnable state with activated owner revisions plus a
legacy writer. If the cutover cannot satisfy the complete focused matrix and
static forbidden list, the schema activation remains absent.

### D2b.0b.V — closure and adversarial acceptance

- run fresh/legacy/crash/two-connection/two-process tests and the complete
  recovery/promotion/weight matrix;
- run frozen v1 goldens, full suite, compile, and diff check;
- perform two independent final reviews with no open P0/P1;
- update the operating docs and freeze this plan only after the evidence exists.

No work package wires positive candidate evaluation or lease DML.

## Test and acceptance matrix

### Schema and codec invariants

- fresh and legacy Branch/H schema; revision zero, non-null, nonnegative;
- repeated initialization and crash-safe schema migration;
- real legacy `champions(version PRIMARY KEY)` migration to the composite key
  before lease creation, repeated reopen, injected migration crash, and exact
  copy cardinality/content validation;
- dormant lease partial uniqueness by Branch and H;
- lease campaign/champion foreign keys, release-state checks, and revision
  checks;
- `foreign_keys=ON` on every connection and clean `foreign_key_check` after
  bootstrap;
- partial auxiliary-column presence and unknown migration provenance fail;
- fresh completion tables are created in full by schema bootstrap; pre-existing
  auxiliary columns without exact provenance are corruption, not
  `not_required` adoption;
- owner revisions absent from models, source-H identity, v1 payloads, intent
  JSON, hashes, transaction IDs, completion IDs, provider inputs, and reports;
- auxiliary full-storage digests do not change any frozen canonical byte;
- all existing Branch/H and Decision/rejection golden bytes unchanged.

### Store and race semantics

- insert-once returns revision zero;
- duplicate equal and duplicate drift both conflict without replacement;
- Branch/H CAS advances exactly `n -> n + 1`;
- same revision with different canonical payload fails before UPDATE;
- no-op mutation rejects without revision change;
- missing ID, wrong owner ID, stale revision, malformed row, and active lease
  produce distinct zero-write failures;
- two connections using the same token: exactly one winner;
- ABA A -> B -> A: the old token still loses;
- active lease versus ordinary CAS race is resolved by SQL transaction order;
- H insert/status is blocked by an active lease on its Branch even when the H
  ID differs;
- two concurrent H inserts for one exact Branch/attempt authorization cannot
  both become active;
- released/nonmatching lease does not block ordinary CAS;
- connection participant rollback leaks neither value nor revision;
- arbitrary/deferred connections cannot call a sealed participant;
- participant never commits or rolls back its caller's transaction;
- multi-CAS conflict rolls back every preceding row;
- duplicate IDs in one batch and revision overflow fail before mutation.

### Completion and recovery

- Decision/rejection prepare captures exact revisions under `BEGIN IMMEDIATE`;
- duplicate canonical payload with different revisions conflicts;
- H-first and Branch-first injected failures roll back both owners and intent;
- faults after Branch/H/event and before phase update remain `prepared` with no
  committed owner mutation;
- changing only durable H `proposal_digest` without advancing revision after a
  new prepare makes reopen fail the expected storage digest, even though frozen
  v1 H bytes still match;
- `state_committed` and `committed` reopen never advance revisions;
- Decision without terminal H status advances Branch only;
- post-Decision callback performs zero authority writes;
- legacy prepared exact revision-zero adoption succeeds once;
- legacy prepared target-shaped, drifted, leased, missing, or nonzero owner
  fails closed;
- legacy state-committed target at exact revision zero completes cleanup only;
  revision greater than zero or ABA-shaped drift fails closed;
- legacy committed historical counts remain valid after a later legal Branch
  CAS, while the distinct current-owner verifier fails;
- pre-existing null prepared data without migration provenance, one-column
  schema drift, and mixed-null pairs in every phase are corruption;
- proposal/provider/archive and typed event validation remain exact.

### Campaign and promotion behavior

- successful mutation refreshes both token and detached projection;
- a three-party loser-reload/winner-commit/loser-install interleaving never
  downgrades the local revision;
- a stale mutable projection cannot borrow the registry's latest token;
- failed mutation leaves no stale mutable target schedulable;
- Branch/H creation failure does not leave an in-memory owner;
- startup raw lease rows hold before champion setup, recovery, restore, or
  provider access;
- a legacy SQLite connection opened before bootstrap with
  `recursive_triggers=OFF` cannot INSERT/REPLACE or nonrevision UPDATE after
  protocol activation;
- offline cutover refuses a live campaign process/DB handle and every new
  runner holds the process-lifetime execution lock;
- execution lock tests cover a second runner, fork/exec descriptor isolation,
  async-worker nonownership, and automatic release after abnormal process exit;
- verified-candidate recovery covers artifact publication, prepared Branch CAS,
  filesystem candidate commit, committed Branch CAS, and a CAS conflict at each
  boundary; token/projection/H state converges once;
- rollback H terminalization cannot overwrite a newer status;
- promotion conflict leaves champion, promoted Branch/H, and every stale Branch
  unchanged;
- weight conflict leaves champion revision and all Branches unchanged;
- pre-first-dispatch comparison guard blocks champion/weight mutation;
- historical lease defers only its exact Branch while allowing the frozen
  comparison to advance; returned deferred IDs are exact;
- an external Branch committed before promotion/weight `BEGIN IMMEDIATE` is in
  the durable stale set; a later writer waits and must bind the new champion;
- any event, optimization-fact, champion, H, promoted-Branch, or stale-Branch
  fault rolls back the complete promotion/weight transaction;
- two threads and two processes preparing the same promotion/weight successor
  publish disjoint object paths; loser commit/cleanup/late exit cannot change or
  delete the winner's path, bytes, or hash;
- reverse lock acquisition and nested participant transactions are rejected;
- no ordinary writer can mutate an active leased Branch or H.

### Static closure

Production Python must contain:

- zero `INSERT OR REPLACE INTO branches` or `hypotheses`;
- zero direct `UPDATE branches` outside `lineage/branch_owner_store.py` and zero
  direct `UPDATE hypotheses` outside `lineage/hypothesis_owner_store.py`;
- zero production `.save()` Branch/H calls;
- zero ID-only `mark_status()` calls;
- zero production imports of the deleted combined `lineage.branch_store`;
- zero imports of Decision-private Branch SQL;
- zero catches that log and continue after an authoritative Branch/H conflict;
- zero production no-op owner stores, optional authoritative persistence
  callbacks, `getattr(..., lambda: None)` owner fallbacks, or direct private
  token-map mutation;
- zero direct field mutation of a controller/current-H-owned projection;
- zero public caller-selectable evaluation authorization flag;
- zero production lease DML or positive slot, dispatch, receipt, retry, cap,
  budget, or truncation writer introduced by D2b.0b.

Focused suites must include all touched lifecycle, completion, recovery,
promotion, and weight modules. Acceptance additionally requires the correctly
rooted complete Scion suite, `compileall`, `git diff --check`, and two
independent final reviews with no open P0/P1.

## Explicit non-goals

D2b.0b does not:

- implement snapshot/slot pairing, dispatch capability, executor transport,
  receipt, uncertain execution, operator resolution, or evaluation recovery;
- activate the dormant lease table in production;
- change Branch/H frozen payload or canonical intent schemas;
- add automatic retry, repair retry, replacement, attempt limit, experiment
  budget, time cutoff, or truncation;
- change Protocol cases, Decision thresholds, research gates, provider calls,
  cleanup call counts, or scientific observation counts;
- implement D2e successor-slot transfer, advanced-H semantics, stale overlay,
  SourceLedger, replay, or D4 promotion;
- infer ownership from payload equality, mutable workspace state, artifact
  presence, logs, or directories.

Any implementation that requires one of these changes returns to design review
instead of extending this slice ad hoc.
