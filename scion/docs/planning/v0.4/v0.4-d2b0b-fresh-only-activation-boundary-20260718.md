# Scion v0.4 D2b.0b Fresh-Only Activation Boundary

Status: design frozen; implementation and end-to-end acceptance pending

Date: 2026-07-18

## 1. Decision

V0.4 activates durable-owner runtime state only for a new explicit campaign
database whose target path is proved stably absent. It does not adopt, migrate,
reopen, repair, or activate any database that existed before the activation
invocation.

The complete authority rule is:

```text
explicit target
+ target absent through a descriptor-pinned parent-directory authority
+ exclusive initializer lock bound to that directory and basename
+ complete staging database committed and synced under the same directory
+ atomic `renameat2(RENAME_NOREPLACE)` publication succeeds
+ directory and receipt state are synced without identity drift
= fresh bootstrap may proceed

anything else
= no activation authority
```

This is a structural safety boundary, not a research gate. It runs once at
fresh campaign initialization. It adds no retry, model-call budget, search cap,
patch limit, truncation, automatic expansion, or per-observation approval.

## 2. Why this supersedes historical activation work

The accepted v1 historical addendum froze artifact bytes but did not close the
semantic classifier. The attempted v2 correction enumerated 24 schema families,
30 physical table variants, row decoders, event joins, D1 bindings, reason
predicates, digest preimages, and aggregate invariants. Independent review found
that making all of those rules executable through JSON metadata would require a
second programming language and interpreter. The intermediate schema exceeded
700 KiB while still containing opaque or narrative operations.

Architecture v3 gives the tie-breaker:

- deterministic logic belongs in code;
- the framework exists to make optimization research credible, not to become a
  general agent or migration framework;
- excessive governance that drives the agent toward small changes is a known
  failure mode.

The historical corpus currently proves no adoptable proposal authority. A
complex compatibility classifier therefore has zero activation benefit for the
v0.4 research objective. Historical compatibility is moved to a dormant support
lane; fresh research is no longer blocked by it.

## 3. Authority ranking

When sources disagree, use this order:

1. `scion-architecture-v3.md` and its v0.4 direct-runtime addendum;
2. this fresh-only boundary and its reviewed implementation source bundle;
3. adversarial golden vectors and independent-verifier results;
4. evidence JSON Schema and passive legacy-family manifests;
5. historical activation drafts, audit notes, and corpus reports.

JSON Schema validates artifact shape. It does not execute activation policy.
Passive family manifests may describe old databases but cannot grant authority.

## 4. Closed state table

| Mode | Stable observed target state | Activation result |
|---|---|---|
| `explicit_target` | absent under the pinned directory authority and atomically published no-replace | `fresh_empty_activate` |
| `explicit_target` | any present regular file, including exact-empty SQLite | no authority; `existing_target_hold` |
| `explicit_target` | symlink, nonregular path, incomplete bundle, alias, or identity race | invocation failure; publish nothing |
| `explicit_target` | lock, directory, staging, publication, or receipt identity changes | invocation failure; publish nothing |

There is no `already_active_exact`, legacy adoption, completion-only adoption,
or historical selection/receipt result in this policy. Active reopen and crash
recovery belong to the separately implemented active runtime and must be bound
to a receipt produced by a successful fresh bootstrap.

The production policy has no `corpus` mode. An existing empty SQLite file is
not absence. A target created by another process before no-replace publication
causes publication failure and is never treated as fresh. A present legacy or
active-looking database is never opened by the bootstrap path.

The caller intent is a closed union. `create_fresh` carries the normalized
parent/basename and no cutover ID; any present target is a terminal hold.
`recover_cutover` carries an externally selected cutover ID and may only advance
its exact incomplete phase chain. `reopen_exact` carries a cutover ID plus its
exact final receipt. Neither can fall back to `create_fresh` or search for a
plausible database. No `auto`, `open_or_create`, or legacy mode is accepted.

The path threat model covers every ancestor from the configured campaign root
to the pinned parent. Production opens the chain with Linux descriptor-relative
no-follow resolution and rejects symlink, mount/descriptor substitution,
non-directory ancestors, a pre-existing target, and any target inode with more
than one link. The initializer does not fall back to path-string checks when the
required descriptor/no-replace primitives are unavailable.

## 5. Minimal module boundary

The production implementation is deliberately small and explicit:

- `fresh_activation/source_snapshot.py` owns normalized basename, descriptor-
  pinned ancestor/parent identity, target absence, exclusive initializer lock,
  and publication-race checks. It never opens a present target.
- `fresh_activation/policy.py` is a pure typed function over the pinned
  authority and publish facts. It
  contains the closed state table as ordinary deterministic code and has no
  plugin, registry, callback, or expression-language surface.
- `fresh_activation/bootstrap.py` consumes a one-shot `StagingCapability`. It
  creates the complete database at one exclusive staging basename using the
  offline bootstrap journal protocol below. It never creates SQLite state at
  the final target.
- `fresh_activation/publish.py` alone performs Linux
  `renameat2(RENAME_NOREPLACE)`, directory sync, and no-overwrite receipt-state
  transitions.
- `fresh_activation/receipt.py` owns immutable prepared, staging-committed,
  target-published, final, and aborted phase artifacts under one cutover ID.
- `fresh_activation/active_reconcile.py` accepts only explicit
  `recover_cutover` or `reopen_exact` requests carrying an external cutover ID.
  It never infers authority from an active-looking or legacy database.
- `verify_fresh_activation.py` independently observes the pre-publication
  authority and reconstructs policy, schema, writer closure, publication, and
  receipt. It must not import any `fresh_activation.*` implementation module.
  Before publication it writes and syncs one immutable, no-overwrite canonical
  prepublication report artifact; an in-memory verdict is not authority.

The evidence schema owns only closed artifact fields, enums, canonical
encodings, and digest preimages. It does not own reason ASTs, join algorithms,
WAL parsers, decoder templates, or a generic rule evaluator.

## 6. Writer and runtime boundary

Fresh bootstrap is accepted only if:

1. one directory-scoped initializer lock is held on the pinned parent and exact
   target basename;
2. a random cutover-bound staging basename is created with `O_EXCL` in that
   same parent, and the final target remains absent;
3. before the database commit, an immutable prepared receipt is published and
   synced at a cutover-ID object name; it binds the bootstrap payload
   and cannot be reused for another basename or staging inode;
4. one SQLite transaction creates the complete durable-owner schema plus a
   singleton committed activation row containing policy generation, cutover ID,
   schema generation, writer generation, pinned parent identity, basename,
   bootstrap payload digest, and prepared-receipt digest;
5. bootstrap uses a dedicated offline connection with rollback-journal mode and
   full synchronous durability, never the production WAL connection factory.
   After commit it closes every handle, proves the main file is self-contained,
   proves `-wal`, `-shm`, and `-journal` absent, independently checks the exact
   schema/integrity/FK facts, and only then publishes `staging_committed`;
6. the database, staging file, phase artifact, and parent directory are synced
   before the only `RENAME_NOREPLACE`; publication failure grants no permit or
   receipt;
7. every production Branch, H, event, completion, candidate, promotion, and
   weight writer is switched to the new owner path before the runtime is made
   runnable;
8. a fixed writer manifest maps every authoritative table/action pair to one
   fully qualified owner symbol, pins the sole production composition root, and
   lists denied legacy constructors, helpers, and direct SQL mutation sites;
9. static dependency and SQL closure proves the manifest complete, every denied
   site unreachable, and legacy stores unable to write the new generation;
10. no intermediate process can observe active revisions with a legacy writer;
11. bootstrap failure before publication removes the staging file or publishes
   an immutable aborted phase; uncertainty after publication is owned by exact
   cutover recovery and is never retried as a new create;
12. the active runtime enables WAL only after final receipt acceptance and
   `CampaignDatabaseAuthority` issuance;
13. reopen accepts only the exact sealed generation and receipt state.

Two implementation-private capabilities remove the issuance cycle. The non-
serializable, non-copyable `StagingCapability` binds the initializer lock,
pinned parent device/inode, target/staging basenames, absence observation,
cutover ID, and policy/schema/writer generations; bootstrap consumes it before
creating SQLite state. After bootstrap is closed, synced, main-only, and
independently verified, policy may issue a separate `PublicationPermit` bound to
the same authority plus staging inode, bootstrap payload, prepared receipt,
activation row, staging-main, staging-committed, and independent prepublication-
report digests. Publish atomically
marks that permit spent before `RENAME_NOREPLACE`; success, failure, exception,
cancellation, or uncertainty all leave it permanently spent.

The external receipt state machine is append-only:

```text
absent -> prepared -> staging_committed -> target_published -> final
                    \-> aborted
```

Each phase is a separate immutable no-overwrite artifact. The no-cycle digest
DAG is exact: `bootstrap_payload -> prepared_receipt -> activation_row ->
staging_main -> staging_committed -> prepublication_report -> target_published
-> final_receipt`. The
activation row contains only upstream payload/prepared digests and its own
digest computed with that digest field omitted. `staging_main` hashes the
closed main-only file containing that row. Downstream phase digests are never
written back into the database.

Every structured node is SHA-256 over canonical JSON
`{"domain":DOMAIN,"items":[OBJECT]}` with UTF-8, `ensure_ascii=false`,
`allow_nan=false`, sorted keys, separators `,`/`:`, and no terminal LF. The
closed domains and object fields are:

- `scion.fresh-activation.bootstrap-payload.v1`: cutover/policy/schema/writer
  generations, pinned parent device/inode, target/staging basenames,
  staging device/inode, schema-manifest SHA, and writer-manifest SHA;
- `scion.fresh-activation.prepared-receipt.v1`: exact phase plus bootstrap-
  payload SHA;
- `scion.fresh-activation.activation-row.v1`: cutover/policy/schema/writer
  generations, pinned parent device/inode, target basename, bootstrap-payload
  SHA, and prepared-receipt SHA; the stored activation-row SHA is omitted from
  its own preimage, and the duplicated path/generation fields must equal the
  bootstrap-payload fields exactly;
- `staging_main_sha256`: raw closed main-file bytes, with no domain wrapper;
- `scion.fresh-activation.staging-committed.v1`: exact phase plus bootstrap-
  payload, prepared-receipt, activation-row, staging-main, schema-manifest, and
  writer-manifest SHAs;
- `prepublication_report_sha256`: raw complete canonical report artifact bytes
  including one terminal LF; the report closes the independent target-absence,
  parent/lock, staging-main, schema/writer, integrity/FK, sidecar, and receipt-
  DAG observations immediately before publication;
- `scion.fresh-activation.target-published.v1`: exact phase, staging-committed
  SHA, prepublication-report SHA, pinned parent device/inode, and target
  basename/device/inode;
- `scion.fresh-activation.final-receipt.v1`: exact phase, target-published SHA,
  independent-verifier report SHA, schema-manifest SHA, and writer-manifest SHA;
- `scion.fresh-activation.aborted.v1`: exact phase, bootstrap-payload SHA,
  prepared-receipt SHA, and a closed terminal reason.

All objects are closed; no timestamp, exception text, path spelling, or later
runtime/WAL bytes enter these authority digests. The independent-verifier
report SHA is over its complete canonical JSON artifact bytes including one
terminal LF; it is not a structured-envelope digest.

The caller union therefore has three intents. `create_fresh` starts a new
cutover. `recover_cutover(cutover_id)` owns an incomplete phase chain:

- prepared with no committed staging publishes `aborted` and never a target;
- staging-committed plus an exact, main-only staging inode and absent target may
  reacquire the same directory lock, reproduce and persist a new exact
  prepublication report for the same cutover, and continue the single no-replace
  publish;
- an exact published target may append a missing target-published/final phase;
- a competing target, missing/drifted staging, backwards phase, digest mismatch,
  or unknown sidecar is a read-only hold.

`reopen_exact(cutover_id)` accepts only final. Recovery is monotonic continuation
of one cutover, not a second mutation attempt or a new create. A published target
without the bound prepublication report can never advance and is a read-only
hold because past absence cannot be reconstructed.

The writer manifest is frozen and fixed-hash reviewed after D2b-D4 and L1-L3
finish changing the production composition. Earlier bootstrap work is dormant
and fixture-only; it cannot make production runnable.

Historical databases remain byte-preserved and read-only. V0.4 makes no claim
that they can be reopened by the new runtime.

## 7. Acceptance matrix

The implementation is not accepted until all of the following pass:

### Policy goldens

- explicit stable absence is the only positive case;
- every present-target fixture returns zero permits;
- symlink/non-directory ancestors, nonregular target, hard-link alias, parent
  replacement, mount/descriptor substitution, competing target creation,
  staging collision, lock mismatch, and output-under-root publish nothing;
- no-replace publication and required descriptor operations have no weaker
  fallback path;
- property tests mutate every non-authoritative metadata field without turning
  a negative case positive.

### Bootstrap and writer goldens

- fresh create succeeds with the exact schema and writer generation;
- the bootstrap commit is closed main-only under the offline journal protocol;
  no WAL/SHM/journal sidecar exists at publication;
- failure at every create/publication boundary leaves no runnable mixed state;
- the fixed writer manifest covers every authoritative table/action and exact
  production composition symbol;
- every listed legacy constructor/helper/direct-SQL site is unreachable or
  database-rejected for the new generation;
- neither capability can be constructed, copied, serialized, or consumed twice;
  the publication permit exists only after exact staging verification and binds
  the complete upstream digest DAG.

### Reopen and recovery goldens

- clean reopen reconstructs the same owner root and runtime generation;
- crash before commit, after commit/before receipt publication, and after
  receipt publication has one deterministic recovery result;
- `create_fresh`, `recover_cutover`, and `reopen_exact` are distinct caller
  intents; only recovery advances an incomplete phase chain and only reopen
  accepts final;
- every crash boundary from prepared publication through lock release has one
  expected phase/target/staging tuple and one monotonic result;
- receipt/schema/writer mismatch fails closed without mutation;
- a second initializer cannot create a competing campaign root.

### Independence

- an independent observer runs before publication and seals its own view of the
  live directory authority into the synced no-overwrite prepublication report;
  post-publication verification checks that bound artifact and does not claim
  to reconstruct past absence from the final path;
- the verifier imports no `fresh_activation.*` module and independently owns
  path syscalls, SQLite inspection, canonicalization, digest, phase, and policy
  code; it shares only fixed artifact schemas and literal domain bytes;
- bootstrap and verifier agree on all positive, negative, race, and crash
  fixtures;
- two independent reviews close with no P0 or P1;
- focused tests, the correctly rooted Scion suite, `compileall`, and
  `git diff --check` pass.

Before final receipt or any reopen authority, the independent verifier checks a
descriptor-pinned main/bundle snapshot, exact activation row and digest DAG,
actual schema digest and writer manifest, SQLite integrity/FK facts, file/link
identity, and allowed sidecar set. A singleton match alone never authorizes
runtime.

Final ordering is strict: persist and sync the independent prepublication
report; issue/consume its bound publication permit; append and sync target-
published; independent postpublication verification accepts; append and sync
final; issue `CampaignDatabaseAuthority`; open the owned runtime connection and
enable its WAL policy; publish runtime-runnable; release the initializer lock
last.
Every kill point that can affect this authority sequence remains mandatory C/V
coverage. Only richer non-authoritative diagnostics may be deferred.

## 8. Historical diagnostic lane

Historical inventory work is parked and nonblocking. It may later publish
read-only facts for retention, provenance research, or a future migration
version. It may retain the 24 observed family hashes and 30 literal physical
variants in a passive manifest. It must satisfy all of these limits:

- it cannot produce a bootstrap permit, selection manifest, activation receipt,
  adoption row, writer cutover, or active-reopen decision;
- it is not imported by campaign initialization or the research loop;
- its failures do not block a fresh campaign;
- no v0.4 completion claim depends on scanning every historical root.

If a future diagnostic corpus tool is implemented, it must have a statically
separate CLI/package with no import path into fresh initialization. Its hard-
zero activation behavior is a diagnostic invariant, not part of D2b.0b.C/V
acceptance.

The rejected executable-classifier draft remains an audit record, not a queued
implementation task.

## 9. Research-path stop rule

Authority work stops blocking research as soon as a fresh campaign can safely
execute and recover this path:

```text
H -> C -> isolated candidate snapshot -> Protocol receipt -> DecisionOutcome
  -> clean/provisional/pivot continuation -> exact stage reuse
  -> replay -> promotion or terminal non-promotion
```

Once the path passes independent review and an end-to-end no-LLM control, work
must move to CVRP and Warehouse experiments. Historical compatibility, richer
crash projections, extra diagnostics, large-file cleanup, and optional
instrumentation remain follow-up work unless new evidence proves they block the
fresh path.

## 10. Scientific work that can proceed in parallel

The following work does not create proposal ownership and may proceed while the
fresh runtime is implemented:

- CVRP canonical, pure-ALNS, initial-VNS-only, and embedded-VNS-only no-LLM
  characterization;
- CVRP H1-only, SWAP-family-only, and cumulative fixed-arm ancestry controls;
- Warehouse protocol/manifest reconciliation and locked-group probes;
- Warehouse champion, destroy-only, merge-only, and cumulative fixed arms.

Generative experiments wait for the accepted fresh runtime path. Fixed/no-LLM
science does not.
