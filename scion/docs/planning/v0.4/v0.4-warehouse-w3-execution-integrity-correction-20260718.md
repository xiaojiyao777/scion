# Scion v0.4 Warehouse W3 Minimal Trusted Execution Correction

*Date: 2026-07-18*
*Status: replacement architecture candidate; implementation locked*
*Architecture authority: `scion/design/scion-architecture-v3.md`*
*Scientific parent: `v0.4-warehouse-w3-fixed-arm-matrix-20260718.md` at
  `5538a81b6d7980888cf594b07244a0b4863c57db85f3a04beb8f84555ad4bb35`*

## Decision

The first W3 implementation and dry root ending `120346Z-r6-claw` remain
rejected at manifest SHA
`d59fd7a37dd3aa91cd4b025940f43bcc7a747bb8093e5ce1c253277f9c615aa2`;
no formal job started. The later
execution-integrity candidates through
`3d6cdbfda8f5a5b052b5ef4aceb757f3a728dbf617c1eb1ee1696d4e0fa01519`
are also rejected. They corrected real authority and descendant-lifecycle
defects, but expanded into a root-owned malicious-code sandbox with exact
dynamic-loader, syscall, audit, mapping and physical-power-loss governance.
That scope exceeds v3 Runtime Isolation, creates a large core maintenance
surface, and risks turning ordinary Python/library behavior into an experiment
gate.

This replacement freezes the minimum execution integrity needed for W3:

1. an accepted external authority chooses exact pushed/materialized bytes;
2. one systemd-owned invocation runs the frozen serial schedule once, without
   retry, resume or reuse;
3. each child is born in a job cgroup with a pidfd, and no descendant may
   survive a job or service;
4. generic runtime records closed process/output facts while Warehouse-owned
   code alone validates Oracle and raw-row semantics;
5. scientific closure is accepted only after the service has exited
   successfully and `ExecStopPost` has proved the delegated subtree drained.

It does not change the four arms, 43 cells, four arms per cell, seeds,
stage-local Williams order, solver stopping rule, Protocol thresholds,
statistics or follow-up rule. It adds no model call, experiment retry,
automatic rerun, outer solver timeout, budget, cap, truncation, prompt input,
reward input or candidate gate.

## 1. Threat boundary

### 1.1 Properties this design claims

The accepted artifact may claim:

- **selection integrity**: a campaign-writable checkout/root cannot authorize
  itself; an external accepted authority binds the pushed commit/tree,
  scientific/correction designs, manifest, source/input table, sealed-store
  aggregate, environment receipt, root basename and nonce;
- **byte identity**: formal solver and validator code, workspaces, cases,
  registries, W1/W2/R3 inputs and analysis code are read from one root-owned
  read-only materialization whose bytes are independently reviewed;
- **single execution**: one nonce is consumed before STARTED, 172 jobs run in
  the manifest order, and no job/root is retried, resumed or reused;
- **process containment**: every solver is atomically spawned into its job
  cgroup with a pidfd; a row is impossible until the leader is reaped and that
  cgroup is empty;
- **semantic ownership**: generic runtime does not interpret Warehouse output;
  the accepted Warehouse validator independently reconstructs the required
  Oracle/objective/initial/locked-group/counter facts;
- **exit closure**: results cannot become accepted evidence until the systemd
  invocation reports success and an external `UNIT_DRAINED` receipt proves no
  supervisor/job descendant remains;
- **replay**: every raw byte, closed process observation, W2 result, result,
  report, receipt and closure marker is independently byte-checkable without
  calling a model or rerunning a solver.

### 1.2 Trusted computing base

The host root/systemd/kernel, the accepted `claw` Python environment, the
accepted small generic guardian/spawn module, the accepted Warehouse problem
layer and the root-owned authority/materialization are trusted after identity
review. Formal code is treated as frozen research code, not hostile native
malware.

Accidental drift, stale paths, crashes, signals, partial files, duplicate
launches and ordinary child descendants are in scope. Intentional in-process
memory corruption, ROP, hostile C extensions, root compromise, deliberate
ptrace/process-vm attacks, adversarial loader manipulation and a solver that
intentionally edits cgroup controls are out of scope. A future hostile-code
sandbox would require a separate v3 design and cannot be smuggled into W3.

Consequently W3 has no exact syscall allowlist, seccomp user-notification
broker, Python audit/call-site gate, executable-map automaton, W^X attestor,
full dynamic-loader constructor proof, tracee-memory reader or per-import
runtime hold. Legitimate loader/allocator/syscall variation cannot invalidate a
scientific row by itself.

This correction claims process-crash durability through no-replace operations
and file/parent-directory fsync. It does not claim a universal physical power-
loss model. After an actual host/storage power loss, the root is a read-only
integrity hold until an independently designed filesystem/device-specific
audit accepts it; a process-crash fixture is never presented as a power-cut
proof.

## 2. Ownership and maintainable module boundary

The v3 split is literal:

```text
generic optional execution guardian (core/runtime):
  external-authority and sealed-store schemas
  systemd invocation/cgroup/pidfd child lifecycle
  exact stdout/stderr/output capture and closed process observation
  generic no-replace state/row/artifact publication primitives

Warehouse problem layer:
  W1/W2/R3 identity and W2 replay
  W3 schedule/workspace/preflight/counter construction
  Warehouse Oracle/solution/raw-row validator
  results/report/receipt analysis and replay

thin tool entry:
  fixed argument parsing and composition only
```

The generic API is closed and problem-agnostic:

```text
prepare_invocation(accepted_authority) -> InvocationToken
start_job(InvocationToken, GenericJobSpec) -> BlockedJob
release_and_collect(BlockedJob) -> ClosedJobObservation
commit_opaque_row(InvocationToken, job_ordinal, observation_digest, row_bytes)
finish_raw(InvocationToken) -> RawCompleteFact
seal_unit_drained(InvocationLineage, closed_cgroup_observation) -> UnitDrainedFact
observe_unit_final(InstallationRecord, UnitDrainedFact) -> UnitFinalFact
accept_invocation(RawCompleteFact, UnitFinalFact, opaque_problem_acceptance_digest)
  -> CompleteFact
publish_opaque_artifact_bundle(CompleteFact, opaque_named_bytes) -> ClosedFact
```

`ClosedJobObservation` contains immutable copied facts only: job/role identity,
argv/cwd/environment digest, output inode and complete bytes/digest, complete
stdout/stderr bytes/digests, start/end wall and monotonic nanoseconds, pid,
starttime, pidfd identity, wait status/return code, signal facts and job-cgroup
lineage/empty proof. It contains no FD, mutable path, callback, Warehouse type,
Protocol result or publication authority.

`WarehouseW3Campaign` calls those generic operations in the exact manifest
order. It passes `ClosedJobObservation` plus the sealed job/preflight inputs to
the Warehouse validator, receives canonical row bytes, and gives those opaque
bytes back to `commit_opaque_row`. The generic layer checks ordinal,
observation digest, one-shot token, raw SHA and no-replace publication, but does
not parse or rewrite the Warehouse row. The Warehouse layer has no cgroup,
pidfd, nonce-ledger or generic publication implementation. There is one
composition, not a parallel Warehouse guardian/helper family.

The optional native surface is limited to
`runtime/native/spawn_into_cgroup.c`: fixed `clone3(CLONE_INTO_CGROUP |
CLONE_PIDFD)`, a blocked-child release FD, exact close/exec error reporting and
pidfd wait/kill/reap helpers. Its ABI freezes `exit_signal=SIGCHLD`; a child FD
allowlist of `/dev/null` stdin, the stdout/stderr pipe writers, the release-pipe
reader and the close-on-exec exec-error writer; and zero other inherited FDs.
The child closes non-allowlisted copies, blocks for one release byte, closes the
release reader, `dup3`s stdout/stderr, and calls exact `execve`. Success closes
the exec-error writer by `CLOEXEC`; failure writes one fixed errno record and
calls `_exit(127)`. The parent closes its child-end copies, publishes
`ACTIVE_JOB`, writes exactly one release byte, closes the release writer, then
polls pidfd/stdout/stderr/exec-error to terminal. It contains no filesystem
materializer, Warehouse/Protocol semantics, Python import policy or alternate
lifecycle.

## 3. External authority, materialization and environment

### 3.1 One-way authority

The accepted checkout contains
`warehouse_w3_launch_authority.v1.json` only as a review candidate; it is not
launch authority in place. Its canonical content deliberately does **not**
contain its own raw SHA or any realized path derived from that SHA. It binds two
content-independent static templates, `scion-w3@.service` and
`scion-w3-close@.service`, whose raw SHAs are known before the authority is
serialized. Each template receives only a root-owned launch ID through `%i`;
neither template embeds an authority SHA, root basename or nonce.

After design/code/dry-manifest review, an external root-owned import action
copies the exact reviewed authority bytes to:

```text
/var/lib/scion/authorities/w3/<authority-sha256>.json
```

under root-owned non-writable parents. The authority is created outside the
dry root and binds:

- schema/version, but not its own raw SHA;
- pushed Git commit and tree;
- W3 scientific/correction design raw SHAs;
- exact manifest raw SHA and authoritative root basename;
- exact sorted source/input provenance, path, size and raw-SHA table;
- exact Python/environment receipt raw SHA;
- exact static run/close unit-template raw SHAs and generic guardian/spawn/
  thin-tool/closer source and artifact SHAs;
- one 64-lowercase-hex nonce and fixed nonce-ledger parent;
- the expected sealed-store aggregate and inclusion schema.

Every source/input entry has exactly one provenance kind:

- `git_blob`: exact commit/tree path, blob OID, size and raw SHA; the importer
  reads the object from the pushed tree, not ordinary campaign-checkout bytes;
- `external_evidence`: root-reviewed source identity plus size/raw SHA, opened
  through pinned nofollow dirfds;
- `generated`: exact accepted generator source SHA, complete ordered input
  digests, canonical generation rule and expected output raw SHA.

An untracked or modified checkout file cannot satisfy `git_blob`. Generated
bytes are admitted only when exact regeneration matches the predeclared SHA.

After importing and sealing, the root-owned installer computes the authority
raw SHA and creates one no-replace
`/var/lib/scion/installations/w3/<launch-id>.json`. That installation record
binds authority SHA/path, sealed-store aggregate/mount, exact run root, nonce,
environment receipt, both template SHAs, expanded unit properties and launch
ID. It is the sole `%i` selector. Its fields do not flow back into the authority
or static templates, so the dependency graph is acyclic. Formal run and close
templates reopen this record, then the authority and sealed executable bytes,
before nonce claim or closure. A copied or self-consistently rewritten root
fails before nonce claim.

`launch-id` is exactly 64 lowercase hex. The installer writes canonical record
bytes by unnamed-file/file-fsync/no-replace-link/parent-fsync, reopens and
rehashes them, then closes the record and its parents root-owned `0444/0555`.
A partial or mismatched installation path is never startable.

The installer then creates a root-owned `0555` projection at
`/var/lib/scion/projections/w3/<launch-id>/` with fixed names only:
`installation.json`, `authority.json`, `sealed/`, `environment/`, `run/`, and
`nonce-claims/`. The first four are read-only bind projections of the accepted
objects; `run/` and `nonce-claims/` are exact bind projections of only the
authority-bound writable directories. The projection is mounted and reopened/
rehashed before `systemctl start`; it cannot be rewritten by `clawd`. Static
templates derive every path mechanically from `/var/lib/scion/projections/w3/%i`
and never parse installation JSON to widen a systemd writable-path property.

### 3.2 Root-owned sealed store

The same external import action reads every authority-declared input according
to its provenance rule, copies it into a fresh
`/var/lib/scion/sealed/w3/<manifest-sha>/` tree, file/tree-fsyncs it, reopens and
rehashes every byte, verifies the sorted aggregate, and closes files/parents to
root-owned `0444/0555`. It then bind-mounts that tree read-only for the formal
unit. There is no named-temp fallback and no mutation of an accepted store.

The store includes manifest/design bytes, W1/W2/R3 authority/evidence,
materialized arm workspaces, all 31 W1 cases, selected 43 W3 cells, registries,
solver/validator/counter/analysis sources and fixed fixtures. It excludes the
external authority, nonce ledger, run state, raw rows, stdout/stderr, results,
report, receipt and closure marker. The authority itself is therefore not
inside the aggregate it authorizes.

### 3.3 Accepted environment receipt

The pre-install environment receipt binds, without pretending to sandbox
hostile code:

- real Python path, regular-file identity, raw SHA and `python -VV`;
- `claw` prefix identity and exact requested package versions;
- raw SHAs of imported Python sources, extension modules and native libraries
  used by W2 preparation, W3 solver/validator and analysis preflight;
- normalized locale/timezone/hash-seed/environment and exact argv/cwd schema;
- host kernel/systemd versions and the static run/close template SHAs.

It does not bind an expanded authority path or realized unit property and thus
does not point back to the authority. The later root-owned installation record
binds the realized read-only/write paths and actual `systemctl show` property
receipt to the already computed authority SHA.

The formal unit sees the accepted environment and sealed store read-only. One
pre-STARTED probe and one post-RAW_COMPLETE probe rehash the same declared
environment table. Drift makes the invocation incomplete. There is no per-
import or per-syscall gate and no claim that unlisted host native code is
malicious.

The formal solver command remains exactly the scientific parent's invocation:

```text
PYTHON workspace/solver.py CASE --phase 1 --seed SEED --time-limit 30
  --max-iter 200 --registry workspace/registry.yaml --output FRESH_OUTPUT
```

`--time-limit 30` and `--max-iter 200` are the already frozen algorithm
stopping rule, not an execution-envelope budget. The guardian adds no outer
timeout.

The installation record selects the fixed `scion-w3@.service` systemd 255
template with these material values. `%i` is only the root-owned launch ID; the
thin tool follows the installation-record chain to authority and sealed bytes:

```text
User=clawd

UMask=0077
ExecStart=/var/lib/scion/projections/w3/%i/environment/bin/python -B -s /var/lib/scion/projections/w3/%i/sealed/bin/scion-w3-tool run %i
ExecStopPost=/var/lib/scion/projections/w3/%i/environment/bin/python -B -s /var/lib/scion/projections/w3/%i/sealed/bin/scion-w3-tool seal-unit-drained %i
Restart=no
ExitType=main
OnSuccess=scion-w3-close@%i.service
OnFailure=scion-w3-close@%i.service
KillMode=control-group
SendSIGKILL=yes
TimeoutStopSec=infinity
OOMPolicy=stop

DelegateSubgroup=supervisor

PrivateMounts=yes
ProtectSystem=strict
ProtectHome=read-only

ReadOnlyPaths=/var/lib/scion/projections/w3/%i/environment
ReadWritePaths=/var/lib/scion/projections/w3/%i/run
ReadWritePaths=/var/lib/scion/projections/w3/%i/nonce-claims
```

The separately hashed `scion-w3-close@.service` freezes:

```text
Type=oneshot
User=clawd
Group=clawd
UMask=0077
After=scion-w3@%i.service
ExecStart=/var/lib/scion/projections/w3/%i/environment/bin/python -B -s /var/lib/scion/projections/w3/%i/sealed/bin/scion-w3-tool close %i
Restart=no
TimeoutStartSec=infinity
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=read-only
ReadOnlyPaths=<the same four exact %i projection paths>
ReadWritePaths=<the same exact %i run and nonce-claims paths>
```

`OnSuccess`/`OnFailure` queues it while systemd still holds the run-unit
instance and invocation result; the `After` dependency pins that unit until
generic terminal observation is durable. There is no external
observe-inactive/start-closer gap, closure timeout, or solver rerun.

The installation-record property receipt distinguishes configured
`systemctl show` values from current-invocation observations. At invocation,
the guardian records boot ID from the ordinary read-only
`/proc/sys/kernel/random/boot_id`, systemd `INVOCATION_ID`, service cgroup
path/inode, main PID/starttime, unit/result selectors and exact mount identities.
`ProcSubset=all` deliberately keeps the boot-ID source available; no fictional
`OpenFile` handoff to `ExecStopPost` is used.

`DelegateSubgroup=supervisor` leaves the service root as a cgroup-v2 internal
node and places the main process in `supervisor`. Immediately before job `n`,
the guardian creates one sibling `job-<n>-<nonce-prefix>` cgroup. The native
spawn operation atomically creates the child in that cgroup and returns a
pidfd while the child is blocked before exec. Only after `ACTIVE_JOB[n]` is
durable does the guardian release the child to exec the exact sealed solver.
The guardian is a single-threaded process and uses nonblocking poll/epoll for
pipe draining; pre-spawn `/proc/self/task` must contain exactly its sole task.
The clone child executes only the reviewed async-safe native close/dup/exec
stub and never returns to CPython.

The guardian drains complete stdout/stderr to supervisor-owned unnamed files
while the child runs. There is no byte cap, line cap, tail-only replacement or
truncation. Allocation/storage error makes the invocation incomplete.

After pidfd wait/reap, the guardian requires the exact wait status and
`cgroup.events populated=0`. A surviving child, grandchild or `setsid`
descendant is an execution-integrity failure: the guardian calls `cgroup.kill`,
waits for empty and publishes INCOMPLETE; it never turns that job into a row.
An empty job cgroup is removed only after row/control cleanup is durable. If
the runner/guardian dies, systemd enters control-group stop and never restarts
the service; a descendant that does not exit keeps the unit unaccepted. The
guardian's accepted signal path immediately marks the invocation incomplete,
uses `cgroup.kill` for an active job and waits for empty.
`TimeoutStopSec=infinity` deliberately avoids turning descendant drain,
`ExecStopPost`, storage latency or fsync into a hidden five-second acceptance
gate. A wedged or uninterruptible task leaves the service unaccepted until
operator intervention; forced intervention cannot produce successful
`UNIT_FINAL`. This is neither a solver timeout nor a scientific budget.

### 5.1 Service-drained receipt

`ExecStopPost` runs the sealed generic `seal_unit_drained` operation in
systemd's `.control` subgroup. Warehouse code cannot write `UNIT_DRAINED`. The
operation publishes a nonce-scoped receipt only if the external nonce claim and
root invocation claim are already durable; a pre-claim failure consumes nothing
and emits no receipt.

On the same boot it reopens the accepted root/claim, verifies boot ID,
`INVOCATION_ID`, service-cgroup inode and systemd-provided `SERVICE_RESULT`,
`EXIT_CODE` and `EXIT_STATUS`. From a pinned service-root cgroup dirfd it
enumerates the complete child-cgroup set: `supervisor`, `.control` and any
recorded current job are the only permitted names. `supervisor` and every job
must be empty; `.control` must contain only the sealer's PID/starttime and no
descendant. Extra/nested cgroups, inode drift or any other task produce no
receipt.

For `RAW_COMPLETE` with main result success, the inventory is stricter: only
empty `supervisor` and the sealer-only `.control` may exist; no `job-*` cgroup,
even empty, is permitted. A recorded current job is accepted only in a failed/
interrupted INCOMPLETE drain receipt.

The exact external
`<nonce>.unit-drained.json` is written by unnamed-file/file-fsync/no-replace-
link/ledger-directory-fsync. It binds the self exception, complete cgroup
inventory, main-command service result and invocation lineage. It cannot start a child,
publish a row or claim scientific success. The external generic closer accepts W3 only
after the unit is inactive and a separate no-replace `UNIT_FINAL` observation
binds the same `INVOCATION_ID`, drained-receipt SHA and final
`Result=success`/main status from systemd. Thus the drained writer does not
claim its own future exit status. Missing/failed `ExecStopPost`, unsuccessful
final unit result or unknown lineage remains INCOMPLETE/UNKNOWN and cannot
become CLOSED.

## 6. One-use invocation and job state machine

The nonce ledger parent is fixed at
`/var/lib/scion/runs/w3/.nonce-ledger/claims/`. Formal launch first creates
`<nonce>.claim.json` with `O_CREAT|O_EXCL`, writes canonical authority/root/
manifest/invocation bytes, file-fsyncs and parent-fsyncs it. It then publishes
the same canonical bytes as root `INVOCATION_CLAIMED` with no-replace write and
control-directory fsync. A crash after the external claim consumes the nonce;
an external sealer may mark it abandoned but no path may retry or reuse it.

Only then may the guardian publish STARTED and durably remove PREPARED. The
complete visible execution states are:

```text
PREPARED:
  dry root only; nonce unconsumed; STARTED/child impossible

CLAIMED_PRESTART:
  external claim and optional matching root claim; PREPARED present;
  no child; nonce consumed if external claim exists

STARTED_WITH_PREPARED:
  STARTED durable but PREPARED unlink not durable; no child; a stopped service
  may only be externally marked INCOMPLETE

ACTIVE_IDLE(r), r=0..172:
  STARTED, PREPARED absent, exact ROW/JOB_EVIDENCE prefix length r;
  no ACTIVE_JOB or FRESH_OUTPUT

PREACTIVE_JOB(n), n=0..171:
  ACTIVE_IDLE(n) plus pinned FRESH_OUTPUT and zero-or-one job cgroup/blocked
  child; ACTIVE_JOB not durable and child cannot have been released

ACTIVE_JOB(n), n=0..171:
  ACTIVE_IDLE(n) plus exact ACTIVE_JOB[n], pinned FRESH_OUTPUT[n], job cgroup,
  blocked/running/exited leader and complete growing stdout/stderr evidence

EVIDENCE_ONLY(n), n=0..171:
  ACTIVE_JOB(n) plus durable JOB_EVIDENCE[n], but ROW[n] absent

ROW_COMMITTED_CLEANUP(n), n=0..171:
  ROW[n] and JOB_EVIDENCE[n] durable; ACTIVE_JOB/FRESH_OUTPUT cleanup pending

RAW_COMPLETE:
  exact 172-row/evidence prefix; no active/output/job cgroup; execution service
  has not yet been accepted as drained

INCOMPLETE:
  exact prior state plus no-replace INCOMPLETE; no further execution allowed

UNIT_DRAINED:
  ExecStopPost same-invocation main-result/drained receipt

UNIT_FINAL:
  unit inactive; external same-invocation systemd Result=success observation
  binds UNIT_DRAINED raw SHA and ExecStopPost completion

COMPLETE_UNCLOSED:
  generic closure has accepted RAW_COMPLETE + UNIT_DRAINED + UNIT_FINAL plus
  opaque problem-acceptance digest and published no-replace COMPLETE;
  artifacts not yet atomically closed

CLOSED:
  COMPLETE plus exact results/report/receipt directory and closure marker

UNKNOWN_INTEGRITY_HOLD:
  any extra name, non-prefix row/evidence set, identity drift or unlisted state
```

Every transition uses canonical bytes, `O_EXCL` or unnamed-file plus
no-replace link, file fsync and owning-directory fsync. There is no overwrite
or state reconstruction from a summary boolean. Process-crash tests cover each
link/unlink boundary; this section makes no physical-power-loss claim.

`STARTED_WITH_PREPARED`, `PREACTIVE_JOB`, `EVIDENCE_ONLY` and
`ROW_COMMITTED_CLEANUP` are named crash windows, not resume points. The live
guardian may finish their one forward transition; after guardian/service death,
systemd drains the cgroup and the external generic closer may publish only
INCOMPLETE. `ACTIVE_IDLE(172)` may advance only to RAW_COMPLETE during the same
live invocation. No later process reconstructs execution authority from any of
these states.

### 6.1 Exact job sequence

For job `n` the guardian:

1. creates `FRESH_OUTPUT[n]` by literal `O_CREAT|O_EXCL|O_RDWR|O_CLOEXEC`,
   fixes the solver-writeable file mode, changes the containing per-job
   interchange directory to `0555` for the child lifetime, pins the inode and
   fsyncs file and directory; after reap only the guardian restores its owner
   mode for cleanup. This explicitly preserves the scientific parent's O_EXCL
   boundary;
2. creates the job cgroup and uses the native blocked spawn to obtain pidfd,
   PID/starttime and exact stdout/stderr pipes;
3. publishes `ACTIVE_JOB[n]` binding job spec, output inode, child/cgroup/
   invocation identities and start timestamps, then releases the child once;
4. continuously drains full stdout/stderr, waits/reaps through pidfd and proves
   the job cgroup empty;
5. reopens/revalidates the pinned output path/inode, copies all output/log
   bytes and host/wait/timing facts into one `ClosedJobObservation`, fsyncs the
   complete `JOB_EVIDENCE[n]`, then closes every job FD;
6. calls the exact Warehouse validator, which reparses output and independently
   reconstructs all scientific facts from sealed inputs;
7. publishes the validator's canonical row no-replace with the exact
   observation digest, fsyncs raw, then unlinks/fsyncs FRESH_OUTPUT, removes
   ACTIVE_JOB and the empty job cgroup.

There is no live-child terminal attestation protocol because this threat model
does not claim in-memory syscall/map history. Actual pidfd wait status, complete
captured bytes and empty cgroup after exit are the authoritative terminal
facts. A signal/nonzero return may become only the scientific parent's typed
normal-solver-failure row when the child was fully reaped, the cgroup is empty
and the Warehouse validator accepts the exact observation. Guardian/spawn/
containment/evidence failure makes the whole invocation INCOMPLETE.

## 7. Warehouse-owned validation and science noninterference

The validator is exact problem-owned code in the sealed source table. Given one
closed observation and sealed `JobSpec`/preflight facts, it:

- parses the complete solver output and rejects duplicate/nonfinite/malformed
  identities;
- reconstructs the complete solution and canonical solution SHA;
- runs the current Warehouse Oracle and records feasibility/issue codes;
- recomputes `subcategory_splits`, total cost and lexicographic objective;
- reconstructs the greedy initial solution inside the job identity and
  requires its SHA/objective to equal preflight;
- recomputes final intact/split locked groups, whole-groups-moved and vehicle
  mapping facts;
- binds formal-compatible and arm-eligible counter facts from preflight;
- copies the guardian-owned start/end/wall/monotonic, return/signal,
  stdout/stderr/output and cgroup-observation digests into the parent raw-row
  schema;
- emits exactly one canonical success or typed normal-solver-failure row with
  `ensure_ascii=false`, `allow_nan=false` and one terminal LF.

The validator cannot publish, choose another job, mutate the schedule or call
the model. Generic runtime cannot change an Oracle result. Replay invokes the
same validator in read-only mode over retained JOB_EVIDENCE and requires exact
row-byte equality.

The scientific parent remains authoritative for the quality projection,
rank-24/25 shortlist fixture, comparator-only fixture, case aggregation,
bootstrap statistics, follow-up eligibility and all report fields. Execution
integrity labels are excluded by differential test from Protocol quality,
candidate rank, prompt, hypothesis feedback, reward and solver stopping. They
may reject invalid execution evidence; they may not tell the research agent to
optimize for runtime governance.

## 8. Post-service analysis and closure

Systemd's already queued `scion-w3-close@%i.service` begins after the run unit
has finished `ExecStopPost` and become inactive, while its dependency still
pins the exact invocation result in memory. The close template follows the
installation record to the same sealed thin tool. Missing `UNIT_DRAINED` or a
failed run/stop-post result can publish only generic INCOMPLETE and never
`UNIT_FINAL`. On the success path, generic `observe_unit_final` publishes the
canonical `UNIT_FINAL` observation defined above. Warehouse-owned read-only
validation then verifies authority/store/environment, W1/W2/preflight, 172
continuous rows and matching JOB_EVIDENCE, final service result and drain
lineage, and returns one opaque problem-acceptance digest. Only generic
`accept_invocation` may bind that digest and publish COMPLETE no-replace.

Problem-owned analysis derives exactly:

1. `warehouse_w3_fixed_arm_results.v1.json`;
2. `warehouse_w3_fixed_arm_report.v1.md`;
3. `warehouse_w3_fixed_arm_receipt.v1.json`.

It uses the scientific parent's case-cluster/statistical rules and binds
COMPLETE, UNIT_DRAINED, UNIT_FINAL, every raw/evidence digest, W2 result, schedule,
environment and source identities. Current wall clock, closer PID or mutable
host observations are excluded from these deterministic bytes.

Warehouse analysis returns the three opaque named byte strings to generic
`publish_opaque_artifact_bundle`. The generic operation builds them in one
root-confined staging directory, file/directory-fsyncs each fixed prefix, and
uses `renameat2(RENAME_NOREPLACE)` to publish the complete directory. It then
writes one no-replace closure marker binding all three bytes plus COMPLETE and
UNIT_DRAINED/UNIT_FINAL. Warehouse cannot write terminal state or choose other
artifact names. Process-crash recovery may only continue an exact verified
staging prefix or add the missing marker to an exact final directory. It never
reruns a solver, overwrites bytes, resumes execution or counts as a scientific
retry.

`check-existing` requires external authority, sealed-store and environment
identity, W2 result, exact raw/JOB_EVIDENCE replay, successful UNIT_DRAINED,
UNIT_FINAL, COMPLETE, all three rederived artifacts and closure marker. A self-consistent
root rewrite or missing service-exit evidence fails.

## 9. Acceptance and launch lock

Before a replacement dry root is accepted:

1. two independent reviewers report P0=0/P1=0 on one exact design SHA and
   explicitly confirm the reduced v3 threat boundary;
2. implementation contains one generic guardian/spawn lifecycle and one
   Warehouse problem layer, with no seccomp broker, syscall/audit/map gate,
   root static sandbox, Warehouse lifecycle fork or generic Oracle branch;
3. focused tests cover:
   - acyclic authority/installation/template selectors, `git_blob` tree/blob
     provenance, external/generated provenance, root/store/source/environment
     drift and hash-to-materialized-exec direction;
   - exact W1/W2 identities, complete W2 replay, schedule/workspaces/preflight/
     counters and parent O_EXCL output semantics;
   - native blocked spawn, pidfd wait/reap, wrong exec, leader signal/exit,
     descendant/`setsid` survival, cgroup kill/empty and supervisor/systemd
     death with `Restart=no`;
   - full untruncated stdout/stderr/output capture and storage/allocation
     failure;
   - every visible nonce/STARTED/STARTED_WITH_PREPARED/PREACTIVE/ACTIVE/
     EVIDENCE_ONLY/ROW/ACTIVE_IDLE(172)/RAW/INCOMPLETE process-crash state,
     duplicate nonce/job/row and zero retry/resume/reuse;
   - Warehouse Oracle/objective/initial/locked-group/counter/raw-row
     differential fixtures and exact replay from JOB_EVIDENCE;
   - successful/failed service result, unbounded ExecStopPost `.control`
     topology, wedged drain hold, missing/invalid UNIT_DRAINED and refusal to
     close before drain;
   - generic-only UNIT/COMPLETE/CLOSED publication, opaque Warehouse
     acceptance/artifacts, artifact prefix/final/marker process-crash recovery
     and complete `check-existing`;
   - execution-integrity noninterference with Protocol/prompt/reward/stopping;
4. the final focused suite, compileall, formatting and diff checks pass once on
   the final source hashes;
5. two independent implementation/science reviews report P0=0/P1=0 on the
   same pushed source, authority, manifest and fresh zero-job dry root.

Passing implementation acceptance authorizes only one fresh serial W3 launch
from a new root and nonce. The rejected r6 root and every superseded design/
manifest remain diagnostic non-evidence and are never repaired or launched in
place. F1 may reuse the generic guardian only after its own authority/manifest/
problem-validation composition is separately reviewed; W3 acceptance does not
implicitly unlock F1.
