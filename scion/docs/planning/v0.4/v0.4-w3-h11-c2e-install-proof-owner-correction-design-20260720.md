## 1. Basis 与冲突

本文以以下 accepted 文档为基础：

- indirect snapshot authority correction：
  `590eafd35111dfc99362f1c7eab46920fef9baec072d0171ba6ab71b1ba08657`；
- implementation oracle design：
  `a30f8858873c69d8d2e34b3827325f6c34ae09e1096e43b0048848283f7ffd7b`；
- domain proof owner correction：
  `58fd9dbcd97283154e7fb0374b4d8b9f71c540a4e0d55461639b0fffebb7ad14`。

当前冻结设计存在两个不可同时满足的合同：

1. indirect design 要求 INSTALL receipt 的 fixture identity 与已验证 TREE identity
   相等，但旧 INSTALL signature 不接收 TREE receipt 或 validated fixture identity；
2. implementation oracle 将 `source-identity`、`source-mode`、`source-owner` 登记为
   INSTALL axes，但 accepted SEAL helper 已唯一证明 INSTALL source full five-field
   reference 与 same-role SEAL row 相等、mode `0444`，source actual owner/metadata 又由
   final observation proof拥有。INSTALL 不生成 source spec，source wire也没有 uid/gid。

因此这三个 axis 无法构造“direct、TREE、SEAL、PREFLIGHT完成，INSTALL首拒”的
single-owner delta。co-mutate SEAL再在 INSTALL 重验相同字段会制造重复 gate；凭空补造
source uid/gid则会创造producer不存在的authority。两种做法均禁止。

## 2. Corrected owner partition

### 2.1 Direct、TREE、SEAL 与 final 保持不变

- direct继续唯一证明 retained install receipt/manifest actual sources、harness→receipt、
  receipt→manifest、manifest `receipt_path`、TREE/SEAL/PREFLIGHT source projections；
- TREE继续唯一证明 fixture identity自身的shape、canonical value与运行owner policy；
- SEAL继续唯一证明 installer与`installer-program`、每个 INSTALL unit source full
  `{device,inode,mode,path,sha256}` 与 same-role SEAL row、source mode `0444`；
- top继续证明全部indirect expected path/identity alias闭包；
- final proof继续唯一证明 actual target/source metadata与expected spec、actual owner。

INSTALL不得重复上述 gate，也不得重新读取source bytes或观察filesystem。

### 2.2 INSTALL 独有语义

INSTALL只证明：

1. receipt/manifest intrinsic exact shape、schema、receipt phase；
2. receipt formal-root full identity与已验证 TREE formal-root相等，manifest root path与
   builder `formal_root`相等；
3. receipt fixture user/group/uid/gid与已验证 TREE四字段相等；
4. receipt/manifest三unit同序闭包、harness run/close unit绑定、gc unit closed shape；
5. manager owner、call counts与十行ledger；
6. source的INSTALL独有layout：parent exact为`formal_root / "sealed"`、basename exact
   为unit；receipt source `{path,sha256}`与manifest member同序合并；
7. target snapshot shape/layout/mode/owner policy，source与target snapshot SHA相等；
8. 只为三个target生成spec，按receipt原始ordinal `0,1,2`，不为source生成第二spec。

所有target↔target、target↔source expected path/identity alias统一归top global indirect
alias closure；INSTALL不得抢先重复同一gate。

## 3. Corrected signature

旧 signature 中 `seal_receipt`、`install_receipt_source_reference`、
`install_manifest_source_reference` 的全部可证明关系已经分别归SEAL/direct；继续传入只会
增加噪声与重复gate诱因。以现有 decoded `tree_receipt`替换它们：

```python
def _build_h11_install_target_specs(
    *,
    install_receipt: H11RootFrozenJsonObject,
    install_manifest: H11RootFrozenJsonObject,
    tree_receipt: H11RootFrozenJsonObject,
    harness_manifest: H11RootFrozenJsonObject,
    formal_root: Path,
    require_root: bool,
) -> tuple[H11RootIndirectAuthoritySpec, ...]:
```

全部参数keyword-only、无default/variadic。top仍是唯一caller；调用顺序仍为
`direct -> TREE -> SEAL -> PREFLIGHT -> INSTALL`，internal edge数量不变。INSTALL只从
TREE读取已经由TREE helper验证的`formal_root`与四个fixture fields，不重新解释TREE
directories、FIFOs、prepare manifest、schema或phase。

## 4. Exact receipt、manifest 与 unit closure

Receipt canonical key tuple exact为：

```text
fixture_gid, fixture_group, fixture_uid, fixture_user, formal_root,
install_manifest, installer, load_call_count, manager_ledger,
manager_owner, phase, preflight_receipt, reload_call_count, schema,
seal_receipt, tree_receipt, units
```

Manifest canonical key tuple exact为：

```text
formal_root, preflight_receipt, receipt_path, schema,
seal_receipt, tree_receipt, units
```

Receipt `schema == INSTALL_RECEIPT_SCHEMA`、
`phase == "installed-before-observation"`；manifest `schema == INSTALL_SCHEMA`。Receipt
formal root是exact `{device,inode,path}`并等于TREE formal root；manifest formal root
exact等于`str(formal_root)`。Receipt四个fixture fields分别等于TREE同名字段；文本继续
使用TREE已验证的canonical authority，不在INSTALL重复控制字符policy。

Receipt unit row exact keys：

```text
fragment_path, need_daemon_reload, object_path, role, source, target, unit
```

Manifest unit row exact keys：

```text
role, sha256, source, unit
```

两边长度exact为3，role set exact为
`{run-fragment, close-fragment, gc-fragment}`，role/unit/object path各自唯一；
两边的role、unit、source path与SHA逐ordinal相等。输入顺序允许是producer保存的任意
permutation；consumer不得role-sort。run/close unit分别等于harness run/closer unit；
gc unit只要求closed systemd unit regex与unit唯一。

## 5. Manager ledger

`manager_owner`必须匹配canonical unique bus owner；`reload_call_count == 1`、
`load_call_count == 3`。Ledger exact十行：一行Reload、按receipt顺序三行LoadUnit、再按
每个unit顺序各两行FragmentPath/NeedDaemonReload Get。

每行exact keys为：

```text
arguments, begin_ordinal, interface, member, object_path,
reply, reply_ordinal, signature
```

begin/reply ordinals exact覆盖`1..20`；interface、member、object path、signature、
arguments与reply均绑定相应unit。`fragment_path == target.path`，
`need_daemon_reload is False`，ledger FragmentPath reply等于target path，
NeedDaemonReload reply exact为`False`。

## 6. Source、target 与 observation boundary

Receipt source由SEAL前置合同保证为exact full five fields；INSTALL只消费其path/SHA，
不重复验证source identity/mode。
Source path必须位于sealed root且basename等于unit。Manifest member只携带
`{role,unit,source,sha256}`，与receipt的窄projection逐ordinal相等。

Target必须是exact full seven fields。Path basename等于unit，三target共享一个absolute
canonical parent；`require_root=True`时parent exact为`/run/systemd/system`。Target SHA
canonical且等于source SHA，mode exact `0644`。Target uid/gid canonical；root模式exact
`0:0`；nonroot模式保留producer receipt声明pair，不把TREE fixture owner扩张成target
owner policy。

Target device/inode仅作为producer snapshot expected metadata：INSTALL验证canonical
uint并原样进入spec，不把任意valid numeric delta称为INSTALL drift；expected跨class
alias归top，actual是否相等仍只由
final proof判断。INSTALL target specs的`accepted_owners`来自上述policy。

## 7. Corrected semantic matrix

INSTALL axes改为exact 11项：

```python
(
    "receipt",
    "manifest",
    "unit-role-ordinal",
    "manager-ledger",
    "source-path",
    "receipt-manifest-source-merge",
    "source-target-hash",
    "target-path",
    "target-identity",
    "target-mode",
    "target-owner",
)
```

删除`source-identity`、`source-mode`、`source-owner`；旧`source-member-merge`明确改名为
`receipt-manifest-source-merge`，只证明receipt source窄projection与manifest member；
旧`source-hash`/`target-hash`合并为`source-target-hash`，以source-side coherent、
target-side valid mismatch与target noncanonical三个subcases覆盖同一条SHA equality。
旧`target-alias`迁出五domain registry。五domain registry exact总数从73改为68。

每个negative必须走top builder并记录：direct、TREE、SEAL、PREFLIGHT完成，INSTALL
进入但未完成，observation不得执行。另需一个producer-valid canonical positive与一个
两份unit rows、ledger同步permutation的合法reordered positive，证明不偷偷role-sort。

top alias axes在既有两个direct-only axes之外增加：

```python
(
    "indirect-path-alias",
    "indirect-identity-alias",
)
```

`indirect-path-alias`覆盖可达的target-source subcase；target-target path相等会与已证明的
unique unit、shared parent、basename exact unit合同矛盾，不构造producer不可能通过
INSTALL的假top用例。`indirect-identity-alias`覆盖target-target与target-source两个
subcases。五个domain helpers必须全部完成，top在observation前首拒。这两项不计入五
domain registry 68，与final actual observed四轴分开。

最低subcases包括：

- receipt/manifest missing、extra、schema、phase/root/fixture；
- unit长度、role set/duplicate、manifest order、unit/object/fragment/reload binding；
- manager owner/count/length/row shape/ordinal/order与四种exact call binding；
- source input-parent、wrong basename；两者必须同步重绑same-role SEAL row、receipt full
  reference与manifest narrow reference，使SEAL完成且唯一错误是INSTALL layout；
- receipt↔manifest source path-only/SHA-only；
- source↔target SHA的source-side coherent、target-side valid与noncanonical delta；
  source-side必须同步重绑SEAL row、receipt与manifest，使SEAL完成；
- target basename/parent、noncanonical identity、mode、owner；
- top target-source expected path/id alias，以及target-target expected identity alias。
