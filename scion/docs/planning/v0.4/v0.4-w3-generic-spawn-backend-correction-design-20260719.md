## 1. Rejection basis

The rejected implementation has six structural defects:

1. FD-returning operations and native capture/pidfd moves can be interrupted
   after the kernel/C operation but before Python records the result. A typed
   return can therefore leak an unobservable FD or capability.
2. `PRE_NATIVE_READY` is not a real phase. Context-manager entry, native call,
   and context-manager exit share one exception boundary and can publish false
   `native_called`/`child_creation` facts.
3. live wrapper consumption, backend-state transition, cleanup-permit
   consumption and cgroup removal are not enclosed by one fail-closed commit
   boundary. An asynchronous interruption can strand authority after its only
   public alias is consumed.
4. the poll set is mutable across iterations. `unregister` plus local state is
   not one atomic operation, `cgroup.events` incorrectly includes `POLLIN`, and
   draining one ready stream to `EAGAIN` can starve an already-ready pidfd or
   cgroup event.
5. non-`EAGAIN` pipe read errors are falsely converted to EOF. Capture failure
   does not prove channel EOF, and exec-error uncertainty is never an ordinary
   contained result.
6. the service authority retains a strong live `_JobCgroup` alias while the
   backend wrapper also owns it. The required exact move is therefore not
   represented by the object graph.

## 2. Cancellation boundary

`spawn_backend.py` owns one small issuer-signal guard for acquisition and move
micro-transactions only. It does not mask the unbounded drain or a complete
public lifecycle call. Before `SpawnBackend.open` consumes `ServiceCgroup`, and
before every later public backend operation, the exact process must contain
only the current `/proc/self/task` entry. A multi-threaded caller is rejected
before open consumption and fail-stops after a backend owns authority. This is
required because `pthread_sigmask` is thread-local and cannot protect a Python
handler delivered through another thread.

The guard blocks every valid catchable signal except `SIGKILL` and `SIGSTOP`
around only an FD-returning syscall, native capture move, pidfd duplication,
destructive pipe read or short wrapper/backend state commit. It restores the
exact prior mask immediately after that micro-transaction. It records the
entry pending set so a signal already blocked by the caller is not attributed
to this operation.

The guard has only three operations:

- enter after proving the process is still single-threaded, and copy the exact
  prior mask plus entry pending set;
- query whether a newly pending signal arrived during the guarded operation;
- restore the prior mask exactly once and report a Python `BaseException`
  raised by the restored issuer handler.

The mask protocol is concrete. A pre-existing guard object first queries and
stores the current mask without changing it, marks `block_started`, and only
then calls `SIG_BLOCK`. Thus an interpreter-pending handler raised before or
after that syscall cannot hide the prior mask or an acquired authority. On
restore it marks `restore_started` before `SIG_SETMASK`; whether the call
returns or raises, it queries the current mask without changing it. It reports
an issuer interruption only if that exact mask equals the stored prior mask.
Any other value, failure to query, or exception during recovery is restoration
uncertainty and fail-stops. A guard seen again in `restore_started` state never
blindly restores twice: it first proves the current mask already equals the
prior mask, otherwise it fail-stops. Tests cover both kernel-pending signals
and CPython's pending-handler flag when `sigpending()` contains no signal.

Every micro-transaction writes its result into a pre-existing, caller-owned
ledger before restoring the mask. Therefore an issuer handler raised by mask
restoration, or another exception immediately afterward, cannot hide the
acquired FD/capability: the enclosing phase handler still owns and closes or
settles the ledger. There is no API that attempts to return a newly acquired
integer and an interruption atomically.

Mask acquisition failure, mask restoration uncertainty, double restoration or
abandonment fail-stops. A direct injected `BaseException` while catchable
signals are blocked is handled at the phase boundary if the ledger proves
ownership. If a patched primitive performs a hidden acquisition and then
raises without returning the acquired authority, the outcome is unknowable
and fail-stops. The latter must never become a typed closed result.

This guard is not a deadline, retry or signal-delivery policy. It only defers
issuer delivery across the few Python bytecodes that record an ownership move.
The unbounded poll/drain runs with the caller's exact signal mask and catches
issuer `BaseException` at each resumable phase/dispatch boundary. Once a native
handle exists, a pending, restoration-raised or directly injected issuer
interruption becomes the first `ISSUER_INTERRUPTED` failure at the
then-current phase, followed by explicit containment settlement. A signal is
never deferred for the duration of a potentially unbounded wait.

Every deterministic contained failure uses one global first-failure latch.
The pair `(reason, phase)` may transition only from `(None, None)` to one exact
pair. Release uncertainty, issuer interruption, capture failure and descendant
survival detected later may drive kill/drain settlement but never overwrite an
earlier pair. An ownership, channel, close, mask, wait/reap or empty-proof
uncertainty bypasses the latch and fail-stops.

## 3. Exact pre-native boundary

The cgroup layer replaces the synchronous context-manager borrow with one
package-private, one-shot method:

```text
job._consume_spawn_dirfd_borrow() -> exact int fd number
```

The returned number is neither duplicated nor transferred: `_JobCgroup`
remains the only FD closer. The method verifies, in one call:

- creator and pinned job identity;
- exact service/supervisor/job inventory and sole supervisor process;
- no nested job cgroup;
- exact empty events `populated=0/frozen=0` and empty `cgroup.procs` at this
  pre-native boundary;
- one-shot issuance.

Because the pre-native borrow occurs before clone, it first proves the exact
empty job and returns the pinned number once. After native returns BLOCKED, a
separate `_require_blocked_leader(pid)` proves events `1/0`, exact
`cgroup.procs==(pid,)`, topology and inventory before any release or ACTIVE
handoff.

The backend phases are disjoint:

1. failure before the one-shot dirfd borrow completes is
   `PRE_NATIVE_READY`, `native_called=false`, `NOT_CALLED`;
2. an exception raised by the accepted native call is `NATIVE_NO_HANDLE`,
   `native_called=true`, `NATIVE_INTERNAL_SETTLED`, followed by an independent
   empty-cgroup proof;
3. an exact `native.BlockedChild` returned to Python permanently enters the
   handle-acquired path. No later path may construct `PreHandleFailure`.

If an interruption can occur after the C function returned but before Python
can retain the returned object, the accepted native BLOCKED destructor settles
that transient object and the independent empty proof remains mandatory. The
backend does not claim a Python handle it never retained. A caught issuer
`BaseException` in this call window is exactly phase `NATIVE_NO_HANDLE`, reason
`ISSUER_INTERRUPTED_PRE_HANDLE`; an ordinary accepted native exception is
phase/reason `NATIVE_NO_HANDLE`.

## 4. Handle assembly ledger

After native return, one private assembly ledger is the sole local owner of:

- native `BlockedChild`;
- live `_JobCgroup`;
- stdout/stderr spools;
- capture-reader tuple once moved;
- poll pidfd once duplicated;
- copied process identity once verified.

Signals remain deferred until every successful move is recorded. An ordinary
accepted-ABI error before a move keeps ownership at its prior ledger entry. A
hidden post-move exception without a returned value is ownership uncertainty
and fail-stops. Once the complete ledger is armed, it moves exactly once into
`BlockedSpawn`; the backend stores only an identity guard.

The cgroup service authority stores only the active job object's integer
identity guard, never a second strong live job alias. `_JobCgroup` keeps the
service authority needed for validation and exact close/remove.

## 5. Poll and drain state machine

The drain loop creates a fresh `select.poll()` registration set on every
iteration from the current owned state. It never calls `unregister`, so there
is no poll-object/local-state commit window and simultaneous readiness cannot
double-unregister a descriptor.

Registration masks are exact:

- stream readers: `POLLIN|POLLHUP|POLLERR`;
- poll-only pidfd: `POLLIN|POLLERR`;
- `cgroup.events`: `POLLPRI|POLLERR`, never `POLLIN`.

Each ready stream receives at most one 64-KiB read per dispatch pass. The loop
processes every other authority in the same ready snapshot at most once and
only then constructs and polls the next set. This is fairness,
not a byte cap: total capture remains unbounded and byte-exact. A continually
writing descendant therefore cannot starve terminal or empty-cgroup handling.

Only an actual zero-length `read` sets stream EOF. `EINTR` retries and
`EAGAIN` returns to poll. Any other reader error is channel uncertainty and
fail-stops. stdout/stderr spool write, allocation, fsync, seek or readback
failure marks that stream unavailable, kills containment, continues discarding
and reading until actual EOF, then returns a contained failure. Exec-error
storage/read/shape uncertainty always fail-stops.

Every destructive pipe read uses a pre-existing per-stream read ledger and the
micro-transaction mask. Bytes are placed in that ledger before mask restore.
If a direct injected exception makes it impossible to know whether a read
advanced the FD, exec-error fails-stops; stdout/stderr are permanently marked
`UNAVAILABLE`, killed/drained to a later actual EOF and can never be published
as COMPLETE. The guard is released after one read, so it cannot defer signals
across the drain.

Leader handling commits facts in this order:

1. readiness on the duplicate pidfd;
2. `peek_wait` and copied terminal fact, then phase `LEADER_TERMINAL`;
3. exact original-handle `reap` matching the copied terminal;
4. close the duplicate and enter `LEADER_REAPED_DRAINING`;
5. independently prove stream EOF and cgroup empty.

If a direct issuer exception occurs after reap but before local commit, the
ledger inspects the exact native state and finishes from the already copied
terminal fact; it never calls `peek_wait` or `reap` twice. `POLLERR`, `POLLHUP`
or `POLLNVAL` on pidfd/cgroup authorities is uncertainty and fail-stops. Stream
`POLLERR` is accepted only when a subsequent read proves EOF; otherwise the
read rule above applies.

## 6. Exact move and cleanup commits

`settle_blocked` and `release_and_collect` validate the exact wrapper/backend
binding before mutation. Wrapper consume, backend active-guard clear and local
ledger ownership occur inside one guarded block. If direct issuer delivery
occurs between those assignments, the method completes the local move and
settles from the still-held private fields; it never returns authority to the
consumed alias.

Positive cleanup validates permit, settled job, backend generation, job key
and observation digest before mutation. Exact cgroup removal occurs while the
permit and `SettledJob` remain OPEN. Only after removal and FD closure are
proved do one-shot permit consumption, settled-wrapper consumption and backend
transition to `IDLE` commit. Any removal/close uncertainty fail-stops; no
ordinary interruption can consume the only permit before removal.

One short micro-transaction guard covers the complete cleanup commit from
`rmdir`, exact FD close and post-removal absence proof through permit consume,
`SettledJob` consume and backend `IDLE`. All objects are prevalidated before
entering it. The guard ledger distinguishes pre-remove, removed/closed and
fully committed states; a direct post-rmdir interruption can only finish the
known commit or fail-stop, never return with a consumed permit and live job.

Failure facts are constructed before closing their last live source facts when
possible, then all authorities close under the guarded boundary. If immutable
fact construction or a required close cannot complete, the process fail-stops.
No allocation failure may escape after authority consumption as an untyped
ordinary exception.
