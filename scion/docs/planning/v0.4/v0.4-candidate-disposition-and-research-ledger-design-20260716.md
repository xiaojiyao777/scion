# v0.4 Candidate Disposition and Research Ledger Design

*Date: 2026-07-16*
*Status: historical; its clean-parent rule was superseded on 2026-08-08 by
V3 §11.2 and the active `TASK.md`*
*Architecture authority: `scion/design/scion-architecture-v3.md` plus the
updated v0.4 direct-runtime addendum*

> Historical note: the `REJECT_TO_CODE_PARENT` screening-fail rule described
> below contradicted V3 §11.2. The active runtime now retains a
> Contract/Verification-passing, completed-screening candidate as the verified
> provisional branch head; only Contract/Verification rejection returns to the
> preceding executable source. This document remains as chronology, not current
> implementation authority.

## Decision

Scion currently conflates two different kinds of continuity:

```text
evidence continuity
code inheritance
```

Every safe screening result must remain visible to later research. It does not
follow that code rejected by Protocol should remain in the next executable
candidate.

R11c proves this is not a theoretical distinction. H1's route-elimination code
was Verification-valid but selected 511 times without producing one nonempty
destroy result. Expanded screening failed and the hypothesis was marked
rejected, yet H1 still became the code base for H2 SWAP*. H2 is therefore a
cumulative H1+H2 candidate and cannot isolate SWAP*.

The correction has two connected parts:

1. immutable candidate snapshots plus deterministic post-Protocol disposition
   and continuation-base planning;
2. a normalized, reversible research ledger that preserves all safe evidence
   without repeatedly expanding the same facts into prompt trees.

This is an architecture correction, not a new gate, retry, budget, blacklist,
or model-written branch decision.

## R11c Failure Chain

The current implementation behaves consistently with the old direct-runtime
addendum:

1. Code materializes a staging workspace from the branch head.
2. Verification passes.
3. Before Protocol decides scientific value, staging replaces the durable
   branch workspace.
4. Protocol returns `fail` and Decision maps it to `CONTINUE_EXPLORE`.
5. The finalizer marks the hypothesis rejected but deliberately retains the
   verified workspace.
6. SourceLedger reconstructs current source from every Verification-passed
   branch step, regardless of its later Protocol disposition.
7. A later candidate and eventual promotion therefore inherit rejected code.

Formal candidate artifacts faithfully preserve that cumulative closure. Replay
integrity is not the defect; scientific ancestry is.

R11c also exposed the pre-Protocol side of the same ownership problem. H3 used
a clean champion base, but its Code response left six undefined references.
Light Verification correctly rejected the candidate and restored the clean
workspace. `CampaignLoop` then treated typed `RESEARCH_REJECTED` like every
other non-evaluated outcome and stopped the eight-observation invocation at
four formal results. The rejected attempt was terminal; the requested
observation program should not have been.

The word `clean` is also overloaded. `branch_code_status=clean` currently means
the workspace passed Verification. It does not mean the workspace is free of
Protocol-rejected ancestry.

## R0: Pre-Protocol Attempt Disposition

Candidate disposition after Protocol and pre-Protocol research rejection are
separate typed lifecycles. H Contract, Patch Contract, or Verification may
produce `ATTEMPT_REJECT_TO_BASE` only when the rejection and cleanup are fully
structured and durably finalized.

`ATTEMPT_REJECT_TO_BASE` means:

- the current attempt and H are rejected and immutable;
- no Protocol observation or formal-round count is created;
- the failed staging/candidate is archived by exact reference and cannot enter
  SourceLedger, research head, or promotion ancestry;
- the branch remains on its exact clean code parent;
- Scheduler may create a new attempt with a new H ID on that base;
- the rejected H/C cannot be repaired, regenerated, or called again.

Provider parse/schema failure, infra/resource failure, interruption, replay
conflict, incomplete identity, or scheduler non-progress is not a recoverable
research rejection and stops/holds the invocation fail-closed.

One `ResearchRejectionCompletionStore` owns an immutable intent containing:

```text
completion_id
attempt_id / hypothesis_id
rejection_phase / reason_code / failed_check
structured_diagnostic_metadata
clean_code_parent_id/hash/ref
rejected_candidate/archive_ref
workspace_disposition
target_branch_state
typed_execution_outcome
```

It atomically commits H status, branch/base state, and one typed completion
event, then performs idempotent archive/cleanup with a receipt. Reopen finishes
prepared/state-committed rejection intents before branch restore or any
provider call. A crash before a provable intent yields a hold, not a guessed
rejection or repeated call.

Requested rounds count only formal Protocol observations. Scheduled attempts
and rejection phase/reason remain separate audit counts. A run that reaches its
formal target despite prior rejections is complete/valid; a zero-evaluation
rejection-only run remains invalid; explicit operator stop before the target is
valid-but-incomplete. No rejection cap or attempt budget is introduced.

### R1 implementation contract

R1 is a self-contained pre-Protocol completion slice. It does not implement or
depend on the later candidate-disposition mapper, continuation-base planner,
SourceLedger migration, or normalized research ledger.

One `ResearchRejectionCompletionStore` owns an immutable intent with state
`prepared -> state_committed -> committed`. Its natural unique owner is the
durable provider attempt identity within the campaign, not a mutable in-memory
session reference. Preparation must verify the recorded proposal-attempt
transition, H/branch/phase ownership, persisted exact clean Branch/H source,
and any Verification candidate identity. A stable payload digest provides the
completion ID, while a unique `(campaign_id, provider_attempt_id)` constraint
prevents the same attempt from acquiring a second completion through payload
drift.

The campaign identity itself must first become durable. The campaign database
owns one singleton campaign ID that composition claims before constructing the
evidence recorder or any service that writes campaign-scoped events. Reopen
reuses it instead of generating a new process UUID. A legacy database may adopt
zero or one distinct existing event campaign ID; multiple distinct IDs are an
identity conflict and fail closed. This makes provider-attempt uniqueness,
startup recovery, status queries, and rejection audit counts stable across
reopen.

Provider-attempt validation is control-grade and occurs in the preparation
transaction. The store loads the referenced transition group from SQLite and
requires one coherent `started -> generated` sequence with no conflicting
terminal row. Code-attempt rejection must additionally prove its generated H
parent, continuation ID, H ID, and H digest. Report-oriented trajectory readers
and process-local proposal refs are not completion authority. The same
`BEGIN IMMEDIATE` covers transition/H/Branch/candidate validation, natural-key
conflict detection, and intent insertion; a natural-key hit is idempotent only
when the complete payload digest is identical.

One SQLite `BEGIN IMMEDIATE` transaction changes the H status to
`research_rejected`, restores/upserts the exact clean Branch target, writes one
typed rejection event keyed by the completion ID, and advances the intent to
`state_committed`. Verification rejection then completes only through a
completion-ID-derived, identity-checked archive/cleanup receipt. Missing or
tampered candidate/archive identity is a conflict, not a successful cleanup.
H/Patch Contract rejection records `workspace_disposition=none`. Only after
cleanup is proven does the store mark the intent `committed`.

The H Contract, Patch Contract, and Verification paths all call one thin
`ResearchRejectionFinalizer`; they no longer independently mark H, save Branch,
record the authoritative rejection event, archive, or clean. A returned
`StepResult` and its audit projection carry an immutable typed
`ATTEMPT_REJECT_TO_BASE` marker and completion ID only after the store proves
`committed`. The marker alone grants no authority. Process-local approved-H,
patch, current-H, and pending-candidate bindings are then removed so the next
scheduled call can only create a new H.

`CampaignLoop` schedules forward only when both conditions hold:

```text
execution_outcome == RESEARCH_REJECTED
attempt_disposition == ATTEMPT_REJECT_TO_BASE with a committed completion ID
```

Before continuing, the loop calls the store's read-only committed verifier; the
verifier binds the marker to the intent digest, typed event, Branch, H, provider
attempt, phase, and any required archive receipt. It increments
scheduled/rejection audit counts but not formal rounds. A repeated completion
ID in the same invocation is a non-progress identity conflict and stops
fail-closed; it is not a retry cap. Every other non-`EVALUATED` outcome, an
uncommitted/legacy research rejection, and reconcile-lifecycle rejection retain
the current invocation-terminal behavior.

Durable completion rows seed rejection counts after reopen; `StepRecord` and a
new process's in-memory counters are not recovery authority. Run validity treats
committed scheduler-forward rejection as a zero-formal-count audit outcome:
reaching the requested formal target remains valid and complete, a
rejection-only run is invalid, and an explicit operator stop before the target
after at least one evaluation is valid but incomplete. Other non-evaluated
outcomes remain blocking.

Startup recovery order is:

```text
recover pending research rejection completions
recover pending Decision completions
restore persisted active branches
audit unowned active attempts and install a conservative hold
```

A crash before a provable rejection intent cannot be guessed into a rejection
or another provider call. The unowned audit walks the active-H ownership graph,
not every historical attempt row. It excludes a valid code child, a committed
rejection child, a verified-candidate/Decision owner, and stale/reconcile
lifecycle ownership. It holds one owning H for a generated H with no code
owner, a started code attempt without a terminal transition, a generated code
attempt without rejection/verified-candidate ownership, or ambiguous identity.
Parent H and code child cannot create duplicate holds. A stale branch or changed
champion anchor is an identity conflict; R1 never rewrites it to `EXPLORE`.
Reopen holds a genuinely unowned attempt as `NOT_EVALUATED`.
Fault coverage must span prepare, H update, Branch upsert, typed event, SQLite
commit, archive receipt, partial cleanup, and final mark, converging to one
completion/event/archive with zero provider calls during recovery.

R1 acceptance on 2026-07-16 closes this contract. The implementation binds the
durable campaign singleton, exact provider transition, canonical complete-H and
rejected-Patch digests, clean Branch/H source and target, typed event, and any
candidate archive receipt. Startup recognizes exact committed Decision and
physically validated candidate owners before auditing legacy transition graphs;
unrelated historical malformed rows cannot poison a current exact owner, while
rows claiming that owner still fail closed. Independent review found no P0/P1.
The complete Scion suite passes `2145` with `1` skipped in `490.33s`, compileall
and `git diff --check` pass, and no solver interchange file remains. D1 is the
next implementation slice.

## D1: Immutable Candidate Snapshots

Verification produces an immutable, content-addressed candidate snapshot. It
must not overwrite the branch research head.

Each snapshot records at least:

```text
candidate_id
candidate_code_hash
candidate_snapshot_ref
code_parent_candidate_id/hash/ref
base_champion_id/hash
evidence_parent_hypothesis_id
hypothesis_id
mechanism_owner_id
verified_touched_files
proposal_patch_ref/digest
verification_result_ref
```

The following identities are distinct:

- `code_parent_candidate_id`: which exact code was inherited;
- `evidence_parent_hypothesis_id`: which prior evidence informed H;
- `base_champion_id`: the declared champion ancestry;
- `research_head_candidate_id`: the candidate eligible to act as a future code
  base;
- `evaluated_candidate_id`: the exact candidate currently entering Protocol.

Evidence ancestry may include a rejected attempt. Code ancestry may not inherit
it unless a later fixed replay explicitly materializes that rejected snapshot
as a diagnostic arm.

## D2: CandidateDispositionMapper

After Protocol and deterministic Decision, a pure mapper derives one typed
candidate disposition from trusted fields only.

| Decision and typed Protocol gate | Disposition | Code consequence |
|---|---|---|
| `EXPAND_SCREENING` / `EXPAND_VALIDATION` | `EXACT_REUSE` | same candidate hash continues with no H/C |
| `QUEUE_VALIDATE` / `QUEUE_FROZEN` | `EXACT_REUSE` | same candidate hash enters the next stage |
| `CONTINUE_EXPLORE` and gate `fail` | `REJECT_TO_CODE_PARENT` | candidate is archived; research head returns to its clean code parent |
| `CONTINUE_EXPLORE` and gate `unclear` or `continue` | `PROVISIONAL_HEAD` | candidate may be refined, but a mechanism pivot still uses a clean base |
| `ABANDON` | `REJECT_TERMINAL` | candidate archived and branch terminalized |
| `PROMOTE` | `PROMOTE_EXACT` | exact frozen candidate snapshot becomes champion |

The typed gate outcome is authoritative. A statistical label such as
`uncertain` cannot override `gate=fail`; R11c H1 must map to
`REJECT_TO_CODE_PARENT`.

The mapper reads no hypothesis prose, mechanism telemetry, prompt content, or
problem-specific operator name. It does not change Protocol or Decision.

Hypothesis status becomes explicit:

```text
rejected     -> gate fail or abandon
provisional  -> unclear/continue and eligible for bounded refinement
advanced     -> exact candidate queued/expanded
promoted     -> exact frozen candidate promoted
```

### D1 implementation contract

The implementation-slice names below are authoritative: D1 contains the
immutable snapshot foundation and the pure disposition truth table described
in the preceding D1/D2 sections. D2 wires those facts into Decision completion;
D3 adds continuation planning and problem-owned mechanism binding; D4 migrates
SourceLedger, promotion, and replay.

D1 is independently testable but does not switch production branch ownership.
It adds two cohesive components:

```text
CandidateSnapshotStore
CandidateDispositionMapper
```

It does not modify `Branch`, `StepRecord`, `DecisionFinalizer`,
`DecisionCompletionStore` v1, SourceLedger, promotion, formal replay, prompt
history, status, or postrun accounting. It does not write a shadow snapshot in
parallel with the current production `VerifiedCandidateCommitRecorder`.
`CandidateSnapshotStore` is the designated successor: D2 will make new
campaigns consume it and retain the old verified-candidate artifact only as a
read-only compatibility owner for exact legacy pending validation/frozen
work. Until D2-D4 are complete, the rejected-ancestry defect remains open and
no new generative matched campaign may start.

This exclusivity is durable, not a composition convention. Each campaign DB
owns one singleton `candidate_ownership_mode` with value
`legacy_verified_commit_v1` or `candidate_snapshot_v1`. The snapshot store must
claim and verify the latter before any prepare; a campaign with legacy verified
candidate ownership claims the former and cannot also write a new snapshot.
D2 selects the mode before Verification and may read the legacy owner only on
the explicit legacy path. Mode is never inferred from artifact presence, and
mixed new writes fail closed.

`CandidateSnapshot` is frozen and versioned. Its stable full-length SHA-256
`candidate_id` binds the canonical ownership identity, including campaign,
typed origin, Branch/lineage, candidate code and executable snapshot hashes,
typed code parent, champion anchor, H/evidence parent, mechanism owner,
actual touched files, Patch digest, and stable Verification identity digest. `created_at`,
absolute paths, physical refs, temporary paths, and JSON presentation do not
enter the ID. Thus executable content identity and candidate lineage identity
remain distinct:

```text
executable_snapshot_hash = execution-relevant materialization identity
candidate_id             = canonical snapshot ownership identity
```

The legacy workspace tree hash is retained for compatibility but is not a
collision-free manifest encoding because it concatenates path and content
without length framing. Candidate ID therefore also binds canonical parent and
candidate execution-manifest digests over ordered path, per-file SHA-256, role,
and the legacy aggregate hashes. One candidate ID cannot name two different
file partitions even when their legacy aggregate hash is equal.

A code parent is typed `champion` or `candidate`. Champion parents have no
fabricated candidate ID but require an exact hash and root-contained ref.
Candidate parents require ID, hash, and ref. `mechanism_owner_id=unclassified`
is allowed during D1 but grants no provisional-refinement authority; D3 may
write a classified owner only for a newly created snapshot and never mutate an
existing one.

Champion ancestry and immediate code parent cannot disagree. A champion parent
requires `base_champion_hash` equal to its executable parent hash. A candidate
parent requires the child to inherit the exact ancestor snapshot's champion ID
and hash. Snapshot construction never accepts a caller-supplied contradictory
champion anchor or infers one from a path name.

`origin_kind` is an enum: `direct_code_attempt` and `reconcile_transition` are
the D1 inputs, while `fixed_replay` is reserved for D4. `origin_id` is the
durable generated-code attempt, typed reconcile transition, or later replay
manifest-entry identity, never merely an H ID, legacy formal candidate ID, or
process-local session ref. `EXACT_REUSE` refers to the existing candidate ID
and creates no new origin or snapshot. Snapshot `candidate_id` is a distinct namespace from the legacy
formal-candidate artifact's short report ID. D1 never reads a formal-candidate
index or accepts that short ID as snapshot ownership. D4 bridges them only with
two explicitly named fields, `snapshot_candidate_id` and
`formal_artifact_candidate_id`.

The snapshot ref identifies an immutable manifest/delta closure, not another
full copy of the repository. The closure freezes exact parent identity,
parent/candidate execution manifests, full contents for changed and created
identity files, deletion tombstones, normalized Patch, and structured
Verification result. `verified_touched_files` is derived from the actual
parent-to-candidate identity difference, including activation/registry changes;
it is not copied from proposal target paths. Exact materialization applies the
closure to its exact parent and revalidates both code and executable snapshot
hashes. This avoids recreating the Git-restorable static-tree duplication
removed by retention cleanup.

The production-facing store does not accept a caller-assembled closure or a
caller-supplied editable manifest. It accepts a typed `CandidateSnapshotRequest`
without manifest fields and owns a trusted `identity_manifest_for(workspace)`
provider injected at construction. The store obtains both parent and candidate
manifests from that provider, builds the closure, then obtains them again before
prepare and requires the rebuilt execution manifests to be identical. This
double read includes the activation file and closes both incomplete-manifest
substitution and workspace drift between snapshot construction and durable
prepare. The lower-level closure builder remains internal and cannot be the
production recording API.

Candidate-parent closure reads are also registry-pinned. The storage-agnostic
codec accepts a typed ancestor resolver; the store implementation resolves
only a committed row with the exact candidate ID and canonical ref, reads the
artifact once, and decodes it against that row's immutable full-artifact
SHA-256. The same resolver is reused at every recursive parent hop. Candidate-
parent build, validation, and materialization without a pinned resolver fail
closed; champion-parent operation remains standalone. An envelope checksum or
stable candidate ID alone is not a substitute because diagnostic Verification,
Patch hint, and repair-attribution bytes intentionally do not enter candidate
identity.

Artifact filesystem operations pin the root-owned `candidate_snapshots`
directory with a directory descriptor opened using `O_DIRECTORY|O_NOFOLLOW`.
Final and temporary files are opened relative to that descriptor with
`O_NOFOLLOW`, checked as regular files, and renamed, unlinked, and fsynced by
descriptor. A path-level symlink check followed by an absolute reopen is not
sufficient because an intermediate directory can be exchanged between those
operations. Before a registry row can become committed, the store reopens the
canonical campaign root from its trusted parent descriptor, requires it to
match the construction-time and operation-pinned root identity, then reopens
the canonical child and requires that device/inode identity to match the
operation-pinned artifact directory. Writing safely into a renamed-but-orphaned
root or child directory is not a successful commit.

Every changed `code_identity` file must be claimed by the normalized Patch.
An unclaimed delta is allowed only when its manifest role is the explicit
framework-owned `activation` role (currently `registry.yaml`). Hidden or
incidental code-identity drift fails closed even if Verification passed.

The Verification value has two identities. The immutable closure preserves the
complete structured result, including diagnostic detail, metadata, and timing;
the artifact/store digest protects those bytes. `candidate_id` binds a separate
stable `verification_identity_digest` containing only schema, overall pass,
and the ordered typed check name/pass/severity facts. Timing, diagnostic prose,
absolute or temporary paths, and arbitrary metadata never enter candidate ID.
Changing stable check identity changes candidate ID; changing only diagnostic
rendering changes the artifact digest but not candidate ownership identity.
Snapshot creation additionally enforces the Verification invariant: overall
pass requires every uniquely named check to pass, null failure severity/detail,
typed check severity, and nonnegative non-boolean elapsed time. An internally
contradictory or malformed result cannot become candidate ownership.

The store uses one append-only `candidate_snapshots` registry with a natural
unique key `(campaign_id, origin_kind, origin_id)` and immutable canonical
payload digest. Atomic artifact write plus `prepared -> committed` state makes
same-origin/same-payload recording idempotent and same-origin drift a conflict.
All refs remain relative to the campaign root; path escape, symlink traversal,
missing files, manifest or delta tamper, parent drift, and hash mismatch fail
closed. D1 does not emit a formal experiment event or change any formal count.

The pure mapper consumes only a narrow trusted fact record: Decision, typed
Protocol stage/gate, typed Decision reason codes, and the safe candidate versus
champion failure counts needed to validate the existing screening partial-
champion path. It never reads statistical labels, numeric effect estimates,
free text, telemetry, mechanism names, Scheduler state, or problem strings.
Those facts are projected only from the immutable `DecisionOutcome` typed
reason output and its exact `features_snapshot`; callers cannot assemble them
by rereading `ProtocolResult`, raw metrics, mutable Branch summaries, artifacts,
or report JSON. The data flow is one-way:

```text
DecisionOutcome -> CandidateDispositionMapper -> D2 completion
```

Snapshot IDs, disposition values, and continuation facts never enter `DecisionFeatures` or
`SafeFeatureExtractor`; the mapper is a post-Decision ownership projection, not
a second decision layer.
The normal mapping is exactly the table above, including all three stages.
Additional deterministic rules are:

- any post-Verification `ABANDON` maps to `REJECT_TERMINAL`, including hard
  safety outcomes with no usable Protocol gate;
- `CONTINUE_EXPLORE + gate=fail` always maps to `REJECT_TO_CODE_PARENT`, even
  when a statistical label says `uncertain`;
- `CONTINUE_EXPLORE + gate=unclear|continue` maps to `PROVISIONAL_HEAD`;
- `CONTINUE_EXPLORE + gate=pass|expand` maps to `PROVISIONAL_HEAD` only for
  screening with exact `SCREENING_PARTIAL_CHAMPION_EVIDENCE`, zero candidate
  failures, and positive champion failures;
- every other Decision/stage/gate combination fails closed;
- legacy-only `VALIDATION_REPAIR_REQUIRED` is never a new disposition input.

D1 acceptance requires exhaustive truth-table and invalid-combination tests;
free-text/statistical/telemetry noninterference; stable candidate identity and
idempotent recording; field-drift identity changes; create/modify/delete and
activation deltas; path/symlink/tamper/missing-parent failures; crash recovery
around registry and artifact commits; and byte-compatible legacy Decision,
verified-candidate, formal-artifact, prompt, and status behavior. Existing
production behavior must remain unchanged in this slice.

Implementation status (2026-07-16): D1 foundation is complete and remains
unwired. The immutable value/facade, canonical codec, workspace/materialization,
store, SQLite registry, and pure disposition mapper are separated by
responsibility; no production Decision, Branch, StepRecord, formal event, count,
or index imports them. The combined focused suite passes `128`; the correctly
rooted full Scion suite passes `2273` with `1` skipped in `492.10s`; compileall,
Black, and diff checks pass; and independent adversarial review has no open
P0/P1. Its review forced pre-prepare and pre-commit authoritative manifest
reads, exact-payload relocation recovery, digest-pinned recursive ancestors,
and descriptor-pinned artifact/root reachability before commit. Remaining P2
hardening is explicit: standalone low-level workspace/ref reads assume
exclusive orchestrator ownership, canonical Patch identity still lives under
the evidence-recording namespace, the value/codec/materialization facade uses
lazy imports, and the supplied campaign DB path remains a trusted dependency.
These are not permission to wire D1 early; D2-D4 still own production migration
and the rejected-ancestry defect remains open until that migration completes.

### D2 implementation contract

D2 replaces the post-Verification candidate owner for new campaigns and makes
snapshot-mode evaluation and Decision ownership recoverable. It does not
select a creative continuation base, classify a future H, rewrite
SourceLedger, or commit a champion. Those remain D3 and D4 responsibilities.

The mode-dispatched flow is one-way:

```text
candidate_snapshot_v1
  Verification
    -> CandidateSnapshot + initial CandidateEvaluationSlot
    -> dispatch claim
    -> canary/Protocol receipt
    -> exact normalized DecisionOutcome
    -> CandidateDispositionMapper
    -> Candidate DecisionCompletion v2

legacy_verified_commit_v1
  exact pre-D2 pending validation/frozen owner
    -> unchanged DecisionCompletion v1 compatibility completion
```

There is no shadow write, decoder fallback, or in-place mode switch.

#### Atomic campaign open and writer exclusivity

Campaign open uses a typed `CampaignOpenRequest` containing `NEW` or `REOPEN`,
a stable campaign ID, and an optional expected mode. The CLI or caller creates
and persists this identity outside composition and reuses it after a bootstrap
crash; composition never generates or adopts a fresh random ID on reopen. The
first ownership `BEGIN IMMEDIATE`, after schema creation but before any other
writer or recovery, owns `campaign_identity` and
`candidate_ownership_mode` together:

- `NEW` requires no prior durable campaign state, including event, Branch, H,
  champion, completion, or ownership rows, and atomically claims the supplied
  ID with `candidate_snapshot_v1`;
- a successfully bootstrapped request subsequently resolves as `REOPEN` and
  must match the exact durable ID and expected mode;
- a pre-D2 `REOPEN` with identity but no mode atomically claims
  `legacy_verified_commit_v1`;
- a pre-R1/pre-D2 DB without identity may inspect durable event campaign IDs:
  zero or one nonempty ID may be adopted with legacy mode in the same
  transaction, while multiple IDs fail closed;
- missing, contradictory, or ambiguous requests fail closed;
- artifacts, Branch markers, formal indexes, and directory presence never
  choose mode.

Mode remains immutable. Composition installs exactly one positive owner API:

- snapshot mode exposes a writable paired snapshot/evaluation store and v2
  completion store; it has no writable legacy verified-candidate API;
- legacy mode exposes a narrow `LegacyVerifiedCandidateReader` plus v1
  completer with no record/promote methods; it may finish only a physically
  validated exact pending validation/frozen candidate and cannot begin a new
  generative attempt;
- a legacy DB is completion-only in place. Any later creative continuation is
  a new snapshot-mode successor campaign anchored to the exact champion/clean
  parent with an evidence link to the legacy campaign; legacy mode never
  changes in place.

Already durable v1 intents preserve decoder and recovery behavior, including a
historical `legacy-terminal-candidate-identity.v1`. D2 never uses the Branch/H
fallback to prepare a new v1 intent. New compatibility completion requires the
verified artifact, Branch, H, Patch, workspace hash, committed promotion marker,
and pending validation/frozen state to agree physically and canonically. A
legacy root without that exact owner is read-only held.

For identical frozen inputs, v1 `intent_json`, `intent_sha256`, transaction ID,
typed-event audit payload, event ID/kind, decoder, and status transitions remain
byte-compatible. Runtime timestamp and created/updated columns are excluded
from cross-run byte equality unless the test clock is frozen. Golden fixtures
for this surface are captured before D2 changes. The v1 module gains no mode
field or mode branch; the outer dispatcher owns mode.

#### Immutable parent and Verification handoff

The creative pipeline retains distinct typed leases:

```text
parent_lease         exact owner selected before Code/Patch
candidate_workspace isolated staging produced by Patch
```

Every creative lease, including a fresh Branch's `INITIAL_CHAMPION` lease, is
issued by a committed D3 `ContinuationPlanCompletion`. It binds parent kind,
candidate/champion ID, code hash, executable snapshot hash, canonical ref, and
execution-manifest digest. The physical path is validated against the lease but
never supplies ownership identity.

A champion parent is the campaign-local immutable/read-only champion snapshot;
a deletable branch copy cannot be its long-term ref. A candidate parent ref is
the registry-pinned ancestor snapshot artifact; its physical workspace may be
an exact temporary materialization. Branch workspaces never become snapshot
ancestry owners, so all parents remain resolvable after staging and Branch
cleanup.

Snapshot-mode Patch application records candidate hash only in the isolated
lease. It does not call `record_candidate_code()`, change Branch source hashes,
replace `branch_workspaces`, or write a legacy promotion journal. After
Verification and before any post-Verification Branch persistence, the pipeline
builds `CandidateSnapshotRequest` from the parent lease and candidate staging.

A direct origin is the durable completed code-phase proposal-attempt
`attempt_id` bound to the same campaign, Branch, and H. H IDs,
hypothesis-attempt IDs, process-local refs, and formal IDs are invalid origins.
Reconcile first writes a typed `reconcile_transition` binding old/new champion,
Branch, H, Patch, and parent; its transition ID is the reconcile origin.

Mechanism ownership has two typed projections. `ProspectiveHOwner` is computed
after H Contract from Contract-valid structural H fields and is the only
classification used by D3 planning. `VerifiedCandidateOwner` is computed after
Patch Contract and authoritative touched-path Verification and is frozen into
candidate identity. Both return one known owner or `UNCLASSIFIED`.

If D3 selected `PROVISIONAL_CURRENT`, the previous candidate owner,
`ProspectiveHOwner`, and `VerifiedCandidateOwner` must be the same known owner.
A mismatch or any `UNCLASSIFIED` on that path is a typed lineage-integrity
rejection after Verification but before snapshot/Protocol: staging is removed,
the code attempt completes with non-counting rejected ownership, and no
candidate or evaluation slot is created. It never silently replans or retries
the patch. This protects ancestry; it is not a scientific quality gate, budget,
cap, or mechanism preference. Patch Contract checks declared paths early and
Verification closes actual/hidden-path drift. Clean/champion bases accept a
valid `UNCLASSIFIED` result, which remains immutable and conservative.

#### Paired snapshot and initial evaluation ownership

After D2, the writable facade exposes only
`record_for_evaluation(candidate_request, initial_slot_request)`. Bare
`record()` becomes an internal foundation helper and cannot commit a row in a
production campaign. `initial_slot_request` contains only typed pre-snapshot
stage/ordinal and anchor inputs; callers cannot supply a derived snapshot ID or
evaluation ID.

The store builds the closure and seals the slot. One SQLite transaction inserts
both rows as prepared. After the descriptor-pinned artifact rename, a second
SQLite transaction advances the pair together:

```text
snapshot prepared -> committed
slot     prepared -> pending
```

Filesystem rename and SQLite are not physically atomic; the paired recovery
protocol provides logical atomicity. DB triggers and strict validators forbid a
committed snapshot without its initial slot and a pending slot referencing a
noncommitted snapshot. Old or corrupted snapshot-only rows fail closed; recovery
never guesses a slot. `recover_pending()` operates on the pair and either
commits intact bytes or holds both owners.

#### CandidateEvaluationSlot and dispatch receipt

Candidate and evaluation identities are distinct. D2 freezes
`candidate-evaluation-slot.v1`; its canonical full SHA-256 `evaluation_id`
binds exactly:

```text
campaign_id
snapshot_candidate_id
snapshot artifact ref and full SHA-256
branch_id and hypothesis_id
source lineage ID and source_hypothesis_sha256
source_code_anchor_digest
code-parent kind, ID, hash, ref, and manifest digest
comparison champion ID, code hash, weight revision, ref, and manifest digest
problem-spec, Protocol-version, split-manifest, and seed-ledger hashes
typed Protocol stage
stage kind = initial | expansion
stage ordinal
screening and validation expansion counts
hypothesis action and selected structural surface
canonical evaluation request digest
```

`source_code_anchor_digest` covers only stable scientific ownership: campaign,
Branch/lineage, exact source ref/hashes, H identity/proposal digest, code parent,
and stage counts. Timestamps, scheduler control state, diagnostics, infra
observational fields, and public summaries are excluded. A full mutable Branch
digest is not part of `evaluation_id`.

Initial ordinal is zero. Expansion ordinal is positive and equals the
prospective count for that stage; the other stage count is unchanged. Entering
a new stage resets its ordinal to zero but retains cumulative expansion facts.
Contradictory ordinal/count/state combinations fail strict decode. The slot is
armed under the champion lock. Before dispatch, its comparison champion must
still be current and every stable source anchor must match. After dispatch or a
terminal receipt, the pinned comparison snapshot only has to remain resolvable
and unmodified; a later global champion/weight change cannot invalidate or rerun
the completed observation. Nonpromotion completion records the result against
that historical comparison and then applies a typed stale/reconcile overlay.
D4 separately requires current-champion CAS for promotion.

Slot lifecycle is explicit:

```text
prepared -> pending -> dispatched -> receipted -> consumed
                       \-> execution_uncertain
                       \-> blocked_infra -> pending (explicit operator resume)
receipted -- PROMOTE_EXACT -> promotion_pending -> consumed (D4)
receipted -- invalid Decision mapping -> decision_invalid
```

`pending -> dispatched` commits before any external canary/Protocol call.
`claim_dispatch()` atomically validates the current control Branch, applies the
one legal stage-specific Scheduler transition, writes an
`EvaluationDispatchClaim` containing exact pre/post-transition Branch digests,
and advances the slot. The claim, rather than the evaluation ID, owns the
mutable control transition. An operator-resume successor explicitly authorizes
the restored already-running state and another claim with a typed identity
control transition for the same evaluation ID; it does not schedule the Branch
a second time. There is no automatic retry or attempt cap.

A dispatched slot without a terminal receipt is `execution_uncertain` on reopen
and is never automatically dispatched again. If an evaluation-ID-aware backend
can query the exact terminal result, it may install that receipt; otherwise an
operator must resolve the uncertainty. Canary configuration/infra failure takes
the exact `dispatched -> blocked_infra` edge and writes a nonterminal
`EvaluationInfrastructureRecord`, not a Protocol receipt. Only an explicit
operator resolution may restore Branch control state and move the same slot to
`pending`. These states are not a retry, cap, or budget.

`ProtocolEvaluationReceipt` is a non-counting durable owner written immediately
after evaluation returns and before Decision coordination. It binds the
evaluation ID, snapshot and comparison anchors, canonical request, complete
canary result, optional canonical ProtocolResult, raw metrics ref and digest,
case IDs, seeds, dispatch claim, `formal_protocol_observation`, its typed reason
and identity, and receipt digest. The formal-observation flag is validated by
the existing Protocol/accounting rules; mere presence of a ProtocolResult is
not sufficient. These facts reproduce the same SafeFeature extraction and
deterministic Decision without rerunning Protocol. A candidate-attributable
canary failure has no formal Protocol observation but still receives a terminal
receipt. A crash before receipt leaves execution uncertain and creates no
formal observation.

No snapshot-mode `EVALUATED` event, experiment counter, StepRecord, or legacy
formal artifact is written before v2 state commit. Raw metrics and receipts are
non-counting evidence until owned by that completion.

EXACT_REUSE creates a distinct next slot for the same
`snapshot_candidate_id`; it creates no H, C, origin, snapshot, or candidate ID.
D3 must exact-materialize the committed closure for every next slot, or fully
revalidate a retained isolated workspace manifest before reuse. `no cleanup`
never means trusting a post-Protocol mutable path.

#### Exact DecisionOutcome transport and infrastructure boundary

Canary normalization precedes Decision coordination. Candidate-attributable
canary failure produces the exact `ABANDON/CANARY_FAILED` DecisionOutcome,
maps to `REJECT_TERMINAL`, and has zero formal Protocol-observation count.
Canary configuration/infrastructure failure produces `BLOCKED_INFRA` with no
DecisionOutcome, does not call the mapper, consume the slot, change H, or
terminalize Branch, and uses the existing explicit operator-resume lifecycle
for the same evaluation ID. It writes only the nonterminal infrastructure
record and cannot move the slot to `receipted`.

Runtime guard facts and candidate runtime failures inside DecisionFeatures may
affect Decision. Runtime diagnostic projections, public canary diagnostics,
and bypass codes are reports only.

`DecisionCoordinator` creates one frozen normalized `DecisionOutcome` after
the receipt. Outward Decision, engine reason codes, feature snapshot, and
mapper input are derived properties of that object; there is no second mutable
Decision field or separate normalized truth tuple. `EvaluationExecutionResult`
carries the exact outcome and receipt identity through Explore, eval-only,
reconcile, Campaign, and Finalizer.

The mapper never reconstructs input from ProtocolResult, raw metrics, Branch,
mutable maps, artifacts, reports, or diagnostics.

#### Candidate DecisionCompletion v2

D2 adds an independent `candidate-decision-completion-intent.v2` table, codec,
validator, and store. It adds no optional fields to v1. Durable mode selects a
decoder before decode and neither falls back.

Each immutable v2 intent binds:

```text
campaign mode and evaluation ID
full snapshot_candidate_id, registry ref, identity, and artifact SHA-256
slot, receipt, comparison, source Branch/H, and origin identities
canonical normalized DecisionOutcome and digest
typed disposition, desired H status, mapper rule, and output digest
source and target Branch/H payloads and digests
expansion consumption and optional next exact slot
cleanup action/receipt or promotion-pending handoff
```

Outside the closed CandidateSnapshot value, all cross-module fields say
`snapshot_candidate_id`. The 16-character formal report namespace is never
joined or prefix-matched. Snapshot-mode D2 neither constructs nor calls
`FormalCandidatePatchArtifactRecorder` and never appends
`formal_candidates/index.jsonl`; D4 later bridges explicit
`snapshot_candidate_id` and `formal_artifact_candidate_id`.

Physical verification cannot be an SQLite operation. `prepare_v2()` first uses
the D1 descriptor-pinned reader to obtain and digest-verify the closure, then
starts `BEGIN IMMEDIATE` and verifies that mode, registry row, slot, receipt,
campaign, Branch, H, origin, pinned comparison artifact, dispatch claim, and
stable source anchors still bind those bytes. It does not require a receipted
comparison to remain the global current champion. It verifies the mapper output
and identical-payload idempotency.
`commit_state_v2()` and recovery re-read the pinned artifact and revalidate the
same registry digest immediately before applying state. Tamper or disappearance
after prepare fails closed.

All current-champion/weight readers and writers use `champion lock -> BEGIN
IMMEDIATE`. While preparing v2, D2 acquires that lock, chooses and freezes the
post-receipt current-champion drift overlay, and writes a durable
`champion_state_lease` with the prepared intent. D4 promotion and weight writers
cannot commit across that lease. `commit_state_v2()` or startup recovery
reacquires the same lock, CASes the lease/current champion, applies the frozen
target, and releases the lease in the state transaction. Therefore concurrent
stale marking cannot invalidate an immutable prepared v2 target; D2 recovery
precedes D4 recovery after a crash.

For nonpromotion dispositions, one v2 state transaction applies H status,
scientific Branch transition, expansion consumption, current-slot consumption,
optional next exact slot, one typed completion event, the count-owning
experiment event when the receipt marks a formal observation, and intent `prepared ->
state_committed`. Cleanup follows commit and final mark follows an identity
receipt. The committed closure is the rejection archive; cleanup writes a
receipt and removes staging without copying a second full workspace tree.

Event ownership is exact:

```text
candidate-decision-completion:<transaction_id>  non-counting audit event
candidate-evaluation:<evaluation_id>            sole formal experiment event
```

The second row exists and increments formal observation count iff
`receipt.formal_protocol_observation` is true; otherwise count is zero.
Snapshot, slot, receipt, cleanup, and formal-artifact rows never count. Recovery
cannot emit either event twice.

The normative transition table is:

| Stage / Decision facts | Disposition | Target Branch | Actual H | Next slot |
|---|---|---|---|---|
| screening `EXPAND_SCREENING` | `EXACT_REUSE` | `EXPLORE_EXPAND` | advanced | screening expansion, next ordinal |
| screening `QUEUE_VALIDATE` | `EXACT_REUSE` | `READY_VALIDATE` | advanced | validation initial, ordinal 0 |
| screening `CONTINUE`, fail | `REJECT_TO_CODE_PARENT` | `EXPLORE` | rejected | none |
| screening `CONTINUE`, unclear/continue | `PROVISIONAL_HEAD` | `EXPLORE` | provisional | none |
| screening `CONTINUE`, pass/expand with exact reason tuple `SCREENING_PARTIAL_CHAMPION_EVIDENCE`, zero candidate failures, and positive champion failures | `PROVISIONAL_HEAD` | `EXPLORE` | provisional | none |
| screening `ABANDON`, any typed gate or no gate | `REJECT_TERMINAL` | `ABANDONED` | rejected | none |
| validation `EXPAND_VALIDATION` | `EXACT_REUSE` | `VALIDATING_EXPAND` | advanced | validation expansion, next ordinal |
| validation `QUEUE_FROZEN` | `EXACT_REUSE` | `READY_FROZEN` | advanced | frozen initial, ordinal 0 |
| validation `CONTINUE`, fail | `REJECT_TO_CODE_PARENT` | `EXPLORE` | rejected | none |
| validation `CONTINUE`, unclear/continue | `PROVISIONAL_HEAD` | `EXPLORE` | provisional | none |
| validation `ABANDON` | `REJECT_TERMINAL` | `ABANDONED` | rejected | none |
| frozen `PROMOTE` | `PROMOTE_EXACT` | `PROMOTION_PENDING` | advanced; desired promoted | none |
| frozen `CONTINUE`, fail | `REJECT_TO_CODE_PARENT` | `EXPLORE` | rejected | none |
| frozen `CONTINUE`, unclear/continue | `PROVISIONAL_HEAD` | `EXPLORE` | provisional | none |
| frozen `ABANDON` | `REJECT_TERMINAL` | `ABANDONED` | rejected | none |

All rows retain pre-evaluation Branch source hashes. Repeated screening and
validation expansions use state self-loops; their availability is owned only
by preregistered Protocol facts, not a D2 cap or budget. Completion consumes the
current expansion before deriving target counts and next ordinal.

Unsupported combinations, including snapshot-mode
`VALIDATION_REPAIR_REQUIRED`, do not consume or redispatch the slot. They enter
`decision_invalid` integrity hold with the exact outcome retained.

`PROMOTE_EXACT` is a handoff, not a completed promotion. D2 persists the
mapper's desired H status, moves Branch to unschedulable `PROMOTION_PENDING`,
leaves H `advanced`, moves the slot to `promotion_pending`, and commits the
exact disposition and formal observation with v2 state `promotion_pending`.
The immutable v2 payload binds the intermediate Branch/H/slot and both legal D4
successors: promoted final state or champion-CAS conflict final state. D4's
SQLite state transaction binds the unique `promotion_completion_id`, applies
exactly one successor, consumes the handoff, and advances v2 to `committed` or
`promotion_conflicted`. Before that successor exists, the v2 verifier accepts
only the intermediate owner; afterward it verifies the exact D4 successor and
final state. Branch/H can never claim promotion before champion commit.

D2 does not select `next_research_head_candidate_id`, a creative base,
mechanism equality, workspace, pivot successor, or parked lineage. Those facts
cannot exist until a later H exists and belong to D3.

#### Recovery and incomplete-slice boundary

Startup order is fixed:

```text
atomic campaign ID + mode open
mode-specific durable owner inventory and mixed-owner validation
R1 research-rejection recovery
paired snapshot/slot recovery (snapshot mode)
slot/dispatch/receipt validation
mode-specific DecisionCompletion recovery
D3 awaiting-plan/ContinuationPlan/lineage-rejection recovery
D4 promotion/SourceLedger/formal-bridge recovery
Branch/H/workspace restore
active-attempt audit
scheduler availability
```

The pre-recovery inventory may query opposite-mode typed tables/markers only
for negative conflict detection; it never decodes, validates, restores, or
consumes them. Snapshot mode conflicts with a current/pending legacy owner or
unfinished v1 intent. Legacy mode conflicts with any snapshot, slot, receipt,
or v2 row. Formal artifacts and reports are not owner inventory.

Snapshot restore reads only committed closure and typed owners, never a formal
index, legacy marker, or mutable workspace. A pending exact slot causes zero
H/C provider calls. A dispatched slot without receipt remains uncertain and is
not automatically rerun. A receipted slot resumes deterministic Decision/v2
completion without Protocol. Mixed, held, tampered, or drifted ownership blocks
before Scheduler.

D2 alone is not a schedulable snapshot-mode production release. D3 capability
is required before creative or exact-reuse dispatch; D4 capability is required
to consume promotion handoffs. This release-integrity preflight is not an
execution outcome, candidate gate, retry, budget, truncation, or operator hold.
No generative experiment runs between partial D2 merge and D3/D4 activation.

#### Module and acceptance boundary

D2 may add cohesive slot/receipt value-codec-store modules and an independent
v2 completion value-codec-store. It reuses D1 snapshot materialization; it does
not add a second replay helper or collect SQL, codecs, workspace mutations, and
finalization in one file.

Required acceptance includes:

- campaign bootstrap/open crashes, pre-D2 adoption, and exact mode reuse;
- writer API exclusivity and pre-recovery mixed-owner detection;
- direct and reconcile typed origins and immutable parent resolvability after
  every cleanup;
- paired snapshot/slot prepare, rename, commit, recovery, and DB invariants;
- exact slot codec, ordinal/count table, comparison/source/request anchors, and
  drift holds;
- dispatch, blocked-infra, receipt, uncertain, invalid, consumed, and promotion
  handoff crash paths;
- no early snapshot-mode evaluated event, count, StepRecord, or formal writer;
- exact normalized DecisionOutcome transport, canary attribution split, and
  mutable/report noninterference;
- exhaustive transition table and source hashes unchanged through D2;
- exact reuse retaining one snapshot candidate across distinct evaluation IDs,
  with fresh materialization/revalidation and zero H/C/origin/snapshot;
- pinned artifact verification at prepare, commit, recovery, D3, and D4;
- v2 crash injection around H/Branch, events, count, slot, next-slot, SQLite,
  cleanup receipt, and final mark;
- one completion event and exactly one formal count iff the typed receipt marks
  a formal Protocol observation, otherwise zero, never duplicated on reopen;
- PROMOTION_PENDING crash/reopen with old champion never presented as promoted;
- opposite-mode evidence used only to detect conflict, never as positive owner;
- `formal_artifact_candidate_id == snapshot_candidate_id[:16]` causing no DB,
  reopen, replay-filter, status, or index collision;
- frozen v1 golden compatibility, including historical prepared fallback
  recovery but no new fallback creation;
- no next-base, pivot, SourceLedger, formal replay, or champion mutation in D2;
- no retry, cap, budget, truncation, new statistical gate, or model-authored
  topology claim.

## D3: ContinuationBasePlanner

The Scheduler continues to read Branch state, FIFO/priority, execution hold,
and active slots only. A separate deterministic planner owns creative code-base
selection. D3 owns the complete transition from one durable continuation source
to an immutable base lease; it never changes the D2 disposition that supplied
that source.

### Base kinds and deterministic precedence

```text
INITIAL_CHAMPION
EXACT_EVAL_REUSE
CLEAN_CODE_PARENT
PROVISIONAL_CURRENT
CHAMPION_PIVOT
LEGACY_CUMULATIVE_RESET
```

The complete precedence table is:

1. D2 `EXACT_REUSE` -> `EXACT_EVAL_REUSE`. D2 is the sole next-slot creator;
   D3 only validates, materializes, claims dispatch, and executes that already
   committed slot. There is no H/C/origin/plan/snapshot.
2. `REJECT_TO_CODE_PARENT` -> `CLEAN_CODE_PARENT`. New-H owner and provider hint
   cannot override the exact clean parent; failed candidate files never enter
   current source.
3. `FRESH_CHAMPION` -> `INITIAL_CHAMPION`.
4. `PROVISIONAL_HEAD` plus the same known previous and prospective owner:
   `auto`/`refine_current` -> `PROVISIONAL_CURRENT`; `pivot_clean` ->
   `CLEAN_CODE_PARENT`.
5. `PROVISIONAL_HEAD` plus a different owner or `UNCLASSIFIED` ->
   `CHAMPION_PIVOT`; create a successor Branch/lineage and park the old Branch
   as evidence.
6. `LEGACY_SUCCESSOR` -> `LEGACY_CUMULATIVE_RESET`. Use a typed isolated clean
   parent only when its closure is physically proven; otherwise use the exact
   champion. A cumulative workspace is never trusted as a clean parent.

Validation/frozen rejection cannot become a next code head. `UNCLASSIFIED` is a
valid conservative result, does not reject H, grants no provisional-refinement
authority, and two such values never count as the same owner. Missing, invalid,
or incompatible `continuation_intent = auto | refine_current | pivot_clean`
falls back to the deterministic row above. The hint is tainted proposal data,
not a Decision or quality gate.

A legacy-mode DB remains completion-only. Later creative work opens a new
snapshot-mode successor campaign with a `LEGACY_SUCCESSOR` anchor and evidence
link; its mode never changes in place.

Do not restore `clean_fork_diversity_claim`, novelty prose, or any mandatory
model-authored explanation of Branch topology.

### Problem-owned mechanism adapters

Generic core owns the planner interface and typed result. Problem packages own
two adapters: `ProspectiveHOwner` reads only Contract-valid structural H fields,
while `VerifiedCandidateOwner` also closes Patch Contract and authoritative
touched-path facts. CVRP v1 needs at least:

```text
construction
destroy_repair
local_search
acceptance
search_schedule
state_representation
solver_architecture
```

Supporting activation edits may remain under the primary owner; a true
multi-owner architectural patch maps to `solver_architecture`. Warehouse reuses
its problem-owned operator taxonomy. Both adapters return a known owner or
`UNCLASSIFIED`; neither can reject scientific quality. Free text such as
`hypothesis_text`, `target_weakness`, and `expected_effect` never influences
classification or base selection, and changing all free text must leave the
plan unchanged.

### Awaiting-plan ownership and continuation completion

D2 Decision completion and D3 creative planning are separate durable
transactions because the next H does not exist at Decision-completion time and
no provider call belongs inside a database transaction. Every creative attempt,
including a fresh Branch, has one typed source:

```text
ContinuationSource =
    FRESH_CHAMPION
  | D2_DISPOSITION
  | LEGACY_SUCCESSOR
```

The H provider attempt first owns its external call. After H Contract,
`ProspectiveHOwner` is computed and the two are atomically sealed as
`ContinuationHypothesisAttempt(awaiting_plan)`, keyed by the source owner and
provider attempt. It binds the complete structured H, H Contract,
generation-context Branch/lineage digest, optional hint, proposed H ID, and
prospective owner, but it is not yet a Branch-owned `HypothesisRecord`. Thus a
pivot does not leave H attached to the old Branch. D3 recovery owns
`awaiting_plan` before the generic active-attempt audit; reopen never calls H
again or invents another target Branch.

For a creative continuation, the order is fixed:

```text
H provider attempt
  -> H Contract
  -> ProspectiveHOwner
  -> ContinuationHypothesisAttempt(awaiting_plan)
  -> ContinuationPlanCompletion commit
  -> exact base materialization from the committed lease
  -> D4 SourceLedgerCompletion commit
  -> C context construction
  -> C provider
  -> Patch Contract / Verification
  -> VerifiedCandidateOwner
  -> provisional-lineage integrity check
  -> D2 snapshot + evaluation ownership
```

One `ContinuationPlanCompletion` transaction binds:

1. the typed `ContinuationSource` identity and source Branch/lineage/H digests;
2. the awaiting-plan attempt, final H identity, structural proposal digest, and
   prospective owner;
3. the selected base kind and exact snapshot/champion/clean-parent identity,
   hash, artifact ref, and manifest digest;
4. a natural completion key and stable target Branch/lineage IDs;
5. source Branch/lineage CAS, successor creation plus old Branch
   `PARKED_LINEAGE` for a pivot, or exact same-Branch continuation otherwise;
6. creation of the final Branch-owned H and atomic installation of the planner
   base as authoritative Branch research source hash/ref;
7. a reserved `code_attempt_id` in `reserved` state, bound to that final
   Branch/H/lease; and
8. exactly one continuation-plan event.

Stable IDs derive from the natural completion key. Concurrent or reopened
completion must match identical payload; a second successor or changed lease
fails CAS. The transaction does not call C or materialize a workspace. After
commit, exact materialization, SourceLedger, and C context use the same lease.
Immediately before the external C call, a durable dispatch claim advances the
attempt `reserved -> started`; provider return is receipted before it becomes
`generated/completed`. A crash while reserved may safely proceed to the first C
dispatch, while started without a receipt is execution-uncertain and is not
automatically called again. Only a completed direct attempt ID may become a D2
snapshot origin.

If the later `VerifiedCandidateOwner` violates the provisional triple-equality
rule, `LineageIntegrityRejectionCompletion` owns the result. Its natural key is
the continuation-plan ID plus reserved code-attempt ID; its immutable payload
binds the prior/prospective/verified owners, H/Branch/source digests, lease,
Patch/Verification, staging manifest, cleanup action, and one non-counting event.
Its recovery phases are `prepared -> state_committed -> cleanup_receipted ->
committed`.

The state transaction CASes the unchanged planner source, marks H
`research_rejected`, restores Branch to scheduler-forward `EXPLORE` on that same
committed source, terminalizes and clears the active code attempt, and emits the
event with zero formal count. Cleanup then removes staging and records its exact
receipt. Recovery runs with other D3 completion recovery before Branch restore
and active-attempt audit; Scheduler remains unavailable until it reaches a
stable phase. The next action is a fresh H, never a snapshot, Protocol
observation, same-H/C retry, or silent replan of the rejected patch.

`EXACT_EVAL_REUSE` bypasses every creative owner above. D2 already allocated and
armed the unique next slot atomically with the preceding disposition. D3 cannot
generate an evaluation ID or insert a slot; it only revalidates/materializes the
existing candidate closure and dispatches the existing pending slot.

Verification success alone cannot advance the research head, and an H without
a committed `ContinuationPlanCompletion` cannot authorize candidate creation.

## D4: SourceLedger, Promotion, and Replay

SourceLedger is constructed from the exact D3 lease. It must not reconstruct
source by replaying every Verification-passed step. A durable
`SourceLedgerCompletion` is uniquely owned by
`continuation_plan_id + exact_base_manifest_digest`; its canonical payload and
content-addressed artifact bind every source path, digest, content, provenance,
base ref, and materialization digest. Publication uses prepared/renamed/committed
recovery like D1. D3 may build C context only from this committed owner.

Rejected candidate material remains available only through evidence and
artifact references. It cannot appear as:

- `branch_current_code`;
- `branch_history_current` SourceLedger content;
- current touched-file footprint;
- promotion ancestry.

Canonical candidate composition adds:

```text
code_base_kind
typed code parent = champion parent | snapshot parent
code_parent_snapshot_candidate_id/hash (only for snapshot parent)
code_parent_champion_id/hash (only for champion parent)
snapshot_candidate_id/hash
inherited_snapshot_candidate_ids
rejected_ancestor_count
incremental_effect_isolated
```

`incremental_effect_isolated=true` requires a clean/champion base with no
inherited research change. It is a factual composition flag, not a claim that
the observed effect is causal.

Rejected dispositions can never own current SourceLedger content. Their closure
remains evidence only and cannot appear as `branch_current_code`,
`branch_history_current`, current touched-file footprint, or promotion ancestry.

### PromotionCompletion recovery protocol

Promotion reads the exact frozen candidate snapshot, never a mutable Branch
workspace. Promotion ancestry may contain cumulative provisional refinements,
but no snapshot with disposition `REJECT_TO_CODE_PARENT` or `REJECT_TERMINAL`.

D4 consumes D2's durable `PROMOTION_PENDING` handoff through a separate
`PromotionCompletionIntent`. Its immutable payload binds:

```text
promotion_id and source v2 completion ID
evaluation_id, full snapshot_candidate_id, slot, and pinned artifact
expected current champion ID/hash/weight revision
target champion version/hash/content-addressed ref/manifest
source and final H/Branch payloads and digests
stale-target Branch CAS digests
promotion lineage and event identity
promoted and champion-CAS-conflict slot/v2/H/Branch targets
```

The recovery phases are:

```text
prepared
  -> champion_artifact_published
  -> state_committed
  -> cleanup_receipted
  -> committed

prepared | champion_artifact_published
  -> conflict_committed
  -> cleanup_receipted
  -> conflicted
```

Preparation descriptor-pins and verifies the candidate closure and stages an
exact content-addressed champion artifact. D4 fsyncs files/directories and
publishes by rename while the intent remains prepared. Filesystem publication
and SQLite are not physically atomic; the intent provides logical atomicity.

Every champion path uses one lock order: champion lock, then
`BEGIN IMMEDIATE`. The state transaction revalidates the published bytes and
CASes current champion against the comparison champion bound by the handoff. It
then atomically updates champion, H `advanced -> promoted`, Branch
`PROMOTION_PENDING -> PROMOTED`, stale Branches, promotion lineage/event, slot
`promotion_pending -> consumed`, the unique promotion-successor link, v2
`promotion_pending -> committed`, and intent `-> state_committed`.

If another promotion wins the champion CAS, one conflict state transaction
leaves that champion unchanged, moves Branch `PROMOTION_PENDING -> STALE`, keeps
H `advanced`, consumes the slot/handoff, writes one non-counting
promotion-conflict event/link, advances v2 `promotion_pending ->
promotion_conflicted`,
and marks the intent `conflict_committed`. A published losing artifact is then
removed under an orphan-cleanup receipt. D4 creates no evaluation slot and does
not rerun Protocol; later normal stale/reconcile work may create a new
candidate/initial slot through D2 ownership, but is not an automatic successor
of this intent.

Reopen before Branch restore either adopts and commits the exact published
artifact under the still-valid CAS, commits the exact conflict successor, or
writes the matching orphan-cleanup receipt. Reopen after either SQLite terminal
state only completes cleanup/final marking and does not repeat state or events.
Two handoffs based on one old champion can have only one winner. Until promoted
state commit, the current database champion is authoritative; this intent's
target is never reported as promoted without its state commit.

### Formal bridge and replay ownership

`SnapshotFormalArtifactBridge` is an append-only, crash-recoverable owner with
the full `snapshot_candidate_id` as its natural key. It freezes:

```text
snapshot_candidate_id
formal_artifact_candidate_id
formal artifact ref and digest
immediate typed champion/snapshot code parent
complete materialization digest
source-ledger completion ID
```

The legacy short formal ID is display data only. It never selects, joins,
prefix-matches, promotes, or replays a snapshot. Bridge artifact publication and
index append use prepared/committed recovery and an idempotency key derived from
the full snapshot ID; a crash cannot duplicate an index row. Formal replay
records the exact immediate code parent and complete materialization. The old
declared champion remains ultimate ancestry but is not falsely reported as the
immediate parent of a provisional refinement.

D4 acceptance injects crashes before/after SourceLedger rename and registry
commit, every promotion phase, champion CAS conflict, v2 successor commit,
formal artifact rename/index append, and cleanup/final mark. It proves orphan
cleanup/adoption, one promotion winner, no rejected ancestor, exact replay after
workspace deletion, and real prefix collisions without any short-ID lookup.

## L1: Normalized Hypothesis Research Ledger

H still receives all safe screening observations and complete current source.
The transport changes from repeated self-contained display trees to an
explicit, reversible schema:

```text
scion.direct_v3.hypothesis_research_ledger.v1
```

```text
ledger
├── source_branches
├── attempts
│   └── hypothesis, candidate identity/composition, rejection outcome, screening refs
├── screening_observations
│   └── round/cohort, formal aggregate, decision, pair/problem refs
├── case_catalog
├── pair_tables
│   └── metric schema once + every original case/seed row
├── reason_sets
└── problem_evidence
```

The ledger is normalization, not summarization or context compression:

- every screening observation remains distinct;
- every pair row remains present;
- overlapping case/seed cells retain observation membership;
- every objective primitive and runtime-failure fact remains recoverable;
- every problem-owned evidence packet remains complete;
- every visible pre-Protocol rejection is a compact typed fact with attempt,
  phase, reason, failed check, structured metadata, clean parent, archive ref,
  workspace disposition, and completion identity;
- validation/frozen and unsafe lifecycle state remain excluded;
- no recent-N, top-k, token-aware omission, digest-only substitution, or hidden
  compression is allowed.

### Single fact ownership

- Hypothesis and candidate composition are stored once per candidate attempt,
  not once per expansion observation.
- Case features are stored once in `case_catalog` and referenced by pair rows.
- Metric names/order and row columns are declared once per pair table.
- Case aggregates that are exactly derivable from pair rows may use an explicit
  derivation rule. If an old record is not exactly derivable, preserve an
  exception row.
- When `comparison == objective.outcome` or
  `delta == objective.scalar_delta`, an explicit alias may be used. When they
  differ or objective is missing, store the independent value.
- Generic proposal transport stores the proposal-only envelope once; a problem
  provider owns its opaque internal schema.

The codec must prove:

```text
decode(encode(legacy_history)) == legacy_history
encode(decode(ledger)) is canonical-byte stable
```

Malformed references, duplicate observation identities, or non-recoverable
aliases fail closed before provider rendering. They do not affect Protocol,
Decision, or an already-running campaign.

## L2: Source Projection and Rendering

H source uses a typed ledger like C SourceLedger:

```text
path
provenance = champion_current | provisional_current | clean_parent
digest
content
```

Every provider-visible current path appears exactly once. Champion source and a
branch overlay cannot both render the same path.

Rendering uses readable metadata plus compact row transport:

- source remains one code block per file;
- attempt and observation metadata remain readable objects;
- pair/operator tables declare columns once and render one compact row per
  observation;
- the renderer does not pretty-print a deeply repeated object tree.

R11c H2 is the mandatory fixture: two screening observations, 80 pair rows, 20
recoverable case aggregates, both problem-evidence packets, and every current
source file must survive a semantic round trip.

## L3: Durable Owner and Audit Manifest

Canonical history currently has two persistence call sites whose natural key
makes the second write a no-op. New runs have one owner: the finalized
`StepRecord` completion path.

Legacy denormalized records remain read-only and are converted by the codec at
render time. New durable records write the normalized schema; R11c is never
rewritten.

Prompt manifests record truthful non-gating audit facts:

```text
screening_observation_count
pair_observation_count
attempt_count
source_entry_count
semantic_ledger_digest
render_schema_version
```

The current hard-coded zero observation count is removed. These fields never
enter Decision or become launch/readiness gates.
