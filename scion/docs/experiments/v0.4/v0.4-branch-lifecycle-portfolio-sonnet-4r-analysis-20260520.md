## 总结

这次实验验证了两块新修复的基本方向：

- 生命周期策略生效：低 win-rate 但全 tie、无退化的前两轮没有被 T4 单轮 soft abandon，而是 `continue_explore` 并保留分支。
- portfolio scheduler 生效：R1 后创建第二个分支，R2 后创建第三个分支，随后在已建立的分支之间继续探索，而不是一直只跑最老分支。

但实验也暴露了新的 P0 问题：

- gate 使用的事实与 agent 可见事实同源，但不是同一个高信号 fact packet。gate 能引用精炼的 active solver snapshot 结论，agent 看到的是 8-11 万字符的工具观察，且 `agentic_tool_observations` 在所有 manifest 中都被截断。结果是 gate 经常比 agent “看得更清楚”。
- 当前 `scion/scion/proposal/active_solver_snapshot.py` 在 generic proposal 层硬编码了 `_ALNSVNSSolver`、`_shaw_removal`、`_or_opt_*`、Clarke-Wright、route-cap rejection 等 CVRP/ALNS/VNS 语义。这违反 v3 边界，应迁移到 `scion/problems/cvrp/` 的 adapter/provider。
- `telemetry_failed_experiments=0` 是真实的：formal screening 没有出现 repairable telemetry failure。activation missing 出现在 proposal smoke/code preview 阶段，不能解释为 formal guard 漏报。
- activation missing 的根因需要更细诊断。本次有“代码未接入或未仪表化”“机制触发条件未到”“expected_telemetry 把 effect counter 当 activation”三类，不能简单记为算法失败。

## v3 对照

相关设计约束来自：

- `scion/docs/AGENT_ONBOARDING.md`：Scion core 只拥有 campaign lifecycle、proposal orchestration、Contract、Verification、Protocol、Decision、lineage；problem packages 拥有 objective、feasibility、solver hooks、runtime audit field meanings、prompt rendering。
- `scion/docs/AGENT_ONBOARDING.md`：不要把 CVRP、ALNS/VNS、route/capacity/demand 或 `_ALNSVNSSolver` 语义直接放到 generic `core`、`proposal`、`contract`、`protocol`、`runtime`。
- `scion/design/scion-architecture-v3.md`：1 branch = 1 方向，可迭代 hypothesis；screening fail 可以在当前代码上继续迭代；分支内深度探索，分支间广度探索。
- `scion/design/v0.4/v0.4-agentic-proposal-session-design.md`：problem-specific algorithm knowledge belongs in problem packages, adapters, and declared research surfaces, not in Scion core。

本次框架行为大体符合“分支内深度 + 分支间广度”：

## Mechanism gates

### Route-limit/fleet premise gate

Result in this experiment:

- It blocked explicit positive/default fleet-violation premises correctly.
- It did not show the previous false-positive class.
- It still allowed repeated route-limit-family hypothesis attempts to consume LLM/tool budget before blocking.

Conclusion:

- The gate is useful as a safety net.
- It should consume the same adapter-rendered fact packet that the agent sees, with fact ids and evidence spans.
- The prompt should render those same facts in a compact, non-truncated “active_algorithm_facts” section before the bulk tool observations.

### Removal duplicate precision

This run only validates the `_shaw_removal` duplicate path:

- `double_bridge_perturb` claimed related/proximity-cluster destroy was missing.
- Gate correctly pointed to `_shaw_removal`.

No R12-style removal-savings/worst-position/cost-of-remove duplicate appeared. This run cannot validate whether `_worst_removal` / `route.cost_of_remove(pos)` now outrank `_shaw_removal` for that specific case.

### Repeated mechanism suppression

Still weak:

- Route-limit/fleet default-state family was proposed at least three times across `periodic_reheat`, `guided_savings_construction`, and `noisy_savings_construction`. The gate blocked each, but only after the LLM/tool attempt.
- `sa_data_driven_reheat` ran two separate code sessions (`ec8f0282`, `ae99854c`) and hit the same C9e patch graph class twice.
- `elite_archive` and `load_balanced_or_opt` each consumed multiple code retries on activation missing. Some retry is appropriate, but after the same activation field remains missing, the branch memory should force a different trigger/instrumentation plan or park the mechanism.

Recommendation:

- Add a short-lived branch/campaign fact such as `blocked_signature=(target_file, mechanism_id, failure_code, evidence_fact_ids)` and render it as a hard constraint before hypothesis generation.
- Code-stage repeated failures should also count. If the same mechanism id and same C9e/activation field fails twice, require a materially different integration plan or reject before another code session.

## Agent context quality

Every session used the expected solver-design grounding tools. For representative sessions:

- `f5bcbeb9`: `context.read_active_solver_design` 4 times, `context.read_algorithm_file` 9 times, feedback and memory queried.
- `5f2d547a`: same plus `context.read_branch_state`, contract preview, algorithm smoke.
- `5e02da7a`: additionally used `context.read_algorithm_symbol` 6 times while trying to repair code.
- `d2b9ee8c`: used code context, branch state, contract preview twice, algorithm smoke once.

The issue is not missing tool calls. The issue is signal-to-noise:

- Hypothesis manifests routinely rendered 77k-110k chars of `agentic_tool_observations`, always `truncated=true`.
- Gate decisions cite concise semantic facts. Those facts are buried in the tool observations and active snapshot, not promoted into a stable, compact adapter facts section.
- Because of this, agent outputs repeatedly contradicted facts that the system technically exposed.

P0 fix should not be “tell the LLM harder”. It should make agent and gate consume the same structured adapter facts:

```text
adapter_fact_id: cvrp.solver.starts_feasible
claim: active solver starts from feasible construction
evidence: active_solver_snapshot::<path/symbol>
used_by_prompt: true
used_by_gate: true
```

Then the gate can say “contradicts fact cvrp.solver.starts_feasible” and the prompt can make that same fact visible before any raw code or transcript.

- `scion/scion/proposal/tools/previews/algorithm_smoke_feedback_runtime.py` references `solver_algorithm_fleet_violation`, `fleet_violation`, and `total_distance`.
- `scion/scion/contract/gate.py` has `vehicles` / `vehicle_ids` reserved terms.
- `scion/scion/core/models.py` has a `vehicles` field.

Not all of these are equally severe. The hard P0 is `active_solver_snapshot.py`: it is a generic proposal module carrying detailed CVRP/ALNS/VNS research-object facts. This is exactly the layer that feeds both prompt and gate behavior. It should be a generic facade delegating to a CVRP provider.

Suggested migration shape:

- Move CVRP active solver snapshot construction to `scion/scion/problems/cvrp/...`, for example a `solver_design_facts_provider`.
- Generic proposal code asks the problem provider for:
  - active algorithm facts
  - call graph summary
  - allowed target files
  - mechanism novelty facts
  - premise predicates
  - telemetry field meanings
- Gate consumes fact ids from that provider instead of hard-coded CVRP strings.

## 是否保留 novelty/premise gate

Short term: keep it, but bind it to adapter facts.

The current gate caught real duplicates and contradictions in this run. Removing it outright would allow several invalid proposals into code. But its current architecture is too opaque because:

- gate fact rendering is sharper than prompt fact rendering;
- CVRP semantics are in generic proposal code;
- repeated invalid families still consume attempts;
- telemetry activation failures are collapsed too early into code-generation failure.

Medium term: simplify to “adapter facts + evidence-based generic contradiction gate”:

- Adapter supplies fact ids, predicates, and evidence spans.
- Prompt renders the exact same fact ids.
- Hypothesis schema can cite which fact ids it relies on.
- Gate rejects only contradictions against cited or mandatory facts.
- Novelty provider remains problem-owned and returns structured duplicate evidence.

This preserves the useful safety behavior while removing private gate knowledge.

## 修复建议

P0: shared adapter facts

- Add a problem-owned `active_algorithm_facts` provider under CVRP.
- Render this compact facts packet in hypothesis and code contexts before tool observations.
- Make premise/novelty gates consume the same packet and record contradicted fact ids.
- Add tests where the agent-visible fact packet and gate fact packet are byte-for-byte or hash-equivalent for route-limit, `_shaw_removal`, cross-route Or-opt, and starts-feasible facts.

P0: migrate CVRP/ALNS/VNS content out of generic proposal

- Replace `scion/scion/proposal/active_solver_snapshot.py` hard-coded CVRP snapshot with a generic facade.
- Move `_ALNSVNSSolver`, `_shaw_removal`, `_or_opt_*`, Clarke-Wright, route-cap, VNS/ALNS facts into `scion/scion/problems/cvrp/`.
- Move CVRP runtime field meanings such as `fleet_violation` and `total_distance` into CVRP provider rendering. Generic telemetry schema can still support opaque field names.

P0: activation missing as diagnostic lifecycle signal

- Keep formal telemetry repairable results non-counting as designed.
- Extend proposal smoke activation missing with root-cause categories:
  - `not_connected`
  - `trigger_not_reached`
  - `instrumentation_missing`
  - `expected_telemetry_mapped_to_effect`
  - `smoke_budget_or_case_insufficient`
- Store the category in branch memory and render it to the next code/hypothesis prompt.
- Do not call these ordinary algorithm failures without this classification.

P1: repeated mechanism/failure suppression

- Suppress same `mechanism_id + target_file + failure_code + failed_field` within recent branch/campaign memory.
- Apply to code-stage failures as well as hypothesis-stage premise failures.
- Require a materially different integration/trigger/instrumentation plan before retry.

P1: expected telemetry guidance

- Prevent pseudo dotted aggregate paths like `solver_algorithm_phase_best_delta.vns` unless a provider explicitly declares that dotted field as valid.
- Encourage activation paths to be mechanism-specific runtime/context records, and effect paths to be aggregate metrics or mechanism-specific improvement counters.

P1: prompt compaction

- The LLM used the right tools, but the rendered observations were too large and always truncated.
- Promote a small facts-and-risks block above raw tool observations.
- Move raw file excerpts behind fact ids unless the code phase needs exact symbols.

## Final judgment

The run is a useful positive framework test, not an algorithmic success. It confirms low-signal branch preservation and portfolio scheduling, and it confirms formal telemetry repairable accounting did not falsely count failures in this campaign. The main blocker is now architectural: agent and gate must share one adapter-owned active algorithm fact source, and generic Scion proposal/core layers must stop owning CVRP/ALNS/VNS content.
