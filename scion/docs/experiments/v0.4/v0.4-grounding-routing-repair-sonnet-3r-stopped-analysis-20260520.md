## Root Cause Judgment

Primary causes:

1. Adapter facts exposure gap: `_two_opt_intra` is active code but absent as a primary fact/gate target.
2. Gate false-positive: Or-opt contradiction rule misclassified intra-two-opt contrast prose.
3. Repeated gate over-blocking: broad `alns_vns` family blocked materially different local-search candidates before code.
4. Prompt feedback mismatch: contradicted-premise feedback entered context but described the wrong mechanism, letting the agent rationalize repeats.
5. Planner inefficiency: broad repeated file reads created huge truncated observations instead of targeted symbol verification.

Secondary causes:

- Agent quality remained weak: it ignored available Shaw/route/regret/Or-opt facts and used invalid activation fields.
- C11 activation diagnostics helped but still consumed attempts because invalid activation reached hypothesis contract paths.

This is not a Scion core CVRP-semantics problem in the sense of needing CVRP rules in core/proposal. CVRP existence/novelty facts belong in the CVRP adapter/provider. The generic core issues are mechanism identity granularity, repeated gate provenance, feedback consistency, and planner/tool budget behavior.

## Recommended Fixes

1. Add CVRP adapter facts for registered VNS operators.
   - Add explicit facts for `_two_opt_intra`, `_swap`, `_relocate`, and the full `_default_vns_operators` registration.
   - Include source symbols and fact ids such as `cvrp.local_search.intra_two_opt_reversal`.
   - Provider novelty should be able to reject “missing intra-route 2-opt” using that fact, not through Or-opt predicates.

2. Tighten CVRP Or-opt premise predicates.
   - Do not classify a hypothesis as claiming Or-opt is missing when it says Or-opt exists and contrasts it with another missing intra-route operator.
   - Treat contrast phrases like “covers Or-opt but lacks X” as evidence that Or-opt is acknowledged, not missing.

3. Narrow generic repeated mechanism identity.
   - Do not use broad `algorithm_family` as the first mechanism-family key for history blocking.
   - Prefer explicit `mechanism_changes[].id` and `novelty_signature.improvement_strategy`.
   - If broad family matching is needed, require same concrete mechanism id or same structured novelty signature, not just same target file + `ALNS+VNS` + failure code.

4. Make repeated-history feedback precise.
   - Include previous hypothesis id, previous mechanism id, previous target file, and matched key.
   - Distinguish “same concrete mechanism” from “same broad family”.
   - Do not imply fact provenance when the source is campaign history.

5. Use premise feedback as hard targeted planner guidance.
   - After a local-search premise failure, force the next planner round to read specific symbols such as `_default_vns_operators` and the claimed missing function before drafting.
   - Prefer `context.read_algorithm_symbol` over another broad file read when the claim is symbol-level.

6. Reduce raw observation truncation risk.
   - Keep active facts primary.
   - For owner files, provide compact symbol/function summaries plus operator registries before full raw content.
   - Ensure decisive facts are in the primary packet, not only in raw observations.

7. Move invalid activation rejection earlier.
   - Reject `.vns`, `.alns`, and whole telemetry maps in hypothesis preview before they become DB `hypothesis_contract` failures.
   - The feedback should say exactly: use `solver_algorithm_phase_runtime_ms.<mechanism_id>` or create explicit `context.record_phase` / `context.record_move` evidence for the new mechanism.

8. Preserve v3 boundary.
   - Do not hardcode CVRP mechanism semantics in Scion core/proposal.
   - Put CVRP facts and predicate fixes in the CVRP adapter/provider.
   - Keep core fixes generic: identity extraction, repeated-history matching, feedback alignment, and planner budget strategy.
