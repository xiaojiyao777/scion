## Provider collection and failure policy

The runner first attempts only the two provider calls in the declared order,
stopping the provider phase if either reached arm is nonterminal.
Each terminal response is written unchanged with provider diagnostics and
usage facts. Both terminal provider responses must be durably present before
any production parse, Contract, workspace materialization or V3/V4 scoring
begins. The first response and its content cannot affect the second prompt or
tool payload.

A terminal provider response remains an evaluable arm outcome even if its
returned tool arguments later fail production parse, Contract,
materialization, V3 or V4. Those are measured mechanical failures, not reasons
to suppress the arm or request another C response. Both arms are evaluated
after provider collection completes.

Any timeout, authentication failure, connection/transport failure, missing
terminal response or other nonterminal provider outcome makes the pair
`PAIR_INCOMPLETE / UNIDENTIFIABLE`. An unambiguous provider-side rejection of
one tool definition is recorded as an arm-local transport incompatibility, but
the pair is still incomplete. In every such case:

- the paired endpoint is not scored;
- no missing arm is retried or resumed;
- no alternate provider response is substituted; and
- a later attempt would require a newly preregistered experiment and fresh
  authorization.

Once both terminal responses exist, the provider phase is permanently closed.
The frozen runner has no score-only, resume or automatic rerun path.

An unexpected local harness, source-fixture or workspace invocation exception
seals `RUN_INVALID_LOCAL_INFRA`, with no automatic scorer rerun or resume, and
is not a treatment negative. In contrast, a
successfully invoked production stage that rejects the candidate response—such
as source-binding, Contract, materialization or an executed V3/V4 failure—is a
measured arm outcome. Neither condition authorizes another provider call.

## Provider-free mechanical endpoint

Each arm is scored independently from the same fresh B0 source in a separate
workspace using the production path:

```text
terminal raw response
  -> production _parse_patch
  -> production source binding
  -> production Patch Contract
  -> production WorkspaceMaterializer
  -> non-skipped CVRP V3
  -> non-skipped CVRP V4
```

The primary endpoint is the per-arm mechanical `full_executable` vector:

```text
parse_pass
source_bind_pass
contract_pass
materialization_pass
v3.executed / v3.pass
v4.executed / v4.pass
full_executable = all required facts above are true
```

An earlier failure leaves later stages explicitly not reached and makes
`full_executable=false`; it is not converted into a provider failure. V3 and
V4 must actually execute rather than skip after successful materialization,
and each runs once independently: a V3 failure does not prevent V4 from being
run and recorded. They contain the configured subsecond problem-owned
micro-solver fixtures, but they are executable consistency checks rather than
formal case-quality comparisons.

Primary scoring is performed under opaque cell labels. The mechanical scorer
receives each stored raw response and the shared canonical source/context
needed by the production parser and evaluator, but it does not receive the arm
name, call order or old/new tool mapping. It writes both primary score records
before the runner writes the arm reveal. Descriptive edit-intent diagnostics
are computed only after that reveal and therefore cannot change
`full_executable`.

The scorer also records these descriptive secondary diagnostics:

- raw edit-intent counts;
- whether the raw response chose an indentation-neutral
  `exact_line_replace` for the logical line `annealing.cool()` with
  `replace_all=true`;
- production selector match counts for any such line edit;
- the corresponding descriptive line-selection indicator; and
- remaining scheduler calls to `annealing.cool()` after materialization.

No particular edit intent is required. A selector count of five and zero
residual calls can explain how a response behaved, but neither is a host gate
or a component of the primary endpoint. An exact or full-file expression that
is mechanically executable counts as `full_executable`; a line expression
that fails Contract or V3/V4 does not.
