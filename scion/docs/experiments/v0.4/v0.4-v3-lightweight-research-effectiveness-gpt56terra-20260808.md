### Mechanism interpretation

- Round 1 was a composite negative candidate. The cross-exchange edit also
  used a broad full-file rewrite that accidentally removed a terminal return
  from `_two_opt_star`. Allocation collapsed from 1631 to 51 ALNS iterations,
  so the result cannot isolate cross-exchange quality. The framework correctly
  rejected and removed the candidate, while the failure exposed a provider
  authoring weakness.
- Round 2 was a coherent three-file adaptive-credit patch informed by the
  champion's accepted/best-update evidence. It executed, but post-segment
  operator-choice exposure occurred in too few paired runs and allocation
  diverged in only 1/32 pairs. The policy was under-activated/saturated in this
  screening design; it was not shown to improve the solver.
- Round 3 exposed the related route-limit condition in 31/32 candidate runs
  and completed only 74 ALNS iterations versus 1631 for champion, roughly 22x
  lower throughput. The raw absolute route-limit count fell from 86 to 31 only
  because the search did far less work; its event rate became much worse. The
  combined ejection-chain candidate is clearly negative, but no direct chain
  invocation counter exists, so the chain itself is not isolated.
- Round 4 was a clean, local evaluator change. Aggregate VNS calls rose 0.625%
  and a rough aggregate call rate rose about 0.86%, but there is no direct
  fast-path, fallback, symmetry-check, or 2-opt-probe counter. There was no
  objective gain: 31 pair ties and one distance loss of 2. Both independent
  reviewers therefore classified the movement as weak association only, not a
  demonstrated fast-path or solver improvement.

Every CVRP H source ledger was the clean champion v1 source. Rejected code from
rounds 1-4 was excluded from later executable ancestry, and the terminal
workspace returned to the clean parent. This is direct behavioral evidence for
the simplified candidate-disposition design.

## Residuals and post-control corrections

1. CVRP H input grew approximately 20.7k -> 47.3k -> 73.7k -> 100.2k tokens
   because complete prior evidence is repeated losslessly. This was well within
   the provider context in the four-round control but would become expensive in
   a much longer run. The next design step, if needed, is reversible structural
   normalization of repeated schemas/case catalogs, not top-k selection,
   truncation, summarization, or a token gate.
2. The historical prompt manifest reported `observation_count=0` even when the
   full prompt contained prior observations. The prompt itself was complete;
   this was diagnostic accounting, not context loss. The manifest now derives
   the count from that same prompt history.
3. Localized existing-file C authoring now consistently prefers ordered
   `exact_replace` edits and preserves unmentioned source. A regression test
   reproduces the Round 1 terminal-return hazard. This is guidance and
   deterministic composition, not another research-style gate.
4. Historical source ledgers were clean, but canonical candidate composition
   mislabeled clean current-step candidates as cumulative. Warehouse modify
   candidates also contained a semantic no-op `registry.yaml` reserialization,
   so those diffs were not byte-minimal. Both issues are corrected post-control
   and do not change the recorded comparisons.
5. Neither problem has declared a rename/permutation invariance requiring a
   universal metamorphic gate. Such probes remain problem-owned and are added
   only when the problem semantics make the transformation meaningful.

These post-control corrections affect authoring guidance, attribution labels,
and diagnostic accounting, not the recorded Protocol thresholds or Decision
outcomes. The completed multi-round campaigns therefore need no scientific
reinterpretation. The fresh one-round Warehouse and CVRP regressions above
exercise the corrected proposal, staging, Protocol, Decision, replay-artifact,
and cleanup path without changing the M5/M6 scientific claim boundary.
