## 0. 结论摘要

本次实验不是正常完成的 3 round campaign，而是在 2026-05-22 17:37 左右被外部
`SIGTERM` 提前停止。`status.json` 记录 `requested_rounds=3`、`attempts=3`、
`effective_rounds_completed=1`、`screened_experiments=1`、
`proposal_quality_blocks_consumed=1/6`，`stopped_reason=signal:SIGTERM`。

唯一有效 screening 是 Round 1。该轮完成 hypothesis、code、contract preview、algorithm
smoke、verification 和 formal screening，但被正确 abandon：screening case win rate 为
0.0，7/8 case loss，`median_delta=-10.25`，`ci=[-38.0,-5.25]`，同时 telemetry guard
失败，decision reason 为 `SCREENING_TELEMETRY_FAILED`。

Round 1 telemetry failure `TELEMETRY_ACTIVITY_NOT_OBSERVED` 的直接原因是：hypothesis 把
`solver_algorithm_neutral_accepted_moves` 声明为 expected activity；candidate 16/16 run 都
present，但 positive=0；champion positive=15。按当前“声明即义务、activity 必须被观察到”
的 telemetry guard 设计，fail closed 是一致的。语义上它不等于 candidate 没有算法活动：
candidate 的 `adaptive_vns_selector` activation/runtime/effect 都被观察到，且
`solver_algorithm_accepted_moves` 在 14/16 run 为正。更准确的归因是 agent 过度声明了一个
不适合 VNS selector 的 aggregate activity 字段，而 guard 的错误码/文案把“全零”表达成
“not observed”，需要改进可读性和 activity 字段语义。

第二个 proposal attempt 没有进入 formal evaluation。它提出 `sa_reheat_scheduler`，code 阶段
连续 3 次生成 scheduler patch，contract preview 都通过，但 algorithm smoke 都拒绝：
`solver_design static smoke rejected broad-loop acceptance telemetry`。这是明确的
`algorithm_smoke_failure`，`e741.../output.json` 中 `termination_reason=code_generation_failed`、
`failure_category=algorithm_smoke_failure`、`failure_detail` 有完整原因。此前“failed 无原因”
的判断应纠正为：原因存在，但状态/字段命名和 index 摘要不利于人工回溯，尤其容易误查
`failure_reason` 而漏掉 `failure_detail`。

`partial_hypothesis_only` 本身符合 APS 设计：hypothesis-only artifact 可作为 tainted memory
保存，不能直接进入 evaluation，必须等 ContractGate 批准后再生成 patch。但当前可观测性仍有
问题：partial session 的 `output.json` 里有 hypothesis，DB 的 `agentic_proposal_session`
event 和 summary 中 `hypothesis_text=null`；同时 `failure_category=contract_boundary_failure`
会让“等待批准”看起来像失败。应把它表达为更直观的 paused/awaiting 状态，并在 index 中暴露
hypothesis 摘要/ref。

另一个更强的可观测性问题是 SIGTERM 时留下了未索引残片：目录中有
`agentic_sessions/a65f4f9a-.../scratch/api_visible_prompt_manifest_0001_hypothesis.json`，
并且 17:36:30-17:36:53 有一组新的 LLM trace，最后一个 `generate_hypothesis` trace
`finished_at=null`、`ok=null`、`response=null`。但该 session 不在
`agentic_session_index.json` 中，也没有 `output.json`/`transcript.json`。停止实验需要从 raw
trace 才能重建这一事实。

v3 边界整体保持住了：agent 使用 `context.read_problem`、`context.read_surface` 和
adapter/spec-rendered facts；Contract C11、telemetry guard、algorithm smoke 都依赖 problem
package/surface 声明。没有看到 DecisionEngine 或 core promotion logic 硬编码 CVRP 目标。
问题主要不是“core 混入研究对象”，而是 problem-owned static smoke/provider 比 agent 更清楚
“effect telemetry 必须因果归因”的规则，agent 即使拿到失败反馈也无法修出合格 patch。

`e741...` 的 code repair retries 还加入 previous patch 和 preview feedback，所以 prompt/observation
体积继续上升。

### 4.2 是否重复读取

有重复，但分两类：

- session 内部有去重：例如 code phase 再读 `context.read_surface` 时返回 already-read reference，
  而不是完整 payload；fallback 也会跳过已经成功的 mandatory tools。
- session 之间大量重复：hypothesis session 和 code session 会重新读取 surfaces/problem/active
  solver/call graph/相同 algorithm files；第二轮又重复读取一批相同文件。相同 idempotency key
  下也没有跨 session observation cache 复用到足够细。

还有有意重复：

- `feedback.query_screening` 常在 planner-selected 与 fallback-selected 各执行一次；
- code repair retries 会携带 previous patch 和 failure feedback，属于必要上下文，但可以摘要化。

### 4.3 是否被截断

是。多个 manifest 显示：

- `agentic_tool_observations` 在 hypothesis manifest 中 `truncated` 或 `omitted`；
- `agentic_research_diagnosis` 在第二轮被 `truncated`；
- `agentic_preview_feedback` 在 code repair retry 中被 `omitted`；
- tool result summary 本身也出现 `[truncated by proposal tool result budget]`。

因此系统已经有压缩/省略机制，但 `observation_chars` 仍高，说明计数更接近“原始工具观察累计量”
或“可用观察池”而非最终 prompt 中真正展开的文本。

### 4.4 必要性判断

第一轮为了让 agent 在 solver_design surface 内做真实算法修改，读取 problem summary、surface
interface、active solver facts、call graph、target files 是必要的。但 99k-115k 的常态化上下文
不是必要最小集合，尤其不应在每个 hypothesis/code session 里重复展开多份相同事实。

框架需要更强的压缩/分层：

- active algorithm facts 应以 digest + named fact packet 复用；
- algorithm files 应先给 symbol map / call graph / relevant snippets，再按 target lazily expand；
- feedback/runtime summaries 应只暴露失败字段和 top deltas，不重复整段 screening context；
- code repair retries 应传 patch diff + exact smoke failure，不再重传完整 tool observation pool；
- observation budget 应区分 raw observation pool、prompt-visible chars、LLM input chars。

## 5. 可观测性问题归因

### 5.1 `failed` 但原因字段不直观

纠正：`e741...` 不是无原因失败。`output.json` 中：

- `status=failed`
- `termination_reason=code_generation_failed`
- `failure_category=algorithm_smoke_failure`
- `failure_detail=algorithm smoke did not pass ... static smoke rejected broad-loop acceptance telemetry ...`

问题是人工回溯不直观：

- 很容易查 `failure_reason`，但 APS output 使用 `failure_detail`。
- `agentic_session_index.json` 只列 status/termination/failure category/code 等摘要，不列
  `failure_detail`。
- campaign summary 的 `proposal_session_ref.primary_failure.detail` 会截断；step 的
  `failure_detail` 有长串嵌套前缀。

归因：不是 framework 完全丢失失败原因，而是 observability schema/summary 命名不统一、索引层缺少
primary detail。

### 5.2 `partial_hypothesis_only` 与 `hypothesis_awaiting_approval`

合理部分：

- APS 设计文档明确 partial sessions 可作为 tainted proposal memory，不能进入 evaluation。
- hypothesis-only output 等待 ContractGate approval 后才进入 code generation，这是 v3 tainted
  boundary 的正常做法。
- 两个 partial output 的 `hypothesis` 都非空，且 schema/target preview 已通过。

问题部分：

- DB 的 `agentic_proposal_session` event 中 `hypothesis_text=null`，需要打开 artifact 才能看到
  hypothesis。
- `failure_category=contract_boundary_failure` 把“等待批准”表现成失败，和真正失败混在一起。
- `termination_reason=hypothesis_awaiting_approval` 比 status 更准确，但 index/summary 没有把
  target/hypothesis 摘要一起展示。

归因：状态本身合理；可观测性和命名需要修复。建议把这种状态命名为
`awaiting_contract_approval` 或 `paused_for_hypothesis_approval`，并在 index 中记录
`hypothesis_ref`、`target_file`、`mechanism_changes`。

### 5.3 SIGTERM in-flight session 未登记

`a65f...` 是本次 stopped run 的最大 audit 缺口：

- 有 prompt manifest；
- 有 8 次 tool_selection trace；
- 有 1 次 unfinished hypothesis trace；
- 没有 output/transcript/index row；
- status 只记录 campaign-level SIGTERM。

归因：signal handling 没有为 active APS 写 terminal stub。主会话如果不读 raw trace，会漏掉最后
一个未完成 attempt。

## 6. v3 符合性判断

### 6.1 Agent/gate 是否共享 adapter facts

基本符合。

证据：

- 每个 indexed session 都先读 `context.read_problem`，结果是 adapter/spec-rendered problem summary。
- 每个 session 都读 `context.read_surface` 或 surface-related facts，selected surface 为
  `solver_design`。
- `problem-v1.yaml` 中 solver_design surface 声明了 target files、allowed components、
  required runtime fields、runtime field roles、mechanism activation/effect patterns。
- Contract C11 的 rejected messages 与 `problem-v1.yaml` 的 telemetry roles 对齐：aggregate
  effect field 不允许冒充 activation。
- telemetry guard 使用 candidate surface runtime summary 中的 `telemetry_guard`，field ids 来自
  selected surface declaration。

限制：

- prompt-visible facts 很大且被截断/省略，agent 不一定稳定看到最关键的 causal telemetry rule。
- problem-owned static smoke 对 `sa_reheat_scheduler` 的 effect attribution rule 比 agent prompt
  更硬。agent 在失败后看到了完整 smoke message，但连续两次 repair 仍没有跳出被拒绝模式。

结论：不是“core 比 agent 清楚”，更准确是“problem package 的 gate/static-smoke rule 比 agent
可操作的 prompt contract 更清楚”。

### 6.2 是否有研究对象内容进入通用层

未发现本实验导致新的通用层污染。

- CVRP-specific static smoke 位于 `scion/scion/problems/cvrp/solver_design/static_quality.py`。
- CVRP solver_design provider/guidance 位于 `scion/scion/problems/cvrp/solver_design_provider.py`。
- Surface declaration 位于 `scion/scion/problems/cvrp/problem-v1.yaml`。
- core telemetry validation 是 generic：它处理 `candidate_present`、`candidate_positive`、
  `champion_positive`、category/code/schema，不解释 CVRP route 或 ALNS 语义。
- Decision 读取的是 structured reason/features，没有根据 CVRP free text promotion。

有一个历史残留但非本次核心问题：`scion/scion/contract/gate.py` 中有
`_LEGACY_PROBLEM_SCALE_NAMES`，包含 `routes/customers/nodes/orders/vehicles` 等 legacy scale
terms。它是旧问题的 fallback，不是本实验的 decision/smoke 逻辑来源。后续可继续迁到
problem-owned surface bounds，但不构成这次 v3 违规。

### 6.3 是否仍存在 core/gate 看得比 agent 清楚

存在“gate 看得更清楚”的现象，但主要在 problem package 层，而非 Scion core 层。

表现：

- Agent 能声明 `sa_reheat_scheduler` 并生成 scheduler patch；
- Contract preview 只验证 telemetry schema/target/action，因此通过；
- Algorithm smoke 拥有更细的 causal attribution rule：acceptance/temperature effect telemetry
  不能在 scheduler broad loop 中记录；
- Agent repair prompt 收到失败文字后，仍只是在同一 scheduler branch 中重写 `record_move`，
  没有改变机制归因策略。

这说明 provider prompt 应更早、更结构化地把 static smoke 的禁止模式转成 code-generation 前置约束，
或者提供一个 acceptance/reheat 专用 surface/API，使 agent 有可执行的合格实现路径。

## 7. P0 / P1 修复建议

### P0：立即修复

1. **为 SIGTERM/abort 中的 active APS 写 terminal stub。**
   当 campaign 收到 SIGTERM 或 campaign_abort 时，当前 session 必须进入
   `agentic_session_index.json`，并生成最小 `output.json`/`transcript.json`：`status=failed` 或
   `status=aborted`、`termination_reason=campaign_abort`、last trace ref、last phase、last
   prompt manifest ref、`response=null`。否则 stopped run 必须读 raw trace 才完整。

2. **统一 agentic failure detail 的索引字段。**
   不需要删除 `failure_detail`，但 index/summary 必须暴露 `primary_failure.detail`，并提供
   `failure_reason` alias 或明确 schema 文档。最低要求：`agentic_session_index.json` 对 failed
   session 显示 `failure_category`、`failure_code`、`failure_detail`、`termination_reason`。

3. **修正 partial session 的 audit 表达。**
   `partial_hypothesis_only + hypothesis_awaiting_approval` 不应落成
   `contract_boundary_failure` 这种失败口径。建议 terminal state 使用
   `awaiting_contract_approval`，并在 DB event/index 中记录 hypothesis artifact ref、target file、
   mechanism ids。这样 partial 不会被误读为 failure，也不会出现“summary hypothesis null 但
   output 有 hypothesis”的断裂。

### P1：后续优化

1. **改进 telemetry activity guard 的语义和错误码。**
   对 present-but-all-zero 应给出 `TELEMETRY_ACTIVITY_ZERO` 或
   `TELEMETRY_ACTIVITY_FIELD_ALL_ZERO`，不要只说 not observed。对 activity fields 支持 surface
   声明中的 `required` / `optional` / `any_of`，避免 agent 把 broad aggregate field 加进
   expected telemetry 后导致机制已观测仍 formal fail。

2. **把 expected activity 从“字段列表全部 hard required”升级为机制证据计划。**
   对 solver_design 这类机制，activation/effect 应是 hard requirement；aggregate activity
   应能表达为“至少 search_iterations/move_attempts/accepted_moves 中若干项为正”。这不应弱化
   promotion，而是减少错误归因。

3. **将 static smoke 的 causal attribution 规则前置到 provider contract。**
   对 acceptance/temperature/reheat 机制，prompt 应在 code 生成前明确：
   - scheduler loop 只能记录 activation/budget；
   - effect telemetry 必须在 acceptance decision helper 或直接 accepted move path；
   - 如果当前 surface/API 不支持合格 effect attribution，应选择别的 mechanism 或只声明可验证字段。

4. **为 acceptance/reheat 类机制提供 problem-owned 可编辑 surface/API。**
   本次 `sa_reheat_scheduler` 的 target 是 `scheduler.py` broad loop，static smoke 又拒绝该位置的
   effect telemetry。更好的形状是 problem package 提供 `acceptance_restart_policy` 或
   acceptance helper surface，使 reheat decision 与 accepted move telemetry 有明确归因点。

5. **压缩/分层 agentic observations。**
   将 active algorithm facts、active mechanisms、file reads、screening feedback 做 digest/ref
   级复用。跨同一 idempotency key 的 hypothesis/code session 不应重复计入同一批大文件观察。
   code repair retry 应只携带 patch diff、target snippets 和 exact smoke failure。

6. **拆分 observation accounting。**
   同时记录：
   - raw tool observation chars；
   - prompt-visible chars；
   - omitted/truncated chars；
   - LLM input chars。
   当前一个 `observation_chars` 难以判断成本来自工具返回、prompt 展开还是被省略的观察池。

7. **整理 DB decision reason。**
   experiment row 中 `decision=abandon` 但 `decision_reason=null`，decision event row 才有 reason。
   建议 experiment row 同步写入 effective decision reason codes，避免分析者必须跨事件 join。

## 8. 最终判断

本次 stopped 短实验对 v3 的结论是：边界基本正确，失败主要集中在 proposal/session
可观测性、telemetry activity 语义过硬、以及 problem-owned static smoke 规则没有足够早地转成
agent 可执行约束。

Round 1 是一个完整且有效的负样本：算法主体 patch 通过所有前置 gate，但 screening 质量下降且
telemetry activity 失败，abandon 正确。Round 2 是一个正确 fail-closed 的 code-quality block：
失败原因明确存在于 `failure_detail`，不应再归因为“无原因 failed”。SIGTERM 残留 session 没有被
登记，是本次 stopped run 最需要立即修复的 audit 缺口。
