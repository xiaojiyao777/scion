## v3 Principles Used

From `scion/design/scion-architecture-v3.md`:

- Scion's core value is branch governance, deterministic boundaries,
  protocol control, lineage, auditability, and traceability.
- The LLM is the creative/proposal layer only. LLM hypothesis text, code, tool
  observations, and explanations are tainted and cannot directly drive
  promotion or deterministic decisions.
- Candidate evidence must pass Contract, Verification, Protocol, and safe
  feature extraction before Decision consumes it.
- Contract owns structure/boundary checks; Verification owns semantic
  correctness; Protocol owns split/seed/evidence exposure.
- Screening detail may be exposed to later proposal context. Validation and
  frozen detail must remain exposure-controlled.

From `scion/docs/AGENT_ONBOARDING.md`:

- The active v0.4 CVRP research boundary is `solver_design`, implemented by
  `policies/baseline_algorithm.py` plus focused modules under
  `policies/baseline_modules/`.
- Active algorithm facts are adapter-owned. Proposal agents and semantic gates
  must share the same digest/provenance/fact ids; gates must not be better
  informed than the agent.
- Agent-quality blocks such as contradicted premises, duplicate mechanisms,
  and activation diagnostics are not infrastructure failures, but must be
  preserved as branch-local tainted feedback and rendered into the next
  hypothesis context.
- Proposal-smoke activation-missing evidence is diagnostic feedback, not
  formal validation evidence.
- After every real-cost APS experiment, trace-level review must inspect
  hypothesis context, tool calls/results, code context, preview/smoke results,
  branch patch, and Decision evidence.

## Why `SCION_PROPOSAL_QUALITY_LOOP_LIMIT=5` Did Not Fire

The current outer campaign loop tracks several non-effective attempt buckets.
The env var controls only cumulative `agent_quality_blocked_attempts`.
`_is_agent_quality_blocked_attempt` checks only `StepResult.reason` and
`attempt_kind` text for `agent_quality_blocked`.

In this run:

- Third branch `failure_codes` in DB:
  `["PROPOSAL_PREMISE_CONTRADICTED", "PROPOSAL", "PROPOSAL", "PROPOSAL_PREMISE_CONTRADICTED"]`
- Only the two premise contradictions were surfaced as
  `reason=agent_quality_blocked`.
- The duplicate and repeated-mechanism blocks were generic proposal/code
  generation blocks, so they went into `bad_proposal_attempts`, whose default
  cap for 3 requested rounds is `requested_rounds * 5 + 10 = 25`.
- Therefore `proposal_attempts=6` in `status.json` does not imply the
  proposal quality loop counter reached 6. The counter relevant to
  `SCION_PROPOSAL_QUALITY_LOOP_LIMIT=5` reached only 2.

Recommended broader pre-screen loop:

- Add a separate consecutive counter for non-effective pre-screen proposal
  blocks since the last effective screening.
- Count categories such as `agent_quality_blocked`,
  `proposal_premise_contradicted`, `duplicate_mechanism`,
  `repeated_mechanism`/`mechanism_novelty_rejected`,
  `patch_not_generated`, proposal schema/preview rejection, and proposal-smoke
  activation diagnostics.
- Keep truly repairable activation telemetry and same-family retries in their
  own existing budgets, but do not let duplicate/premise/mechanism loops fall
  into the broad `bad_proposal_limit=25` bucket.
- Reset the broader counter on an effective screened experiment, or on a
  candidate that reaches Contract/Verification and produces formal evidence.
- Persist a normalized reason such as
  `proposal_quality_blocked:<category>:<code>` in StepRecord, DB branch
  failure history, compact negative memory, and summary. Avoid `code_generation`
  when no code LLM call happened.
- If `SCION_PROPOSAL_QUALITY_LOOP_LIMIT` remains the public knob, document it
  as the broader pre-screen quality cap, not only the agent-quality subcap.
