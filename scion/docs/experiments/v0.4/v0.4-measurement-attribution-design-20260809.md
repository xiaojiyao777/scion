# v0.4 Measurement Attribution Design

Date: 2026-08-09
Status: prospective diagnosis design; excluded from Decision

## Purpose and boundary

A campaign without a promotion does not by itself identify whether the limiting
factor was the proposed algorithm, mechanism exercise, search budget, case and
seed sampling, estimator semantics, or provider context and edit friction.
This design separates those explanations without changing an active campaign
or adding another candidate gate.

The V3 `Contract -> Verification -> Protocol -> Safe Features -> Decision`
path remains the only promotion authority. The experiment manifest states once
that every diagnostic output is excluded from Decision and cannot rejudge R3 or
any accepted Warehouse promotion; this notice is not repeated in every result
row. No deployment, identity, lease, signing, receipt, hash chain, model grader,
retry loop or algorithm-quality gate is introduced.

## Phase questions and estimands

The research loop is not one undifferentiated score. Each phase answers a
different question and keeps its own input population and estimand:

| Phase | Question | Minimum estimand or record |
|---|---|---|
| H | Did the provider produce a source-grounded algorithm hypothesis from the available scientific evidence? | schema completion, named owner/symbol, mechanism focus and use of actionable evidence |
| C | Did the provider express the approved H as an exact causal source change? | parse/apply/Contract result plus blinded H-obligation and source-anchor fidelity |
| Verification | Does the materialized candidate still solve the declared problem within its semantic boundary? | declared checks and typed failure, never style or novelty |
| Screening | Does candidate B improve over its immediate base A on the frozen discovery population? | paired case effects under the declared screening estimator |
| Validation | Does a screening-eligible candidate retain improvement on the distinct validation population? | its own paired aggregate; not an increment on screening |
| Frozen/final | Does the candidate retain the declared claim on protected cases or against B0? | its own protected aggregate and completeness |
| Provider-free diagnosis | Which sampling, order, budget or expression factor limits interpretation? | matched contrasts at candidate granularity, always outside Decision |

Effects from disjoint screening, validation and frozen populations are separate
robustness evidence. They are not plotted or summarized as a within-candidate
trajectory unless a shared population and estimator make that contrast valid.

## Reuse before invention

Execution reuses the existing problem-owned paths:

- ordinary campaign branch/step/H lineage in `scion.db` and terminal C traces;
- existing branch workspaces and champion snapshots when they prove exact
  candidate and immediate-base source;
- paired case/seed execution through `ExperimentProtocol.run_experiment` and
  `LocalSubprocessRunner`;
- the existing raw pair JSON and case-level aggregation;
- exact Warehouse snapshots through `champion-heldout-comparison`.

The active runtime deliberately does not write
`artifacts/formal_candidates/index.jsonl`. The historical
`fixed_candidate_replay` reader is used only when an old compatible artifact is
actually present. It is not restored as an active recorder or treated as
candidate identity, replay authority or a prerequisite for scientific lineage.

At most one experiment-owned analysis command, capped at 220 lines, may be
added. It materializes only an exact outcome-blind cohort, orchestrates the
existing Protocol/runner for atomic blocks, reads completed raw pair files and
emits bounded aggregates; production campaign modules remain unchanged. It
never enters Decision. Cell manifests and diagnostic outputs live in the
experiment root, not in framework policy.

Before the first expensive factor or budget replay, the existing Protocol
runner receives the bounded analysis-complete record described below. A replay
that cannot establish fresh subjects, scheduled/actual order, both absolute
objective vectors, feasibility, elapsed time and time limit does not launch.
This avoids knowingly spending the frozen cohort while leaving order, warm
state, headroom and CPU overlap unidentifiable. The correction adds no runner,
ledger, gate or Decision input.

## CVRP candidate cohort

After R3 is terminal, correlate ordinary branch/step records with each terminal
C trace and source snapshot in chronological order. For each
Verification-passed proposal, an experiment-owned materializer must recover the
approved H, complete terminal patch, exact pre-patch branch source and exact
post-patch candidate source. It may replay deterministic patch composition in a
temporary experiment directory and compare it with an available branch
workspace or champion snapshot. This is a one-time analysis adapter, not a new
production recorder or lifecycle authority.

Select the first `min(8, N)` candidates for which both candidate and immediate
base source are exact. Deduplicate repeated stages of the same source. Never
select a cohort from favorable W/L/T or replace every base with B0. If a trace,
patch, ancestry edge or exact source is missing or ambiguous, omit that
candidate with a bounded reason; do not infer or repair it.

An outcome-blind feasibility audit of the active R3 lineage through the seven
completed terminal C traces found six unique Verification-passed candidates.
There is no formal-candidate index, candidate workspace archive or candidate
identity artifact. Each code `proposal_call` instead carries a direct
`diagnostics.trace_ref`; its trace response contains the primary typed edit and
ordered `additional_changes`. Starting each branch from its declared champion
snapshot, applying only Contract- and Verification-passed C responses in
proposal time order reproduced all three current durable branch workspaces
byte-for-byte across their Python source. No result, W/L/T or effect value was
used.

The terminal materializer repeats that proof after the campaign drains. It
deduplicates expansion rows by `hypothesis_id`; a hypothesis's later display
status and `parent_hypothesis_id` are proposal history, not source ancestry.
Verified non-terminal candidates remain the next source on their branch, while
a C that did not pass Verification never enters source composition. The minimal
cohort manifest records only ordinal, first verified time, branch, hypothesis,
trace reference and `champion` or prior-candidate base. It adds no digest or
identity field.

Omit from the first ambiguous edge onward on a branch if the champion snapshot
is missing, a code trace is missing or non-unique, an edit is unsupported or
non-exact, the branch base changes without an available snapshot, or a
reconstructed terminal head disagrees with its durable workspace. Never fill a
vacancy with an outcome-selected candidate.

With fewer than four eligible candidates, report execution feasibility and
candidate-specific directions only. General factor attribution is
`UNIDENTIFIABLE`.

## Case and seed factor replay

Run the unchanged source/base and dimension budgets in these cumulative cells,
but execute only the four non-overlapping atomic blocks below:

- first 8 cases x first 4 seeds;
- first 8 cases x all 8 seeds;
- all 12 cases x first 4 seeds;
- all 12 cases x all 8 seeds.

Analysis must first decompose them into non-overlapping blocks:

| Block | Cases | Seeds |
|---|---|---|
| Q00 | first 8 | first 4 |
| Q01 | first 8 | added 4 |
| Q10 | added 4 | first 4 |
| Q11 | added 4 | added 4 |

For every exact candidate and cumulative cell, report pair W/L/T, each case's
seed-median effect, case W/L/T, net score, loss rate, the case-effect median and
the existing deterministic bootstrap interval. Rule components are descriptive
and are not a new Protocol verdict.

Report seed sensitivity on the same first 8 cases and case sensitivity on the
same seed prefixes. Q11 is only the joint added-cases/added-seeds atomic block;
this diagnosis has no pre-registered interaction contrast, so interaction is
`UNIDENTIFIABLE`. The unit of cohort aggregation is the candidate, not every
pair. Family and size summaries are descriptive; cumulative or multi-mechanism
candidates cannot support single-mechanism causal credit.

The terminal-R3 diagnosis uses an experiment-owned `protocol_factory` that
explicitly constructs
`ExperimentProtocol(..., champion_result_cache_enabled=False)`. Let A be the
reconstructed immediate base and B the exact candidate; schedule AB when
`(candidate_ordinal + block_ordinal + case_ordinal + seed_ordinal) mod 2 == 0`
and BA otherwise. Both subjects run fresh. Persist both scheduled and actual
order, block/case/seed ordinals, each side's full objective mapping,
feasible/success, elapsed/time limit and one bounded failure or exit fact. The
manifest contains the cohort source references and diagnostic boundary once.
This is a small extension of the existing Protocol record, not a second runner.

The paired specification itself bypasses cache even if a caller constructed
the Protocol with caching enabled. Case and seed ordinals are positions in the
complete frozen master rosters, not indexes restarted at zero inside Q01, Q10
or Q11. Each atomic block is selected explicitly and invoked once; cumulative
`expand=True` is not used to obtain suffix blocks. AB/BA changes execution order
only, never the semantic A/base and B/candidate roles. A thrown runner exception
records only the actual partial order and makes that diagnostic cell incomplete.

The factory also preserves the production scientific semantics: ProblemSpecV1
metric/objective wiring, problem measurement enabled, declared safe data-root
wiring, `selected_surface="solver_design"`, a 30-second Protocol fallback and a
separate runner hard guard of at least 135 seconds for the largest 120-second
dimension budget. Missing selected-surface telemetry stays diagnostic-only;
only existing blocking process/runtime/feasibility failures and incomplete raw
evidence invalidate a cell.

Execute every block once in `Q00 -> Q01 -> (Q10 union Q11)` order. Expansion
aggregates immutable prior blocks and never reruns any completed block.

## Matched sensitivity boundary

The completed same-seed A/A/null diagnostic constrains only a limited
false-pass question. It does not establish the power or MDE of the future
12-case x 8-seed case-median design at practical delta `2`.

Before freezing another promotion campaign, estimate sensitivity using that
exact roster, estimator, equivalence semantics, seed structure and dimension
budgets. Record the supported empirical MDE and the claim it permits. If the
design cannot establish useful sensitivity near delta `2`, either add
independent cases outcome-blind before launch or retain the design and state
that a negative result cannot exclude improvements smaller than the matched
MDE. Additional seeds are repeated observations within a case, not additional
independent cases. This calibration chooses a claim and future design; it does
not create a candidate futility gate or reinterpret R3.

## Budget response

Use the same frozen cohort and the 8 x 4 core at `0.5x`, `1x` and `2x` the
dimension-only budget. Reuse the 1x cell above; execute only the missing 0.5x
and 2x cells. Keep cases, seeds, source, base and surface unchanged, run
serially, disable result reuse, and prohibit concurrent tests or solver work.
Freeze half-up integer budgets before execution: `15/23/30/45/60` seconds at
0.5x, `30/45/60/90/120` at 1x and `60/90/120/180/240` at 2x. Counterbalance
the three budget-arm orders by a deterministic rotation over candidate, case
and seed ordinals. If the legacy fixed replay cannot materialize that rotation,
execute its frozen order once and label whole-arm machine drift
`UNIDENTIFIABLE` rather than claiming counterbalance.

Interpret evidence in this order:

1. mechanism loaded and attempted;
2. state changes were accepted;
3. best updates occurred;
4. longer time increased search opportunity;
5. final objective responded to that opportunity.

Budget exhaustion alone does not establish opportunity constraint. Missing
attempt/accept/best-update telemetry makes activation attribution
`UNIDENTIFIABLE`, while final paired objective response may still be reported.

If that comparison remains useful, run one clean provider-free replay over the

every case once per exact comparison, then derive the selector and estimator
arms offline:

- historical action-dependent selector;
- equal-count evenly spaced selector;
- equal-count size/headroom/structure-stratified selector;
- first two versus all four seeds;

Select a future regression population only by coverage and stability across
seed/estimator arms, never by which arm enlarges an accepted effect. Existing
Warehouse promotions remain accepted and synthetic and production effect sizes
remain separate.

## Context and edit-surface diagnosis

Provider-visible context is an experimental input, not another authority
packet. H receives one research core: objective and semantic invariants, solver
mechanics, legal positive edit surface, complete branch-current source once,
screening-level algorithm evidence and the latest actionable rejection. Branch,
champion and version identifiers, schema/taint bookkeeping, repeated
Decision-exclusion notices, validation/frozen detail, negative frozen patterns
and duplicated edit rules remain host trace or Contract concerns.

C receives the approved H value, approved target, unique canonical path/content
pairs and concise target API guidance. It does not receive protected Protocol
outcomes or host identity/digest/ledger metadata. Offline analysis receives raw
Protocol facts and source references but never becomes provider proposal input.

The current one-shot complete-source surface is sufficient on observed R3 H
evidence, so no provider shell, execution, network, search/read loop or patch
grader is added. A later source-navigation A/B is considered only after two
independent terminal C calls depend on the same source/API/callsite fact and the
trace proves that fact was absent rather than ignored. Any such treatment is
limited to list/read/search over the same already legal source, cannot read
protected evidence and cannot reject or rank a proposal.

An H research-core A/B is allowed only after at least two independent completed
H calls show the same schema/context friction: invalid schema or abnormal
completion, required source/objective/mechanics/legal surface missing or
truncated, or an explicit misunderstanding caused by repeated wrappers. Token
count or weak ideas alone do not trigger it.

A C expression A/B is allowed after either one deterministic typed-edit apply
or multi-file-anchor failure, or two independent schema-valid, structurally
closed C traces omit the causal use/update sites required by complete,
source-grounded multi-site H proposals. R2 and R3 each contain one
scaffolding-only time-aware-credit trace, so the second diagnostic trigger is
met without claiming schema causality. Freeze the approved H and source, then
compare one-shot current expression with one-shot source-bound unified diff.
Normalize both to the same `PatchProposal` before unchanged Contract and
deterministic apply; use no fuzzy repair, retry, shell or model tool loop. Score
parse/apply success and blinded H-obligation/source-anchor coverage only, never
solver W/L/T.

Run this as a post-R3 diagnostic without changing the production proposal or
campaign path. Freeze four solver/Protocol-outcome-blind fixtures: the R2 and
R3 time-aware-credit omissions plus two chronological successful multi-file C
contexts selected only by existing parse/apply facts. Each fixture receives
exactly one control and one treatment call, counterbalanced by fixture ordinal,
using `gpt-5.6-terra`. Both arms reuse the same frozen H and serialized provider
context, check that its `approved_hypothesis` value equals H, and then run the
unchanged `validate_patch(..., approved_hypothesis=H)` after normalization.

The durable result contains the frozen H/source/tool values, raw terminal
response, canonical patch, parse/apply and Contract results. Blind reviewers
see neither arm nor raw expression format. Before calls, freeze both ordinal
rubrics: H-obligation coverage is 0 missing, 1 partial/unused scaffolding, 2
complete causal use/update wiring; source-anchor coverage is 0 wrong owner or
symbol, 1 correct file with incomplete sites/data flow, 2 all required owner,
update and consumer anchors closed. Diagnostic production-code growth is zero.
Only an adopted treatment may promote a strict diff normalizer into the core,
with complete schema/parser wiring capped at 220 lines.

## Identifiability stops

Report `UNIDENTIFIABLE` rather than filling gaps when the campaign is not
terminal, the cohort was outcome-selected, exact source/base cannot be
materialized, a factor cell is incomplete or contaminated, fewer than four
candidates exist, telemetry required for an activation claim is absent, CPU
competition overlaps any factor, budget or Warehouse atomic block, or the
requested population exceeds the fixed cases and seeds actually measured. An
overlapped block is contaminated as a whole; do not select individual pairs by
observed outcome or reconstructed overlap guesses.
