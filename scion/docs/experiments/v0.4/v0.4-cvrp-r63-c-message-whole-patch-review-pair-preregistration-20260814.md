## Provider collection and failure policy

The runner attempts the calls serially in fixed order and first collects their
terminal provider outcomes without scoring either arm. Both terminal provider
outcome envelopes must be durable before any production parse, source binding,
Contract, materialization, V3/V4 execution or sidecar begins. A parsed raw tool
payload is preserved unchanged when the public production client abstraction
exposes it. Otherwise the envelope records `raw_response_available=false` plus
the available production diagnostic/error; R63 does not claim that an invalid
argument payload or message text can be recovered when that abstraction does
not expose it.

A provider-completed outcome with wrong-tool output, invalid JSON, missing
fields or another mechanically unusable result remains an evaluable arm
failure from the available terminal diagnostic or raw arguments. Such a result
is not a reason to request another C response.

A timeout, authentication error, network/upstream close, missing terminal
response, request-level tool-definition rejection or other nonterminal outcome
makes the pair `PAIR_UNIDENTIFIABLE_PROVIDER_FAILURE`. Then:

- the paired classification is undefined;
- no missing arm is retried, resumed, repaired or replaced;
- no historical response is substituted; and
- any later attempt requires a fresh preregistration and explicit
  authorization.

Once both terminal outcome envelopes exist, the provider phase is permanently
closed.
An authority/fixture failure discovered before the first request seals
`PREP_INVALID` with zero provider calls. After request acquisition, an
unexpected local harness, frozen-fixture or workspace invocation exception
seals `RUN_INVALID_LOCAL_INFRA` without another provider call or automatic
scorer resume. A successfully invoked production stage that rejects a response
is instead a measured mechanical arm outcome.
