## Proposal-Block Ceiling Accounting

The d0d3b0a change is effective at the StepResult dimension. `CampaignLoop._attempt_kind()` treats a non-counting result with `attempt_kind="screening"` as a proposal block unless it matches telemetry/same-family special cases. That matters because the pipeline's proposal-only blocks in this run expose `counts_toward_max_rounds=false` and a generic `attempt_kind="screening"` in status.

Completed StepResult proposal blocks:

1. Step 1: `position_removal` premise contradiction.
2. Step 3: `noise_insertion_repair` premise contradiction.
3. Step 5: `segment_destroy` premise contradiction.
4. Step 6: `double_bridge_perturbation` premise contradiction.

With `SCION_PROPOSAL_QUALITY_LOOP_LIMIT=5`, the ceiling had reached 4/5 when the run entered attempt 7. It therefore should not have stopped as `proposal_quality_loop`.

Why `proposal_attempts=7` did not imply ceiling exhaustion:

- `proposal_attempts` is campaign `_round_num`, not the proposal-quality-block counter.
- It includes effective screened attempts 2 and 4.
- It includes in-flight attempt 7, which never produced a StepResult.
- APS internal retries do not count as StepResults: hypothesis semantic retries, schema/preview retries, and code preview/smoke retries are contained inside one outer attempt.
- Hypothesis-only `hypothesis_awaiting_approval` sessions (`5783943e`, `2e512bda`, `c115098d`) are agentic-session audit events, not failed StepResults. They are part of successful outer attempts that later continued into code sessions.

There is still a reporting gap: `total_rounds`/`proposal_attempts` are named like completed rounds, but they include an in-progress outer attempt. `n_steps` is the completed StepResult count. For stopped/in-flight runs, `n_steps` is the safer completed-work counter.

Inference:

- The artifacts do not identify the sender. It may have been a process-group stop, terminal/session cleanup, or another external supervisor. There is no evidence that Scion self-stopped as a proposal-quality loop.
- `launch.sh` for this run did not install TERM/INT traps. It writes `exit.txt` only after the Python command returns:

```bash

printf "EXIT_CODE:%s\n" "$code" > "$RUN_ROOT/exit.txt"
```

If the process group was signaled, both the shell and Python process could receive TERM; Python handled it and wrote campaign artifacts, while bash could exit before the post-command `exit.txt` write. This explains the missing `exit.txt` without requiring an orphaned child.
