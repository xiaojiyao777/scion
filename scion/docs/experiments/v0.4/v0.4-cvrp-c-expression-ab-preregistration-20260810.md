# v0.4 CVRP C-expression matched A/B preregistration

## Question and boundary

Does one-shot source-bound unified-diff expression improve faithful
implementation of an already approved multi-site H relative to the current
one-shot typed exact/full-file edit expression?

This is a proposal-surface diagnostic, not a solver experiment. It cannot read
Protocol W/L/T, rank algorithms, alter a candidate, retry a provider call or
enter Decision. Contract and deterministic source application remain
authoritative. The run starts only after the active R3 campaign is terminal.

## Trigger

The trigger is outcome-blind:

- one R3 multi-site exact-edit response left a removed `cool()` use site and
  reached a deterministic Verification rejection; and
- independent R2 and R3 complete, source-grounded time-aware-credit H calls
  each received schema-valid C responses that added unused scaffolding without
  the required measurement, reward and update use sites.

The same current schema also expressed faithful multi-file patches. The trigger
therefore establishes expression friction, not schema causality.

## Matched provider input

For each fixture, both arms reuse byte-for-byte:

- the historical C trace's `system_blocks` and `user_prompt`;
- model `gpt-5.6-terra` through `http://127.0.0.1:8080`;
- provider SDK retry zero and one required terminal tool call;
- the approved H value, complete editable source and target/API guidance
  already embedded in that prompt.

Before either call, parse the prompt's approved H and require value equality
with the frozen H trace response. Require the two arms' system and user strings
to be equal directly. A mismatch invalidates that fixture; do not repair or
substitute context.

The only treatment difference is the terminal tool schema.

## Arms and normalization

### Exact arm

Use that fixture's historical `generate_patch` tool schema unchanged. It may
return the primary typed exact/full-file operation and its bounded
`additional_changes` set.

### Diff arm

Use the same `generate_patch` tool name with one strict object:

```json
{
  "diffs": [
    {"file_path": "visible/editable/path.py", "unified_diff": "..."}
  ],
  "evidence_refs": ["..."],
  "test_hint": "optional tainted text"
}
```

The diagnostic parser accepts ordinary unified hunks only for the declared
visible editable file. Context and removed lines must match the frozen source
exactly; hunk positions, counts and final bytes must be deterministic. Reject
overlap, duplicate paths, missing or extra context, `/dev/null`, rename,
binary, mode, fuzzy/offset repair and undeclared trailing text.

Normalize both arms into the same ordinary `PatchProposal`, apply each to a
fresh copy of the frozen source and run unchanged
`validate_patch(..., approved_hypothesis=H)`. There is no shell/model tool loop,
same-call repair, retry, solver, Protocol or Verification-quality grader. The
experiment-owned command and parser are capped at 220 lines; production
campaign growth is zero.

## Measurements

For every fixture and arm record:

- provider terminal status, finish reason, tool name and JSON/schema validity;
- normalized file/action/edit set;
- deterministic apply result and unchanged Patch Contract result;
- exact changed symbols and use/update sites;
- H-obligation coverage: `0=missing`, `1=partial or unused scaffold`,
  `2=complete causal wiring`;
- source-anchor coverage: `0=wrong owner/symbol`, `1=correct file but incomplete
  sites/data flow`, `2=all required owner, update and consumer anchors closed`.

Two blind reviewers receive H, frozen source, normalized resulting patch and
the two rubrics, but not arm, raw expression format, historical C response or
solver/Protocol outcomes. Resolve rubric disagreement by reporting both scores;
do not create a model grader or majority gate. The adoption conditions below
must hold independently under both reviewers' scores.

## Interpretation and adoption

All eight provider calls must terminalize without retry. A missing cell makes
schema causality `UNIDENTIFIABLE`; keep the production expression unchanged.

The diff arm is eligible for later adoption only if:

1. all four cells parse, apply and pass the unchanged Patch Contract;
2. neither successful-control fixture regresses on either blind rubric;
3. neither omission fixture regresses, and at least one omission fixture
   improves H-obligation coverage;
4. total H-obligation and source-anchor scores are each strictly higher than
   the exact arm.

Otherwise retain the current exact/full-file schema. Even a qualifying result
supports only a strict diff normalizer experiment; it does not prove better
algorithm ideas or solver outcomes. Any adopted production implementation is a
later reviewed change, retains the 220-line core ceiling and receives focused
tests before a fresh campaign.
