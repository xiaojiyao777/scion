# v0.4 Premise Scope And C11 Feedback Repair - 2026-05-21

## Trigger

Post-P0D Sonnet validation finished successfully but showed noisy proposal
control:

- `screened_experiments=4`
- `proposal_attempts=12`
- champion remained `v1`
- repeated blocks came from CVRP premise false positives, C11 telemetry schema
  mistakes, C9e integration retries, and algorithm-smoke activation failures.

The most important framework-adapter issue was not that Scion gates had facts
the agent could not see. Facts digest/provenance were present in hypothesis,
code, and tool-selection prompts. The issue was that the CVRP novelty provider
matched broad text spans too aggressively and treated some variant claims as
missing-premise contradictions.

## Repairs

### CVRP Premise Scope

`local_search` premise checks now avoid blocking proposals that list an existing
operator as grounding context and then propose a different variant:

- existing `_two_opt_intra` plus a cross-route segment-reversal variant is not
  treated as "missing intra-route 2-opt";
- existing `_or_opt_1/_or_opt_2/_or_opt_3` plus a cross-route 3-opt /
  double-bridge variant is not treated as "missing Or-opt-1".

The old hard blocks remain for explicit false premises such as "baseline lacks
intra-route 2-opt" or "baseline lacks cross-route Or-opt segment relocation".

### CVRP Shaw/Cluster Scope

`destroy_repair` premise checks now require a closer match to the active
`_shaw_removal` fact before hard-blocking a missing-premise claim. Generic
positional/arc/geographic destroy variants are allowed through when they are
not claiming Shaw/related removal is absent. Explicit "lacks related removal"
and generic "new proximity-cluster removal operator" duplicate claims remain
blocked.

### C11 Expected Telemetry Feedback

Hypothesis preview retry feedback now includes an
`allowed_expected_telemetry_template` with concrete mechanism-specific runtime
keys, for example:

```json
{
  "activity": ["solver_algorithm_search_iterations"],
  "activation": [
    "solver_algorithm_context_records.<mechanism_id>_iterations",
    "solver_algorithm_phase_runtime_ms.<mechanism_id>"
  ],
  "effect": ["solver_algorithm_phase_improvement_counts.<mechanism_id>"],
  "budget": ["solver_algorithm_phase_runtime_ms.<mechanism_id>"]
}
```

This is intended to reduce repeated invalid activation declarations such as
`solver_algorithm_phase_runtime_ms.vns` for newly declared mechanisms.
