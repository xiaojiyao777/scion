## v3 Principles Used

From `scion/design/scion-architecture-v3.md`:

- Scion's value is boundary governance, protocol trust, and traceability; the
  LLM is an executor/proposer, not a decision maker.
- LLM outputs are tainted and must pass Contract, Verification, Protocol, and
  safe feature extraction before they can affect deterministic decisions.
- Context Manager controls exposure. Contract checks structure and boundaries;
  Verification checks semantic correctness; Protocol controls evidence and
  leakage.
- Screening details may be exposed, but validation/frozen raw details must stay
  exposure-controlled.

From `scion/docs/AGENT_ONBOARDING.md`:

- Scion core must stay problem-agnostic. CVRP semantics belong in
  `scion/problems/cvrp/` or problem-owned providers/hooks.
- Problem packages own allowed research surfaces, runtime audit field meanings,
  prompt rendering, and problem-owned tests.
- Active algorithm facts are adapter-owned. The proposal agent and semantic
  gates must share the same active fact packet, digest, provenance, and fact
  ids; gates must not be better informed than the agent.
- Proposal-smoke activation-missing evidence is a diagnostic signal, not a
  formal validation telemetry failure.
- Agent-quality blocks, including contradicted premises and activation
  diagnostics, should be preserved as branch-local tainted feedback and rendered
  into later proposal context.

## Key Failure Analysis

### 1. Reactive Best Intensification Smoke Failure

The first approved hypothesis declared:

- `expected_telemetry.activation` included
  `solver_algorithm_context_records.reactive_best_intensification_iterations`
  and `solver_algorithm_phase_runtime_ms.reactive_best_intensification`

Evidence:

- `campaign/agentic_sessions/d3eb6529.../output.json:hypothesis.expected_telemetry`
- `campaign/agentic_sessions/cbc6531a.../output.json:failure_detail`
- `campaign/agentic_sessions/cbc6531a.../transcript.json:failure_ledger.entries[0]`
- `campaign/llm_traces/20260521T153739586325_code_ef46043ca8_f0ded913.json:user_prompt`

The agent received clear C11 and telemetry guidance:

- The hypothesis prompt stated that activation must use mechanism-specific
  activity evidence, not objective/effect fields.
- The code retry prompt included the exact failure and repair guidance:
  add direct activation telemetry with
  `context.record_iteration('reactive_best_intensification', ...)` or
  `context.record_phase('reactive_best_intensification', ...)`.
- The selected surface also exposed helper signatures:
  `context.record_phase`, `context.record_iteration`, and
  `context.record_move`.

The generated code did add mechanism-specific telemetry, but only inside
`_reactive_intensify(...)`, and that helper was called only after
`candidate.total_cost + _EPS < best.total_cost`. Smoke cases apparently did not
hit a new-best event. Therefore runtime evidence had no positive
`reactive_best_intensification` activation even though the code contained the
right helper calls. The later retries preserved the same rare trigger and
failed the same smoke gate.

Conclusion: the agent had enough guidance about field names and helper APIs,
but not enough behavioral discipline to ensure the declared mechanism executes
on smoke cases. This is an agent-quality/code-repair failure, with a framework
P1 edge: activation smoke should distinguish "declared mechanism unreachable on
smoke spread" from "missing telemetry helper" more explicitly and require the
next repair to adjust trigger observability, not just add more records inside a
non-executed branch.

  acceptable because active facts stayed separate and intact.

Residual issue: repeated full file-read planning across attempts burns wall
time. A branch-local cached read summary keyed by active fact digest and file
hash would reduce tool-selection churn without weakening exposure control.

### 4. Stop Semantics and v3 Compliance

The pre-screen blocks themselves mostly fit v3:

- No LLM free text entered Decision.
- No formal screening, validation, frozen holdout, or promotion evidence was
  produced.
- `status.json:n_experiments=0` and `screened_experiments=0` remained correct.
- Branch failures were stored as agent-quality classes, not as ordinary formal
  experiment failures.
- Active facts and premise gates shared digest/provenance.
- CVRP-specific facts and telemetry roles came from the CVRP problem package
  and champion snapshot, not generic Scion core.

The run lifecycle did not fit v3 tightly enough:

- `stopped.txt` says the run was stopped at `15:43:46Z`.
- The campaign child process continued until at least `15:51:21Z`, producing
  more DB events and status updates.
- `run.log` captured only the first two failure messages and did not reflect
  the later orphaned sessions.
- `status.json:total_rounds=5` exceeded `launch.env:ROUNDS=3` because
  pre-screen proposal attempts did not count as effective experiments and the
  manual stop did not actually terminate the child process.

This is a framework lifecycle/control defect. It does not contaminate formal
CVRP evidence, but it undermines audit finality: a stopped run must become
artifact-stable at the recorded stop time.

## Root Cause Classification

### Framework P0

1. Stop propagation failed. `stopped.txt` was written while the actual campaign
   process continued to create LLM traces, DB events, session outputs, and
   status updates. This violates audit finality for stopped experiments.
2. Run accounting is confusing for "3R smoke" when all attempts are pre-screen.
   `ROUNDS=3` became `status.json:total_rounds=5` because blocked proposals did
   not count as effective experiments. That may be intentional internally, but
   the run needs an explicit proposal-attempt ceiling and stop reason for
   no-effective-round loops.

### Framework P1

1. Algorithm-smoke effect telemetry is too strict for pre-screen diagnostics.
   Failing closed on `solver_algorithm_phase_improvement_counts.<mechanism>`
   requires the smoke cases to observe objective improvement, not just mechanism
   activation and valid search effort. This can reject plausible candidates
   before formal screening.
2. Algorithm-smoke repair feedback for rare activation triggers should say
   "the trigger did not execute on smoke cases" and point to the actual runtime
   fields observed, not only "add telemetry helper calls".
3. Run observability is split: `run.log` stopped after two messages while DB and
   status continued. Raw artifact consumers need one authoritative post-run
   summary of every proposal-quality block.
4. Cross-attempt tool reads are repetitive. The active fact digest and file
   hashes are stable, so a branch-local cached context packet could reduce wall
   time and repeated LLM tool-selection calls.

### Algorithm/Candidate Quality

1. `reactive_best_intensification` was a rare-trigger mechanism. On smoke, no
   new best occurred, so the mechanism never activated.
2. `sa_reheat` and `post_repair_2opt` did not produce positive effect telemetry
   in smoke. That may be weak algorithm behavior, overly strict smoke gating,
   or both.
3. Several hypotheses framed existing mechanisms as missing instead of
   proposing variants of existing mechanisms.

### Model Behavior

1. The model ignored active facts that explicitly listed `_regret2_insertion`,
   `_regret3_insertion`, and `_route_removal`.
2. Repair attempts tended to add telemetry where the code already ran, but did
   not reason enough about whether the mechanism path would execute in smoke.
3. The model eventually responded to negative memory by switching toward
   `create_new`, so feedback was not lost; it was just inefficient.

## Recommendations

1. P0: make stop propagation atomic. When a stop marker is written, terminate
   or signal the live campaign child, wait for exit, and write a final immutable
   stop summary containing final pid, exit status, last DB event, last trace id,
   and final status hash.
2. P0: add a proposal-quality-loop ceiling distinct from formal rounds:
   e.g. `max_pre_screen_agent_quality_blocks` and
   `max_wall_time_without_effective_experiment`. Persist the reason in
   `status.json` and DB, not only in `stopped.txt`.
3. P1: split algorithm-smoke telemetry checks into activation-required and
   effect-advisory. Activation for a declared mechanism should fail closed when
   the mechanism is claimed to run; positive objective effect should become
   advisory unless the hypothesis declares guaranteed effect on smoke.
4. P1: improve smoke repair feedback to include observed audit keys and trigger
   reachability: "mechanism path not reached" vs "path reached but no
   `record_iteration`" vs "path reached, activation passed, effect not
   observed".
5. P1: preserve and render a compact "do not claim missing" table before the
   hypothesis task block, not only inside memory text. Include fact id,
   mechanism name, and one-line allowed-variant guidance.
6. P1: cache cross-attempt active solver reads by
   `(fact_packet_digest, file_digest)` and expose a compact "already-read
   active object" summary to tool selection. This keeps v3 exposure while
   reducing repeated tool calls.
7. Model/prompt: when a mechanism is rare-triggered, require the hypothesis to
   state a smoke-observable activation path or declare that the mechanism is not
   suitable for algorithm-smoke activation gating.

## Bottom Line

The semantic boundary and active-fact sharing repairs largely held: the premise
gates cited adapter-owned facts with the same digest/provenance the agent could
see, and the failures stayed in agent-quality categories without becoming formal
screening evidence. The main framework regression is lifecycle control: the
campaign kept running after the manual stop marker. The second-order control
problem is algorithm-smoke telemetry semantics: activation diagnostics are
useful, but effect-field fail-closed behavior is too strong for pre-screen
smoke unless the mechanism is guaranteed to improve on smoke cases.
