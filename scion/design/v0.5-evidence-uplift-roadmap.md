# Scion v0.5 Roadmap — Evidence Uplift（让证据水准追上设计水准）

*Date: 2026-06-11*
*Status: 方向与设计提案（待 BigBOSS 裁决后转入任务清单）*
*Lineage: v3 基石架构 → v0.4 泛化+agentic 改造 → 本文档*

---

## 0. 定位与核心论断

v0.1–v0.3 已经反复证明：**Scion 闭环在"效应量充足"的问题上能稳定产出晋升**
（warehouse 多次晋升，VRP 也有过一次 runtime 晋升）。v0.4 暴露的不是闭环失效，
而是两个叠加问题：

1. **标的错配**：CVRP 强基线下可提案机制的效应量（0.1%~3%）低于当前协议
   的测量分辨率，campaign 在仪器分辨率以下空转。
2. **复杂度跃升**：v0.3→v0.4 治理代码量上升数个量级，治理机器自身开始
   产生失败模式（scheduler 死锁、replay 空耗、上下文膨胀），而研究产出
   没有同步增长。

由此得出 v0.5 的唯一主题：

> **不再增加治理能力，转而建立"科学产出能力"的证据。**
> 一切新工作必须直接服务于：在可测量的标的上，以可对照的方式，
> 产出可复现的晋升。

v3 不变量全部保持：LLM tainted、DecisionFeatures 唯一决策输入、
三级 split 暴露控制、问题域事实不进决策层。

### 0.5 与 v0.4 的分工修正

本文档最初把若干 measurement/runtime/context 工作写入 v0.5，是因为它们
服务于 evidence uplift。采纳后的版本应按以下边界执行：

- **v0.4 closeout 必须完成修复与可运行验证**：measurement/readiness 声明、
  A/A 噪声标定、`practical_delta` 解析、budget-exhausting runtime 语义、
  runtime tie speedup 晋升语义、分支深度/机制族可见性、上下文蒸馏，以及
  VRP/CVRP 与 warehouse 的 focused validation。
- **v0.5 的核心目的不是继续修仪器，而是做对照实验**：治理消融、复现矩阵、
  问题族对照、上下文/提示消融、机制轨迹分析，用于全面评估 Scion 的真实价值。
- 因此，下文 W1/W4 中凡属于当前实验可信性和 VRP/warehouse 有效研究能力的
  工程修复，应前移到 v0.4；W2/W3/M4/M5 仍主要属于 v0.5 证据项目。

## 1. 三个方向性裁决（先于一切设计）

这三个决定是方向层面的，建议先拍板，再做任何代码：

### D1：CVRP/VRP 在 v0.4 先作为测量修复与效率晋升验证标的

CVRPLIB 强基线 + 30s 预算的组合，处于"LLM 提案最难、配对评估最测不出"
的死区。继续在上面只调 gate/lifecycle/context 是在空转方向上加转速。
但这不等于放弃 VRP。历史上已有 runtime/algorithm-efficiency 晋升模式：
候选质量不劣于 baseline，同时计算时间显著更短。v0.4 必须把这种证据路径
修到可审计、可复现，并解决当前 CVRP 测量分辨率、runtime 饱和语义和
分支深度不足问题。

新角色定位：
- CVRP 保留为**测量学边界和 runtime 晋升语义的压力测试**——既要验证
  "框架知道自己测不出"，也要验证"质量不退化 + runtime 改善"的晋升证据
  能否被正确测量。
- 若未来要在 VRP 域要晋升证据，换 VRPTW/带业务约束的变体或弱化基线
  （例如禁用 VNS 的 ALNS-only champion），让效应量回到可测区间。
- v0.5 不应把 CVRP 单一标的的结果当成 Scion 价值裁决；它应进入更大的
  问题族和消融矩阵。

### D2：主战场 = "弱基线、强约束、业务形态"的问题族

Scion 的真实甜区是 warehouse 这类形态：基线远非最优、约束多、
正确性风险高（fail-closed 验证是刚需）、效应量以 % 计而非 ‰ 计。
v0.5 应新增 1 个该形态的第三问题（候选：多车型装载、订单批次排产、
或 warehouse 的更难变体），目的有二：
- 把"晋升可复现"从 n=1 问题做到 n≥2 问题；
- 验证 ProblemAdapter 泛化成本（第三个问题的接入工时是泛化质量的
  直接度量）。

### D3：v0.5 冻结治理面，所有治理改动走"减法白名单"

v0.5 期间不新增治理组件。允许的治理改动只有三类：
(a) 删除/合并冗余路径；(b) 修复已知 bug（如 practical_delta 死配置）；
(c) 为 W1–W4 工作流提供必要的最小钩子。
每个治理 PR 必须回答："这个改动让哪个实验的哪个证据更强？"

## 1.5 裁决判据（Kill / Survive Criteria）——v0.5 的全部意义

v0.5 不是又一个功能版本，是一次**裁决**。项目的核心论题
（"分支治理版 autoresearch 对组合优化有净价值"）从 v0.1 至今
从未被对照检验过。v0.3 推文 8/9 列出的机制问题（分支何时有帮助？
广播何时有帮助？晋升何时导致过早利用？搜索何时坍缩？）至今零进展
——这是项目自己开出的科学债账单。v0.5 用以下判据偿还：

### 杀死判据（任一触发 → 诚实结项或转型，不再续建仪器）

| # | 判据 | 检验实验 |
|---|---|---|
| K1 | **治理消融无差异**：在有信号标的上，naive 单链循环与全治理 Scion 的"frozen 级真晋升 / 单位成本"无显著差异，且 naive 假阳性率可接受 | W2 三臂对照 |
| K2 | **晋升不可复现**：warehouse 同配置 ≥3 次独立 campaign 的晋升产出方差大到无法区分于运气 | W3 复现矩阵 |
| K3 | **永远只有一个问题**：在自造 surrogate 之外，没有任何外部可校准问题域能产出 MDE 之上的晋升（前提：W1 标定确认协议有功效——排除"仪器测不出"的归因混淆） | W1 + W3 |

### 存活判据（满足 → 项目从"信念"升级为"结论"）

| # | 判据 | 支撑叙事 |
|---|---|---|
| S1 | 治理消融显示：全治理臂假阳性显著更低，或单位成本真晋升显著更高 | 论文核心证据 + 工业卖点 |
| S2 | ≥2 个问题域、各 ≥3 次独立 campaign，稳定产出效应量 > MDE 的 frozen 晋升 | 复现性主张成立 |
| S3 | 对 v0.3 推文 8 给出至少一个机制性答案（用 v0.3 12-campaign 数据 + 新对照数据回答："4 次复合晋升的轨迹与停滞轨迹的区分变量是什么"） | 学术叙事的独有素材 |

执行纪律：

- **v0.5 期间只做能触发 K 或 S 判据的工作，其余一切冻结**（D3 的上位原则）。
- K1 是最高优先级——若触发，推文 1–5 的全部差异化主张作废；
  若 S1 成立，它是项目第一个不可替代的证据。**两个方向都应该被欢迎。**
- 若杀死判据触发：产出是一个干净的、有完整证据链的负结果 +
  一套可复用的实验基础设施。这是 v0.3 推文 9 承诺过的研究形态，
  不是失败。

### 科学债清单（S3 的具体待偿项，按数据可得性排序）

1. v0.3 `sonnet-4-6_synthetic_seed29` 的 4 连晋升轨迹复盘：
   逐次晋升的效应量、机制族、提案上下文差异 vs 同期停滞 campaign
   ——数据已存在于 v0.3 lineage，纯分析工作，零算力成本。
2. 晋升上下文是否强化了正确方向（推文 8 候选解释之三）：
   对比晋升后下一轮 hypothesis 与晋升前的机制连续性。
3. 协议是否意外偏向某条路径（候选解释之五）：
   检查该 campaign 的 split/seed 与其他 campaign 的噪声差异
   ——W1 标定工具可直接复用于此。

## 2. 工作流设计（四条主线）

```
W1 测量学声明层（Measurement Layer）     ← 框架核心，本版本最重要的抽象
W2 对照实验协议（Governance Ablation）   ← 回答"治理值不值"
W3 第三问题接入 + 晋升复现矩阵           ← 把 n=1 做成 n≥2
W4 复杂度削减与上下文蒸馏                ← 减法，回收维护带宽
```

依赖关系：W1 先行（W2/W3 都要消费它）；W4 与 W1 并行；
W2 在 W1 完成后启动；W3 贯穿。

## 3. W1 — 测量学声明层（核心设计）

### 3.1 问题陈述

当前 `ProblemSpecV1` 声明了"能改什么"（surfaces / objectives / telemetry），
但没有声明"这个问题在该协议下能测出什么"。后果：协议参数（cases/seeds/
time_limit/gate 阈值）与问题的噪声特性脱节，框架对"实验设计无功效"
这一最致命的失败模式没有任何感知。CVRP 8R 全部 10 个候选死于
SCREENING_FAIL_WIN_RATE，但没有任何组件能说出"这个门在当前噪声下
本来就过不去"。

### 3.2 设计原则

- 测量学事实是 **problem-owned 诊断**，与 BKS/gap 同级：可以进提案上下文、
  可以做 campaign readiness 闸门，**永不进 DecisionFeatures**（v3 边界不破）。
- 标定数据来自确定性重放（champion vs champion），不引入新的 LLM 依赖。
- 声明 + 标定 + 自检三件套，缺一不可：声明没有标定是空话，
  标定没有自检不会被执行。

### 3.3 Schema 提案（加入 ProblemSpecV1）

```yaml
measurement:
  # 求解器运行时模型：决定 runtime 治理语义
  runtime_model: budget_exhausting   # | comparative
  # 配对有效性：solver_design 类编辑是否保持 RNG 轨迹可配对
  pairing_validity: trajectory_divergent   # | trajectory_stable
  # 效应量纲：gate 的 practical delta 以什么单位解释
  effect_scale:
    metric: total_distance
    unit: relative_pct        # delta 解释为相对百分比
    practical_delta_screen: 0.2    # 0.2% 才算实质改进（替代死配置 0.001）
    practical_delta_validate: 0.1
  # 标定产物引用（由 W1 标定工具生成，campaign preflight 校验）
  calibration_ref: formal/calibration/aa_noise_floor.json
  calibration_max_age_days: 90
```

### 3.4 A/A 标定工具（`tools/calibrate_aa_noise.py`）

输入：problem.yaml + protocol.yaml + split + seeds + champion workspace。
执行：champion vs champion，每个 screening case 跑 `n_seeds × n_replicates`
（建议 replicates=3，用不同 RNG 流模拟 trajectory divergence）。
输出 `aa_noise_floor.json`：

```json
{
  "per_case": [
    {"case": "...", "seed_var": ..., "pair_tie_rate": ...,
     "false_win_rate": ..., "delta_p50_abs": ..., "delta_p90_abs": ...}
  ],
  "protocol_power": {
    "false_pass_rate_at_current_gate": ...,
    "mde_at_power_80": ...,     // 当前协议 80% 功效的最小可检测效应
    "recommended_min_seeds": ...,
    "recommended_min_effect_pct": ...
  },
  "calibrated_at": "...", "champion_version": ..., "protocol_version": "..."
}
```

实现要点：
- 功效计算用 bootstrap 模拟：把标定得到的 per-case 噪声分布注入
  "真实效应 = x%" 的假想候选，重放 case 级多数投票 + gate 判定，
  扫描 x 得到功效曲线。纯数值计算，无需新依赖。
- champion 结果可复用现有 champion_result_cache，标定增量成本低。

### 3.5 Campaign Preflight 自检（最小钩子）

CLI `run` 启动时（在现有 production boundary 检查处追加）：
- `measurement` 声明存在且 `calibration_ref` 可读、未过期、
  champion_version/protocol_version 匹配 → 否则 **fail-closed**
  （可用 `--allow-uncalibrated` 显式逃生，写入 run_status 警告）。
- 若 `mde_at_power_80 > practical_delta_screen × 3`，写入
  `MEASUREMENT_POWER_INSUFFICIENT` 警告到 status.json 与提案上下文
  （advisory，不阻断——让人和 agent 都知道这台仪器的分辨率）。

### 3.6 消费方（按 v3 权限矩阵）

| 消费方 | 用法 | 边界 |
|---|---|---|
| protocol gates | `practical_delta_*` 从 measurement.effect_scale 解析（修死配置） | 数值阈值，合法 |
| runtime 治理 | `runtime_model=budget_exhausting` 时：saturation 降为 info、禁用 runtime-tie fresh replay、V9 语义改为"预算合规+无超时" | 语义开关，合法 |
| lifecycle policy | 按 `mde/practical_delta` 比值选阈值档位（低信噪档：zero_win_streak_limit 4→5、允许同机制证据累积） | 数值档位，合法 |
| 提案上下文 | 注入 per-case 噪声画像 + "本协议 MDE=x%" 一行事实 | 诊断可见，不进 Decision |
| DecisionFeatures | **禁止** | v3 边界 |

### 3.7 验收标准

- CVRP 标定报告产出，且能定量复盘 v0.4 8R："当前协议 MDE=x%，
  10 个候选效应估计均 < x% → 全灭是测量学必然"。
- warehouse 标定报告显示 MDE 远小于历史晋升效应量（解释为什么它一直能晋升）。
- 两个问题包的 protocol.yaml 删除 practical_delta 字符串占位，
  改由 measurement 声明解析；`min_practical_delta` 硬编码 property 删除。
- runtime_model=budget_exhausting 下，CVRP 重跑不再出现
  RUNTIME_TIE_FRESH_CHAMPION_REQUIRED 占轮和 saturation 告警刷屏。

## 4. W2 — 对照实验协议（治理 ablation）

### 4.1 要回答的问题

项目根基命题——"研究过程治理值回成本"——目前是信念不是结论。必须回答：
同样的 LLM、同样的轮数预算、同一个问题，朴素 generate-and-filter
比 Scion 全治理差多少？差在哪个维度？

### 4.2 实验设计

三臂对照，每臂同问题、同 champion 起点、同 rounds、同模型、≥3 个随机重复：

| 臂 | 配置 | 实现方式 |
|---|---|---|
| A: full-governance | 现状 Scion | 不变 |
| B: naive baseline | 单轮提案 → 仅 verification（防崩溃）→ 单次 screening 点估计 keep/discard；无分支治理、无三级 split、无暴露控制 | 新增 `--governance-profile naive` 组合开关，用配置降级复用现有组件，不写第二套系统 |
| C: mid（消融轴） | 治理开、统计协议降级（screening 单 seed 点估计） | 同上 profile 机制 |

测量维度（数据源都已存在，只需汇总脚本）：
- 晋升数 + B/C 臂"晋升"用 A 臂 frozen 协议**事后复检**的留存率
  ——这正是治理防假阳性能力的直接度量；
- 假阳性率：B/C 臂 keep 的候选有多少在完整协议下是噪声；
- 单位成本产出：token / 墙钟 / protocol 次数 ÷ 每个"真晋升"。

### 4.3 标的选择

必须在"有信号"的标的上做（warehouse 或 W3 新问题）。
低信噪标的上三臂全 0，什么也证明不了——这是 D1/D2 裁决先行的原因。

### 4.4 把对照"做透"的完整矩阵（预注册）

为避免"跑了一组就下结论"的弱对照，W2 预注册以下设计：

```text
标的:     warehouse（必做） + 第三问题（W3 接入后必做）
臂:       A full-governance | B naive | C 统计降级
重复:     每臂每标的 ≥3 个独立 campaign（不同 campaign seed）
模型:     主模型 1 个（与 v0.4 一致）；可选加 1 个弱模型复刻 v0.3
          的 Sonnet/GPT-mini 分布 → 区分"框架做功"vs"模型做功"（N3）
预算对齐: 同 LLM token 预算上限 + 同 protocol 评估次数上限
          （不是同 rounds——naive 臂单轮便宜，按总预算对齐才公平）
事后复检: B/C 臂的每个"晋升"用 A 臂完整 frozen 协议盲复检
          → 直接测量假阳性率
预注册:   全部 gate 阈值、复检规则、判定统计量在跑前写入
          本文档附录，跑后不得修改
```

输出指标（每臂每标的）：

- 真晋升数（通过盲复检的晋升）；
- 假阳性率（宣称晋升但复检失败的比例）；
- 单位成本：token / 墙钟 / protocol 评估次数 ÷ 真晋升；
- 最佳 champion 终点质量 vs 共同基线（终点视角，防"晋升次数"偏差）；
- 机制多样性轨迹（探索是否坍缩——直接回答推文 9 第四问）。

### 4.5 验收标准

一份 `reports/governance-ablation-*.md`：完整矩阵 + 预注册判定。
结论必须明确触发 K1 或 S1 之一（或声明数据不足并给出补样计划）。
**两个方向的结果都有价值，都必须如实发布。**

## 5. W3 — 第三问题 + 晋升复现矩阵

### 5.1 选型准则（按 D2）

打分维度：基线弱（手写启发式起步）、约束密集（fail-closed 有用武之地）、
评估快（单 case ≤10s，统计功效便宜）、与 warehouse 形态差异足够大。
候选优先级：
1. 多车型三维装载（约束密集、效应量大、与 routing 互补）；
2. 订单批次/波次排产（业务形态典型）；
3. warehouse 难变体（成本最低，但泛化证据弱，仅保底）。

### 5.2 接入即度量

第三问题接入本身就是 v0.4 泛化质量的验收实验。记录并报告：
接入工时、需触碰的 scion core 文件数（理想=0）、problem 包代码量。
core 文件数 >0 的每一处都归档为泛化缺口。

### 5.3 晋升复现矩阵（v0.5 核心证据物）

```
问题 × {≥3 个独立 campaign} → 晋升数、frozen 留存、效应量 vs MDE
```

目标证据语句："Scion 在 ≥2 个问题上、≥3 次独立 campaign 中稳定产出
frozen 级晋升，且晋升效应在 A/A 标定的 MDE 之上。"
这句话成立，证据水准就追上了设计水准。

## 6. W4 — 复杂度削减与上下文蒸馏（减法）

### 6.1 上下文蒸馏（用 6/9 报告分类法做前后对照）

目标不是缩 token，是提高研究信号密度。三个动作：
- **Cross-Branch Research Map 重渲染**：每条 lesson 压成
  `signature + 一句话结论 + 证据计数 + maturity`；required_response
  合规模板移到输出 schema 校验侧，不在输入里重复教学。预期 23k→~3k chars。
- **Runtime Feedback 表格化**：per-case 一行摘要（case | W/L/T | delta |
  机制激活 | 异常），原始 telemetry 串留 artifact。预期 12k→~2k chars。
- **机会画像注入**（problem-owned，仅提案可见）：champion per-case
  gap-to-BKS、噪声带宽（来自 W1 标定）、跨候选机制族-效应排行。
  让 agent 知道"哪里还有可测的肉"，替代纯负反馈。

验收：CVRP hypothesis prompt 中位 chars 降 ≥40%，且蒸馏前后各跑
同规格对照，机制多样性与 screening 信号不回退。

## 10. 一页总结（给未来的自己）

> v0.1–v0.3 证明了机器能转；v0.4 证明了机器在没有可测信号时会
> 完美地空转，并且为对抗空转付出了数个量级的复杂度。
> 项目的真实状态：一台造价很高、精度经过验证的仪器，
> 放在一个还没开始的实验室里。
>
> v0.5 只做一件事：**用这台仪器做它当初承诺要做的实验。**
> 核心论题（分支治理有净价值）从未被对照检验；v0.3 推文 8/9
> 列出的机制问题零进展——这些是项目自己开出的账单，1.5 节的
> K/S 判据就是还款计划。
>
> 退出 v0.5 时，要么手里有 S1+S2（治理有效 + 跨问题复现）的
> 证据链，要么有 K 系列触发的、同等诚实的负结果——
> 两者都是 v0.3 推文 9 承诺过的研究形态。
> 唯一不可接受的退出状态是：又造了一年仪器，还是没有裁决。
