# P1：问题自有的公开执行入口

*2026-11-15 · 实施设计；纯数据接口先行，执行验收另行跟踪于 TASK*

本文件给出 P1 的完整接口与问题实例化，依赖
[P0](v0.5-p0-interface-and-boundary-contract.md)。P1 定义声明、纯数据校验及固定
runner/checker 入口；P2 负责真正隔离执行，P3 才向 agent 开放 observe。
P1 不把 solver import 到 host，不调用正式 Protocol，不修改问题目标或冻结 oracle。

## 1. 模块边界与 Python 接口

新增 `scion.problem.public_observation` 放问题中立的数据类型与 Protocol；
具体 provider 在两个现有 problem package 中。通过 adapter 的可选工厂
`public_observation_provider()` 取得一个对象；关闭能力时不读取工厂并返回 None，
显式启用而缺工厂时返回 typed unavailable，不向
`ProblemAdapter` 增加每个问题必须实现的成员，也不创建 provider registry。

```python
class PublicObservationProvider(Protocol):
    def describe(self) -> PublicObservationSpec: ...
    def validate_input(self, value: JsonObject) -> JsonObject: ...
    def validate_args(self, value: JsonObject) -> JsonObject: ...
    def source_config(self, available_files: tuple[str, ...], *, initial: bool) -> JsonObject: ...
    def validate_source_config(self, value: JsonObject,
                               available_files: tuple[str, ...]) -> JsonObject: ...
```

source_config 由 P3 在 host 已选定的源码副本条件下调用：CVRP 返回空配置；
Warehouse 有实际 registry 时选择 registry，只有初始 source 明确无 registry 才选择
defaults，物化 source 丢失配置必须失败。它不读文件、不解析算法语义、不接受 agent 参数。
各项 validate 只处理已通过 P0 字节/深度限制的普通 JSON，返回 detached copy；
不读文件、不 import 候选、不访问 benchmark、无副作用。失败抛受限
`PublicInputError(reason_code, public_field_path)`；不能把用户值拼入宿主 traceback。
problem-owned validator 负责语义，generic core 不识别 route/order/cache。

```text
PublicObservationSpec = {
  schema_version: 1,
  fixture_paths: tuple[relative path],
  subject_workspace_paths: tuple[relative file or declared directory],
  subject_optional_workspace_paths: tuple[relative file],
  subject_package_paths: tuple[relative package file or declared directory],
  checker_package_paths: tuple[relative package file or declared directory],
  neutral_support_paths: tuple[explicit frozen support file],
  checker_neutral_support_paths: tuple[explicit frozen support file],
  subject_dependencies: tuple[explicit third-party package/file],
  checker_dependencies: tuple[explicit third-party package/file],
  runner_module: fixed module string,
  checker_module: fixed module string,
  input_description: string,
  args_description: string
}
```

所有路径/模块来自安装的 problem provider 声明，不来自 agent 的 JSON。
fixture 和 package 路径相对冻结 `ProblemSpecV1.root_dir`；workspace 路径相对
选定 current/base/draft 的实际源码根。CVRP 两者初始位于问题包，Warehouse 位于
surrogate。neutral support 相对冻结 scion 包根。runner/checker 模块来自安装的
adapter 包，P1b 必须将这两个固定入口文件列入 P2 的精确运行闭包，不能通过声明
一个 module 字符串获得整个包。上述根都由 host 已有问题/源码配置取得，agent 无权指定。
`neutral_support_paths` 只供 subject，checker 用独立的
`checker_neutral_support_paths`，不能继承 subject 的完整依赖。optional workspace
文件存在时必须复制；Warehouse 的 `registry.yaml` 属此集合。optional 只表示不同
初始 source 形态可以没有此文件，不表示需要 registry 的已物化 source 丢失它后可
回退默认配置；P1b/P2 必须核对实际 source 条件并保存配置模式。
composition 用既有公开闭包规则校验并展开精确文件集合；目录只能是显式代码目录，
禁止递归加入数据根、整个 `scion/`、campaign 或 home。冻结后的文件集合记录在
operator 侧，provider view 只列公开文件与接口说明。完整 source 保存和 sandbox
公开执行闭包分别处理，不能将正式输入夹带进挂载。

工厂返回错误类型/坏 descriptor 是配置错误，拒绝启用；不声称“没有 capability”后
偷偷改用另一个 solver。无 provider 且 O/M 均关闭时不加载工厂，保持旧行为。
P1a 的 descriptor 检查只验证纯数据结构与规范相对路径；存在性、symlink、formal
路径别名与真实依赖闭包检查属于 P1b/P2 composition，不能以纯数据检查代替。
P1b 的配置绑定合同和实际隔离 profile 见 [P2](v0.5-p2-isolated-observation-execution.md)。
第三方依赖只挂载明确的 pydantic 纯支持依赖或 yaml；默认不暴露 site-packages。
固定 bootstrap 与 `observation/wire.py` 是 host 的通用执行/字节传输代码，按具体
文件复制，不允许由此 import 框架控制树。runner/checker 均为独立固定入口文件。
纯数据实现分为 `scion.problem.public_observation`（声明和可选解析）与
`scion.problem.public_input`（PublicInputError、严格 JSON 和通用标量检查）。
decoder 的字节/深度上限在 JSON 解析前检查，collection items 是全对象/数组累计
成员数，解析后检查；前两个上限限制解析分配。问题 validator 接收已经受限的
JSON object，额外拒绝问题域里的 bool/int 混用、非有限数值和字段歧义。

## 2. 固定子进程协议

P2 从合法 descriptor 构造固定 argv，agent 没有 command/module 参数。
虚拟路径约定 `/subject`（只读算法闭包）、`/public`（只读 fixture）、`/input/request.json`
与 `/scratch`；包依赖安装在固定只读 import root，环境不得含宿主 PYTHONPATH、
SCION_PROBLEM_DATA_ROOT 或 SCION_CVRP_DATA_ROOT。不得依赖 cwd 外的自动查找。

request.json 是 host 生成的严格 JSON：

```json
{"schema_version":1,"instance":{},"seed":17,"public_args":{"time_limit_sec":1.0}}
```

`instance` 是 fixture/input_ref 经验证后的实际普通值。runner 只读固定 request 文件，
从 `/subject` 装载当前完整算法。输出到受控 descriptor 的单个 JSON 对象：

```text
SubjectPayload = {
  schema_version: 1,
  outcome: "returned" | "algorithm_error" | "invalid_solution",
  solution: JsonObject | null,
  reported_objective: JsonObject,
  diagnostics: JsonObject
}
```

subject stdout/stderr 另外捕获，不能与结构化 JSON 拼接；算法打印日志不能污染控制帧。
无 JSON/多 JSON/非法数值为 DATA_INVALID；未捕获异常为 SUBJECT_ERROR。
algorithm_error/invalid_solution 是 problem runner 报告，仍属 tainted 开发证据。
全部字节受 P0 总输出限制。runner 不能写 host final record。

### 独立 checker

checker 是单独的干净子进程，只读公开 instance、序列化 solution 和冻结检查闭包，
**不加载 editable source 或 analysis script**。输出固定形状：

```text
PublicCheck = {
  schema_version: 1,
  consistency: "pass" | "fail" | "not_evaluated",
  feasibility: "pass" | "fail" | "not_evaluated",
  recomputed_objective: JsonObject | null,
  reason_codes: list[problem-owned enum]
}
```

先检查输出类型/完整性，再检查一致性，失败后不对非法 route/order 强行计算 objective。
只有可定义时才返回重算值，不能以 0 替代未取得；solution 的 objective/feasible
自报值不参与重算。checker 异常是 CHECKER_ERROR，不是 solver 无收益。
checker 预算单列且在动作开始前预留，不能先耗尽预算再假定检查通过。
这些结果只供研究，不调用 VerificationGate、不生成 ProtocolResult，不建立新的
正式 oracle。参考检查复用问题已有冻结语义，由 P1 小例子独立复核。

## 3. CVRP 实例化

当前来源是 `scion.problems.cvrp` 的 models、adapter、solution_checks 和
`solver_runtime.algorithm_runtime`。第一版 public instance 仅接受现有 JSON 几何
格式，后续 `.vrp`/矩阵生成支持需要另行扩展，不能悄悄复用 formal 文件解析入口。

|字段|约束|
|---|---|
|name|非空字符串，仅作标注，无路径语义|
|capacity|严格正整数|
|depot|严格整数，必须是 nodes 中唯一 depot|
|allowed_routes|正整数或 null，必须显式提供；null 表示该公开实例不声明 fleet 上限|
|use_integer_cost|严格 bool；保留问题现有 EUC_2D 舍入语义|
|nodes|至少 depot＋一个 customer；每项恰为 id:int、x/y:finite number、demand:int；id 唯一；demand 非负、depot demand=0，customer demand≤capacity|

顶层字段全部必需，未知字段拒绝，特别不接受 bks/bks_routes、答案、任意路径或
callable。坐标、节点数和输入总大小受明确开发资源配置约束，非算法质量 gate。
`public_args` 仅 `{time_limit_sec: positive finite number}`；seed 在 P0 顶层，
不允许替换 construction mode、policy path、solver hook 或实际算法模块。

runner 使用所选 source 的 `policies/baseline_algorithm.py::solve` 及完整
`baseline_modules/`，复用 `load_baseline_algorithm` 所需 context/计时语义。
现有 `solver.py::_main` 在主算法失败后会调用 fallback，**不得把它直接作为公开
subject 入口**。新固定 runner 在 active algorithm 不可用、返回 None 或运行失败时
明确输出 algorithm_error，不回退到 `solver.solve` 的构造器。
引用的 runtime helper 若先行拒绝无效解，则输出 invalid_solution，不能生成可行
fallback 掩盖它；已有 formal CLI 行为不在本模块改写。

checker 用冻结 CVRP 模型核对所有 customer 恰好出现一次、无 depot 混入、载重不
超 capacity；重算 fleet_violation、total_distance、routes。fleet_violation 是既有
objective，不能在 generic 层新增硬可行性规则。自报 distance 完全忽略。
已有 solution_checks 的“reported objective 必须存在”检查不能强迫信任自报数值：
公开 checker 应先独立检查 routes，再计算值，用计算值构造已有检查输入。

公开 fixture 使用现有 `data/tiny_development.json`；新增可核验小例子单独放在
public development 目录，不能复制 formal/canary。闭包为 descriptor 中声明的
models/adapter/solution_checks/solver_runtime、其必要 problem-neutral 类型与 telemetry
依赖，以及选定 policies；不挂载整个 framework 或 CVRP data 根。
checker 仅包含模型与检查必要依赖，不含 policies 或 solver runtime。

现有 CVRP helper 会 import `scion.problem.contracts/spec` 和 telemetry 类型。
因此“无框架挂载”的精确定义是无框架**控制树或整目录**，允许逐文件复制已审查的
纯支持闭包：`problem/contracts.py`、`problem/spec.py`、后者所需的
`core/operator_interface.py`、`runtime/telemetry_events.py`；namespace 初始化使用
空文件，不执行完整框架 `__init__`。checker 仅需 contracts 与问题模型/检查，
无需 spec、operator_interface 或 telemetry。不得选择现有 development 的 suite
profile 来获得整框架挂载；P2 要新增明确观察 profile，并验收无法 import
campaign、Decision、Protocol、provider client。缺依赖返回 unavailable，不放宽目录。

## 4. Warehouse 实例化

实际 solver 位于 `surrogate/`，并非 CVRP 风格的包内 solver。
第一版 observation 固定使用现有 phase=1 问题语义；phase=2 不作为可选参数偷偷
改变约束。输入是现有 public `data/instance_development.json` 的规范结构：

- 顶层仅 `orders`、`amount_limits`，两者必需；不接受 loader 当前会忽略的
  vehicle_types 或额外字段。
- 每个 order 必须含 `order_id, vehicle_category, vehicle_subcategory, urgent,
  hazard_flag, hazard_quantity, pickup_name, pickup_province, pickup_city,
  declaration_amount, lsp, ship_method, destination_country, spu_list`；
  `locked_vehicle_id` 可省略或为 null/非空字符串。ID 唯一；vehicle_category 和
  vehicle_subcategory 为严格非负 int，其余文本字段为非空字符串，
  urgent/hazard_flag 为 bool，数量与金额非负且有限，数量为严格 int。
- spu_list 每项恰含 packing_type 与 quantity；packing_type 使用冻结模型的
  PALLET_TYPE/BOX_TYPE，quantity 非负严格 int。amount_limits 是字符串到有限
  非负数的 mapping。不能通过输入覆盖车型容量/价格或 oracle。
- loader/validator 保留原值，不静默去重 order、丢字段、强制转换 bool/int，
  不“修复”输入以让实验成功。可行性由真实解检查，不把复杂可行性搜索塞进 validator。

`public_args` 恰为 `{time_limit_sec: positive finite number, max_iterations: positive int}`。
这些是声明的运行预算；seed 只来自 P0。pool size、no_improve_limit、operator weights
等取选定 source 的既有配置，不能由公开请求随意替换；记录其实际值作为运行条件。
runner 调用该 source 的 `solver.solve(instance, cfg, registry_path)`，仅对 cfg 设置
声明的 seed/time/max_iterations。registry 是当前 source 对应的已有问题配置，
由 host 的现有 workspace 路径确定，不接受 agent 路径。

若当前 source 含 registry 配置就必须使用其实际副本，不能因传参缺失落回 solver
的硬编码默认算子。缺失必要 registry/config 返回 unavailable；只有初始问题声明
明确采用默认算子时才能 registry=None，且要记录该模式。candidate 派生配置必须
沿已有 materialization 路径取得，不由 observation 临时猜测一个“等价配置”。

checker 在干净进程用冻结 models/oracle，独立核对 assignment 与 vehicles 的一致、
每单恰好一次、车型/容量/区域/危险品/锁定组等现有可行性规则，重算 subcategory_splits
和 total_cost；时间采用宿主实际计时，不由 solve_time_ms 自报建立性能声明。
checker 闭包无需 operators，避免把候选模块导入参考检查进程。

subject 闭包为所选 surrogate 算法文件、operators 完整声明集合、实际 config/registry；
fixture 仅开发输入。输出保留完整 vehicles/assignment 及允许 runtime 诊断，
不只返回一个 PASS，也不向 core 教授车型或分组意义。

## 5. P1 验收用例

所有真实执行用例最终必须经 P2 隔离后完成；P1 可先验证纯 validator/descriptor
及冻结参考值，不能用 host 直接 import 候选作为测试捷径。未实现的用例保持待验收。

|用例|输入/设置|预期证据|
|---|---|---|
|P1-01|无工厂且 O/M 均关闭；开启 O/M 而无工厂|旧路径无新依赖；显式启用被 typed 拒绝|
|P1-02|返回坏 descriptor、路径逃逸、混入 formal 目录|composition 拒绝，无子进程/provider dispatch|
|P1-03|合法输入传给两个 provider|原值不变，输出 detached，core 不含问题名判断|
|P1-04|未知键、重复 JSON 键、NaN、bool seed/int、超深/超大|精确层次拒绝，无隐式修复/静默删值|
|P1-05|CVRP depot(0,0)，customers(3,0)/(0,4)，两 demand=1，capacity=2，allowed_routes=1，integer_cost=true|routes=[[1,2]] 的 distance=12、routes=1、fleet_violation=0；不靠 solver 自报确认|
|P1-06|同例 routes=[[1],[2]]；重复/漏 customer|前者 distance=14、fleet_violation=1；后者一致性失败，未定义 objective 不伪造0|
|P1-07|CVRP active algorithm 抛异常/返回 None，但 fallback 可给可行解|结果仍 algorithm_error，不能把 fallback 当完整 subject 成功|
|P1-08|Warehouse 一个非危 Dongguan 订单、1 FULL_PLT、单个 T3、完整一致 assignment、无锁定/金额冲突|冻结 oracle 与独立手算都给 subcategory_splits=0、total_cost=800；错误自报价格不影响重算|
|P1-09|Warehouse 重复 order、漏 assignment、错误车型、违反锁定组|输入错误与解错误区分；不得因 serializer 正常退出而视作有效解|
|P1-10|Warehouse 当前配置含区别于默认的测试算子/权重|实际调用来自选定 source/config；遗漏 registry 明确失败，不能跑默认集|
|P1-11|在隔离测试 source 放可辨识行为，修改宿主原 repo、切换 sibling|执行仍使用冻结选定树；输出可追到实际 source，不回读 repo|
|P1-12|subject 自报 feasible=true、伪造 objective 或修改自己进程中的 oracle|干净 checker 不受影响；不会变成正式 Verification/Decision 输入|
|P1-13|checker 异常、输出错型或预算不足|分别 CHECKER_ERROR/DATA_INVALID/明确资源结果，无默认为 pass|
|P1-14|合法 fixture + 同 seed/预算重复；profile/analysis 与 subject 比较|记录运行条件；差异可研究，不把重复计时当独立框架样本或仪器化时间当正常性能|

数值例子是接口正确性样本，不是性能数据或算法改进证据。P1-08 的完整 fixture
字段及合法性由实现测试显式构造，不能从科学 held-out 挑一个方便例子。

## 6. 实施次序与边界复核

P1a：类型/可选工厂/纯 validator/descriptor；验证 P1-01–04 的纯数据部分和冻结数值，
其中 P1-02 的真实文件闭包、P1-04 的 observe envelope/seed 由 P2/P3 集成补齐。
关闭 O 时的旧路径继续可用。P1b：两个 problem-owned runner/checker 的固定协议与
精确闭包，等待 P2 提供隔离执行后完成 P1-05–14 集成证据。
P2 可以依赖已通过的 P1a 与 P1b 接口设计开发执行器；**P1 的运行验收与 P2
集成共同完成**，不要求先无隔离执行 P1，也不伪称 P1a 测试等于全 P1 完成。
P3 必须等这条纵向路径验证后才向真实 agent 开放。

V3 §3/§4：core 只管通用声明和结果数据，科学链无输入变化；§5：未开放任意
算法执行主体；§8/§15：开发闭包不含正式数据；§10.3：检查复用冻结语义，agent
不能自建 oracle 权威；§16：候选与分析代码不在宿主或 checker 解释器中执行。
P1 不解决 M 的跨 campaign 导入、统计功效、旧 schema 债务或原 CVRP retained 目标。
