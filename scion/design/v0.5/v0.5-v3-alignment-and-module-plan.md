## 1. 结论：方向成立，开工设计仍有缺口

v0.5 增强的是 agent 在正式提案之前取得证据、检验解释及延续研究的能力，
这符合 V3 的自动算法研究目标，也回应 §21“治理过强退化为小修小补”的风险。
四层验收已正确区分工程、过程能力、机制效果和独立算法收益。
但 D/O/M/E 只是阶段划分，尚不能作为逐模块实施合同。

当前不足分为三类，不能统称“待实验验证”：

|缺口|为什么影响落地|在何时解决|
|---|---|---|
|新增执行/暴露能力尚未回写权威契约|H 执行和 C handoff 超出现有接口；不能以“Decision 没改”跳过边界设计|P0，任何新能力进入正式路径前|
|problem-owned observation 入口只有原则|输入校验、运行闭包、结果解析、开发 oracle 的 writer 和可信性需要具体签名|P1 设计先完成，再实现|
|资源失败只有分类，无完整路由|动作失败、当前 session 结束、campaign 停止容易混在一起；可能形成第二套调度器|P2 设计先完成，再实现|
|材料的写入、读取、缺依赖和 H 导出事务未细化|仅保存文件不足以保证后续可用；不能让失败写入返回可用引用|P2/P3/P4 各自设计退出项|
|研究效果验收尚未成为可执行评测|缺任务清单、rubric、抽样数、预算和可执行分析规则|P5 先完成诊断任务设计；P6 冻结正式参数|
|现有 A/B 对照的归因过窄|B 同时增加观察、当前 attempt 文件和 H→C 交接|立即修正文案；只支持这一组能力的总效果|

初次审查完成缺口定位和模块合同拆分；后续 P0/P1 文档已补齐接口设计。
设计完成不等于 V3 扩展已生效或运行验收已通过，状态以 TASK 为准。
工程签名/路由等可在实现前确定；耗时、方差、样本量需要公开 pilot，不能要求
尚未存在的实现先给出性能证据，也不能以此为由让接口长期保持含糊。

## 2. 对 V3 蓝图的逐项判断

V3 的原始目标、职责与权限是约束；旧模型名、算子池例子、retry/压缩等不是必须
复建的功能清单。V3 §0 已明确 addendum 对这些旧例子的解释。不能用回归原蓝图
作为恢复已退役机制的理由，也不能用 addendum 越过 V3 的权威边界。

|V3 位置|v0.5 变化/要求|判断及核验方式|
|---|---|---|
|§0、§1.1–1.5 自动研究、人在回路不在循环|agent 自选调查，人定义问题与核验结果|符合；逐轮人工指路的 trace 不计自主证据，host 不选择算法机制|
|§2.3 不做通用 agent、自动定义问题或无 baseline 从零设计|analysis 可执行研究脚本|有偏移风险；脚本仅在既定优化问题的公开闭包中工作，无通用 shell/network/服务工具，不改 objective/oracle|
|§3.1、§4.1–4.3 职责/tainted/Decision 输入|新增 observation 与 notes|符合条件是它们只进入 Creative；host 执行事实不等于科学事实，不能借“结构化指标”进入 Safe Features|
|§5 两轮 Proposal|H 内调查，C 在 approved H 后实现|属于能力扩展；正式仍最多一个 H/绑定 C，开放研究不是新增第三种正式提案|
|§5.2 C 不见历史|C 获得当前 H 选定材料及本 C 输出|需显式扩展输入表；不能把“公开”理解为允许 C 读取全部历史，不能声称权限完全未变|
|§8.2–8.8 科学协议与隔离|开发观察可重复，正式 Protocol 保持|开发 case 不因曾被观察便成为独立确认；私有阶段不经笔记导入；框架重复单位与 solver case 单位分别保持|
|§9–10、§10.3 Contract/Verification/oracle|执行前纯结构检查、可选开发参考计算|preflight 不是 Verification；agent 自写 reference 不变成冻结 oracle；不以观测正收益作为提交门槛|
|§11.1–11.4 分支方向与完整源码连续|普通问题内容跨 attempt/branch 阅读|问题可关联多个分支，不替代分支方向/状态；材料不得换 base、合并 sibling、恢复失败 draft|
|§12 Scheduler|agent 在已获配 session 内选实验|局部动作选择不等于分配 branch/campaign 预算；调度仍按现有 state/priority/FIFO，不读问题“已解决”或研究质量评分|
|§13 与 addendum 失败解释|新增观察错误、无收益、预算耗尽|须有路由表；观察不能清除 exact-value falsifier veto，错误不能伪造成正式负结果|
|§14 lineage、§15 context|普通研究文件和完整可取的正文|延续记录职责；不建第二正式总账。失败解释可供 Creative 使用，不能把 §1.2“仅存档”解释成可驱动 Decision|
|§16 subprocess/isolation|subject 与 analysis 分进程|加强隔离；同进程 monkeypatch 不能冒充原算法运行；测试不能声称完整恶意代码防护已证明|
|§17 direct API、§19 版本路线|有限工具动作与逐模块实现|保留直接 provider 调用；不引入外部 coding-agent runtime。版本路线是历史计划，完整 solver 空间已是当前基线，不再包装为 v0.5 新能力|
|§21 风险|材料越积越多、治理越来越重|采用普通文件和可读取索引；每项组件必须对应实际职责，不能增加完成证明、质量评分、机制 blacklist|

因此结论是**目标及裁决骨架对齐，新增 Creative 能力和暴露例外必须显式设计**，
而不是“完全无变化”或“已经偏离 V3”。本评审未修改 V3 或 addendum。

### P0 应形成的最小权威差异文本

采纳后回写 V3 对应章节，当前 addendum 继续如实描述 v0.4，不将未来能力写成现状：

- §4 数据矩阵增加研究笔记/脚本、公开观察结果：允许 Creative 读取，Decision 不读；
  agent 不能写宿主执行记录或正式 metrics。
- §5 增加 H 的受限公开执行、C 的 base/draft 观察、当前 H 的冻结材料集合；保留
  C 无通用历史访问、approved-H 绑定、正式 H/C 不可修复和 exact-falsifier 规则。
- §14–16 解释普通材料延续、源代码与材料分别继承、fresh-campaign import 与
  两类进程隔离；不恢复 mutable terminal state。
- §11–12 明确问题文本是研究内容，局部实验选择不授予调度/预算分配权。

每项回写要有对应反例测试和现有源码落点。不能只写“遵守 V3”便勾选 P0。

## 3. 从设计到实施的模块合同

细化后的依赖顺序：`P0 设计 → P1a 纯接口/校验 → P1b 入口 + P2 隔离集成 → P3 → P4`；
P1b 的真实执行验收依赖 P2，不能先在宿主运行候选来打勾 P1。P5 的任务/rubric 设计可在 P1 前准备，
真实能力验证分别在 P3、P4 后进行；`P3/P4 + P5 → P6 → P7`。
P1/P2 是短的纵向支撑模块，不能扩张成先建设通用实验平台。

|模块|范围、主要落点|编码前的设计退出项|实现后的模块证据|
|---|---|---|---|
|P0 权威与接口总表|V3 差异、机制设计、H/C context 边界|新增能力/数据权限/正式导出/失败分层无冲突；每项有负责组件和反例；不要求预先跑新机制实验|文档对照完成；不能用单测替代设计判断|
|P1 问题公开执行入口|problem provider/runtime；两个现有问题包|入口签名、JSON 输入/参数允许集合、公开依赖、输出 schema、开发 oracle 与可用性；缺 capability 时保持旧路径|provider-free 的已知小例子独立核对关键输出；两个问题包共用 core，问题语义留在包内|
|P2 观察执行与本次材料|development isolation、普通输出保存、资源计数|subject/analysis 进程及挂载；实际 source/input/script 保存；状态与捕获分离；读分页/写失败；全套路由表|源代码不能被 analyzer 改写；假状态文件无效；超限/取消/残留进程/磁盘错误有准确记录；无正式状态写入|
|P3 H/C 集成与交接（完成 O）|research sessions、context snapshot/manager、ready|动作 schema、允许集合、H finalize 时冻结 handoff 的时序、C 自身材料可读、开关默认值、关闭能力的旧路径|H 自主调查→正式 H→C 观察→原有正式链；abstain/abandon；failed falsifier→正观察→ready 仍拒绝；capability off 不改变旧行为|
|P4 材料延续（完成 M）|普通文件 corpus、workspace cleanup、fresh import|跨 attempt 可见集合、只追加修订、实际 parent 保留、引用失效/导入同名/公开闭包；M 开关不影响 O 审计保存|完整原件可取，旧结论有源码条件；失败 draft 不成 base；fresh import 不恢复状态；Decision 后保存失败不改裁决|
|P5 研究过程验证|问题自有诊断任务、真实 provider 轨迹及离线复核|任务/参考答案/有效结论 rubric、资源、停止、外部干预记录；任务不给目标算法或必走步骤|观察后解释确有改变，跨 attempt 实际读材料且核对条件；同时报告失败轨迹；小任务不冒充开放发现|
|P6 机制效果|预注册 A/B/C 与独立分析|全部启动参数冻结；同期对照、统计单位、主效果、缺失、成本、确认提名规则|按预定矩阵完成，报告两项 contrast 和不确定性，不以获得正结果为停止条件|
|P7 完整 solver 收益与阶段判断|原 Protocol/Decision、独立确认、报告|确认人口/基线/预算/次数/结果回流与提名预先锁定|E4 给独立结论；CVRP 三类 baseline 不互换；负/不确定/未完成有分别结论|

模块完成证据必须说明：实际代码版本、设计差异、行为检查命令/结果、失败或未覆盖
路径、对后续模块的限制。不新增机器可审批的“模块认证”系统，不把此表带进运行时。
P1a 验证通过后推进 P1b/P2 联合纵向验证，再推进 P3/P4；共享边界集成后跑相应全套回归和跨问题控制。
已有边界失败会阻止相关能力进入正式路径，不要求每个小改动都重跑长 campaign。

## 4. 必须补到接口设计里的具体决定

### 4.1 一个动作的失败不能误变成一轮研究失败

P2/P3 应逐行确定以下路由，沿用已有 typed outcome，不建立另一套 campaign 状态机：

|事件|当前动作|session / campaign|
|---|---|---|
|请求不合法、缺公开依赖、preflight 拒绝|不启动 subject，返回枚举，计已发生成本|剩余预算允许时继续；不能改为无收益|
|子进程异常/局部超限/输出不完整|结束进程组，保存实际部分及资源|开放会话可调查/改请求；无自动 retry、无 formal round|
|本地会话额度耗尽|停止新增动作|按已有 proposal-local 关闭语义结束 attempt，正式计数不增加|
|共同研究预算耗尽|不启动超额动作；已用资源保留|既有 resource stop；不能以 fresh H 绕过共同上限|
|隔离能力失效、无法保证公开闭包|不执行；不降级为宿主直接运行|沿用相应 operational stop/hold，不能当普通脚本错误继续不安全执行|
|记录持久化失败|不返回虚假可读引用|禁用受影响动作或停止，按故障范围设计；已有 Decision 不回滚|
|用户中断、真实 auth/quota|保留已完成材料，终止相应运行|既有 typed stop；不恢复半截状态|

预留/结算只在现有资源执行责任内完成，不加 lease/receipt 服务。未启动、已启动
失败和完整完成三者成本分别记；host 拒绝不虚增一次 solver run。
硬限制先用显式保守开发配置实现，再用公开 pilot 校准正式额度，避免“先有 pilot
才能配置、先有配置才能 pilot”的循环依赖。所有动作开始前必须有完整有效配置。

### 4.2 材料可用不等于所有目录都交给 agent

P3 冻结的 handoff 和正式 H 必须来自同一次 finalize；复制失败不能导出带失效引用
的 H，也不能导出后补写。开放会话可收到有限反馈再选择；正式 H 已导出则不可改。
P4 要区分结构无效导入（拒绝输入）、缺依赖历史材料（明确 unavailable）和可读取的
完整记录；不能用当前 source 补缺，也不能静默丢弃后称全量导入。

当前 [`research_input.py`](../../scion/core/research_input.py) 只处理
`current_question` 与 opaque observations，并有现成大小限制；不能把无限材料
正文塞进它或另建第二份当前问题状态。新引用接口、版本兼容和旧输入保留方式
在 P0/P4 明确。当前 [`context_snapshot.py`](../../scion/proposal/context_snapshot.py)
的 C allowlist 无研究材料；必须显式增加精确投影，不能放宽为任意 mapping。

### 4.3 数据收集不是科学因果解释

观察记录须区分所选完整算法、仪器化脚本、公开输入、seed、运行参数、是否 profile
及完成状态。计时对照需同条件并平衡顺序；调试模式或详细 tracing 的开销不能直接
算作正常 solver 性能。完整输出也可能由错误脚本生成，复核仍需要问题自有参考值。

P2 就保存执行依据。当前 [`workspace_service.py`](../../scion/core/workspace_service.py)
接受新候选后会清理旧树，P4 的 parent 保留必须先于该 cleanup；保存不等于把树
提升为 executable head。现有 [`code_development.py`](../../scion/core/code_development.py)
依赖 draft 和开发 suite，不能直接改名就充当 H observation。

## 5. 验收补强与声明范围

现有 E1–E4 足以组织评价，但不足以声称验收准备完成。补充以下要求：

1. **正常路径也要验收。** 不只证明不能越权，还要证明合法公开实验能跑、结果
   能读、H→C 能用、关闭 O/M 时旧流程仍可用；否则可能得到“安全但无法研究”的框架。
2. **连续性覆盖状态变化。** 至少检查同源码复用、源码改变后旧观察仍绑定旧条件、
   sibling 材料不自动合并、champion 改变后的 stale reconcile 不改变材料出处，
   以及缺旧源码时明确 unavailable。工程 fixture 可以固定场景，真实自主轨迹不能带做。
3. **有界开放研究不可缺席。** P5 除答案可核验的小任务外，还需在一个真实完整 solver
   上完成预定预算的开放研究试验，并对另一问题包做边界控制；不要求小预算必有正收益。
   仅小例子通过只支持诊断能力。有限开放试验也不支持普遍可靠性，后者由 P6 估计。
4. **归因针对实际干预。** B−A 是 O 整组能力（观察＋本次材料＋handoff）的效果，
   C−B 是额外跨 attempt 材料暴露的效果。若要声称某个单工具有效，另设消融。
5. **评测可复算。** P6 开始前用人工构造的正/负/缺失数据验证分析脚本，明确
   rubric 分歧、无候选和不完整运行处理；不能看结果后重定“有信息量”。
6. **CVRP 目标仍独立开放。** 框架阶段完成、诊断更好、一次 promotion 均不能
   取代原始 B0 上的独立 retained evidence；新旧 comparator 明确分开。

P5 任务数量、每项预算和停止规则必须在运行前给定；P6 的任务人口、重复数、
实际意义阈值和统计精度由公开 pilot 支持。当前没有这些运行结果，不能标记通过。
