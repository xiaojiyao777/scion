## Purpose

The clean current-sync CVRP run accepts the repaired continuation/rejection
loop, but it also confirms that v0.4 is not closed: CVRP still lacks
positive-at-MDE solver progress, and postrun/readiness semantics are
accumulating inside oversized helper scripts. The next repair must therefore be
design-first and subtractive.

This document defines three port-based designs:

- Design N: split postrun/readiness lifecycle logic into generic typed ports.
- Design O: stabilize the measurement declaration consumption path.
- Design P: add problem-owned solver-opportunity providers for CVRP/VRP.

The goal is to make Scion a better general combinatorial-optimization research
framework, not a VRP-specific framework.

## Boundary Requirements

- Generic core may own artifact identity, current-run evidence lifecycle,
  fail-closed readiness, schema validation, exposure control, and normalized
  measurement/runtime fields.
- Problem-owned layers own CVRP/VRP/warehouse review semantics, including BKS,
  CMT cases, route counts, ALNS/VNS/two-opt vocabulary, warehouse movement
  operators, practical deltas, opportunity classes, and mechanism rankings.
- `DecisionFeatures` remains problem-neutral. It must not contain raw BKS,
  case hardness, free-form diagnostics, raw calibration replay, mechanism
  rankings, prompt text, or problem-specific opportunity summaries.
- Proposal context may receive compact problem-owned diagnostics only through
  deterministic schema-validated fields marked proposal-only.
- Do not add more behavior to oversized postrun/readiness helpers except as
  temporary call-through wiring into the new ports.

## Design N: Postrun Readiness Typed Ports

### Problem

`postrun_analysis_brief.py`, `check_postrun_acceptance.py`, launch-readiness
checks, and artifact-inventory helpers now mix four concerns:

- generic run lifecycle and current-run evidence checks;
- artifact inventory and stored-vs-live consistency;
- exposure policy for prompts, source, patches, and logs;
- problem-specific review readiness such as CVRP large-twoopt or warehouse
  plateau status.

This makes it too easy to add problem rules to generic helpers.

### Target Model

Introduce typed ports under the Scion package, not as additional tool-local
helper functions:

```python
class PostrunInventoryPort(Protocol):
    def load(self, run_root: Path) -> PostrunInventory: ...

class RunEvidenceLifecyclePort(Protocol):
    def evaluate(self, inventory: PostrunInventory) -> RunEvidenceLifecycle: ...

class ExposurePolicyPort(Protocol):
    def summarize(self, inventory: PostrunInventory) -> ExposureSummary: ...

class ProblemReviewPort(Protocol):
    problem_family: str

    def review(self, inventory: PostrunInventory) -> ProblemReviewSummary: ...
```

Generic readiness composes these ports:

```python
@dataclass(frozen=True)
class PostrunReadinessSummary:
    run_root: str
    inventory_status: str
    lifecycle: RunEvidenceLifecycle
    exposure: ExposureSummary
    problem_review: ProblemReviewSummary | None
    failed_required_checks: tuple[str, ...]
    failed_optional_checks: tuple[str, ...]
    current_run_analysis_ready: bool
    delegation_ready: bool
    decision_features_excluded: bool = True
```

### Generic Core Owns

- Stored inventory loading and fallback policy.
- Current-run vs copied/resume evidence distinction.
- Wrapper/postrun exit status interpretation.
- Required artifact identity and schema validation.
- Prompt/source/patch/log exposure summaries.
- Fail-closed readiness aggregation.

### Problem-Owned Review Owns

- CVRP large-twoopt review readiness.
- CVRP protected-case evidence interpretation.
- Warehouse plateau/continuous-improvement review readiness.
- Future VRP, TSP, scheduling, or warehouse-specific diagnostics.

### Acceptance

- `check_postrun_acceptance.py` becomes a thin CLI over the readiness
  orchestrator and problem-review registry.
- Generic tests use dummy problem reviews with no CVRP/warehouse vocabulary.
- CVRP/warehouse tests live under problem-owned or problem-review test modules.
- Existing readiness JSON shape remains backward-compatible during migration.
- File-size trend is controlled: new semantic modules should stay below 1000
  lines, and tests should split by port instead of adding one mega-test file.

## Design O: Measurement Declaration Consumption

### Problem

Measurement readiness is now present, but consumers are still spread across
protocol config, launchers, prompt context, postrun summaries, and readiness
checks. The boundary is correct in intent but too implicit in code shape.

### Target Model

Problem specs declare measurement semantics. Generic core consumes only a
reduced, normalized view:

```python
@dataclass(frozen=True)
class MeasurementConsumerView:
    problem_family: str
    measurement_declared: bool
    readiness_status: str
    readiness_reason_code: str
    runtime_model: str
    pairing_validity: str
    effect_metric: str
    effect_unit: str
    mde_at_power_80: float | None
    practical_delta_screen: float | None
    practical_delta_validate: float | None
    calibration_freshness: str
    evidence_depth: str
    decision_features_excluded: bool = True
```

### Generic Core May Use

- readiness status and reason code;
- normalized runtime model;
- effect scale;
- pairing validity;
- MDE/practical-delta scalar fields;
- calibration freshness tier;
- compact evidence-depth tier.

### Generic Core Must Not Use

- raw calibration rows;
- calibration artifact paths in `DecisionFeatures`;
- BKS tables or case hardness;
- mechanism rankings;
- free-form opportunity diagnostics;
- problem-specific case names as gates.

### Acceptance

- One typed consumer object feeds protocol config, launch readiness,
  proposal-context rendering, and postrun readiness.
- Proposal context may render compact provenance, but raw replay rows stay out.
- Tests assert that `DecisionFeatures` receives none of the forbidden fields.
- CVRP/warehouse measurement declarations remain problem-owned.

Current implementation status: `MeasurementConsumerView` is present in
`scion.measurement`, exposes compact status/readiness payloads without
calibration refs or replay rows, and `ProtocolConfig.with_problem_measurement()`
consumes it. Proposal-context measurement diagnostics also consume it while
preserving proposal-only calibration provenance, and prepared measurement
handoff builders consume it for launch focus. Local/WSL launcher/handoff
focused tests pass (`34 passed` each). Postrun research-efficiency artifact
fallback uses the same typed view for copied calibration artifacts; local/WSL
postrun/measurement focused tests pass (`54 passed` each). Launch-readiness and
postrun brief paths consume reduced prepared/report payloads rather than
interpreting measurement declarations directly.

## Design P: Problem-Owned Solver Opportunity Provider

### Problem

The framework can now continue and reject CVRP hypotheses, but the agent still
does not receive a compact enough problem-owned opportunity picture to choose
high-quality solver moves. Repeating generic gates or hard-coding CVRP rules in
core would overfit the framework.

### Target Model

Problem packages expose proposal-only opportunity summaries:

```python
class ProblemOpportunityProvider(Protocol):
    problem_family: str

    def build_opportunity_summary(
        self,
        context: OpportunityContext,
    ) -> ProblemOpportunitySummary: ...
```

The generic renderer treats the summary as a typed proposal-context block:

```python
@dataclass(frozen=True)
class ProblemOpportunitySummary:
    schema_version: str
    problem_family: str
    objective: str
    residual_opportunity: tuple[OpportunityAxis, ...]
    mechanism_evidence: tuple[MechanismEvidenceSummary, ...]
    evidence_requirements: tuple[OpportunityEvidenceRequirement, ...]
    protected_cases: tuple[ProtectedCaseSummary, ...]
    measurement: MeasurementConsumerView
    default_avoid: tuple[AvoidedMechanismSummary, ...]
    proposal_visibility_only: bool = True
    decision_features_excluded: bool = True
```

For CVRP/VRP, the problem-owned provider may summarize:

- residual gap or opportunity against appropriate baselines;
- protected cases and why they matter;
- mechanism activation/effect counters;
- required next evidence, protected-case coverage, and proposal-only recipes;
- direct objective deltas and route/fleet feasibility;
- MDE comparison;
- mechanisms already rejected in current lineage;
- time-budget model constraints.

The generic renderer must not interpret these fields beyond schema validation,
size control, and exposure audit.

### Acceptance

- CVRP/VRP opportunity summaries render into proposal context and postrun
  visibility reports as proposal-only material.
- No CVRP/VRP fields are added to `DecisionFeatures`.
- No generic scheduler, lifecycle, target-intent, runtime-pressure, or Protocol
  gate uses BKS/CMT/two-opt/ALNS/VNS terminology.
- A postrun report can prove whether the opportunity summary was rendered and
  whether later proposals used, contrasted, ignored it, repeated default-avoid
  families, or selected the prepared top opportunity without a proved required
  evidence checklist.

## Implementation Slices

1. Design N skeleton:
   create typed dataclasses/protocols and a registry, then adapt the current
   CLI to call them without changing output. Skeleton dataclasses/protocols,
   registry, orchestrator, and generic dummy tests are implemented.
   `check_postrun_acceptance.py` now has a compatibility adapter that computes
   the typed readiness payload without changing default CLI output. Generic
   lifecycle/current-run evidence and wrapper marker checks now use
   `PostrunLifecycleAcceptancePort`; artifact identity/schema checks now use
   `PostrunArtifactAcceptancePort`; Phase 4 evidence coverage, prepared
   contract consistency, and current-run report-family checks now use
   `PostrunEvidenceConsistencyAcceptancePort`. Review-input summary schema,
   boundary, count, and rebuilt-consistency validation now use
   `PostrunReviewInputAcceptancePort`; required summary selection still comes
   from the checker/problem policy. Prompt/source visibility envelope checks
   now use `PostrunPromptVisibilityAcceptancePort`; expected-summary rebuild
   and active-subject legacy-prefix policy remain in the checker/problem
   boundary. Research-telemetry checks now use
   `PostrunResearchTelemetryAcceptancePort`; failure-taxonomy signature
   comparison is isolated in a named telemetry evaluator, while expected
   summary rebuild and problem-family enablement remain in the checker
   boundary. Problem-summary actionability policy now lives in problem-owned
   `ProblemSummaryActionabilitySpec` values. Problem-summary input-consistency
   checks now use a common input projection plus problem-owned warehouse and
   CVRP consistency functions. The remaining Design N work should be driven by
   concrete problem-review needs rather than generic checker growth.
2. Design N migration:
   move CVRP large-twoopt and warehouse follow-up checks behind problem-review
   providers, preserving existing JSON fields. CVRP large-twoopt is
   implemented as `CvrpPostrunSummaryProvider`,
   `CvrpLargeTwoOptReviewPort`, and problem-owned large-twoopt classifiers;
   warehouse follow-up is implemented as `WarehousePostrunSummaryProvider`,
   `WarehouseFollowupReviewPort`, and problem-owned follow-up classifiers.
3. Design O:
   centralize `MeasurementConsumerView` and update protocol config, launch
   readiness, proposal context, and postrun summaries to consume it. The
   typed view, protocol-config consumer, proposal-context consumer, and
   prepared handoff consumers are implemented. Postrun research-efficiency
   fallback uses the typed view for copied calibration artifacts; remaining
   postrun/readiness migration should happen through Design N ports without
   adding raw calibration/problem fields to generic core.
4. Design P:
   implement CVRP/VRP opportunity provider first, then wire it into proposal
   context and visibility reports. The generic `scion.opportunity` schema and
   CVRP `CvrpOpportunityProvider` skeleton are implemented and focused-tested;
   proposal renderer wiring and postrun section-visibility aggregation are
   implemented. CVRP-owned postrun usage interpretation is implemented as a
   report-only summary over structured proposal fingerprints; generic core does
   not parse raw prompts/responses or receive CVRP solver semantics. The CVRP
   opportunity-quality slice now carries a problem-owned evidence-requirement
   recipe for prepared large-instance two-opt, CMT2/CMT4 protection, and
   measurable opportunity classes, and distinguishes selected-but-checklist-
   unproven usage for the prepared top family as report-only postrun evidence.

Each slice should have disjoint file ownership when delegated to workers.

## Subagent Assignment Guidance

- Worker A, generic core: `PostrunInventoryPort`,
  `RunEvidenceLifecyclePort`, `ExposurePolicyPort`, readiness orchestrator, and
  compatibility tests. It must not touch CVRP/warehouse review semantics.
- Worker B, problem reviews: CVRP large-twoopt and warehouse follow-up provider
  modules plus problem-owned tests. It must not change generic readiness
  aggregation semantics.
- Worker C, measurement/opportunity: `MeasurementConsumerView` and CVRP/VRP
  opportunity provider. It must keep all opportunity fields proposal-only and
  out of `DecisionFeatures`.

Workers must read `scion/design/scion-architecture-v3.md` first and state how
their patch preserves the v3 boundary.

## Non-Goals

- No new CVRP-specific scheduler, lifecycle, target-intent, Protocol, or
  runtime-pressure gate.
- No promotion rule changes.
- No broad budget/truncation/compression policy.
- No raw prompt, response, patch, calibration replay, BKS table, or source body
  exposure in status docs.
- No file-size-neutral move that simply renames a large helper while retaining
  the same mixed responsibilities.

## Exit Criteria

- Current readiness outputs stay compatible for existing roots.
- Generic port tests pass without problem-specific vocabulary.
- CVRP/warehouse review tests prove problem-specific semantics are owned by
  problem-review providers.
- Proposal-context visibility reports can show whether problem opportunity
  summaries were rendered, and CVRP postrun reports can summarize whether later
  proposal fingerprints used, contrasted, ignored/unproven, or repeated
  default-avoid opportunity families without making them Decision input.
- `git diff --check` is clean, and no new production or test file grows past
  1000 lines without an explicit split justification.
