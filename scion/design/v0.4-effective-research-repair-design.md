# Scion v0.4 Effective Research Repair Design

*Date: 2026-06-23*
*Status: Design A, Design B, and the typed fresh-runtime opportunity-signal
cleanup are implemented in the current worktree; post-commit full readiness
validation and clean CVRP relaunch remain open*

This document defines the next repair slice needed before another long CVRP or
warehouse campaign. It is intentionally design-first: the goal is to restore
generic Scion research behavior without turning Scion into a CVRP-specific
framework or adding another layer of helper-function patches.

## 1. Scope

v0.4 must prove that Scion can support effective research before v0.5 starts
the broad comparison matrix. The current blocker is not a new CVRP heuristic.
The current blocker is framework semantics:

- branch scheduling conflates live branch records, schedulable work, and scarce
  active slots;
- prepared research focus is copied through launch/readiness/postrun tools by
  ad hoc projection helpers and string probes;
- problem-specific CVRP contract details have leaked into generic projection
  and readiness code;
- free-form opportunity diagnostics can create lifecycle or scheduler pressure
  unless reduced to typed evidence signals;
- very large scripts and tests are accumulating repeated contract fixtures.

The design below keeps v3 boundaries intact:

- LLM output remains tainted proposal material.
- Decision still reads only `DecisionFeatures`.
- Problem diagnostics may guide proposal context, readiness, runtime
  governance, and lifecycle policy only through deterministic, schema-validated
  fields.
- CVRP, VRP, warehouse, and future problem semantics stay in problem-owned
  providers.

## 3. Design A: Branch Scheduling Status

### Problem

Active-slot accounting currently answers "does this branch count?" by walking
branch state, `branch_code_status`, feedback tier, lifecycle blocks, and
scheduler-owned release predicates. The same facts are reconstructed in the
scheduler, branch cards, status summaries, and postrun reports. The result is
string-driven and hard to audit.

### Target Model

Introduce one deterministic status object owned by scheduling, not by CVRP:

```python
@dataclass(frozen=True)
class BranchSchedulingStatus:
    branch_id: str
    branch_state: str
    evidence_tier: str
    lineage_status: str
    lane: str
    schedulable: bool
    consumes_active_slot: bool
    release_reason: str
    next_action_reason: str
    promotion_boundary: str = "not_a_promotion_or_validation_decision"
    decision_features_excluded: bool = True
```

The `lane` is a generic scheduling lane, for example:

- `promotion_stage`
- `validation_stage`
- `stale_reconcile`
- `weak_positive_followup`
- `diagnostic_followup`
- `low_signal_followup`
- `clean_exploration`
- `not_schedulable`

The scheduler, active-slot inventory, branch cards, and status summaries should
consume this status object instead of recomputing separate helper predicates.

### Rules

- Terminal, abandoned, and decision-parked branches never consume active slots.
- A branch can be reportable while not consuming an active slot.
- A branch can be active-slot consuming only if it has a schedulable lane or a
  deliberate recovery reason that still needs capacity.
- Scheduler-origin reclaim may park only branches that are explicitly eligible
  by deterministic status, and the status must explain why this is not a
  promotion or quality judgment.
- Resumed branches must be reconciled into `BranchSchedulingStatus` before
  active-slot inventory is computed. Copied weak-positive state is not enough;
  the current status must reflect the latest evidence tier and current
  schedulability.
- If all slots are consumed but no branch can make forward progress, the
  campaign should report an actionable scheduling-state failure rather than
  looking like a successful research stop.

### Acceptance

- Unit tests build generic dummy branches; no CVRP mechanism names are required.
- A resumed weak-positive branch with superseding inactive or non-actionable
  current evidence does not block all clean exploration capacity.
- A true weak-positive branch with current actionable evidence remains
  schedulable and can consume a slot.
- Quality-regression and hard-negative branches still fail closed or release
  slots according to deterministic lifecycle evidence.
- Branch cards and `status.json` agree with scheduler selection because both
  are rendered from the same status object.

## 4. Design B: Research Guidance Contract

### Problem

Prepared launch guidance is currently shaped by problem launchers but projected
through generic tools by helper functions. The generic context manager and
readiness tools know keys such as `large_instance_two_opt_constraints`, and
readiness checks look for strings such as `CMT2`, `CMT4`, or
`large_instance_intra_route_two_opt_seed`. That is a boundary leak.

### Target Model

Problem packages should expose a typed research-guidance contract through a
stable port:

```python
class ProblemResearchGuidanceProvider(Protocol):
    def build_guidance_contract(self, context: GuidanceContext) -> ResearchGuidanceContract:
        ...
```

The generic contract shape should be problem-neutral:

```python
@dataclass(frozen=True)
class ResearchGuidanceContract:
    schema_version: str
    problem_family: str
    current_question: str
    required_mechanisms: tuple[RequiredMechanism, ...]
    evidence_requirements: tuple[EvidenceRequirement, ...]
    avoid_rules: tuple[AvoidRule, ...]
    continuity_requirements: tuple[ContinuityRequirement, ...]
    guidance_blocks: tuple[GuidanceBlock, ...]
    measurement_summary: MeasurementGuidanceSummary | None
    decision_boundary: str
    proposal_visibility_only: bool = True
    decision_features_excluded: bool = True
```

Problem-specific content lives inside typed blocks with stable ids and
categories. Generic code may validate and render these blocks, but it must not
interpret CVRP case names or mechanism ids.

### Ports

- Problem-owned provider:
  `scion/scion/problems/<problem>/research_guidance.py`
- Generic schema and renderer:
  `scion/scion/research_guidance/schema.py`
  and `scion/scion/research_guidance/rendering.py`
- Generic validators check schema, visibility flags, required block ids, and
  rendered-path coverage.
- Problem-owned validators check CMT2/CMT4, bounded two-opt, warehouse
  champion-v2 evidence, or future domain-specific requirements.
- Tool scripts become thin CLI wrappers around these ports.

This is modularization by responsibility, not a new pile of helper files.

### Acceptance

- `rg "large_instance_intra_route_two_opt_seed|CMT2|CMT4|large_instance_two_opt_constraints" scion/scion/core scion/scion/proposal/context_manager`
  has no production hits outside tests or problem-owned providers.
- Generic prompt projection accepts a dummy problem guidance contract and
  renders its required mechanisms and evidence blocks without knowing the
  domain.
- CVRP launcher/readiness tests still prove the CVRP provider emits the
  bounded large-instance two-opt contract, but those assertions live in CVRP
  provider or launcher tests.
- Existing prepared roots remain readable during one compatibility window by
  adapting old `research_focus` manifests into the new contract at the
  problem-owned boundary.

## 5. Design C: Fresh Runtime Opportunity Signal

### Problem

Fresh-runtime follow-up is a useful control-plane mechanism, but it must not be
created from proposal prose. Before this cleanup, generic lifecycle and
scheduler paths treated non-empty `opportunity_diagnostics` strings as an
actionable-loss signal. That made free-form diagnostics capable of creating
fresh-runtime markers or replay pressure.

### Target Model

`FreshRuntimeOpportunitySignal` is the shared generic interpretation boundary:

- It records whether structured phase evidence or structured reason-code
  families support an actionable-loss follow-up.
- It records when free-form `opportunity_diagnostics` text was present but
  ignored as a scheduler/lifecycle source.
- It stays proposal/control-plane visible and explicitly excluded from
  `DecisionFeatures`.

Lifecycle marker creation and fresh-runtime replay materialization both consume
this typed signal. Pair-level weak-positive replay remains supported, but
`RUNTIME_TIE_FRESH_CHAMPION_REQUIRED` alone is only a freshness precondition; it
is not an actionable diagnostic source.

### Acceptance

- Text-only `opportunity_diagnostics` plus fresh-runtime-required status does
  not create an actionable-loss follow-up marker.
- A stale or text-only pending marker is not replayed unless the current summary
  carries pair-level or structured actionable-loss signal sources.
- Structured phase activation/effect evidence and diagnostic/telemetry reason
  codes still allow actionable-loss fresh-runtime follow-up.

## 6. Code Quality Guard

Large files are now a design smell for this area. The next repair should not
increase the helper-script surface.

Guidelines:

- New production modules should be cohesive and normally stay well below 1000
  lines.
- Existing files above 1000 lines may be touched for compatibility shims, but
  new behavior should move behind named ports or typed models.
- Test fixtures for prepared roots and research guidance should move into
  reusable fixture builders instead of being copied through multiple large
  tests.
- Tool scripts should orchestrate; they should not own domain contracts.

## 7. Migration Order

1. Add `BranchSchedulingStatus` and route scheduler, active-slot inventory, and
   branch-card active-slot fields through it. Keep behavior equivalent except
   for the current slot-block bug.
2. Add regression tests for the WSL failure shape using dummy mechanisms:
   two stale or copied weak-positive branches plus one inactive diagnostic
   branch must not terminate the campaign by slot blockage when a clean
   exploration lane is available.
3. Add the generic `research_guidance` schema and renderer with a dummy problem
   fixture.
4. Move CVRP prepared focus construction to a CVRP provider and make the
   launcher call it. Keep a compatibility adapter for existing prepared
   manifests.
5. Move warehouse prepared focus construction to a warehouse provider.
6. Replace generic projection/readiness string probes with contract validators.
7. Split repeated prepared-root test builders into fixture modules.

No new long CVRP relaunch should be used as acceptance until steps 1 and 2 are
complete. No broad prepared/readiness refactor should start until steps 3 and 4
have characterization tests.

## 8. Non-Goals

- Do not tune CVRP heuristics in generic core.
- Do not move BKS, case gap, CMT case details, warehouse domain facts, or raw
  calibration rows into `DecisionFeatures`.
- Do not add broad proposal budgets, truncation, compression, or decorative
  gates to mask scheduler or context-design problems.
- Do not solve v0.5 governance ablation in this slice.
