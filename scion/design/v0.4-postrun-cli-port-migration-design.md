# Scion v0.4 Postrun CLI Port Migration Design

*Date: 2026-06-28*
*Status: design-first migration plan. Do not treat this as implementation
approval for runtime or scheduler behavior changes.*

## Purpose

The v0.4 postrun/readiness architecture has moved in the right direction:
`scion.postrun` now contains typed ports and problem-owned review providers
exist for CVRP and warehouse. The remaining code-quality risk is that two CLI
tools still bypass those boundaries:

- `scion/tools/postrun_artifact_inventory.py`
- `scion/tools/rebuild_prepared_handoff.py`

These tools should become adapters over Scion package ports. They should not
continue to accumulate helper functions that interpret CVRP, VRP, warehouse, or
prompt-readiness semantics.

This design is intentionally subtractive. It preserves legacy JSON/Markdown
outputs while moving semantics into named generic ports or problem-owned
providers.

## Continuation Note: Prompt-Context Audit Boundary

The first prepared prompt-context extraction moved readiness build/render logic
out of `rebuild_prepared_handoff.py`, but the shared audit helpers still need a
second split: generic `scion.postrun.handoff` code may orchestrate artifacts,
compare boundary flags, and dispatch through a problem prompt-bridge spec, but
it must not own CVRP/warehouse prompt-summary semantics or synthetic
problem-shaped prompt contexts.

Target split:

- generic `scion.postrun.handoff.prepared_prompt_context` keeps only
  problem-neutral summaries such as research guidance and research-shape prompt
  visibility;
- `scion.problems.cvrp.prompt_bridge` owns CVRP active-subject and measurement
  diagnostics prompt-summary rendering and required fields;
- `scion.problems.warehouse_delivery.prompt_bridge` owns warehouse active-subject
  and measurement diagnostics prompt-summary rendering and required fields;
- `check_launch_readiness.py` should call a named package validation function
  for prepared prompt-context readiness artifacts instead of retaining the
  artifact-specific validation helper block locally.

Acceptance: legacy readiness payload and failure reasons remain compatible,
raw prompt/source bodies remain excluded, no new generic source file exceeds
1000 lines, and problem vocabulary moves into problem packages rather than a
new generic helper layer.

## Boundary Rule

Generic Scion code may own:

- artifact identity and schema checks;
- stored-vs-live inventory loading policy;
- current-run vs copied/resume evidence distinction;
- wrapper, preflight, and postrun lifecycle status;
- fail-closed readiness aggregation;
- prompt/source/patch/log exposure boundaries;
- generic evidence-family presence counts.

Problem packages own:

- CVRP, VRP, warehouse, or other problem-family vocabulary;
- BKS, CMT cases, protected cases, route counts, ALNS/VNS/two-opt terms;
- warehouse movement operators and plateau/follow-up semantics;
- problem-specific opportunity requirements and default-avoid rules;
- interpretation of whether a mechanism was implemented, measured, or useful.

`DecisionFeatures` remains problem-neutral. It must not receive raw BKS, case
hardness, case names, route counts, mechanism rankings, prompt text, raw LLM
responses, patch/source bodies, calibration replay rows, problem opportunity
summaries, opportunity commitments, or postrun review interpretations.

## Current Responsibility Leaks

`postrun_artifact_inventory.py` currently mixes at least four concerns:

- run-root artifact discovery, sqlite counters, and report inventory;
- prepared manifest contract checks, git/path/secret validation, and lifecycle
  evidence;
- generic Phase 4 evidence-family coverage;
- CVRP and warehouse handoff semantics such as large-twoopt constraints, CMT
  protection, split membership, warehouse v2 checkpoint, required evidence,
  and default-avoid coverage.

`rebuild_prepared_handoff.py` currently mixes:

- prepared handoff rebuild orchestration and file writing;
- prompt-context readiness aggregation;
- source-marker checks for prompt bridges and problem adapters;
- CVRP/warehouse research-focus semantics for measurement opportunity,
  large-twoopt, CMT protection, warehouse plateau/follow-up, and default avoid
  signals.

The implementation smell is not line count by itself. The problem is mixed
ownership: tool-local helpers are becoming a parallel semantic system next to
the package ports.

## Target Modules

### Generic Package Ports

`scion.postrun.inventory.loader`

- Implements `PostrunInventoryPort`.
- Loads run-root artifacts, campaign artifacts, sqlite counters, stored
  inventories, LLM trace counts, and report directories.
- Does not interpret problem-family fields.

`scion.postrun.inventory.prepared_contract`

- Defines `PreparedRunContractInventoryPort`.
- Checks manifest schema, required launcher fields, path resolution, git
  identity, secret-free payloads, report-only markers, and
  `decision_features_excluded` markers.
- Does not check CVRP/warehouse opportunity or handoff content.

`scion.postrun.inventory.phase4`

- Defines `PostrunEvidenceCoveragePort`.
- Counts generic evidence families: formal candidate artifacts, prompt
  manifests, prompt signal density summaries, measurement readiness presence,
  protocol accounting summaries, runtime feedback summaries, source visibility,
  and current-run report families.
- Receives problem-specific coverage from a registry without interpreting it.

`scion.postrun.handoff.rebuild`

- Defines `PreparedHandoffRebuildPort`.
- Writes analysis brief, inventory, launch readiness, prompt-context readiness,
  and rebuild manifest artifacts.
- Owns file layout and compatibility output, not problem semantics.

`scion.postrun.handoff.prompt_context_readiness`

- Defines `PreparedPromptContextReadinessPort`.
- Aggregates generic signal availability and problem-provider summaries.
- Does not maintain CVRP/warehouse source-marker tables.

### Problem-Owned Providers

`scion.problems.cvrp.postrun_handoff`

- Defines `CvrpPreparedHandoffReviewPort`.
- Owns CVRP measurement reason codes, measurable opportunity classes,
  large-twoopt constraints, CMT2/CMT4 protected-case split checks, direct-effect
  rules, missing-primary-telemetry rules, and resume-continuity requirements.

`scion.problems.warehouse_delivery.postrun_handoff`

- Defines `WarehousePreparedHandoffReviewPort`.
- Owns warehouse v2 checkpoint, plateau/follow-up question, required evidence,
  default avoid, and warehouse measurement/runtime handoff checks.

Existing problem-owned modules remain the right home for postrun interpretation:

- `scion.problems.cvrp.postrun_review`
- `scion.problems.cvrp.opportunity`
- `scion.problems.warehouse_delivery.postrun_review`

### CLI Adapters

`scion/tools/postrun_artifact_inventory.py` should eventually contain only:

- `argparse` and exit-code handling;
- calls into `PostrunInventoryPort` and renderer functions;
- legacy JSON/Markdown rendering adapters;
- temporary compatibility exports during migration.

`scion/tools/rebuild_prepared_handoff.py` should eventually contain only:

- `argparse` and family selection;
- calls into `PreparedHandoffRebuildPort`;
- legacy output format and strict-mode handling;
- temporary compatibility exports during migration.

## Migration Order

1. Extract inventory loading behind `PostrunInventoryPort`.
   Keep `build_inventory()` output bit-compatible.
   Acceptance: golden/fixture JSON comparison for prepared-only, resumed, failed
   preflight, and completed current-run roots.

2. Extract generic prepared-contract checks.
   Move only schema, path, git identity, launcher command, report-only, and
   `DecisionFeatures` exclusion checks.
   Acceptance: generic tests contain no CVRP/warehouse vocabulary.

3. Move CVRP and warehouse prepared-handoff checks into problem-owned ports.
   Acceptance: CVRP assertions live under CVRP tests; warehouse assertions live
   under warehouse tests; generic adapter tests use a dummy problem family.

4. Extract prepared prompt-context readiness.
   Tool code should aggregate provider summaries, not inspect problem adapter
   source markers directly.
   Acceptance: legacy readiness payload stays compatible; raw prompt/source
   bodies remain excluded.

5. Split Phase 4 problem-specific coverage through registry dispatch.
   Acceptance: generic coverage code contains no CMT, large-twoopt, ALNS, VNS,
   warehouse-v2, or plateau vocabulary; problem tests prove legacy fields still
   appear for CVRP and warehouse roots.

6. Thin the CLI files.
   Acceptance: both tools are adapters only; no production or test file exceeds
   1000 lines without an explicit split note; `git diff --check` and focused
   postrun/launcher/readiness tests pass.

## Non-Goals

- No scheduler, Protocol, promotion, runtime-pressure, or Decision behavior
  change in this migration.
- No CVRP-specific generic gates.
- No broad budget, truncation, compression, or quality-gate policy change.
- No raw prompt, response, patch, source, or calibration replay exposure.
- No file-size-neutral rename that preserves the same mixed helper structure.

## Delegation Plan

Worker A, generic inventory:

- owns `scion.postrun.inventory.*` and generic tests;
- must not touch CVRP/warehouse review semantics.

Worker B, problem handoff providers:

- owns `scion.problems.cvrp.postrun_handoff`,
  `scion.problems.warehouse_delivery.postrun_handoff`, and problem tests;
- must not change generic readiness aggregation.

Worker C, handoff rebuild adapter:

- owns `scion.postrun.handoff.*` and the CLI adapter shrink;
- must preserve legacy output shape and strict-mode behavior.

All workers must read `scion/design/scion-architecture-v3.md` first and state
how their changes preserve the v3 boundary.
